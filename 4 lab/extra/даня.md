Здесь секретный ключ `SECRET_KEY` просто записан прямо в коде.

Почему это плохо:

Как я понимаю, так делать не очень безопасно, потому что если кто-то увидит исходный код, то он сразу увидит и ключ.  
Дальше уже могут быть проблемы с безопасностью. Например, насколько я понял, через такой ключ могут подделываться некоторые данные приложения, которые связаны с защитой.

Рекомендации по устранению:

- не хранить такой ключ прямо в файле с кодом
- выносить его в переменные окружения или в отдельные настройки
- не выкладывать такие данные в репозиторий

## Фрагмент кода 2

Недостаток:

Поле пароля сделано как обычное поле `TextField`.

Почему это плохо:

Пароль тогда будет показываться как обычный текст, а не как скрытые символы. Это плохо, потому что его можно просто подсмотреть.  
Еще тут я не вижу нормальной проверки введенных данных. То есть пользователь может ввести что угодно, а форма сама по себе не выглядит защищенной.

Рекомендации по устранению:

- использовать не `TextField`, а специальное поле для пароля, например `PasswordField`
- добавить хотя бы базовую проверку данных
- проверить длину пароля и то, что поле вообще заполнено

## 1. Какие наиболее распространенные атаки предотвращает джанго

Насколько я понял, в джанго уже есть встроенная защита от нескольких частых атак, если использовать ее нормально и не отключать без необходимости.

### CSRF

Джанго умеет защищать сайт от CSRF.  
Если совсем просто, то это атака, когда от имени пользователя пытаются отправить запрос без его ведома.  
В джанго для этого, насколько я понял, используется специальная проверка токена или секрета в запросе.

### XSS

От XSS джанго тоже частично защищает.  
Шаблоны по умолчанию экранируют опасные символы, поэтому просто так вставить вредный код уже сложнее.  
Но, как я понял, если разработчик сам отключит экранирование, то проблема может появиться снова.

### SQL-инъекции

От SQL-инъекций джанго тоже помогает защищаться.  
Обычные запросы через ORM безопаснее, потому что данные пользователя не вставляются в запрос совсем уж напрямую.  
Хотя, если писать SQL вручную, то ошибиться все равно можно.

### Clickjacking

Еще есть защита от clickjacking.  
Насколько я понял, она связана с заголовком `X-Frame-Options`. Это нужно, чтобы другой сайт не мог открыть страницу в рамке и как-то обманом заставить человека нажать не туда.

Итог:

Наиболее распространенные атаки, от которых джанго помогает защищаться, это:

- CSRF
- XSS
- SQL-инъекции
- clickjacking

## 2. Как устроено управление пользовательскими сессиями в джанго

Сессии в джанго нужны для того, чтобы сайт помнил пользователя между запросами.

Работает это так:

1. Для работы сессий подключается `SessionMiddleware`.
2. Дальше джанго создает сессию для пользователя.
3. Сами данные, насколько я понял, обычно хранятся на сервере, часто в базе данных.
4. В браузер уходит куки, где лежит идентификатор сессии.
5. Потом при следующих запросах браузер отправляет этот куки обратно, а джанго уже по нему понимает, какая это сессия.
6. После этого с данными можно работать через `request.session`.

Если используется хранение в базе данных, то данные сессий обычно лежат в таблице `django_session`.

Через сессии можно хранить, например:

- информацию о том, что пользователь вошел в систему
- его идентификатор
- какие-то временные служебные данные

Для безопасности сессий в джанго есть важные настройки:

- `SESSION_COOKIE_SECURE`  куки идут только по HTTPS
- `SESSION_COOKIE_HTTPONLY`  JavaScript не может просто так прочитать куки
- `SESSION_COOKIE_SAMESITE`  это тоже помогает от части межсайтовых атак
- `SESSION_COOKIE_AGE`  задает время жизни сессии
- `SESSION_EXPIRE_AT_BROWSER_CLOSE`  позволяет завершать сессию после закрытия браузера

Еще важный момент, который я увидел в документации, это то, что джанго не добавляет идентификатор сессии в адресную строку. Это тоже полезно для безопасности.

Если пользователь выходит из системы, то сессия очищается. Старые сессии тоже должны удаляться по времени жизни.
