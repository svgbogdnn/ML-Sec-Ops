1. 
Название CVE - CVE-2025-4427
Источник — https://nvd.nist.gov/vuln/detail/CVE-2025-4427
Тип (OWASP REST API TOP 10) — Broken Authentication
Недостаток — в API-компоненте возможен обход аутентификации, из-за чего атакующий получает **доступ к защищенным API-ресурсам** без корректных учетных данных
Причина — в API-компоненте реализован `authentication bypass` через альтернативный путь доступа к API —— из-за чего запросы к защищенным API-ресурсам проходят **без корректной проверки учетных данных**
Последствия — несанкционированный доступ к защищенным API-ресурсам приложения

2. 
Название CVE - CVE-2025-58121
Источник — https://nvd.nist.gov/vuln/detail/CVE-2025-20348
Тип (OWASP REST API TOP 10) — Broken Function Level Authorization
Недостаток — в нескольких REST API endpointах Checkmk пользователь с низкими привилегиями может выполнять действия, которые разрешены только администратору, и также получать чувствительную информацию
Причина — отсутствует нормальная авторизационная проверка на части REST API endpointов. Сервер проверяет, что пользователь вошел в систему —— но недостаточно проверяет, имеет ли он право выполнять именно этот API-вызов
Последствия — выполнение неразрешенных действий и получение чувствительной информации при наличии **только низкоуровневой учетной записи**

3. 
Название CVE - CVE-2025-10732
Источник — https://nvd.nist.gov/vuln/detail/CVE-2025-10732
Тип (OWASP REST API TOP 10) — Broken Object Property Level Authorization
Недостаток — пользователь через REST API endpoint может получить чувствительные настройки и ключи, без разрешения на это
Причина — некорректная реализация контроля доступа на endpointе `/wp-json/sureforms/v1/srfm-global-settings`
Последствия — утечка API ключей, административных email адресов и настроек безопасности формы

**1.** 
На главной странице у нас: 
`{ "создать базу": "/createdb",     "посмотреть информацию обо всех пользователях": "/users/v1",     "посмотреть подробную информацию обо всех пользователях": "/users/v1/_debug",     "регистрация нового пользователя": "/users/v1/register (HTTP POST)",     "вход в приложение": "/users/v1/login (HTTP POST)",     "просмотр пользователя по имени": "/users/v1/{username}",     "удалить пользователя по имени (только для админов)": "/users/v1/{username} (HTTP DELETE)",     "изменить email пользователя": "/users/v1/{username}/email (HTTP PUT)",     "изменить пароль пользователя": "/users/v1/{username}/password (HTTP PUT)",     "все книги": "/books/v1",     "добавить книгу": "/books/v1 (HTTP POST)",     "просмотр книги": "/books/v1/{book}",      } `
То есть приложение вывело **список всех доступных ендпоинтов**. Получается, что даже **без авторизации** можно увидеть какие маршруты есть в апи, где находится регистрация, логин и, например, дебаг страница.
Вывод - приложение раскрывает **внутреннюю структуру API**. Это не критично, однако злоумышленнику не придется угадывать маршруты —— приложение само показало куда можно обращаться для чего-то нехорошего.
Тип недостатка - **Improper Inventory Management** (из OWASP API Top 10). Открытая карта ендпоинтов на главной странице, из-за чего без авторизации видно структуру API. OWASP относит к этой категории проблемы с учетом, документированием и контролем API endpointов.
Меры предотвращения:
1. Не показывать публично полный список endpointов, так еще и на главной странице.
2. Маршрут _debug должен быть отключен в прод-версии приложения, или хотя бы закрыт закрыт авторизацией.
3. Вести актуальный список всех API endpointов: какие публичные, какие служебные, какие вообще должны быть удалены.
4. Разделять dev/test endpointы и прод-окружения, чтобы отладочные функции не попадали в рабочую версию приложения.
5. Закрывать непубличные endpointы авторизацией.



**2.** 
После этого решил проверить ендпоинт со списоком пользователей 
`http://localhost:8080/users/v1`
и вижу 
`{"users":[{"email":"mail1@mail.com","username":"name1"},{"email":"mail2@mail.com","username":"name2"},{"email":"admin@mail.com","username":"admin"}]}`
То есть приложение без логина, без токена, да вообще без ничего просто сразу выдало список всех пользователей так еще и их почты, это вообще отлично.
Вывод - API отдает больше данных, чем нужно. Плохой человек может взять ник пользователя из списка и обращаться к ендпоинту конкретного пользователя.
Тип недостатка - **Broken Object Property Level Authorization**. Ендпоинт `http://localhost:8080/users/v1` возвращает не один чужой объект по `username` —— а сразу весь список пользователей с их свойствами `username` и `email`. OWASP относит это к ситуациям, когда API возвращает свойства объекта, которые пользователь не должен видеть.
Меры предотвращения:
1. Требовать авторизацию перед выдачей списка пользователей.
2. Проверять права доступа перед каждым ответом, где есть пользовательские данные.
3. Возвращать только минимально необходимые поля.
4. Разрешить получение полного списка пользователей только администраторам.
5. Для каждого endpointа заранее определить, какие поля можно отдавать наружу, а какие должны оставаться скрытыми.



**3.**
После списка пользователей я пошел по конкретным пользователям по никам
`http://localhost:8080/users/v1/name1`
Ответ - 
`{"username": "name1", "email": "mail1@mail.com"}`

`http://localhost:8080/users/v1/name2`
Ответ - 
`{"username": "name2", "email": "mail2@mail.com"}`

`http://localhost:8080/users/v1/name3`
Ответ - 
`{ "status": "fail", "message": "User not found"}`
Не, ну вдруг в базе написанно нет, а на деле есть.

`http://localhost:8080/users/v1/admin`
Ответ - 
`{"username": "admin", "email": "admin@mail.com"}`

Получается что приложение отдает данные конкретного пользователя просто по значению `username` в URL. При этом не требуется ничего - ни логин, ни пароль, ни токен. Сервер фактически берет параметр из адреса, ищет юзера в базе и возвращает его данные —— но не проверяет, имеет ли запрашивающий право смотреть именно этот профиль.
Вывод - Сервер отдает чужой объект без проверки прав. 
Тип недостатка - **Broken Object Level Authorization**, он же BOLA / IDOR (из OWASP API Top 10). OWASP относит это к ситуациям, когда API endpoint  получается идентификатор объекта от клиента (`id`, `username`) и выполняет действие с этим объектом, но не проверяет права доступа именно к этому объекту.
Меры предотвращения:
1. Требовать авторизацию для endpointа `/users/v1/{username}`.
2. После авторизации проверять не только сам факт входа, но и право доступа к конкретному объекту.
3. Обычному пользователю разрешить получать только собственный профиль.
4. Не доверять параметру username из URL.
5. Использовать централизованный механизм авторизации, чтобы проверка прав не писалась случайно в отдельных местах, а выполнялась одинаково для всех похожих endpointов.



**4.**
Теперь проверю ендпоинт `_debug`, которого в нормальном проде вообще не должно быть. 
Перехожу по 
`http://localhost:8080/users/v1/_debug`
И получаю 
`{"users":[{"admin":false,"email":"mail1@mail.com","password":"pass1","username":"name1"},{"admin":false,"email":"mail2@mail.com","password":"pass2","username":"name2"},{"admin":true,"email":"admin@mail.com","password":"pass1","username":"admin"}]}`

То есть получаю полный дамп вообще всех юзеров - ники, почты, проверку на админа, пароли. И все это конечно же без авторизации, ну а зачем она нужна. Полная компрометация учетных записей.
Вывод - в приложении оставлен открытый debug endpoint, который без авторизации раскрывает всю информацию о всех пользователях.
Тип недостатка - **Security Misconfiguration** (из OWASP API Top 10). По OWASP, недостаток может возникать на разных уровнях API: от сетевого уровня до уровня приложения. Дополнительно это и CWE-489, то есть Acitve Debug Code, потому что в приложении оставлена вся активная debug функциональность.
Меры предотвращения:
1. Полностью убрать /users/v1/_debug из прод-версии приложения.
2. Никогда не возвращать пароли в API-ответах.
3. Хранить пароли только в виде безопасных хешей, а не в открытом виде.
4. Перед публикацией приложения проверять, что в нем не осталось debug endpointов, тестовых маршрутов и лишних служебных функций.
5. Настроить разные конфигурации для разработки и прода, чтобы debug-режим не мог случайно попасть в рабочую версию.
