🔸 Секрет 1 — строка подключения к PostgreSQL [ВЫСОКИЙ]

Файл docker-compose-postgres.yml
Строка 19
Тип детектора Postgres
Найденное значение postgresql://webgoat:webgoat@webgoat_db:5432

⬩ Почему это секрет?

В найденной строке находится подключение к PostgreSQL бд. Внутри строки прямо указаны учетные данные

webgoat:webgoat

Первое значение — имя пользователя, второе — пароль. Также указан хост базы данных webgoat_db и порт 5432. TruffleHog нашел это как **Detector Type: Postgres**, а в логе указаны файл docker-compose-postgres.yml, строка 19 и сам результат postgresql://webgoat:webgoat@webgoat_db:5432 .

Очевидно, что логин и пароль к базе не должны лежать прямо в docker-compose или в истории Git. Например, OWASP относит database credentials, то есть наш случай, к секретам.

⬩ Правильный способ хранения

Строку подключения лучше не хранить целиком в репозитории — пароли не должны присутствовать в коде в любом виде. Правильнее вынести чувствительные части отдельно

POSTGRES_USER=${POSTGRES_USER}
POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
POSTGRES_HOST=${POSTGRES_HOST}
POSTGRES_PORT=${POSTGRES_PORT}

Реальные значения нужно хранить в .env, переменных окружения, CI / CD secrets или secret manager. .env при этом должен быть добавлен в .gitignore чтобы не было шансов случайно попасть в Git.

Если такие данные уже попали в репозиторий, их нужно считать скомпрометированными — заменить пароль, удалить секрет из текущих файлов и при необходимости очистить Всю историю Gitа.

🔸 Секрет 2 — URI с логином и паролем [СРЕДНИЙ]

Поле Значение
Hash коммита 68b80fa14f8c2ece71df20ac0a3e3e710bbcd368
Дата/Commit 2012-09-09
Файл webgoat-5.4/src/main/scripts/webgoat.sh
Строка 53
Тип детектора URI
Найденное значение http://guest:guest@127.0.0.1:8080

⬩ Почему это секрет?

В этом URI прямо указаны учетные данные для доступа

guest:guest

Формат такой:

http://username:password@host:port

То есть guest до двоеточия это имя пользователя, а guest после двоеточия это уже пароль пароль. TruffleHog определил это как Detector Type: URI.

Это опасно даже если адрес локальный (127.0.0.1), потому что проблема не в самом адресе — а в том, что логин и пароль записаны в скрипте и попали в историю Git. Кроме этого, использование формата user:password в поле userinfo является устаревшим, а приложения не должны хранить такие данные в незашифрованном виде.

⬩ Правильный способ хранения

Нельзя хранить логин и пароль прямо внутри URL, особенно в shell-скрипте, конфигурационном файле или другом файле, который попадает в Git. Формат http://user:password@host плох тем, что учетные данные становятся частью обычной строки — они могут попасть в историю команд, логи, скриншоты, историю Git или вывод ошибок.
Правильно делать так:

  1. Убрать пароль из URL

    В адресе оставить только хост и порт, например http://127.0.0.1:8080

  2. Передавать учетные данные отдельно

    Логин и пароль должны передаваться не как часть URL, а через отдельный механизм аутентификации.

  3. Вынести значения из скрипта

    В самом shell-скрипте не должно быть реальных значений guest:guest. Вместо этого нужно использовать переменные

WEBGOAT_USER="${WEBGOAT_USER}"
WEBGOAT_PASSWORD="${WEBGOAT_PASSWORD}"
WEBGOAT_HOST="127.0.0.1"
WEBGOAT_PORT="8080"

  1. Хранить реальные секреты вне репозитория

    Для локального запуска можно использовать .env, но сам .env должен быть добавлен в .gitignore.

  2. Заменить пароль, если он уже попал в Git

    Если логин и пароль уже были закоммичены, простого удаления строки недостаточно. Старое значение остается в истории Gitа, поэтому пароль нужно считать скомпрометированным и заменить на новый.

Строка 10
Тип детектора JDBC
Найденное значение jdbc:postgresql://webgoat_db:5432/webgoat?user=webgoat&password=webgoat

⬩ Почему это секрет?

Это JDBC-строка подключения к базе данных PostgreSQL. В ней указаны не только адрес базы и имя базы данных но и учетные данные — user=webgoat&password=webgoat.

То есть в конфигурации прямо записаны логин и пароль от базы данных.

Опасность в том что любой человек, получивший доступ к репозиторию или его истории, может увидеть параметры подключения и попробовать использовать их для доступа к базе данных.

⬩ Правильный способ хранения

Нельзя хранить JDBC-строку подключения вместе с реальным логином и паролем прямо в docker-compose.yml, Java-конфиге, shell-скрипте или другом файле, который попадает в Git.
Правильно делать так:

  1. Разделить строку подключения и секретные значения

  2. Передавать логин и пароль через переменные окружения

    Например:

POSTGRES_USER: ${POSTGRES_USER}
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
  1. Не коммитить .env с реальными значениями
  2. Использовать secret manager или защищенные переменные CI/CD
  3. Заменить пароль после утечки

⬩ Почему это секрет?

webgoat в контексте SQL Server-детектора и файла web.xml похоже на значение из конфигурации подключения к базе данных: имя пользователя, пароль, имя базы.

Опасность в том, что такие значения часто оказываются дефолтными логинами или паролями. Если приложение использует одинаковое значение webgoat как имя пользователя, пароль или имя базы — атакующий может попробовать его при подключении к базе данных.

⬩ Правильный способ хранения

Нельзя хранить учетные данные базы данных или похожие конфигурационные секреты прямо в web.xml или других XML-конфигурациях, если эти файлы попадают в Git.

Правильно делать так:

  1. Не использовать дефолтные пароли

    Значения webgoat, admin, password, test, guest нельзя использовать как реальные пароли. Они легко угадываются и часто первыми проверяются при атаке.

  2. Вынести значение из XML-конфига

    В web.xml лучше оставить только ссылку на внешнюю настройку, а не само значение секрета.

  3. Использовать разные значения для разных окружений

    Для локальной разработки, тестового стенда и реального окружения должны быть разные учетные данные.

  4. Хранить секреты отдельно от кода

    Реальные значения нужно хранить в переменных окружения, защищенных переменных CI / CD или secret manager.

  5. Заменить значение, если оно попало в Git

⬩ Почему это секрет?

В этом значении снова используется URI-формат с учетными данными внутри адреса — http://guest:guest@127.0.0.1/
Здесь первое guest — имя пользователя, второе guest — пароль.

Этот секрет похож на секрет #2, но это отдельная найденная строка: там был адрес с портом :8080, а здесь адрес без явного порта. То есть учетные данные встроены прямо в URL внутри shell-скрипта.

Опасность в том, что URL с логином и паролем легко попадает в историю Git, логи, историю команд, скриншоты или вывод ошибок.

⬩ Правильный способ хранения

Нельзя хранить логин и пароль прямо внутри URL, даже если адрес ведет на 127.0.0.1. Локальный адрес не делает пароль безопасным — учетные данные лежат в открытом виде в скрипте и попадают в Git-историю. Также нельзя использовать одинаковые дефолтные значения вроде guest:guest.

Правильно делать так:

  1. Убрать учетные данные из URL

    В скрипте должен остаться только адрес без логина и пароля — http://127.0.0.1.

  2. Передавать логин и пароль отдельно

    Учетные данные должны передаваться через отдельный механизм авторизации, например через HTTP-заголовок Authorization — а не через user:password@host.

  3. Вынести значения в переменные окружения

    В скрипте лучше использовать не реальные значения, а переменные —

WEBGOAT_USER="${WEBGOAT_USER}"
WEBGOAT_PASSWORD="${WEBGOAT_PASSWORD}"
WEBGOAT_HOST="127.0.0.1"

  1. Хранить реальные значения вне Git

    Для локального запуска можно использовать .env но его нужно добавить в .gitignore.

  2. Заменить пароль после попадания в репозиторий

    Если такие данные уже попали в репозиторий, их нужно считать скомпрометированными — заменить пароль, удалить секрет из текущих файлов и при необходимости очистить Всю историю Gitа.
