#!/usr/bin/env python3
from flask import Flask
from mod_api import mod_api
app = Flask('vuln_app')
app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'
app.register_blueprint(mod_api, url_prefix='/api')

Недостаток

  • Секретный ключ SECRET_KEY записан прямо в исходном коде приложения.
    Это очень плохо потому что SECRET_KEY во Flask используется для безопасной подписи session cookie и других защитных механизмов приложения. В доках Flaskа написано, что секретный ключ нельзя раскрывать и нельзя коммитить в код. Если такой файл попадет в репозиторий или утечет — злоумышленник сможет использовать этот ключ для подделки или изменения подписанных данных, например сессионных cookie.
    Если атакующий узнает SECRET_KEY он может попытаться подделать данные сессии. Например, если приложение хранит в session cookie информацию о пользователе или его роли — то при знании ключа появляется риск изменить эти данные и выдать себя за другого пользователя или администратора. Также этот ключ могут использовать расширения Flask для CSRF защиты и других механизмов безопасности.

Рекомендации по устранению

  • Не хранить SECRET_KEY прямо в коде. Например, вынести ключ в переменную окружения:
import os
app.config['SECRET_KEY'] = os.environ.get('SECRET_KEY')
  • Хранить значение ключа отдельно от кода — например в .env-файле, настройках сервера или секретах CI / CD.
  • Добавить .env и другие файлы с секретами в .gitignore, чтобы они не попали в репозиторий.
  • Использовать разные ключи для разработки и для продакшена.
  • Если ключ уже мог попасть в открытый доступ, его нужно заменить на новый. После замены старые сессии пользователей могут стать недействительными, но это нормальное поведение при ротации секретного ключа.

🔸 Фрагмент кода 2

from flask_wtf import Form
from wtforms import TextField
class LoginForm(Form):
    username = TextField('username')
    password = TextField('password')

Недостатки

  • Поле password сделано как обычное текстовое поле TextField.
    Из-за этого пароль будет отображаться на экране как обычный текст, а не скрываться точками или звездочками. Для пароля нужно использовать PasswordField.
  • Нет валидаторов для обязательного заполнения.
    Сейчас форма явно не требует чтобы username и password были заполнены. Пользователь может отправить пустые значения. В WTForms для таких проверок используются валидаторы, например DataRequired. Валидаторы проверяют, соответствует ли введенное значение нужному условию и при ошибке вызывают ValidationError.
  • Нет ограничения длины ввода.
    Пользователь может отправить слишком длинный username или password. Это может привести к ошибкам обработки, проблемам в базе данных или лишней нагрузке. Для ограничения длины обычно используют Length.

Рекомендации по устранению

  • Вместо password = TextField('password') нужно использовать PasswordField (т.е. password = PasswordField('password')), чтобы пароль не отображался на экране открытым текстом.
  • Поле username лучше оформить как StringField (т.е. вместо username = TextField('username') использовать username = StringField('username')), потому что это обычный текстовый идентификатор пользователя а не пароль.
  • Добавить проверку (валидаторы) обязательного заполнения. Для username и password нужно добавить DataRequired() или InputRequired(), чтобы форма не принимала пустые значения. WTForms валидаторы проверяют, соответствует ли ввод нужному условию, а при ошибке вызывают ValidationError.
  • Ограничить длину логина и пароля. Например для username поставить Length(min=3, max=64), а для password - Length(min=8, max=128)`. Это защитит от пустых, слишком коротких и чрезмерно длинных значений.
  • Использовать FlaskForm вместо обычного Form. FlaskForm лучше подходит для Flask-приложения и дает нормальную интеграцию с Flask-WTF, включая CSRF-защиту.
  • Добавить CSRF-токен. В HTML-форме вывести {{ form.csrf_token }} — это нужно чтобы защитить форму логина от поддельных POST-запросов с другого сайта.

def post(self):
    username = self.get_argument('username')
    password = self.get_argument('password').encode('utf-8')
    email = self.get_argument('mail')
try:
    username = username.lower()
    email = email.strip().lower()
    user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})
    user.validate()
    save_user(self.db_conn, user)
except Exception, e:
    return self.render_template("success_create.html")

Недостатки

  • Пароль не хешируется перед сохранением, и хранитс просто в открытом виде.
    В коде пароль только переводится в байты через .encode('utf-8'), но это не его не защищает. Если такой пароль сохранить в базу он фактически будет храниться в открытом виде. При утечке базы злоумышленник сразу получит настоящие пароли пользователей.
  • При любой ошибке показывается страница успешного создания пользователя.
    В блоке except Exception приложение возвращает success_create.html. Это неправильно потому что ошибка могла произойти где угодно: невалидный email, занятый username, ошибка базы данных, ошибка валидации. Но пользователь все равно увидит страницу успеха и будет думать что аккаунт создан.
  • Исключение никак не логируется.
    Код просто проглатывает ошибку и разработчик потом не увидит что именно сломалось.

Рекомендации по устранению

  • Хешировать пароль перед сохранением.
    Вместо сохранения password после .encode('utf-8') нужно сохранять только хеш пароля. Для этого лучше использовать специальные алгоритмы для паролей, например Argon2id, bcrypt, scrypt или PBKDF2.
  • Страницу успеха показывать только после реального сохранения пользователя, то есть е возвращать success_create.html при ошибке.
    success_create.html должен возвращаться только после того как прошли user.validate() и save_user(...). Сейчас в коде при любой ошибке приложение все равно показывает успех, хотя пользователь мог вообще не создаться.
  • В блоке except возвращать страницу ошибки, а не страницу успеха — то есть разделить успешный сценарий и ошибку.
    Если произошла ошибка — нужно показать пользователю понятное сообщение: например “Пользователь не был создан”, “Некорректный email” и т.д. При этом нельзя показывать пользователю технический traceback или внутренние детали приложения, потому что ошибки могут раскрывать информацию о системе.
  • Разные ошибки обрабатывать отдельно.
    Не стоит ловить все через общий except Exception без разбора. Ошибку валидации, ошибку дубликата пользователя и ошибку базы данных лучше обрабатывать разными блоками except, потому что действия в каждом случае разные.
  • Добавить логирование ошибок.
    Если произошла неизвестная ошибка — ее нужно записать в лог. Удобно использовать logger.exception(...) потому что он записывает сообщение об ошибке вместе со stack trace и вызывается именно внутри обработчика исключения.
  • Нормализовать входные данные до создания пользователя.
    username и email нужно приводить к нормальному виду — например, убрать пробелы через .strip(), привести к нижнему регистру через .lower(), проверить формат email и допустимую длину username. Это точно уменьшит риск дублей и ошибок при сохранении.

🔸 1. Какие наиболее распространенные атаки предотвращает django?

Django имеет встроенные механизмы защиты от нескольких распространенных атак на веб-приложения. Однако Django не делает приложение полностью безопасным автоматически — но он закрывает многие типовые ошибки, если разработчик использует стандартные механизмы фреймворка и не отключает их вручную.

1. XSS — Cross-Site Scripting

XSS — атака при которой злоумышленник пытается внедрить JavaScript-код в страницу, которую потом откроет другой пользователь. Django защищает от XSS за счет автоматического экранирования данных в шаблонах. То есть если в шаблон передать строку с тегами <script> то Django по умолчанию не даст браузеру воспринять ее как настоящий HTML/JavaScript. Опасные символы будут преобразованы в безопасные HTML-сущности. Например <, >, ", ', & будут показаны как текст, а не как начало HTML-тега.

2. CSRF — Cross-Site Request Forgery

CSRF — атака при которой злоумышленник пытается заставить браузер авторизованного пользователя отправить нежелательный запрос на сайт. Django защищает от CSRF с помощью CSRF-токенов. В формы добавляется специальный токен, который должен присутствовать в небезопасных запросах, например в POST реквестах. Если запрос пришел без правильного токена, Django его отклонит. Это мешает стороннему сайту просто так отправить форму от имени пользователя.
То есть Django проверяет что запрос действительно был сформирован внутри приложения, а не пришел с чужого сайта. Для этого нужно чтобы в проекте был включен CsrfViewMiddleware, а в HTML-формах использовался CSRF-токен.

3. SQL-инъекции

SQL-инъекция — атака при которой злоумышленник пытается вставить SQL-код в пользовательский ввод. Django защищает от SQL-инъекций за счет ORM. Когда разработчик использует стандартные методы Django ORM, параметры запроса передаются отдельно от SQL-кода. Это значит что пользовательский ввод не превращается в часть SQL-команды, а обрабатывается как значение. Но риск останется если разработчик пишет сырой SQL вручную через raw() или cursor.execute() и сам склеивает строку запроса с пользовательским вводом.

4. Clickjacking

Clickjacking — атака при которой злоумышленник встраивает страницу настоящего сайта в невидимый или замаскированный iframe и заставляет пользователя нажать не туда. Django защищает от clickjacking с помощью специальных HTTP-заголовков, в частности через X-Frame-Options. Для этого используется middleware который запрещает или ограничивает встраивание страниц сайта во фреймы.

5. Host Header Injection

Host Header Injection — атака связанная с подменой заголовка Host. Django защищает от таких атак через настройку ALLOWED_HOSTS. В этой настройке указывается список доменов, с которых приложение имеет право принимать запросы. Если заголовок Host не совпадает с разрешенным значением — Django вызывает ошибку SuspiciousOperation.

6. Атаки на сессии

Django также помогает защищать пользовательские сессии. Для безопасности сессий Django поддерживает настройки cookie — HttpOnly, Secure, SameSite, время жизни сессии и другие параметры. Например HttpOnly мешает JavaScript читать cookie, что снижает риск кражи сессии при XSS. Secure заставляет передавать cookie только по HTTPS. SameSite помогает уменьшить риск CSRF-атак.

7. Небезопасная передача данных без HTTPS

Django имеет настройки которые помогают безопаснее работать через HTTPS. Например можно включить перенаправление с HTTP на HTTPS, настроить secure-cookie и использовать HSTS. Это не атака в прямом смысле, скорее защита от перехвата данных при передаче.

🔸 2. Описать, как устроено управление пользовательскими сессиями в django

Сессии в Django нужны для чтобы сайт мог помнить пользователя между разными HTTP-запросами. Сам HTTP не хранит состояние — если пользователь открыл страницу, потом перешел на другую, сервер сам по себе не знает что это тот же самый человек. Сессия решает эту проблему — Django связывает браузер пользователя с определенными данными на сервере.

Как включить

Чтобы сессии работали, в проекте должны быть подключены два элемента.

В INSTALLED_APPS должно быть:

'django.contrib.sessions'

В MIDDLEWARE должно быть:

'django.contrib.sessions.middleware.SessionMiddleware'

SessionMiddleware добавляет к каждому запросу объект request.session. Через него в коде можно читать и записывать данные сессии.

Где хранятся данные сессии

По умолчанию Django хранит данные сессий в базе данных, через модель:

'django.contrib.sessions.models.Session'

После миграций в базе появляется таблица:

'django_session'

В этой таблице хранятся данные сессий, срок их действия и ключ сессии. При этом в браузер пользователя обычно отправляется не вся информация сессии — а только cookie с идентификатором сессии. То есть пользователь не получает сами данные — он получает только ключ по которому Django потом находит данные на сервере. Django также позволяет настроить другие хранилища — базу данных, cache, filesystem или cookie-based backend.

Рабочий цикл сессии

1. Пользователь впервые открывает сайт

Пользователь заходит на сайт, например http://example.com/. Браузер отправляет обычный HTTP-запрос. Если cookie сессии еще нет — Django пока не знает этого пользователя как постоянного посетителя.

2. Запрос проходит через SessionMiddleware

Когда запрос приходит в Django, его обрабатывает SessionMiddleware. Middleware смотрит, есть ли в запросе cookie с именем sessionid. Если cookie есть — Django берет из него ключ сессии. Если cookie нет — Django работает с новой пустой сессией.
В исходном коде SessionMiddleware при обработке запроса Django берет значение из request.COOKIES по имени session cookie и создает request.session через SessionStore.

3. В коде появляется объект request.session

После middleware во view можно работать с сессией как со словарем:

request.session['cart_id'] = 21
request.session['theme'] = 'pink rose'
request.session['visited'] = True

request.session — объект через который можно хранить и получать произвольные данные на посетителя сайта. Например, можно сохранить id корзины, язык интерфейса, временный флаг, id пользователя после авторизации или другие служебные данные.

4. Если сессия изменилась то Django сохраняет ее

Если во view что-то записали в request.session — Django помечает сессию как измененную. Перед отправкой ответа пользователю Django сохраняет данные сессии в выбранное хранилище.
По умолчанию это база данных. То есть Django сохраняет данные в таблицу django_session, а не отправляет все эти данные в браузер.
Например request.session['user_color'] = 'pretty green' и после этого Django сохранит значение на сервере, а браузеру отправит только cookie с идентификатором сессии.

5. Браузеру отправляется cookie sessionid

В ответе сервер отправляет браузеру cookie примерно такого вида Set-Cookie: sessionid=svgforlife21.... Значение svgforlife21... это ключ сессии. Он нужен чтобы при следующем запросе Django понял, какую запись сессии искать в хранилище.

6. При следующем запросе браузер отправляет sessionid обратно

Когда пользователь открывает следующую страницу, браузер автоматически отправляет cookie обратно на сервер Cookie: sessionid=svgforlife21....
Django берет этот ключ, ищет соответствующую сессию в хранилище и снова делает данные доступными через request.session. Так сайт понимает, что это тот же самый браузер который уже был на сайте раньше.

7. Если пользователь входит в аккаунт

Когда пользователь проходит логин, Django authentication system связывает его аккаунт с текущей сессией. Встроенная система аутентификации в Django работает с пользователями, группами, правами и cookie-based user sessions.
При входе Django сохраняет в сессию служебные данные, по которым потом понимает, какой пользователь авторизован. После этого на следующих страницах можно обращаться к request.user и Django будет знать, авторизован пользователь или нет.

8. При логине Django меняет ключ сессии

При успешном входе Django вызывает смену session key чтобы защититься от session fixation, от атаки когда нехороший человек заранее навязывает жертве известный session ID, а потом пытается использовать его после авторизации. django.contrib.auth.login() вызывает создание нового session key, сохраняя текущие данные сессии чтобы снизить риск session fixation.

9. При выходе из аккаунта сессия очищается

Когда пользователь нажимает logout, Django удаляет данные связанные с авторизацией. Обычно после выхода пользователь уже не считается авторизованным, а старые данные сессии очищаются. Это нужно чтобы после выхода нельзя было продолжить использовать прежнюю авторизованную сессию.

Какие бывают хранилища сессий

Django позволяет настроить, где именно будут храниться данные сессий.

  • Стандартный вариант Database backend — данные хранятся в базе данных, обычно в таблице django_session.
  • Cache backend — данные хранятся в кэше, например Redis или Memcached.
  • File backend — данные хранятся в файлах на сервере.
  • Cookie-based backend — данные хранятся прямо в cookie но подписываются.

Главные настройки для безопасности cookie сессии в Django

Настройка Что делает
SESSION_COOKIE_HTTPONLY = True Запрещает JavaScript читать session cookie что снижает риск кражи cookie при XSS
SESSION_COOKIE_SECURE = True Cookie отправляется только по HTTPS, поэтому его сложнее перехватить в сети
SESSION_COOKIE_SAMESITE = 'Lax' Ограничивает отправку cookie при межсайтовых запросах и помогает против части CSRF-атак
SESSION_COOKIE_AGE = 1209600 Задает время жизни сессии в секундах (по дефолту стоит 2 недели)
SESSION_EXPIRE_AT_BROWSER_CLOSE = True Завершает сессию после закрытия браузера
