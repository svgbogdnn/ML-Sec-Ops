##Часть I
###Инструменты поиска секретов в CI/CD репозиториях

TruffleHog инструмент для автоматического поиска секретов в истории git репозиториев. Он сканирует каждый коммит во всех ветках и ищет строки с высокой энтропией, характерной для паролей, токенов, ключей. Поддерживает сканирование локальных репозиторие, удалённых URL напрямую.
GitLeaks альтернатива TruffleHog с акцентом на скорость. В отличие от TruffleHog GitLeaks работает по большей части по набору регулярных выражений для известных форматов секретов (AWS, GitHub, Slack и др.), что снижает количество ложных срабатываний

Оба инструмента легко встраиваются в CI/CD пайплайны и запускаются автоматически при каждом push или pull request. Это соответствует подходу DevSecOps, смещение проверок безопасности на ранний этап разработки

##Часть II
Запустил Docker-контейнер с Python: `docker run -it python:buster /bin/bash`. Внутри контейнера установил TruffleHog командой `pip install truffleHog`. После установки запустил сканирование репозитория с одновременной записью лога в файл: `trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git | tee -a log.txt`. Он начал обходить всю историю коммитов в ветке develop.
В процессе сканирования TruffleHog нашёл много подозрительных фрагментов кода. Часть из них оказалась ложными срабатываниями, длинные математические константы в JavaScript-коде вроде `0.50000000001`. Ожидаемое поведение, инструмент ищет по энтропии и не может понять, случайная ли строка является осмысленным секретом или просто сложным кодом. Результаты автоматического сканирования требуют ручной валидации
После завершения сканирования с помощью `grep` нашёл в файле лога конкретные секреты.

Первый секрет AWS Access Key ID. В файле `.travis.yml` в истории коммитов оказалась строка `access_key_id: AKIAJQLKPGHXRH2AH5QA`. Ключ доступа AWS предоставляет программный доступ к облачной инфраструктуре. Злоумышленник может использовать его для создания дорогостоящих ресурсов, кражи, уничтожения данных. Правильный способ хранить ключи в переменных окружения CI/CD системы (GitHub Secrets, Travis CI Environment Variables) и никогда не вписывать в файлы конфигурации репозитория
Второй секрет — приватный RSA-ключ. В файле `webgoat-server/privatekey.key` был закоммичен приватный ключ: строка `-----BEGIN PRIVATE KEY-----`. Приватные ключи используются для расшифровки TLS-трафика и аутентификации серверов. Их утечка позволяет проводить атаки типа Man-in-the-Middle и выдавать свой сервер за настоящий. Файлы с приватными ключами никогда не должны попадать в репозиторий, их нужно добавлять в `.gitignore` и доставлять на сервер отдельным безопасным каналом
Третий секрет JWT-ключ для подписи токенов. В файле `webgoat-lessons/jwt/src/main/java/org/owasp/webgoat/plugin/JWTRefreshEndpoint.java` нашёл строку `String PASSWORD = "bm5nhSkxCXZkKRy4"`. Этот ключ используется для криптографической подписи JWT-токенов авторизации. Зная ключ, злоумышленник может подделывать токены и авторизоваться под любым пользователем без знания его пароля. Ключи шифрования должны инжектироваться в приложение через переменные окружения

Четвёртый секрет хардкодированный пароль администратора. В тесте `webgoat-integration-tests/src/test/java/org/owasp/webgoat/ChallengeTest.java` была строка `String PASSWORD = "!!webgoat_admin_1234!!"`. Такой пароль в исходном коде даёт злоумышленнику административный доступ к приложению. Пароли и credentials не должны находиться в коде, нужно передавать их через переменные окружения, внешние конфиги, которые исключены из системы контроля версий.
Пятый секрет, данные для подключения к базе данных. В файле `docker-compose-postgres.yml` нашёл строки `spring.datasource.url=jdbc:postgresql://webgoat_db:5432/webgoat?user=webgoat&password=webgoat` и `POSTGRES_PASSWORD=webgoat`. Эти данные дают прямой доступ к базе данных приложения. При утечке возможна полная компрометация пользовательских данных. В Docker-окружении для этого используют Docker Secrets или файл `.env`, добавленный в `.gitignore`

Итого TruffleHog вместе с ручной проверкой позволил найти 5 различных типов секретов в истории одного репозитория: AWS-ключ, приватный RSA-ключ, JWT-секрет, хардкодированный пароль и credentials базы данных. Все они попали в репозиторий в разные периоды и через разные файлы, что подтверждает важность автоматической проверки на каждом шаге CI/CD пайплайна
