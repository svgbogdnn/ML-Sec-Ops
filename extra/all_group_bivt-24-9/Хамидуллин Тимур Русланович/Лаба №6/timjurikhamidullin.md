# Найденные секреты

## 1. GitHub Token в CI/CD pipeline

### Расположение

Файл: `.github/workflows/release.yml`

### Пример найденного значения

```yaml
GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5
```

### Почему это является секретом

Данный токен используется для авторизации в GitHub API. Через него можно выполнять действия от имени репозитория: создавать релизы, загружать артефакты, делать push и запускать workflow.

Даже если токен позже был удалён из актуальной версии файла, он остаётся доступным в истории Git.

### Как хранить правильно

Подобные значения должны храниться:

- в GitHub Secrets;
- в HashiCorp Vault;
- в переменных окружения CI/CD.

После утечки токен необходимо немедленно отозвать и выпустить новый.

## 2. Приватный RSA-ключ

### Расположение

Файл: `webgoat-server/privatekey.key`

### Пример содержимого

```text
-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSk...
-----END PRIVATE KEY-----
```

### Почему это является секретом

Приватный ключ используется для шифрования и подписи данных. Если злоумышленник получит доступ к такому ключу, он сможет:

- расшифровывать трафик;
- подделывать подписи;
- выдавать себя за сервер.

### Как хранить правильно

Приватные ключи нельзя хранить в Git-репозитории. Для хранения используются:

- Vault;
- Kubernetes Secrets;
- защищённые HSM/KeyStore.

При обнаружении утечки ключ должен считаться скомпрометированным и быть перевыпущен.

## 3. Секреты Travis CI

### Расположение

Файл: `.travis.yml`

### Пример

```yaml
deploy:
  provider: releases
  token:
    secure: pJOLBnl6427PcVg/tVy/qB18JC7b8cKp...
```

### Почему это является секретом

Параметр `secure:` содержит зашифрованные данные Travis CI. Обычно там находятся:

- токены GitHub;
- Docker Hub credentials;
- webhook-ключи;
- API-ключи.

Хотя значения зашифрованы, сам факт наличия подобных секретов в репозитории создаёт риск компрометации.

### Как хранить правильно

Секреты должны храниться внутри самого CI/CD-сервиса и не попадать в Git-историю.
Также рекомендуется регулярно ротировать все используемые ключи.

## 4. Пароль, записанный прямо в коде

### Расположение

Файл:
`webgoat-lessons/password-reset/src/main/java/org/owasp/webgoat/password_reset/ResetLinkAssignment.java`

### Пример

```java
static final String PASSWORD_TOM_9 =
"somethingVeryRandomWhichNoOneWillEverTypeInAsPasswordForTom";
```

### Почему это является секретом

Пароль пользователя хранится в открытом виде прямо в исходном коде приложения. Любой разработчик или человек с доступом к репозиторию сможет увидеть его.

В реальном проекте это считается критической ошибкой безопасности.

### Как хранить правильно

Пароли нельзя хранить:

- в коде;
- в конфигурационных файлах;
- в Git.

Для пользователей необходимо хранить только hash пароля с солью (`bcrypt`, `argon2`).
Для тестовых значений — использовать переменные окружения.

## 5. JWT-токен в тестах

### Расположение

Файл:
`webgoat-lessons/jwt/src/test/java/org/owasp/webgoat/jwt/JWTFinalEndpointTest.java`

### Пример

```java
private static final String TOKEN_JERRY =
"eyJraWQiOiJ3ZWJnb2F0X2tleSIsImFsZyI6IkhTNTEyIn0...";
```

### Почему это является секретом

JWT-токен уже содержит подписанные данные пользователя. Если сервер принимает данный токен, злоумышленник сможет использовать его для авторизации.

Кроме того, наличие готового токена помогает анализировать схему подписи и потенциально подбирать секретный ключ.

### Как хранить правильно

JWT не должен храниться в репозитории в готовом виде. Для тестирования токены необходимо:

- генерировать динамически;
- подписывать отдельным тестовым ключом;
- хранить секрет подписи в Secret-хранилище.

# Дополнительные вопросы

## Что такое BFG Repo-Cleaner

BFG Repo-Cleaner — это инструмент для очистки истории Git-репозитория.

С его помощью можно:

- удалить секреты из старых коммитов;
- убрать большие файлы;
- заменить конфиденциальные строки на безопасные значения.

Инструмент работает значительно быстрее, чем `git filter-branch`.

Однако даже после очистки репозитория секрет считается скомпрометированным, так как кто-то мог успеть клонировать историю до удаления.

---

## Можно ли автоматизировать поиск секретов

Да, автоматизация поиска секретов считается хорошей практикой.

Обычно используются:

- pre-commit hooks;
- встроенные проверки CI/CD;
- Secret Scanning в GitHub/GitLab;
- инструменты типа TruffleHog, Gitleaks, detect-secrets.

Преимущества:

- снижение человеческого фактора;
- быстрое обнаружение утечек;
- контроль всех коммитов и merge request.

Недостатки:

- ложные срабатывания;
- не все секреты обнаруживаются автоматически;
- требуется регулярная настройка правил.

Наиболее правильный подход — совмещать автоматическое сканирование и использование централизованных Secret-хранилищ.
