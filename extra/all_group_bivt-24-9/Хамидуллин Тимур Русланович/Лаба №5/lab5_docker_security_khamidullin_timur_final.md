# Часть II. Dockerfile с запуском не от root

## Dockerfile

Для второй части я написал Dockerfile на основе исходного образа. В нем я создал отдельного пользователя `appuser` с UID/GID `10001` и переключил контейнер на него через инструкцию `USER`.

```dockerfile
FROM ket9/otus-devsecops-owasp-rest:latest

# Создаём отдельного пользователя без root-прав.
# UID/GID 10001 выбран явно, чтобы процесс в контейнере не работал от root.
RUN echo "appuser:x:10001:10001:appuser:/home/appuser:/bin/sh" >> /etc/passwd && \
    echo "appgroup:x:10001:" >> /etc/group && \
    mkdir -p /home/appuser && \
    chown -R 10001:10001 /home/appuser

# Открываем порт приложения
EXPOSE 8080

# Запускаем контейнер не от root
USER 10001:10001

# Дополнительные настройки безопасности, которые можно использовать при запуске:
#
# 1. Не использовать --privileged, потому что он дает контейнеру слишком много прав.
#
# 2. Запрещать повышение привилегий:
#    --security-opt=no-new-privileges
#
# 3. Убирать лишние capabilities:
#    --cap-drop=ALL
#
# 4. Делать файловую систему контейнера read-only:
#    --read-only
#
# 5. Ограничивать количество процессов:
#    --pids-limit=100
#
# 6. Ограничивать память:
#    --memory=512m
#
# 7. Не монтировать /var/run/docker.sock внутрь обычного приложения.
#
# Пример запуска:
# docker run --rm -p 8080:8080 \
#   --read-only \
#   --cap-drop=ALL \
#   --security-opt=no-new-privileges \
#   --pids-limit=100 \
#   --memory=512m \
#   secure-owasp-rest:1.0
```

## Сборка образа

Образ я собрал командой:

```bash
docker build -t secure-owasp-rest:1.0 .
```

Сборка завершилась успешно. В выводе было видно, что Docker взял базовый образ:

```text
ket9/otus-devsecops-owasp-rest:latest
```

и выполнил инструкцию, где в `/etc/passwd` и `/etc/group` добавляется пользователь `appuser`.

## Проверка пользователя внутри нового контейнера

После сборки я запустил новый образ:

```bash
docker run --rm -it --entrypoint sh secure-owasp-rest:1.0
```

Внутри контейнера выполнил:

```bash
whoami
```

Результат:

```text
appuser
```

![Скриншот части II](lab5_images_khamidullin/part2.png)

## Вывод по второй части

После пересборки контейнер запускается уже не от `root`, а от пользователя `appuser`.

Это лучше с точки зрения безопасности, потому что процесс приложения получает меньше прав. Даже если в приложении будет уязвимость, атакующему будет сложнее сразу получить полный контроль внутри контейнера.

Но важно понимать, что `USER appuser` — это только один уровень защиты. Его нужно дополнять настройками запуска:

- `--read-only`;
- `--cap-drop=ALL`;
- `--security-opt=no-new-privileges`;
- `--pids-limit=100`;
- `--memory=512m`.

# Часть III. Сканирование образа через Trivy

## Запуск Trivy

Для проверки безопасности созданного образа я использовал сканер Trivy.

Команда:

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:latest image secure-owasp-rest:1.0
```

Trivy просканировал образ `secure-owasp-rest:1.0` и отдельно показал уязвимости в системных пакетах и Python-зависимостях.

## Результат по базовой системе

Для базового образа на Alpine 3.14.2 Trivy показал:

```text
Total: 72
UNKNOWN: 0
LOW: 0
MEDIUM: 16
HIGH: 48
CRITICAL: 8
```

![Скриншот Trivy: системные пакеты](lab5_images_khamidullin/part3_1.png)

В выводе видно, что среди уязвимых пакетов есть `busybox`. Например, Trivy показывает несколько CVE уровня `HIGH`, связанных с `busybox`, и указывает исправленную версию.

## Результат по Python-зависимостям

Также Trivy отдельно проверил Python-пакеты:

```text
Total: 41
UNKNOWN: 0
LOW: 4
MEDIUM: 23
HIGH: 14
CRITICAL: 0
```

![Скриншот Trivy: Python-зависимости](lab5_images_khamidullin/part3_2.png)

В Python-зависимостях видны проблемы в таких библиотеках, как:

- Flask;
- Jinja2;
- Werkzeug;
- PyJWT;
- setuptools;
- urllib3.

Например, в выводе есть `Flask 1.1.4` с уязвимостью `CVE-2023-30861`, для которой указаны исправленные версии `2.3.2` и `2.2.5`.

## Анализ результата

По результатам сканирования видно, что образ нельзя считать безопасным для production.

Основные причины:

1. **Старый базовый образ.**  
   В выводе Trivy видно, что используется Alpine 3.14.2. Старые базовые образы часто содержат устаревшие системные пакеты.

2. **Много HIGH и CRITICAL уязвимостей.**  
   Для системной части найдено 48 HIGH и 8 CRITICAL. Это серьезный показатель, даже если образ используется только как учебный.

3. **Устаревшие Python-зависимости.**  
   Trivy отдельно показал 41 уязвимость в Python-пакетах, включая 14 HIGH.

4. **Non-root пользователь не исправляет CVE.**  
   После пересборки контейнер действительно запускается от `appuser`, но уязвимые пакеты внутри образа от этого не обновляются. То есть запуск не от root снижает риск эксплуатации, но не заменяет обновление зависимостей.

## Что нужно сделать для улучшения безопасности

Для реального проекта я бы сделал так:

1. Обновил базовый образ до актуальной версии.
2. Обновил Python и Python-зависимости.
3. Пересобрал образ заново.
4. Снова прогнал Trivy и сравнил количество уязвимостей.
5. Оставил запуск от non-root пользователя.
6. Запускал контейнер с ограничениями `--cap-drop=ALL`, `--read-only`, `--security-opt=no-new-privileges`.
7. Не использовал бы устаревший учебный образ в production.

# Итоговый вывод

В первой части я проверил исходный контейнер и увидел, что он запускается от `root`.

Во второй части я написал Dockerfile, где добавил отдельного пользователя `appuser` и переключил контейнер на него. После сборки команда `whoami` внутри контейнера показала `appuser`, значит цель второй части выполнена.

В третьей части я просканировал образ через Trivy. Сканер нашел много уязвимостей: 72 в системной части образа и 41 в Python-зависимостях. Это показывает, что образ устарел и небезопасен для реального использования без обновления.

Главный вывод: безопасность контейнера состоит из нескольких уровней. Нужно не только запускать приложение не от root, но и обновлять базовый образ, обновлять зависимости, ограничивать capabilities и периодически сканировать образ на CVE.
