# Часть I. Анализ фрагментов кода

## Фрагмент кода 1

```python
#!/usr/bin/env python3
from flask import Flask

from mod_api import mod_api

app = Flask('vuln_app')
app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

app.register_blueprint(mod_api, url_prefix='/api')
```

### Недостаток

Главная проблема в этом фрагменте — секретный ключ `SECRET_KEY` записан прямо в исходном коде.

На первый взгляд может показаться, что это просто настройка приложения, но на самом деле это чувствительный секрет. В Flask `SECRET_KEY` используется для подписи session cookie и других механизмов, где нужна криптографическая подпись.

### Почему это плохо

Если код попадет в GitHub, в архив, в общий репозиторий или просто к другому человеку, секретный ключ тоже станет известен.

Из-за этого могут появиться проблемы:

- злоумышленник сможет пытаться подделывать подписанные данные;
- могут пострадать пользовательские сессии;
- при утечке кода придется менять ключ и инвалидировать старые сессии;
- один и тот же ключ могут случайно использовать в разных окружениях.

То есть проблема не в том, что ключ короткий или длинный. Проблема в том, что он лежит прямо в коде.

### Как исправить

Я бы исправил это так:

```python
import os
from flask import Flask

from mod_api import mod_api

app = Flask('vuln_app')
app.config['SECRET_KEY'] = os.environ.get('SECRET_KEY')

if not app.config['SECRET_KEY']:
    raise RuntimeError('SECRET_KEY is not set')

app.register_blueprint(mod_api, url_prefix='/api')
```

### Рекомендации

1. Не хранить `SECRET_KEY` прямо в исходниках.
2. Передавать секрет через переменные окружения.
3. Для локальной разработки можно использовать `.env`, но не добавлять его в Git.
4. Для production использовать секреты из CI/CD, Docker secrets, Kubernetes secrets или другого хранилища секретов.
5. Если ключ уже попал в репозиторий, его нужно заменить, а старый считать скомпрометированным.

## Фрагмент кода 2

```python
from flask_wtf import Form
from wtforms import TextField

class LoginForm(Form):
    username = TextField('username')
    password = TextField('password')
```

### Недостаток

В этом фрагменте я вижу две основные проблемы.

Первая проблема — пароль описан как обычное текстовое поле:

```python
password = TextField('password')
```

Из-за этого в браузере пароль будет отображаться как обычный текст, а не как скрытые символы.

Вторая проблема — у полей нет валидаторов. То есть форма никак явно не проверяет, что логин и пароль вообще заполнены.

### Почему это плохо

Если поле пароля обычное текстовое, пароль может увидеть человек рядом с пользователем. Это простая проблема, но в реальном приложении она неприятная.

Отсутствие валидаторов тоже плохо. Пользователь может отправить пустой логин, пустой пароль или слишком длинные значения. Даже если дальше где-то есть проверка, форму лучше проверять сразу на входе.

Также `TextField` в современных версиях WTForms обычно заменяют на `StringField`, а для пароля нужно использовать `PasswordField`.

### Как исправить

Можно переписать форму так:

```python
from flask_wtf import FlaskForm
from wtforms import StringField, PasswordField
from wtforms.validators import DataRequired, Length

class LoginForm(FlaskForm):
    username = StringField(
        'username',
        validators=[
            DataRequired(),
            Length(min=3, max=64)
        ]
    )

    password = PasswordField(
        'password',
        validators=[
            DataRequired(),
            Length(min=8, max=128)
        ]
    )
```

### Рекомендации

1. Для пароля использовать `PasswordField`, а не обычное текстовое поле.
2. Добавить `DataRequired`, чтобы нельзя было отправить пустую форму.
3. Ограничить длину username и password.
4. Не писать всю логику проверки вручную, а использовать валидаторы WTForms.
5. На стороне сервера все равно проверять данные, потому что проверка в браузере не является надежной защитой.

## Фрагмент кода 3

```python
def post(self):
    username = self.get_argument('username')
    password = self.get_argument('password').encode('utf-8')
    email = self.get_argument('mail')

try:
    username = username.lower()
    email = email.strip().lower()
    user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})
    user.validate()
    save_user(self.db_conn, user)
except Exception, e:
    return self.render_template("success_create.html")
```

### Недостаток

В этом фрагменте сразу несколько проблем.

Первая и самая заметная — при любой ошибке приложение возвращает страницу успешного создания пользователя:

```python
except Exception, e:
    return self.render_template("success_create.html")
```

То есть даже если `user.validate()` упал или `save_user()` не сохранил пользователя, приложение все равно покажет успех.

Вторая проблема — пароль просто кодируется в UTF-8 и дальше передается в объект пользователя:

```python
password = self.get_argument('password').encode('utf-8')
```

Но кодирование — это не хеширование. Если пароль потом сохраняется в таком виде, то он фактически хранится как обычный пароль.

Третья проблема — используется слишком общий `except Exception`. Такой обработчик ловит все ошибки подряд и скрывает реальную причину проблемы.

### Почему это плохо

Если показывать страницу успеха при ошибке, то пользователь будет думать, что аккаунт создан, хотя на самом деле запись могла не сохраниться.

С паролем ситуация еще серьезнее. Пароли нельзя хранить в открытом виде. Если база данных утечет, злоумышленник сразу получит реальные пароли пользователей.

Общий `except Exception` тоже опасен. Он мешает нормально находить ошибки и может скрывать проблемы с базой, валидацией, дубликатами username и другими ситуациями.

### Как исправить

Я бы переписал логику примерно так:

```python
def post(self):
    username = self.get_argument('username', '').strip().lower()
    password = self.get_argument('password', '')
    email = self.get_argument('mail', '').strip().lower()

    try:
        user = User({
            'username': username,
            'password': hash_password(password),
            'email': email,
            'date_joined': curtime()
        })

        user.validate()
        save_user(self.db_conn, user)

    except ValidationError as e:
        self.set_status(400)
        return self.render_template("create_user.html", error="Проверьте введенные данные")

    except DuplicateUserError as e:
        self.set_status(409)
        return self.render_template("create_user.html", error="Пользователь уже существует")

    except Exception as e:
        log.exception("User creation failed")
        self.set_status(500)
        return self.render_template("create_user.html", error="Внутренняя ошибка сервера")

    return self.render_template("success_create.html")
```

### Рекомендации

1. Не возвращать страницу успеха из блока `except`.
2. Обрабатывать разные типы ошибок отдельно.
3. Логировать неожиданные ошибки на сервере.
4. Пароль хранить только в виде безопасного хеша.
5. Для паролей использовать современные алгоритмы: Argon2, bcrypt или PBKDF2.
6. Не путать кодирование (`encode`) и хеширование пароля.
7. Проверять username, email и password до сохранения.
8. Возвращать пользователю понятную ошибку, но не показывать технические детали исключения.

# Часть II. Модель безопасности Django

## 1. Какие распространенные атаки предотвращает Django

Django уже содержит несколько встроенных механизмов защиты. Но важно понимать, что они работают нормально только если разработчик не отключает их без необходимости и использует стандартные инструменты фреймворка.

## XSS

XSS — это атака, при которой злоумышленник внедряет JavaScript в страницу, а браузер другого пользователя этот JavaScript выполняет.

Django защищает от большинства XSS через шаблоны. По умолчанию шаблонизатор экранирует опасные символы в переменных. Например, если пользователь введет:

```html
<script>alert(1)</script>
```

то при обычном выводе через шаблон это не должно выполниться как скрипт.

Но защита не абсолютная. XSS может появиться, если разработчик:

- использует `safe`;
- использует `mark_safe`;
- отключает autoescape;
- вставляет данные в опасный контекст, например в JavaScript или в HTML-атрибут без кавычек;
- хранит HTML в базе и потом выводит его без обработки.

## CSRF

CSRF — это атака, при которой злоумышленник заставляет браузер авторизованного пользователя отправить запрос на сайт без его желания.

Например, пользователь залогинен на сайте, а другой сайт пытается отправить от его имени POST-запрос.

Django защищается от CSRF с помощью CSRF-токена. Для POST-запросов Django проверяет специальный секрет. Если токена нет или он неправильный, запрос не должен пройти.

Важно не отключать эту защиту через `csrf_exempt`, если в этом нет реальной необходимости.

## SQL-инъекции

SQL-инъекция — это атака, при которой пользовательские данные попадают в SQL-запрос как часть SQL-кода.

Django ORM снижает риск SQL-инъекций, потому что запросы строятся с параметризацией. То есть SQL-код и пользовательские параметры передаются отдельно.

Пример нормального подхода:

```python
User.objects.filter(username=username)
```

А вот при ручном SQL все равно можно ошибиться:

```python
cursor.execute("SELECT * FROM users WHERE username = '%s'" % username)
```

Поэтому raw SQL лучше использовать редко и только с параметрами.

## Clickjacking

Clickjacking — это атака, когда страницу сайта открывают внутри iframe на другом сайте и обманом заставляют пользователя нажать не туда.

Django защищает от этого через middleware, который выставляет заголовок `X-Frame-Options`. Этот заголовок говорит браузеру, можно ли открывать страницу во фрейме.

## Дополнительно

Кроме этих атак, Django также помогает с безопасной работой через HTTPS, настройками cookie, заголовками безопасности и проверкой Host header. Но основные атаки, которые обычно спрашивают в этой теме:

- XSS;
- CSRF;
- SQL-инъекции;
- clickjacking.

## 2. Как устроено управление пользовательскими сессиями в Django

Сессии нужны, чтобы сайт мог помнить пользователя между запросами. HTTP сам по себе не хранит состояние, поэтому без сессий сайт не понимал бы, что несколько запросов идут от одного и того же пользователя.

## Общая логика работы

В Django сессии работают через middleware:

```python
django.contrib.sessions.middleware.SessionMiddleware
```

Когда middleware включен, в каждом request появляется объект:

```python
request.session
```

С ним можно работать как со словарем:

```python
request.session['user_id'] = user.id
theme = request.session.get('theme', 'light')
```

## Где хранятся данные

Обычно сессионные данные хранятся на сервере. По умолчанию Django использует database-backed sessions, то есть хранит данные в базе данных.

При этом в браузер отправляется cookie с идентификатором сессии. Важно, что обычно в cookie лежит не вся сессия, а только session ID.

Схема такая:

1. пользователь заходит на сайт;
2. Django создает или использует существующую сессию;
3. данные сессии хранятся на сервере;
4. браузеру отправляется cookie с session ID;
5. при следующих запросах браузер отправляет cookie обратно;
6. Django по session ID находит нужные данные сессии;
7. код приложения работает с ними через `request.session`.

Если используется стандартный database backend, данные лежат в таблице:

```text
django_session
```

## Какие бывают backend для сессий

Django позволяет хранить сессии разными способами:

- в базе данных;
- в cache;
- в файлах;
- в signed cookies.

Вариант с signed cookies отличается тем, что данные сессии хранятся на клиенте в cookie, но подписываются. Это защищает от подмены, но не значит, что туда можно складывать любые секретные данные.

## Когда сессия сохраняется

По умолчанию Django сохраняет сессию, когда она была изменена. Например:

```python
request.session['foo'] = 'bar'
```

Если изменить вложенный объект, Django может не понять, что сессия изменилась. В таком случае можно явно указать:

```python
request.session.modified = True
```

## Завершение сессии

При logout сессия должна очищаться. Для этого используется механизм вроде `flush()`, который удаляет текущие данные сессии и session cookie.

Это важно, чтобы после выхода старые данные нельзя было использовать повторно.

## Срок жизни сессии

Срок жизни сессии управляется настройками:

```python
SESSION_COOKIE_AGE
SESSION_EXPIRE_AT_BROWSER_CLOSE
```

`SESSION_COOKIE_AGE` задает время жизни cookie.  
`SESSION_EXPIRE_AT_BROWSER_CLOSE` позволяет сделать так, чтобы сессия завершалась после закрытия браузера.

Также можно задавать срок жизни конкретной сессии через:

```python
request.session.set_expiry(...)
```

## Настройки безопасности cookie

Для защиты сессий важны настройки cookie:

```python
SESSION_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = 'Lax'
```

Что они дают:

- `SESSION_COOKIE_SECURE` — cookie отправляется только по HTTPS;
- `SESSION_COOKIE_HTTPONLY` — JavaScript не может прочитать cookie;
- `SESSION_COOKIE_SAMESITE` — ограничивает отправку cookie при межсайтовых запросах.

## Почему session ID не должен быть в URL

Django не передает идентификатор сессии через URL. Это правильно, потому что URL может попасть в историю браузера, логи сервера или Referer-заголовок.

Поэтому Django использует cookie-based подход для session ID.
