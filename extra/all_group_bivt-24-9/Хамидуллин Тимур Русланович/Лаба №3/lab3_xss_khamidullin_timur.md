## Подробный разбор двух CVE

### 1. CVE-2021-39201 — WordPress

**Источник:**  
https://nvd.nist.gov/vuln/detail/CVE-2021-39201

### Назначение компонента

WordPress — это система управления сайтом, написанная на PHP и обычно работающая вместе с MySQL или MariaDB. Ее используют для блогов, новостных сайтов, корпоративных сайтов, интернет-журналов и других веб-проектов.

В этой CVE проблема относится к редактору WordPress. Редактор нужен для создания и изменения страниц и записей. Через него пользователь вводит текст, добавляет блоки, ссылки, картинки и другой контент.

### Суть уязвимости

В уязвимой версии пользователь с низкими правами, например автор или контрибьютор, мог выполнить XSS в редакторе. Проблема была в том, что можно было обойти ограничение `unfiltered_html`.

Обычно WordPress не должен давать пользователям с низкими правами вставлять опасный HTML или JavaScript. Но из-за ошибки это ограничение обходилось.

### Причина

Причина в недостаточной обработке HTML-кода в редакторе. Ввод пользователя не был нормально нейтрализован перед тем, как попасть в страницу.

### Возможные последствия

Если атакующий может выполнить JavaScript в редакторе или в контексте страницы, то он может:

- выполнить код в браузере другого пользователя;
- попытаться украсть cookie или служебные данные;
- подменить элементы страницы;
- выполнить действия от имени пользователя, который открыл зараженную страницу.

### 2. CVE-2021-40926 — getID3

**Источник:**  
https://nvd.nist.gov/vuln/detail/CVE-2021-40926

### Назначение компонента

getID3 — это PHP-библиотека для работы с медиафайлами. Она умеет извлекать информацию из MP3 и других аудио, видео и графических форматов.

Например, с помощью getID3 можно получить:

- длительность аудиофайла;
- битрейт;
- разрешение видео;
- ID3-теги;
- EXIF/IPTC/XMP-метаданные;
- другую техническую информацию о файле.

Такой компонент может использоваться в музыкальных сайтах, медиатеках, CMS, загрузчиках файлов и других сервисах, где нужно анализировать медиафайлы на сервере.

### Суть уязвимости

В CVE-2021-40926 XSS находилась в файле:

```text
demos/demo.mysqli.php
```

Проблема проявлялась через параметр:

```text
showtagfiles
```

Если в этот параметр передать HTML или JavaScript, то значение выводилось на страницу без достаточной очистки. Из-за этого браузер мог выполнить внедренный скрипт.

Пример опасной логики:

```php
echo 'Files with Encoder Options <b>' . $_REQUEST['showtagfiles'] . '</b>:<br>';
```

Проблема здесь в том, что значение из `$_REQUEST` сразу попадает в HTML.

### Причина

Причина уязвимости — вывод пользовательского параметра в HTML без экранирования. Сервер должен был воспринимать значение `showtagfiles` как обычный текст, но фактически вставлял его в страницу как HTML.

### Возможные последствия

Такая XSS может привести к:

- выполнению JavaScript в браузере пользователя;
- краже данных сессии;
- подмене содержимого страницы;
- перенаправлению пользователя на другой сайт;
- выполнению действий от имени пользователя.

## Вывод по первой части

После поиска CVE я увидел, что XSS в PHP-компонентах в 2021 году встречалась много раз. Это были не только маленькие учебные проекты, но и известные компоненты вроде WordPress и getID3.

Главная причина почти везде одинаковая: данные от пользователя попадают в HTML-ответ без нормального экранирования или фильтрации. Браузер в таком случае воспринимает ввод не как текст, а как часть страницы и выполняет JavaScript.

# Часть II. Проведение XSS-атаки на стенде

## Запуск стенда

Для практической части я скачал и запустил уязвимый Docker-образ:

```bash
docker pull ket9/otus-devsecops-xss
docker run -d -p 8080:80 ket9/otus-devsecops-xss:latest
```

После запуска я открыл приложение в браузере:

```text
http://localhost:8080/
```

На главной странице была ссылка **XSS-1**. Я перешел в этот раздел и увидел простую форму с полем `comment` и кнопкой `Save Data`.

---

## Ход проверки

### 1. Проверка обычного комментария

Сначала я не стал сразу вставлять скрипт. Я ввел обычный текст:

```text
test comment
```

После нажатия на кнопку `Save Data` комментарий появился на странице в блоке **Comments**.

Из этого я понял, что приложение принимает данные из формы, сохраняет их и потом выводит обратно на страницу.

### 2. Проверка HTML-тегов

Потом я решил проверить, экранируются ли HTML-теги. Для этого ввел:

```html
<b>hello</b>
```

Если бы приложение экранировало HTML, то на странице я увидел бы текст именно в таком виде: `<b>hello</b>`. Но если тег применяется, значит ввод вставляется в HTML как разметка.

После отправки стало понятно, что приложение не воспринимает ввод как простой текст. Поэтому я перешел к проверке JavaScript.

### 3. Попытка выполнить JavaScript

Для проверки XSS я ввел в поле комментария такой код:

```html
<script>alert('XSS by Timur')</script>
```

После нажатия на `Save Data` браузер выполнил JavaScript, и появилось окно `alert`.

Это подтвердило, что скрипт реально выполняется в контексте страницы.

### 4. Проверка ответа приложения

После отправки payload я посмотрел, как комментарий попал в HTML страницы. Логика выглядела примерно так:

```html
<h2>Comments</h2>
<p><script>alert('XSS by Timur')</script></p>
<hr />
```

То есть приложение вставило мой ввод внутрь HTML без экранирования. Браузер увидел тег `<script>` и выполнил его.

### 5. Проверка, хранимый это XSS или отраженный

Я обновил страницу и снова открыл раздел с комментариями. Скрипт остался в списке комментариев и снова выполнялся при открытии страницы.

Из этого я сделал вывод, что это не просто reflected XSS, а **stored XSS**. Payload сохраняется на сервере, а потом показывается всем, кто открывает страницу с комментариями.

---

## Тип найденной уязвимости

Найденная уязвимость — **хранимый XSS (Stored Cross-Site Scripting)**.

Почему именно stored XSS:

- я ввел JavaScript в поле комментария;
- приложение сохранило этот ввод;
- потом приложение вывело сохраненный комментарий на страницу;
- браузер выполнил скрипт при открытии страницы.

Если бы код просто сразу вернулся в ответе и нигде не сохранялся, это был бы reflected XSS. Но здесь комментарий остается и выполняется повторно, поэтому это хранимый XSS.

---

## Почему появилась уязвимость

Уязвимость появилась из-за того, что приложение выводит пользовательский ввод в HTML без обработки.

Опасные символы и конструкции:

| Символ / конструкция | Почему опасно |
|---|---|
| `<` | начинает HTML-тег |
| `>` | закрывает HTML-тег |
| `"` | может закрыть значение HTML-атрибута |
| `'` | тоже может закрыть значение атрибута или строку |
| `&` | используется в HTML-сущностях |
| `/` | может участвовать в закрывающих тегах, например `</script>` |
| `script` | сам по себе не всегда опасен, но как HTML-тег приводит к выполнению JS |
| `onerror`, `onclick`, `onload` | обработчики событий, через которые тоже можно запускать JS |
| `javascript:` | опасная схема в ссылках, если ее не фильтровать |

В моем примере главную роль сыграли символы `<` и `>`, потому что через них я смог вставить тег `<script>`.

---

## Меры предотвращения

Чтобы исправить такую уязвимость, я бы сделал несколько уровней защиты.

### 1. Экранирование при выводе

Самое главное — не выводить комментарии в HTML как есть.

Если приложение написано на PHP, при выводе комментария можно использовать:

```php
echo htmlspecialchars($comment, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
```

Тогда опасные символы будут заменены:

| Было | Станет |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#039;` |
| `&` | `&amp;` |

После этого браузер покажет `<script>alert(1)</script>` как обычный текст, а не выполнит его.

### 2. Фильтрация ввода

Для поля комментария HTML вообще не нужен, поэтому можно запретить теги полностью.

Например, перед сохранением:

```php
$comment = strip_tags($comment);
```

Но одной фильтрации мало. Даже если теги удаляются при сохранении, экранирование при выводе все равно нужно оставить, потому что данные могут попасть в базу другим способом.

### 3. Контекстное экранирование

Экранировать нужно в зависимости от того, куда вставляются данные:

- если данные вставляются в HTML-текст — использовать HTML escaping;
- если данные вставляются в HTML-атрибут — отдельно экранировать кавычки;
- если данные вставляются в JavaScript — использовать безопасное JSON-кодирование;
- если данные вставляются в URL — проверять схему и кодировать параметры.

То есть нельзя одной функцией закрыть все случаи. Нужно понимать контекст вывода.

### 4. Запрет опасных схем и обработчиков

Если в приложении когда-то разрешат часть HTML, например ссылки или форматирование, нужно запрещать:

```text
<script>
javascript:
onerror=
onclick=
onload=
iframe
object
embed
```

Лучше использовать готовый HTML sanitizer, например HTML Purifier, а не писать фильтр вручную.

### 5. Content Security Policy

Дополнительно можно настроить CSP-заголовок, например запретить inline-скрипты:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

CSP не заменяет экранирование, но уменьшает последствия, если XSS где-то все-таки появится.

### 6. HttpOnly и SameSite для cookie

Для cookie сессии нужно ставить флаги:

```text
HttpOnly
Secure
SameSite=Lax или SameSite=Strict
```

`HttpOnly` не даст JavaScript напрямую прочитать cookie. Это не убирает XSS, но снижает риск кражи сессии.

## Итоговый вывод

В ходе лабораторной работы я провел XSS-атаку на стенде через поле комментария.

Сначала я проверил обычный ввод, потом HTML-теги, а затем вставил JavaScript:

```html
<script>alert('XSS by Timur')</script>
```

Скрипт выполнился в браузере, а после обновления страницы остался в комментариях. Поэтому найденная уязвимость относится к **хранимому XSS**.

Основная причина — приложение сохраняет и выводит пользовательский ввод без экранирования. Для исправления нужно экранировать специальные символы при выводе, не разрешать HTML там, где он не нужен, и дополнительно использовать CSP и безопасные настройки cookie.
