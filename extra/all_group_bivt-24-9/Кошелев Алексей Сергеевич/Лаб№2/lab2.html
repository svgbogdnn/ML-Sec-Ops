Часть I. Анализ уязвимостей REST API

Цель: Найти среди CVE за последний год 3 уязвимости, относящиеся к недостаткам REST API из списка OWASP API Security Top-10. Пояснить, в чем заключается недостаток и какова его причина.

Сводная таблица уязвимостей, связанных с OWASP API Top 10

Название CVE Источник Тип (OWASP API Top 10) Недостаток Причина Последствия
CVE-2025-14777
(Keycloak)		 GitHub Issue / NVD API1:2023
Broken Object Level Authorization (BOLA)		 Аутентифицированный субъект, легитимно управляющий одним клиентским окружением, способен манипулировать ресурсами сторонних клиентов через Admin API путем подмены целевого параметра resourceId. Дефект обусловлен архитектурной рассинхронизацией: валидация привилегий осуществляется на верхнем уровне (resourceServer), однако последующие транзакции в базе данных опираются исключительно на переданный идентификатор (resourceId), игнорируя проверку принадлежности объекта инициатору запроса. Несанкционированная модификация или удаление конфигураций сторонних арендаторов, критическое нарушение принципа мультитенантной изоляции.

(Cisco Nexus Dashboard)		 Cisco Security Advisory API5:2023

При обработке запросов к ряду системных эндпоинтов сервер верифицирует наличие сессии, но пропускает этап авторизации прав на вызов конкретной функции. Раскрытие чувствительной телеметрии, несанкционированное взаимодействие с файловой системой узла, вертикальная эскалация привилегий.
CVE-2025-20156
(Cisco Meeting Management)		 NVD
Cisco Advisory		 API5:2023
Broken Function Level Authorization (BFLA)		 Авторизованный пользователь с низкими правами может выполнять административные команды через API (например, эндпоинт /api/ssh_run_command/), хотя в веб-интерфейсе эти функции скрыты. Отсутствие строгой проверки прав пользователя на уровне самого REST API. Сервер удостоверяется в факте аутентификации пользователя, но пропускает шаг авторизации для критических конечных точек. Полный административный контроль над пограничными узлами, выполнение произвольных команд, продвижение вглубь сети.

Вывод

  1. В Keycloak реализован некорректный механизм сопоставления субъекта и объекта доступа: система верифицирует контекст авторизации, но применяет его к нерелевантному идентификатору при обращении к хранилищу данных.
  2. В Cisco Nexus Dashboard наблюдается фрагментарное применение политик безопасности, при котором часть служебных интерфейсов API оказалась исключена из контура ролевой модели доступа.
  3. В Cisco Meeting Management разработчики допустили классическую ошибку Security by Obscurity (безопасность через сокрытие): интерфейсные элементы управления были скрыты от рядовых пользователей, однако механизмы защиты на уровне маршрутизатора API-запросов не были реализованы.

Данные инциденты подтверждают необходимость внедрения концепции Zero Trust на этапе проектирования, требующей обязательной верификации авторизационных прав при каждом обращении к любой функции и каждому объекту данных API.

Часть II. Поиск уязвимости

После запуска контейнера, я открыл приложение по адресу http://localhost:8080/, а затем перешел по ссылке http://localhost:8080/createdb, чтобы наполнить базу тестовыми данными.

1. Ход моих рассуждений и действий

Шаг 1: Проверка доступных данных без авторизации Я решил проверить, какие данные приложение отдает просто так, без всяких токенов и паролей. Запрос к адресу http://localhost:8080/users/v1 сразу же вернул мне список всех зарегистрированных пользователей и их почт:

{"users":[{"email":"mail1@mail.com","username":"name1"},{"email":"mail2@mail.com","username":"name2"},{"email":"admin@mail.com","username":"admin"}]}

Шаг 2: Доступ к конкретному пользователю После этого я попробовал открыть данные конкретного пользователя, подставив его имя прямо в URL. Запрос к http://localhost:8080/users/v1/name1 успешно сработал:

{"username":"name1","email":"mail1@mail.com"}

Точно так же я смог посмотреть данные и по другим пользователям, а также информацию о книгах по адресу http://localhost:8080/books/v1. Вывод: приложение позволяет получить чужие данные, если просто знать и подставить значение username в адресную строку.

Шаг 3: Попытка изменить данные Я решил проверить, можно ли не только читать, но и менять чужие данные. Через командную строку я отправил PUT запрос на изменение почты пользователя name1:

curl -X PUT "http://localhost:8080/users/v1/name1/email" -H "Content-Type: application/json" -d "{\"email\":\"hackernumber1@mail.com\"}"

Сервер выдал ошибку:

{ "status": "fail", "message": "Invalid token"}

Я снова проверил профиль name1 — почта не изменилась. Вывод: Изменять данные пользователей без токена нельзя, но вот читать их через обычный GET запрос может кто угодно.

2. Найденная уязвимость

BOLA (Broken Object Level Authorization) — сервер предоставляет доступ к объекту по его идентификатору (username) без проверки прав и личности запрашивающего.

3. Классификация

API1:2023 Broken Object Level Authorization — критический недостаток, при котором манипуляция ID в запросе позволяет несанкционированно читать чужие данные.

4. Меры предотвращения

  1. Обязательная авторизация: Запрет доступа к любым эндпоинтам /users/* без валидного JWT-токена.
  2. Проверка владения: Сервер должен сопоставлять ID из запроса с ID в токене пользователя, разрешая просмотр только собственного профиля.
  3. Минимизация вывода: Исключение чувствительных полей (email) из публичных ответов API.
