# ЛР 2. Анализ уязвимостей REST API

## Часть 1

### CVE-2025-15414

**Недостаток:**

API выполняет запросы к произвольным адресам, контролируемым пользователем, что позволяет получать доступ к внутренним сервисам, локальным ресурсам или обходить сетевые ограничения

**Причина:**

Отсутствие валидации и ограничения входных данных (URL), а также отсутствие контроля допустимых адресов (whitelist). Сервер доверяет пользовательскому вводу и выполняет запросы без проверки

**Тип OWASP:**

Server-Side Request Forgery (SSRF)

### CVE-2025-32044

**Недостаток:**

API раскрывает избыточную информацию, включая внутренние данные приложения и чувствительные пользовательские данные, что не должно быть доступно внешнему пользователю

**Причина:**

Неправильная конфигурация сервера (включён вывод отладочной информации), а также отсутствие фильтрации данных перед отправкой ответа клиенту

**Тип OWASP:**

Security Misconfiguration

### CVE-2025-10910

**Недостаток:**

API не проверяет, принадлежит ли устройство пользователю, выполняющему операцию. Это позволяет выполнять действия с чужими объектами (устройствами)

**Причина:**

Отсутствие проверки прав доступа на уровне объекта (object-level authorization). Сервер доверяет входным данным и не проверяет принадлежность ресурса пользователю

**Тип OWASP:**

Broken Object Level Authorization (BOLA)

## Часть 2

### Ход выполнения

Для начала я перешла по ссылке `http://localhost:8080/`, увидела там список API

```json
{ "создать базу": "/createdb",     "посмотреть информацию обо всех пользователях": "/users/v1",     "посмотреть подробную информацию обо всех пользователях": "/users/v1/_debug",     "регистрация нового пользователя": "/users/v1/register (HTTP POST)",     "вход в приложение": "/users/v1/login (HTTP POST)",     "просмотр пользователя по имени": "/users/v1/{username}",     "удалить пользователя по имени (только для админов)": "/users/v1/{username} (HTTP DELETE)",     "изменить email пользователя": "/users/v1/{username}/email (HTTP PUT)",     "изменить пароль пользователя": "/users/v1/{username}/password (HTTP PUT)",     "все книги": "/books/v1",     "добавить книгу": "/books/v1 (HTTP POST)",     "просмотр книги": "/books/v1/{book}",      } 
```

Далее по заданию открыла `http://localhost:8080/createdb`, получила

```json
{ "message": "Database populated." }
```

База данных заполнена

Попробую посмотреть список пользователей `http://localhost:8080/users/v1`, получаю

```json
{"users":[{"email":"mail1@mail.com","username":"name1"},{"email":"mail2@mail.com","username":"name2"},{"email":"admin@mail.com","username":"admin"}]}
```

У нас есть три пользователя, пробую получить доступ к конкретному пользователю

`http://localhost:8080/users/v1/admin`

```json
{"username": "admin", "email": "admin@mail.com"}
```

`http://localhost:8080/users/v1/name1`

```json
{"username": "name1", "email": "mail1@mail.com"}
```

`http://localhost:8080/users/v1/name2`

```json
{"username": "name2", "email": "mail2@mail.com"}
```

Получается, я могу получить список пользователей и могу получить данные конкретного пользователя, даже администратора, напрямую, никакой проверки прав доступа нет
Тогда это уязвимость BOLA (Broken Object Level Authorization)

### Меры предотвращения

- Проверка прав доступа на уровне объекта (object-level authorization)
- Запрет доступа к чужим объектам даже при знании ID/username
- Использование принципа least privilege
- Централизованная проверка авторизации в middleware
- Логирование и мониторинг подозрительных обращений к объектам
