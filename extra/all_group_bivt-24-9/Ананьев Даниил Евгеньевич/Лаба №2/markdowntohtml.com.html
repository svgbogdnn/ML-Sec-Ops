CVE, связанные с REST API и OWASP API Top 10

Ниже приведены 3 CVE за последний год, которые связаны с проблемами REST API и подходят под категории из OWASP API Top 10.

Краткий вывод

Во всех трех случаях проблема связана не просто с ошибкой в коде, а с неверной логикой защиты API.

  • В Keycloak плохо проверялся доступ к конкретному объекту.
  • В Cisco плохо проверялся доступ к функциям REST API.
  • В Budibase серверу доверяли слишком широкий набор адресов для исходящих запросов.

Это показывает, что при защите REST API важно проверять не только вход в систему, но и права на каждый объект, каждую функцию и каждый внешний запрос.

Часть 2

Во второй части я выбрал вариант с самостоятельным поиском недостатка в уязвимом приложении.

Сначала после запуска контейнера я открыл приложение по адресу http://localhost:8080/, а затем перешел по ссылке http://localhost:8080/createdb, чтобы наполнить базу тестовыми данными.

Дальше я начал проверять, какие данные можно получить через API без авторизации.

Запрос к адресу http://localhost:8080/users/v1 вернул список пользователей:

{"users":[{"email":"mail1@mail.com","username":"name1"},{"email":"mail2@mail.com","username":"name2"},{"email":"admin@mail.com","username":"admin"}]}

После этого я попробовал открыть данные конкретного пользователя по имени в URL. Например, запрос к http://localhost:8080/users/v1/name1 вернул:

{"username":"name1","email":"mail1@mail.com"}

Аналогично удалось получить данные и по другим пользователям. Из этого я сделал вывод, что приложение позволяет читать пользовательские данные только по значению username в адресе запроса.

Потом я проверил другие доступные данные. Запрос к http://localhost:8080/books/v1 вернул:

{"Books":[{"book_title":"bookTitle82","user":"name1"},{"book_title":"bookTitle98","user":"name2"},{"book_title":"bookTitle68","user":"admin"}]}

Это подтвердило, что API отдает связанные данные без проверки прав доступа.

Далее я решил проверить, можно ли не только читать, но и изменять данные пользователя. Для этого я отправил запрос на изменение email:

curl -X PUT "http://localhost:8080/users/v1/name1/email" -H "Content-Type: application/json" -d "{\"email\":\"hacker@mail.com\"}"

Сервер ответил так:

{"status":"fail","message":"Invalid token"}

После повторной проверки http://localhost:8080/users/v1/name1 оказалось, что email не изменился. Значит, изменение данных защищено, но чтение чужих данных остается доступным.

Найденная уязвимость

В приложении обнаружена уязвимость типа Broken Object Level Authorization (BOLA).

Суть проблемы в том, что сервер позволяет получить доступ к объекту только по идентификатору в URL, но не проверяет, имеет ли пользователь право видеть именно этот объект. В данном случае таким идентификатором выступает username.

Из-за этого можно перебирать имена пользователей и получать их данные без аутентификации. Это уже является нарушением разграничения доступа, даже если изменение данных дополнительно защищено токеном.

К какому типу относится недостаток

Найденный недостаток относится к категории OWASP API Top 10 Broken Object Level Authorization.

Причина в том, что приложение не выполняет проверку доступа на уровне конкретного объекта и просто отдает данные по параметру из URL.

Меры предотвращения

  1. Проверять права доступа к каждому объекту при каждом запросе.
  2. Требовать аутентификацию перед просмотром данных пользователей.
  3. Не отдавать данные пользователя только по значению username в URL.
  4. Ограничить или полностью убрать выдачу списка всех пользователей.
  5. Возвращать только минимально необходимые данные, чтобы уменьшить риск утечки информации.

Вывод по части 2

Во время проверки приложения удалось найти уязвимость BOLA. Через API можно просматривать данные разных пользователей без авторизации, если подставлять их имена в адрес запроса. Это показывает, что даже при защите операций изменения данных REST API может оставаться уязвимым, если нет проверки доступа на уровне объектов.
