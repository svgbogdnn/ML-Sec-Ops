# Секрет #1 — Захардкоженный пароль приложения [КРИТИЧЕСКИЙ]

| Поле | Значение |
|---|---|
| Hash коммита | `e8d086ac9b62efebc9937c5b41659b454f2973c3` |
| Дата / сообщение | `2019-09-20` / `"All successful"` |
| Файл | `webgoat-lessons/challenge/src/main/java/org/owasp/webgoat/plugin/SolutionConstants.java` |
| Строка / контекст | Строки 12–14 (интерфейс `SolutionConstants`) |
| Найденное значение | `String PASSWORD = "!!webgoat_admin_1234!!";` и `String PASSWORD_TOM = "thisisasecretfortomonly";` |

## Почему это секрет?

Два пароля — администратора и пользователя Tom — прописаны как Java-константы прямо в исходном коде. Файл попал в публичный репозиторий и теперь навсегда останется в истории Git: даже если его убрать из последнего коммита, `git log` всё равно покажет исходное содержимое. Любой человек с доступом к репозиторию — разработчик, intern, подрядчик — может в пару команд получить действующие пароли.

Что особенно показательно — в том же файле разработчики оставили комментарий:

```java
//TODO should be random generated when starting the server
```

То есть они сами понимали проблему. Просто отложили на потом, а «потом» так и не наступило.

## Правильный способ хранения

Пароли вообще не должны жить в коде. Варианты, которые реально работают:

- генерировать при старте приложения через `SecureRandom`
- передавать через переменные окружения (`System.getenv("APP_PASSWORD")`)
- хранить в специализированных хранилищах: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault

Любой конфиг-файл с реальными значениями — в `.gitignore`, чтобы случайно не попал в репозиторий.

# Секрет #2 — JWT-токен со слабым HMAC-ключом [ВЫСОКИЙ]

| Поле | Значение |
|---|---|
| Hash коммита | `e8d086ac9b62efebc9937c5b41659b454f2973c3` |
| Дата / сообщение | `2019-09-20` / `"All successful"` |
| Файл | `webgoat-lessons/jwt/src/main/resources/lessonPlans/en/JWT_weak_keys` |
| Строка / контекст | Добавлен блок с реальным токеном в diff |
| Найденное значение | `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...` |

## Почему это секрет?

В учебном файле опубликован настоящий подписанный JWT-токен для пользователя Tom. Payload содержит:

- `username: Tom`
- `Role: Manager / Project Administrator`

Проблема не только в том, что токен реальный, — проблема в том, что ключ, которым он подписан, настолько слабый, что взламывается офлайн-атакой по словарю буквально за минуты. Инструменты вроде `hashcat` или `jwt_tool` с этим прекрасно справляются. Получив ключ, злоумышленник может сгенерировать новый токен с любой ролью — хоть `Admin`.

## Правильный способ хранения

В документации и учебных материалах использовать только фиктивные, заведомо невалидные токены. Рядом должна быть явная пометка: `EXAMPLE` / `PLACEHOLDER` / `DO NOT USE`. Для реальных систем — ключи подписи длиной минимум 256 бит, хранятся в секретном хранилище, ротируются регулярно.

| Поле | Значение |
|---|---|
| Hash коммита | `5dd6b3190592fca16b6d2ea5a5c7f5485be04ebf` |
| Дата / сообщение | `2019-11-17` / `"Adjust lesson template (#704)"` |
| Файл | `.travis.yml` |
| Строка / контекст | Блоки `deploy.api_key.secure` и `env.global` |
| Найденное значение | Travis CI API key, Docker Hub login/password, Slack webhook token |

## Почему это секрет?

В файле `.travis.yml` зашифровано сразу три вида чувствительных данных:

- **GitHub Release API key** — позволяет публиковать релизы
- **Логин и пароль Docker Hub** — полный доступ к публикации образов
- **Slack-токен** — для отправки уведомлений

Да, они зашифрованы ключом Travis CI. Но вся безопасность этой схемы держится на одном RSA-ключе Travis. Если он утечёт (а Travis CI уже переживал инциденты с безопасностью) — все три секрета раскрываются одновременно. Хранить зашифрованные секреты в репозитории — это ложное чувство защищённости.

## Правильный способ хранения

Для Travis CI — переменные окружения через UI: **Settings → Environment Variables**, без записи в репозиторий. Для GitHub Actions — OIDC-интеграция без долгоживущих токенов. Для Docker Hub — токены с ограниченным scope вместо пароля основного аккаунта.

# Секрет #4 — Статический CSRF-токен [ВЫСОКИЙ]

| Поле | Значение |
|---|---|
| Hash коммита | `1a83e2825e2b1e040e2a2042677f03727f654150` |
| Дата / сообщение | `2019-11-03` / `"Code style (#696)"` |
| Файл | `webgoat-lessons/csrf/src/main/java/org/owasp/webgoat/csrf/ForgedReviews.java` |
| Строка / контекст | Строка ~52 |
| Найденное значение | `private static final String weakAntiCSRF = "2aa14227b9a13d0bede0388a7fba9aa9";` |

## Почему это секрет?

MD5-строка используется как Anti-CSRF токен — то есть как механизм защиты от подделки запросов. Но эта строка статическая и одинаковая для всех пользователей и всех сессий. Это принципиально неправильно: смысл CSRF-токена именно в его уникальности.

Злоумышленнику достаточно один раз увидеть значение — в коде, в логах, в перехваченном запросе — и дальше он может подделывать запросы от имени любого пользователя. Ещё хуже: значение уже опубликовано в публичном репозитории, так что оно давно известно.

## Правильный способ хранения

Настоящий Anti-CSRF токен должен:

- быть уникальным для каждой сессии пользователя
- генерироваться криптографически стойким генератором (`SecureRandom`)
- проверяться на серверной стороне при каждом запросе

Проще всего использовать встроенные механизмы фреймворка — в Spring это **Spring Security CSRF protection**, которая всё это делает из коробки.

# Секрет #5 — Захардкоженный пароль в модуле сброса пароля [ВЫСОКИЙ]

| Поле | Значение |
|---|---|
| Hash коммита | `1a83e2825e2b1e040e2a2042677f03727f654150` |
| Дата / сообщение | `2019-11-03` / `"Code style (#696)"` |
| Файл | `webgoat-lessons/password-reset/src/main/java/org/owasp/webgoat/password_reset/ResetLinkAssignment.java` |
| Строка / контекст | Строка ~47 |
| Найденное значение | `static final String PASSWORD_TOM_9 = "somethingVeryRandomWhichNoOneWillEverTypeInAsPasswordForTom";` |

## Почему это секрет?

Пароль пользователя Tom закодирован прямо в Java-классе, который реализует логику сброса пароля. То есть этот модуль, который должен помогать восстановить доступ — сам является местом хранения учётных данных. Это несёт двойную угрозу.

Дополнительно в том же файле раскрывается email:

```java
TOM_EMAIL = "tom@webgoat-cloud.org"
```

Email и пароль доступны вместе — этого достаточно для прямого входа в аккаунт.

## Правильный способ хранения

Модуль сброса пароля в принципе не должен знать текущий пароль пользователя. Правильная схема:

- генерировать одноразовый токен (`UUID` или `SecureRandom`)
- хранить в базе только его хеш (`bcrypt`, `Argon2`)
- выставлять TTL (например, 15 минут) и флаг «уже использован»
- отправлять ссылку с токеном на почту; после перехода — предлагать ввести новый пароль
