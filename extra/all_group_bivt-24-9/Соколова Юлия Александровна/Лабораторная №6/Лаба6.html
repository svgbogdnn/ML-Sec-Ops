Почему это секрет

Два пароля — администратора и пользователя Tom — прописаны как Java-константы прямо в исходном коде. Файл попал в публичный репозиторий и навсегда останется в истории Git: даже если убрать его из последнего коммита, git log всё равно покажет исходное содержимое.

Что особенно красноречиво — разработчики сами оставили комментарий:

Проблему понимали. Просто откладывали. А «потом» так и не наступило.

Правильный способ хранения
  • Генерировать при старте через SecureRandom — никаких констант в коде
  • Передавать через переменные окружения: System.getenv("APP_PASSWORD")
  • Хранить в специализированных хранилищах: HashiCorp Vault, AWS Secrets Manager
  • Любой конфиг с реальными значениями — в .gitignore

Почему это секрет

В учебном файле опубликован настоящий подписанный JWT-токен для пользователя Tom. Payload содержит username: Tom и Role: Manager / Project Administrator.

Ключ подписи настолько слабый, что взламывается офлайн-атакой по словарю буквально за несколько минут — инструменты hashcat или jwt_tool с этим справляются без труда. Получив ключ, злоумышленник генерирует токен с любой ролью, хоть Admin.

Правильный способ хранения
  • В документации и учебных материалах — только фиктивные, заведомо невалидные токены
  • Рядом с примером обязательная пометка: EXAMPLE / PLACEHOLDER / DO NOT USE
  • Для реальных систем: ключи подписи ≥ 256 бит, хранятся в секрет-хранилище, ротируются

Почему это секрет

В файле .travis.yml зашифровано сразу три вида чувствительных данных: GitHub Release API key, логин и пароль Docker Hub, токен Slack для уведомлений.

Да, они зашифрованы ключом Travis CI. Но вся безопасность держится на одном RSA-ключе Travis — если он утечёт, все три секрета раскрываются одновременно. Хранить зашифрованные секреты в репозитории — это ложное ощущение защищённости.

Правильный способ хранения
  • Travis CI: переменные окружения через UI — Settings → Environment Variables
  • GitHub Actions: OIDC-интеграция без долгоживущих токенов
  • Docker Hub: токены с ограниченным scope вместо пароля основного аккаунта
Секрет #4

Статический CSRF-токен

Дата / сообщение2019-11-03 / "Code style (#696)"
Файлwebgoat-lessons/csrf/src/main/java/org/owasp/webgoat/csrf/ForgedReviews.java
Строка / контекстСтрока ~52
Найденное значениеprivate static final String weakAntiCSRF = "2aa14227b9a13d0bede0388a7fba9aa9";
Почему это секрет

MD5-строка используется как Anti-CSRF токен — механизм защиты от подделки запросов. Но она статическая и одинаковая для всех пользователей и сессий. Смысл CSRF-токена именно в уникальности — здесь этого нет.

Злоумышленнику достаточно один раз увидеть значение — в коде, логах, перехваченном запросе — и дальше он может подделывать запросы от имени любого пользователя. Значение уже публично в репозитории, так что оно давно известно.

Правильный способ хранения
  • Уникальный токен для каждой сессии пользователя — никаких статических значений
  • Генерация через криптографически стойкий SecureRandom
  • Проверка на серверной стороне при каждом изменяющем запросе
  • Проще всего — встроенная Spring Security CSRF protection из коробки

Почему это секрет

Пароль пользователя Tom закодирован прямо в Java-классе, реализующем логику сброса пароля. Парадокс: модуль, призванный помочь восстановить доступ — сам является местом хранения учётных данных.

Дополнительно в том же файле раскрывается email:

TOM_EMAIL = "tom@webgoat-cloud.org"

Email и пароль доступны вместе — этого достаточно для прямого входа в аккаунт.

Правильный способ хранения

Модуль сброса пароля вообще не должен знать текущий пароль. Правильная схема:

  • Генерировать одноразовый токен (UUID или SecureRandom)
  • Хранить в БД только его хеш (bcrypt, Argon2)
  • Выставлять TTL (например, 15 минут) и флаг «уже использован»
  • После перехода по ссылке — предлагать ввести новый пароль; старый не нужен
