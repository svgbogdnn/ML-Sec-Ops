Фрагмент 2

from flask_wtf import Form  
from wtforms import TextField

class LoginForm(Form):  
username = TextField('username')  
password = TextField('password')

Недостаток : пароль вводится стандартной формой + ввод не валидируется. Последствия : система не считает, что в этом поле хранится чувствительная информация, что повышает риск того, что эти данные попадут, допустим, в логи. Также символы пароля не будут скрываться в интерфейсе, соответственно, его можно будет банально подглядеть. Бонусом ко всему из-за отсутствия валидации в это поле можно попробовать протянуть инъекции или забрутфорсить пароль. Как устранить : использовать безопасное поле для пароля, проверять содержимое полей ещё на этапе фронта. Ещё пароли надо хэшировать, но, возможно, лучше это делать на более поздней стадии. Впрочем, не уверен.

def post(self):
    username = self.get_argument('username')
    password = self.get_argument('password').encode('utf-8')
    email = self.get_argument('mail')

try:
    username = username.lower()
    email = email.strip().lower()
    user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})
    user.validate()
    save_user(self.db_conn, user)
except Exception, e:
    return self.render_template("success_create.html")

Недостаток : ошибка никак не логируется и не показывается пользователю. Последствия : пользователь будет думать, что данные сохранились, хотя это не так. Потом надо будет долго разбираться, что произошло. Также из-за отсутствия логирования можно не заметить и не предотвратить попытку атаки. Как устранить : если ошибка произошла, сообщить пользователю о ней и записать происходящее в лог.

Какие наиболее распространенные атаки предотвращает django?

  1. XSS : django автоматически экранирует html.
  2. CSRF : в каждом POST-запросе проверяется секретный ключ, недоступный злоумышленнику.
  3. SQL-инъекции : используются параметризированные запросы, и параметры экранируются.
  4. Clickjacking : django по дефолту запрещает встраивать сайт в фрейм. * и только тут я понял, что вопрос подразумевает просто список.

    Как устроено управление пользовательскими сессиями в django

  5. При создании сессии клиенту отправляется ключ, который сохраняется в куку. При этом важно отметить, что вся остальная информация остаётся на сервере.
  6. При каждом запросе клиент отправляет ключ, сервер проверяет его и отдаёт данные клиенту.
  7. Сессия удаляется автоматически при истечении времени жизни токена или вручную, например, при выходе из аккаунта. * ключ псевдослучайный, его фактически невозможно подобрать, плюс, он дополнительно защищается флагами на уровне системы.
