# Лабораторная работа №4

## Проведение симуляции XSS-атаки

## Часть 1. CVE за 2021 год, содержащие XSS в PHP-компонентах

В первой части я искал уязвимости за 2021 год, где XSS связан именно с компонентами, написанными на PHP. В основном такие CVE встречаются у WordPress-плагинов, потому что WordPress и его плагины написаны на PHP и часто обрабатывают пользовательский ввод, который потом выводится в HTML.

### CVE-2021-24177 — File Manager WordPress plugin

**Источник:** https://nvd.nist.gov/vuln/detail/CVE-2021-24177

**Тип уязвимости:** Reflected Cross-Site Scripting.

**Описание:**
В плагине File Manager для WordPress до версии 7.1 была возможность выполнить reflected XSS через endpoint:

```text
/wp-admin/admin.php?page=wp_file_manager_properties
```

Проблема возникала при передаче вредоносного значения в параметр `User-Agent`. Это значение отражалось обратно в ответе веб-приложения без нормального экранирования.

**Для чего используется компонент:**
File Manager — это WordPress-плагин для управления файлами сайта прямо из административной панели. Через него можно просматривать файлы, папки, загружать новые файлы, редактировать и управлять структурой проекта без отдельного FTP-клиента.

**Причина уязвимости:**
Приложение принимало данные из HTTP-заголовка `User-Agent` и выводило их обратно на страницу без достаточной фильтрации и HTML-экранирования.

**Возможные последствия:**
Если администратор или другой пользователь откроет специально подготовленную страницу, в его браузере может выполниться JavaScript-код злоумышленника. Это может привести к краже cookie, выполнению действий от имени пользователя или подмене содержимого страницы.

### CVE-2021-42363 — Preview E-Mails for WooCommerce WordPress plugin

**Источник:** https://nvd.nist.gov/vuln/detail/CVE-2021-42363

**Тип уязвимости:** Reflected Cross-Site Scripting.

**Описание:**
Плагин Preview E-Mails for WooCommerce до версии 1.6.8 был уязвим к reflected XSS через параметр `search_order`, который находился в файле:

```text
~/views/form.php
```

Параметр можно было использовать для внедрения произвольного JavaScript-кода, потому что введённые данные попадали в HTML-ответ без корректной обработки.

**Для чего используется компонент:**
Preview E-Mails for WooCommerce — это WordPress/WooCommerce-плагин, который помогает администратору магазина просматривать письма, отправляемые покупателям. Например, можно проверить, как выглядят письма по заказам, уведомления и шаблоны email-сообщений.

**Причина уязвимости:**
Параметр `search_order` не проходил нормальную проверку и экранирование перед выводом в HTML. Из-за этого браузер воспринимал часть пользовательского ввода не как текст, а как код страницы.

**Возможные последствия:**
Злоумышленник мог подготовить ссылку с XSS-payload и отправить её пользователю с доступом к панели сайта. При открытии ссылки вредоносный скрипт выполнился бы в контексте сайта.

### Общее количество CVE за 2021 год

Для подсчёта общего количества CVE за 2021 год можно использовать статистику NVD/CVE. По найденным данным за 2021 год было зарегистрировано **21 957 CVE**.

Отдельно по XSS точное число зависит от того, как именно искать: только по PHP, только по WordPress-плагинам или вообще по всем XSS. Поэтому в отчёте я фиксирую именно общее количество CVE за 2021 год, как и требуется в задании.

## Часть 2. Проведение XSS-атаки на стенде

### Запуск стенда

Сначала я скачал уязвимый образ:

```bash
docker pull ket9/otus-devsecops-xss
```

Потом запустил контейнер:

```bash
docker run -d -p 8080:80 ket9/otus-devsecops-xss:latest
```

После запуска открыл приложение в браузере:

```text
http://localhost:8080/
```

На главной странице были доступны ссылки, среди них страница:

```text
http://localhost:8080/XSS-1/
```

На этой странице было поле для комментария и кнопка `Save Data`.

### Ход рассуждений и проверка приложения

Сначала я ввёл обычный текст в поле комментария и нажал `Save Data`. После сохранения текст появился ниже в списке комментариев. После обновления страницы комментарий не исчез, то есть данные сохранялись на стороне сервера.

Дальше я попробовал проверить, выводится ли введённый текст как обычный текст или как HTML. Для этого ввёл:

```html
<b>test</b>
```

После сохранения слово `test` отобразилось жирным. Из этого я сделал вывод, что приложение не экранирует HTML-теги и вставляет пользовательский ввод в страницу как HTML.

После этого я проверил выполнение JavaScript-кода. В поле комментария был введён payload:

```html
<script>alert('XSS')</script>
```

После нажатия `Save Data` и обновления страницы в браузере появилось всплывающее окно с текстом `XSS`. Это означает, что JavaScript-код действительно выполнился в контексте страницы.

Затем я открыл страницу заново, как будто это другой пользователь. Сохранённый комментарий остался на странице, и скрипт снова выполнился. Значит, уязвимость не просто reflected XSS, а именно хранимый XSS.

### Найденная уязвимость

В приложении найдена уязвимость **Stored Cross-Site Scripting**.

Суть проблемы в том, что приложение принимает пользовательский ввод из поля комментария, сохраняет его и потом выводит обратно на страницу без фильтрации и экранирования. Поэтому вместо обычного текста можно сохранить HTML или JavaScript-код, который будет выполняться у всех пользователей, открывающих страницу с комментариями.

### Тип уязвимости

Тип уязвимости: **Stored XSS**.

Это хранимая XSS-атака, потому что вредоносный скрипт сохраняется на сервере и выполняется не только у того, кто его ввёл, но и у других пользователей при открытии страницы.

### Возможные последствия

Такая уязвимость может привести к следующим последствиям:

1. выполнение произвольного JavaScript-кода в браузере пользователя;
2. кража cookie или других данных из браузера;
3. выполнение действий от имени пользователя;
4. подмена содержимого страницы;
5. перенаправление пользователя на другой сайт;
6. распространение вредоносного кода через сохранённые комментарии.

### Меры предотвращения

Чтобы предотвратить такую уязвимость, нужно не выводить пользовательский ввод напрямую в HTML.

1. **Экранировать специальные символы HTML:**

   - `<` заменять на `&lt;`
   - `>` заменять на `&gt;`
   - `"` заменять на `&quot;`
   - `'` заменять на `&#039;`
   - `&` заменять на `&amp;`

   В PHP для этого можно использовать функцию:

   ```php
   htmlspecialchars($comment, ENT_QUOTES, 'UTF-8')
   ```

2. **Фильтровать входные данные.**

   Если комментарии должны быть только текстовыми, можно полностью запрещать HTML-теги. Например, удалять или отклонять ввод, где есть конструкции:

   ```html
   <script>
   <img onerror=...>
   <svg onload=...>
   javascript:
   onmouseover=
   onclick=
   ```

3. **Использовать безопасный вывод.**

   Пользовательский текст должен вставляться как текст, а не как HTML. То есть приложение должно показывать строку `<script>alert('XSS')</script>` именно как текст, а не выполнять её.

4. **Добавить Content Security Policy.**

   Например:

   ```http
   Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self';
   ```

   Это не заменяет экранирование, но снижает риск выполнения встроенных скриптов.

5. **Проверять данные и на клиенте, и на сервере.**

   Клиентская проверка удобна для пользователя, но её легко обойти. Основная защита должна быть на сервере.

## Итоговый вывод

В первой части были рассмотрены CVE за 2021 год, связанные с XSS в PHP-компонентах. В качестве примеров были выбраны два WordPress-плагина: File Manager и Preview E-Mails for WooCommerce.

Во второй части на учебном стенде была проведена XSS-атака через поле комментария. Сначала было проверено, что HTML-теги обрабатываются браузером, затем был введён JavaScript-payload `<script>alert('XSS')</script>`. После сохранения и обновления страницы скрипт выполнился, а так как payload сохранялся на сервере и запускался повторно при открытии страницы, уязвимость была определена как Stored XSS.
