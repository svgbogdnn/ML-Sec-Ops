Часть 1. Анализ уязвимостей REST API

В этой части я посмотрел несколько CVE за 2025 год, которые связаны с проблемами в REST API. Для классификации использовал категории OWASP API Top 10. Во всех примерах проблема находится не только в самой технической ошибке, а в логике проверки доступа, обработки входных данных или ограничений на стороне сервера.

CVE Источник Тип по OWASP API Top 10 В чём недостаток Основная причина Возможные последствия
CVE-2025-52554 (n8n) https://nvd.nist.gov/vuln/detail/CVE-2025-52554 Broken Object Level Authorization Пользователь мог остановить чужое выполнение workflow через endpoint /rest/executions/:id/stop, если знал или подбирал чужой execution id В большинстве endpoint проверка прав была, но именно для остановки выполнения не проверялось, принадлежит ли объект текущему пользователю Нарушение работы чужих автоматизаций, остановка бизнес-процессов, влияние на данные и задачи других пользователей

Вывод по первой части

Во всех трёх случаях уязвимость связана с тем, что API слишком сильно доверяет входным данным или не проверяет контекст запроса:

  • в n8n не проверялось, принадлежит ли конкретный объект текущему пользователю;
  • в Better Auth сервер доверял userId из запроса и из-за этого можно было обойти аутентификацию;
  • в Dify сервер выполнял запросы по пользовательскому URL, из-за чего возникала SSRF-уязвимость.

То есть для REST API критично не просто проверять формат входных данных, а ещё проверять права доступа, состояние сессии и то, какие действия сервер выполняет от имени пользователя.

Часть 2. Поиск недостатка в уязвимом API

Во второй части я выбрал вариант с самостоятельным поиском уязвимости в тестовом приложении. После запуска контейнера открыл приложение по адресу:

http://localhost:8080/

Затем перешёл на страницу инициализации базы данных:

http://localhost:8080/createdb

После заполнения базы начал проверять, какие данные API отдаёт без авторизации.

Проверка списка пользователей

Сначала отправил GET-запрос на получение списка пользователей:

http://localhost:8080/users/v1

В ответ приложение вернуло список пользователей:

{
  "users": [
    {
      "email": "mail1@mail.com",
      "username": "name1"
    },
    {
      "email": "mail2@mail.com",
      "username": "name2"
    },
    {
      "email": "admin@mail.com",
      "username": "admin"
    }
  ]
}

Уже на этом этапе видно, что API без авторизации отдаёт список пользователей и их email.

Проверка данных конкретного пользователя

Дальше я попробовал обратиться к конкретному пользователю по имени в URL:

http://localhost:8080/users/v1/name1

Ответ был таким:

{
  "username": "name1",
  "email": "mail1@mail.com"
}

Аналогично можно открыть данные других пользователей, просто подставляя их username в URL. Получается, что сервер отдаёт объект пользователя только по идентификатору из адреса и не проверяет, имеет ли текущий клиент право видеть эти данные.

Проверка связанных данных

После этого я проверил, какие данные можно получить по книгам:

http://localhost:8080/books/v1

Приложение вернуло:

{
  "Books": [
    {
      "book_title": "bookTitle82",
      "user": "name1"
    },
    {
      "book_title": "bookTitle98",
      "user": "name2"
    },
    {
      "book_title": "bookTitle68",
      "user": "admin"
    }
  ]
}

Этот ответ дополнительно показывает, что API раскрывает не только пользователей, но и связанные с ними данные. При этом авторизация для чтения снова не требуется.

Проверка возможности изменения данных

Потом я решил проверить, можно ли не только читать, но и изменять данные пользователя. Для этого отправил PUT-запрос на изменение email:

curl -X PUT "http://localhost:8080/users/v1/name1/email" -H "Content-Type: application/json" -d '{"email":"hacker@mail.com"}'

Сервер ответил:

{
  "status": "fail",
  "message": "Invalid token"
}

После этого я ещё раз проверил данные пользователя:

http://localhost:8080/users/v1/name1

Email остался прежним:

{
  "username": "name1",
  "email": "mail1@mail.com"
}

Значит, изменение данных защищено токеном, но чтение пользовательских данных доступно без нормальной проверки прав.

Найденная уязвимость

В приложении есть уязвимость типа BOLA — Broken Object Level Authorization.

Суть проблемы в том, что сервер отдаёт объект пользователя только по параметру из URL (username) и не проверяет, имеет ли запрашивающий право просматривать именно этот объект. Из-за этого можно перебирать имена пользователей и получать чужие данные без авторизации.

Тип недостатка

По OWASP API Top 10 это относится к категории:

Broken Object Level Authorization

Приложение не выполняет проверку доступа на уровне конкретного объекта. Идентификатор объекта передаётся в URL, а сервер доверяет этому значению и сразу возвращает данные.

Что может сделать злоумышленник

При такой уязвимости злоумышленник может:

  1. Получить список пользователей.
  2. Подставлять разные username в URL.
  3. Читать email и другие данные пользователей.
  4. Связывать пользователей с другими объектами, например книгами.
  5. Собирать информацию без входа в систему.

При этом изменение email в данном приложении защищено токеном, поэтому найденная проблема относится именно к незащищённому чтению данных.

Меры предотвращения

Чтобы исправить такую уязвимость, нужно:

  1. Проверять права доступа к каждому объекту при каждом запросе.
  2. Требовать аутентификацию перед просмотром пользовательских данных.
  3. Не отдавать данные только на основании username из URL.
  4. Ограничить или полностью закрыть выдачу списка всех пользователей.
  5. Возвращать только минимально необходимую информацию.
  6. Реализовать object-level authorization на стороне сервера, а не полагаться на клиент.
  7. Для чужих объектов возвращать ошибку доступа, например 403 Forbidden.

Общий вывод

В первой части я рассмотрел примеры CVE, где проблемы в REST API возникали из-за ошибок авторизации, аутентификации и проверки пользовательского ввода. Во второй части на учебном приложении была найдена похожая по смыслу проблема: API отдаёт данные пользователей без проверки прав доступа.

Главный вывод: в REST API нельзя доверять параметрам из URL или тела запроса. Даже если пользователь знает корректный username, id или другой идентификатор, сервер всё равно должен проверить, имеет ли он право получить именно этот объект. В данном приложении запись данных частично защищена токеном, но чтение осталось открытым, поэтому уязвимость можно классифицировать как Broken Object Level Authorization.
