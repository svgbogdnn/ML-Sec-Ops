# Часть 1. Проверка пользователя внутри контейнера

Сначала я посмотрел список локальных Docker-образов:

```bash
docker image ls
```

После этого до запуска контейнера выполнил команду на хостовой машине:

```bash
whoami
```

Команда показала обычного пользователя моей системы. Затем я запустил командную оболочку `sh` внутри выбранного контейнера:

```bash
docker run -it ket9/otus-devsecops-owasp-rest:latest sh
```

Уже внутри контейнера снова выполнил:

```bash
whoami
```

Внутри контейнера команда показала:


![Скриншот проверки пользователя в исходном контейнере](part1.png)

## Вывод по первой части

По умолчанию контейнер запускается от пользователя `root`. Это небезопасно, потому что при эксплуатации уязвимости в приложении злоумышленник сразу получает максимальные права внутри контейнера. Контейнер — это не полноценная виртуальная машина, поэтому запуск от `root` увеличивает риск выхода за пределы приложения и усложняет защиту.

# Часть 2. Dockerfile с запуском не от root

Для исправления проблемы я написал Dockerfile на основе исходного образа. В нем создается отдельный пользователь `appuser` с UID/GID `10001`, после чего контейнер переключается на него с помощью инструкции `USER`.

```dockerfile
FROM ket9/otus-devsecops-owasp-rest:latest

# Создаем отдельную группу и пользователя без root-прав.
# Используется явный UID/GID, чтобы было проще контролировать права при запуске.
RUN echo "appgroup:x:10001:" >> /etc/group && \
    echo "appuser:x:10001:10001:appuser:/home/appuser:/bin/sh" >> /etc/passwd && \
    mkdir -p /home/appuser && \
    chown -R 10001:10001 /home/appuser

# Порт приложения из базового образа.
EXPOSE 8080

# Запускаем процесс внутри контейнера не от root.
USER 10001:10001

# Дополнительные настройки безопасности, которые лучше применять при запуске контейнера:
# docker run --rm -p 8080:8080 \
#   --read-only \
#   --cap-drop=ALL \
#   --security-opt=no-new-privileges \
#   --pids-limit=100 \
#   --memory=512m \
#   --cpus=0.5 \
#   --tmpfs /tmp:rw,noexec,nosuid,size=64m \
#   secure-owasp-rest:1.0
#
# Смысл настроек:
# --read-only запрещает запись в файловую систему контейнера;
# --cap-drop=ALL убирает лишние Linux capabilities;
# --security-opt=no-new-privileges запрещает повышать привилегии;
# --pids-limit ограничивает количество процессов;
# --memory и --cpus ограничивают ресурсы;
# --tmpfs /tmp дает временную директорию без права исполнения файлов.
```

Собрал новый образ командой:

```bash
docker build -t secure-owasp-rest:1.0 .
```

После сборки зашел внутрь контейнера:

```bash
docker run --rm -it --entrypoint sh secure-owasp-rest:1.0
```

И снова выполнил:

```bash
whoami
```

Результат:

```text
appuser
```

![Скриншот проверки пользователя в защищенном контейнере](part2.png)

## Вывод по второй части

Теперь контейнер запускается не от `root`, а от отдельного пользователя `appuser`. Это не исправляет все возможные уязвимости в приложении, но снижает последствия атаки: даже если злоумышленник сможет выполнить код внутри контейнера, он получит ограниченные права.

Дополнительно в Dockerfile указаны флаги, которые можно использовать при запуске контейнера. Особенно важны `--cap-drop=ALL`, `--security-opt=no-new-privileges` и `--read-only`, потому что они уменьшают доступные привилегии и запрещают лишнюю запись в файловую систему.

# Часть 3. Сканирование образа через Trivy

Для проверки безопасности образа я использовал сканер Trivy. Сканирование можно выполнить так:

```bash
docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image secure-owasp-rest:1.0
```

Trivy проверил системные пакеты базового образа и зависимости приложения. В результате было найдено много известных уязвимостей.

## Результат по системным пакетам

Для базового образа на основе Alpine было найдено:

```text
Total: 72
MEDIUM: 16
HIGH: 48
CRITICAL: 8
```

## Результат по Python-зависимостям

Также Trivy отдельно показал уязвимости в Python-зависимостях приложения:

```text

LOW: 4
MEDIUM: 23
HIGH: 14
CRITICAL: 0
```

![Скриншот вывода Trivy по Python-зависимостям](part3_2.png)

## Анализ результата

Образ содержит большое количество уязвимостей, среди которых есть уровни `HIGH` и `CRITICAL`. Это означает, что такой образ нельзя считать безопасным для продакшена без дополнительной доработки.

Наиболее проблемные места:

- устаревший базовый образ;
- старые системные пакеты;
- устаревшая версия Python;
- старые Python-библиотеки приложения;
- наличие уязвимостей в пакетах вроде `openssl`, `busybox`, `Flask`, `PyJWT`, `Werkzeug`, `setuptools`, `urllib3`.

Важно, что запуск контейнера не от `root` снижает последствия атаки, но не убирает сами CVE из образа. Если в приложении или библиотеке есть известная уязвимость, ее нужно исправлять обновлением зависимостей и пересборкой образа.

## Что нужно сделать для улучшения безопасности

1. Обновить базовый образ до актуальной версии.
2. Обновить Python и зависимости приложения.
3. Удалить из контейнера все ненужные пакеты и инструменты.
4. Запускать приложение только от непривилегированного пользователя.
5. Использовать ограничения при запуске: `--read-only`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, лимиты CPU/RAM/PID.
6. Регулярно запускать Trivy или аналогичный сканер в CI/CD.
7. Пересобирать образ после выхода исправлений безопасности.

В первой части я убедился, что исходный Docker-образ запускается от пользователя `root`, что является небезопасной настройкой по умолчанию. Во второй части я собрал новый образ, где приложение запускается от отдельного пользователя `appuser`, и указал дополнительные флаги для более безопасного запуска контейнера. В третьей части я проверил образ через Trivy и увидел, что в нем много известных уязвимостей, в том числе высокого и критического уровня.

Главный вывод: безопасность Docker-контейнера состоит не только в запуске не от `root`. Также нужно обновлять базовый образ, следить за зависимостями, минимизировать состав контейнера и регулярно сканировать образ на CVE.
