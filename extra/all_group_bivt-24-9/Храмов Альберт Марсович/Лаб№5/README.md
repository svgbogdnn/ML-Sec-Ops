## Часть I. Анализ фрагментов кода

### Фрагмент 1

Что не так: SECRET_KEY захардкожен прямо в коде. Если код утечёт, злоумышленник сможет подделывать сессии.

Как надо: вынести в переменную окружения.

```python
import os
app.config['SECRET_KEY'] = os.environ.get('SECRET_KEY')
```

### Фрагмент 2

Что не так: пароль объявлен как TextField, поэтому отображается в открытом виде в браузере. Нет валидации длины.

Как надо: использовать PasswordField с валидатором.

```python
from wtforms import PasswordField
from wtforms.validators import Length

password = PasswordField('password', validators=[Length(min=8)])
```

### Фрагмент 3

Что не так: блок except перехватывает все ошибки и всегда показывает страницу успеха, даже если регистрация не прошла. Пароль сохраняется без хэширования.

Как надо: обрабатывать ошибки отдельно, показывать реальный результат, хэшировать пароль через bcrypt или argon2 перед сохранением.

## Часть II. Django

### Вопрос 1. От каких атак защищает Django

Django из коробки защищает от SQL-инъекций (ORM использует параметризованные запросы), XSS (шаблонизатор автоматически экранирует вывод), CSRF (токен в каждой форме) и Clickjacking (заголовок X-Frame-Options).

### Вопрос 2. Управление сессиями в Django

Данные сессии хранятся на сервере в таблице django_session. В браузере хранится только cookie sessionid с уникальным ключом. При каждом запросе Django находит сессию по этому ключу и восстанавливает данные.

Cookie по умолчанию имеет флаги HttpOnly (JS не может его прочитать) и Secure (передаётся только по HTTPS). Время жизни сессии задаётся через SESSION_COOKIE_AGE, по умолчанию 2 недели. При выходе Django удаляет запись из базы на сервере.
