Ход выполнения

MobSF я развернула через Docker:

docker run -d --name mobsf-lab7 -p 8000:8000 opensecurity/mobile-security-framework-mobsf:latest

После старта контейнер слушает на localhost:8000. Для входа в mobsf использовала логин и пароль из логов: mobsf и mobsf.

В качестве приложения для скана я взяла Todoist для Android версии 11474 (~57 МБ). Это популярное приложение для управления задачами с синхронизацией, уведомлениями и интеграциями.

Дальше через localhost:8000 загрузила APK в MobSF и запустила скан.

Опасные разрешения (статус dangerous)

MobSF нашёл 6 разрешений со статусом dangerous. Самые важные из них:

Разрешение Риск Почему это проблема
ACCESS_FINE_LOCATION High Точное местоположение через GPS - риск утечки геоданных
ACCESS_COARSE_LOCATION Medium Приблизительное местоположение через сеть
ACCESS_BACKGROUND_LOCATION High Доступ к локации в фоне - пользователь может не знать
RECORD_AUDIO Medium Запись звука с микрофона - риск перехвата приватных разговоров
POST_NOTIFICATIONS Medium Показ уведомлений - может использоваться для фишинга
READ_CONTACTS High Доступ ко всем контактам - утечка личных данных

Для приложения-планировщика часть разрешений логична (интернет, уведомления), но READ_CONTACTS и ACCESS_BACKGROUND_LOCATION выглядят избыточными. Лучше запрашивать такие пермишены только при реальной необходимости, а не при установке.

Network Security (High: 1)

  • 127.0.0.1 permits cleartext
  • Локалхост разрешает незашифрованный трафик - риск для отладочных сценариев

Хотя это касается только localhost, в отладочных сборках такой конфиг может попасть в продакшен. Лучше явно запрещать cleartext на уровне всего приложения.

Проблема с экспортированными компонентами - типичная ошибка. Для приложения с задачами это может привести к утечке данных через чужие приложения.

Самая опасная находка - World Writable SharedPreference. Это значит, что любое приложение с разрешением на чтение внешнего хранилища может получить доступ к данным Todoist. В 2024 году это уже не должно встречаться.

"facebook_client_token":"c5a29925ae6d41fe68136a6edfc5749f"

План по митигации

  1. Исправить World Writable в SharedPreferences: Найти место где создаётся world writable файл или SharedPreference и убрать этот режим. По умолчанию для SharedPreference надо использовать MODE_PRIVATE. Если данные нужно расшарить с другим приложением, использовать Content Provider с правами доступа.

  2. Ограничить экспорт компонентов: Пройти по всем активити, сервисам, броадкаст ресиверам и контент провайдерам. Если они не должны быть доступны другим приложениям, явно проставить exported="false". Если экспорт нужен, защитить его через android:permission с собственным разрешением signature уровня.

  3. Запрос разрешений в рантайме + минимизация: READ_CONTACTS и ACCESS_BACKGROUND_LOCATION для планировщика выглядят лишними и их надо постараться убрать. Если разрешение реально нужно, запрашивать его только в момент использования соответствующей функции, а не сразу при старте приложения.

  4. Заменить небезопасные генераторы и хеши: Заменить Random на SecureRandom во всех местах где случайные числа используются для криптографии, токенов, ключей. Заменить MD5 и SHA-1 на современные хеши, как минимум SHA-256.

  5. Очистить логи от чувствительных данных: Найти все места где логируются токены, пароли или персональные данные. Убрать логирование или использовать безопасный логгер без PII в продакшен сборке.

  6. Настроить Network Security Config: Убрать разрешение cleartext для 127.0.0.1 из network security config. Если открытый HTTP действительно нужен для каких-то локальных кейсов, перечислить домены явно с cleartextTrafficPermitted="true", а не на уровне всего приложения.

  7. Поднять minSdkVersion: Поднять min sdk хотя бы до 29 (Android 10). На таких устройствах уже работают современные механизмы безопасности типа improved permissions и более жёсткая работа с TLS.
