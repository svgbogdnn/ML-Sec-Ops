Вопрос 1: Какие наиболее распространенные атаки предотвращает django?

  1. Защита от атак на основе инъекций (- Django ORM автоматически экранирует пользовательский ввод и предотвращает SQL-инъекции.
  2. Защита от XSS атак. Шаблонизатор Django автоматически экранирует специальные HTML-символы (<, >, &, ', ") при выводе переменных.
  3. Cross-Site Request Forgery (CSRF). При загрузке страницы с формой Django генерирует уникальный секретный токен и вставляет его в скрытое поле формы через тег {% csrf_token %}. Когда форма отправляется, middleware CsrfViewMiddleware сверяет токен из тела запроса с токеном, который хранится в cookie.
  4. Защита от кликджекинга - Django по умолчанию передает заголовок X-Frame-Options: DENY на все запросы. Это нужно для того, чтобы сайт нельзя было встроить в iframe. Это защищает от атаки, при которой злоумышленник встраивает целевой сайт в невидимый iframe на своей странице и накладывает поверх элементы-приманки.
  5. SSL/HTTPS - помогает встраивать HTTPS в сервис а) SECURE_SSL_REDIRECT = True - автоматический редирект с HTTP на HTTPS. б) SECURE_HSTS_SECONDS- заголовок, который сообщает браузеру, что сайт работает только по HTTPS. в) SESSION_COOKIE_SECURE = True - cookie сессии передаются только по HTTPS. г) CSRF_COOKIE_SECURE = True - CSRF-cookie только по HTTPS.

Вопрос 2: Описать, как устроено управление пользовательскими сессиями в django

HTTP - stateless-протокол: каждый запрос независим, сервер не помнит предыдущих взаимодействий. Сессии решают эту проблему. Сессии позволяют сохранять состояние между запросами.

При первом обращении Django генерирует уникальный session ID и отправляет его браузеру, сохраняем в cookie. Сами данные сессии (кто пользователь, его настройки, содержимое корзины) хранятся на сервере, по умолчанию - в таблице django_session

Если обновляете какие-либо данные при помощи ключа сессии тогда не надо беспокоиться о процессе сохранении

# Данное присваивание распознается как обновление сессии
# и данные будут сохранены
request.session['my_car'] = 'mini'

Если обновите информацию внутри данных сессии, тогда Django не распознает эти изменения и не выполнит сохранение данных. В таких случаях вам надо явно указывать, что сессия была изменена.

# Объект сессии модифицируется неявно.
# Изменения НЕ БУДУТ сохранены!
request.session['my_car']['wheels'] = 'alloy'

# Явное указание, что данные изменены.
# Сессия будет сохранена, куки обновлены (если необходимо).
request.session.modified = True

Помимо БД, данные сессий можно хранить в кэше (Redis/Memcached), файлах или в подписанных cookie. Также Django предоставляет несколько настроек для управления временем жизни сессий: 1) SESSION_COOKIE_AGE - время жизни cookie сессии в секундах (по умолчанию 1209600) 2) SESSION_EXPIRE_AT_BROWSER_CLOSE - если True, то сессия истекает при закрытии браузера (по умолчание False) 3) SESSION_SAVE_EVERY_REQUEST - если True, то сессия пересохраняется при каждом запросе (по умолчание False) 4) SESSION_COOKIE_SECURE - если True, браузер будет отправлять cookie сессии только по HTTPS. 5) SESSION_COOKIE_DOMAIN - определяет для какого домена действует cookie (по умолчанию None => cookie привязана только к текущему домену) Стоит помнить, что истекшие сессии не удаляются автоматически из БД. Для очистки нужно периодически запускать ``

python manage.py clearsessions
