Провел SAST-анализ приложения NewPipe через MobSF. Ниже описал что нашел и что с этим делать

Что сканировал

  • Приложение: NewPipe
  • Версия: 0.27.2
  • Инструмент: MobSF v4.5.0
  • Тип анализа: статический (SAST)

    Найденные проблемы

    1. Слишком старая минимальная версия Android

MinSdk выставлен в 21, то есть приложение можно поставить на Android 5.0. Это устройства 2014 года, они уже лет пять не получают никаких патчей безопасности от Google Что делать: поднять minSdk до 29 (Android 10)

2. allowBackup=true в манифесте

Это забытая настройка. Флаг разрешает копировать данные приложения через ADB без рут-прав. То есть если у пользователя включена отладка по USB и кто-то получил физический доступ к устройству - данные утекли.

Что делать: выставить android:allowBackup="false" в AndroidManifest.xml

3. Exported компоненты без защиты

Несколько компонентов приложения торчат наружу без каких-либо ограничений:

  • PlayerService - сервис плеера
  • RouterActivity - обрабатывает внешние ссылки
  • MediaButtonReceiver - перехватывает кнопки медиа
  • PanicResponderActivity, FilePickerActivityHelper

Любое стороннее приложение может к ним обратиться. В теории через RouterActivity можно попробовать подсунуть вредоносную ссылку, а через PlayerService - дёрнуть управление плеером.

Что делать:

  • Те компоненты, которые не нужны внешним приложениям - выставить android:exported="false"
  • Для RouterActivity добавить кастомное разрешение с protectionLevel="signature", чтобы к нему могли обращаться только приложения с той же подписью

4. Разрешение SYSTEM_ALERT_WINDOW

Приложение запрашивает возможность рисовать поверх других окон. Исторически это разрешение используют в оверлейных атаках - когда вредоносное приложение рисует фейковый интерфейс поверх реального

Что делать: переехать на PictureInPictureParams API — это нативный PiP в Android, не требует SYSTEM_ALERT_WINDOW и работает с Android 8+.

5. Запись на внешнее хранилище

WRITE_EXTERNAL_STORAGE — разрешение, которое даёт доступ к общей папке на устройстве. Всё что туда пишет NewPipe, могут прочитать другие приложения

Что делать: использовать getExternalFilesDir() — это папка приложения на внешнем хранилище, изолированная, и не требует разрешения начиная с Android 10. Для загрузок в общую медиатеку - MediaStore API.

6. Использование MD5 и слабого генератора случайных чисел

В коде нашли использование MD5 для хэширования и java.util.Random там где нужна криптографическая случайность. MD5 сломан — для него известны коллизии, то есть можно подобрать два разных файла с одинаковым хэшем

Что делать:

  • MD5 заменить на SHA-256 (MessageDigest.getInstance("SHA-256"))
  • java.util.Random заменить на java.security.SecureRandom

7. Raw SQL запросы

В FinishedMissionStore.java найдены сырые SQL-запросы. Если в них попадает пользовательский ввод без обработки. В случае NewPipe это локальная база данных, так что риск ниже чем в серверных приложениях, но всё равно неприятно.

Что делать: использовать параметризованные запросы или мигрировать на Room ORM - он сам всё экранирует и делает это правильно.

8. Возможный хардкод чувствительных данных

MobSF отметил несколько файлов где могут быть захардкожены какие-то данные — ключи, токены, адреса. Часть из этого скорее всего ложные срабатывания (например IP-адреса серверов Invidious), но проверить стоит.

Что делать: пройтись по файлам вручную, вынести реальные секреты в BuildConfig или Android Keystore. IP-адреса и публичные URL — не секреты, можно оставить.

Итого

Критичных уязвимостей, которые прямо сейчас можно эксплуатировать удалённо не нашел. Основные проблемы это устаревшие практики и недостаточная изоляция компонентов
