Почему это секрет?

Пароли администратора и пользователя Tom хранятся как Java-константы прямо в исходном коде. Файл попал в репозиторий и навсегда остался в истории Git. Любой, у кого был доступ к репозиторию (даже временный), мог извлечь пароли.

Комментарий в коде:

//TODO should be random generated when starting the server

Разработчики сами понимали проблему, но так и не исправили.

Правильный способ хранения

Пароли не должны присутствовать в коде.

Можно:

  • генерировать при старте приложения (SecureRandom)
  • передавать через переменные окружения (System.getenv)
  • хранить в HashiCorp Vault/AWS Secrets Manager

Почему это секрет?

Реальный подписанный JWT-токен для пользователя Tom опубликован в учебном файле.

  • username: Tom
  • Role: Manager/Project Administrator

Строка/контекст Блок deploy.api_key.secure и env.global
Найденное значение Travis API key, Docker login/password, Slack token

Почему это секрет?

В файле .travis.yml находятся три вида зашифрованных секретов:

  • GitHub Release API key
  • логин и пароль Docker Hub
  • токен Slack для уведомлений

Хотя они зашифрованы ключом Travis CI, сам факт хранения в репозитории опасен. При компрометации Travis-аккаунта или утечке RSA-ключа Travis все три секрета будут раскрыты одновременно.

Правильный способ хранения

Использовать переменные окружения, настроенные в UI Travis CI: Settings → Environment Variables

Для GitHub Actions - использовать OIDC-интеграцию без долгосрочных токенов.
Для Docker Hub - токены с минимальным scope вместо пароля аккаунта.

Секрет #4 - Статический CSRF-токен [ВЫСОКИЙ]

Поле Значение
Hash коммита 1a83e2825e2b1e040e2a2042677f03727f654150
Дата/Commit 2019-11-03 \ "Code style (#696)"
Файл webgoat-lessons/csrf/src/main/java/org/owasp/webgoat/csrf/ForgedReviews.java
Строка/контекст Строка ~52
Найденное значение private static final String weakAntiCSRF = "2aa14227b9a13d0bede0388a7fba9aa9";

Почему это секрет?

MD5-строка используется как токен защиты от CSRF-атак, но она статическая и одинаковая для всех пользователей и сессий. Злоумышленник, один раз узнав значение из кода или перехватив запрос, может подделывать любые формы от имени любого пользователя.

Правильный способ хранения

Anti-CSRF токен должен:

  • быть уникальным для каждой сессии
  • генерироваться криптографически стойким генератором (SecureRandom)
  • проверяться на сервере

Следует использовать встроенные механизмы фреймворка: Spring Security CSRF protection

Почему это секрет?

Пароль пользователя Tom захардкожен прямо в Java-классе, реализующем логику сброса пароля. Тип секрета: credential внутри security-логики восстановления доступа.

Дополнительная опасность:

TOM_EMAIL = "tom@webgoat-cloud.org"

Email и пароль раскрываются вместе.

Правильный способ хранения

Для модуля сброса пароля необходимо:

  • генерировать одноразовый токен (UUID, SecureRandom)
  • хранить только его хеш (bcrypt, Argon2)
  • задавать TTL и флаг использования

Текущий пароль пользователя при сбросе не нужен
