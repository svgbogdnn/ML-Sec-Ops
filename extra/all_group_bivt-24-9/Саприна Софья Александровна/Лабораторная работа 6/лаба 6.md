**Тема:** изучение существующих CI/CD с точки зрения доступных инструментов информационной безопасности  
**Проверяемый репозиторий:** `https://github.com/OtusTeam/DevSecOps_secret-finding.git`  
**Использованный инструмент:** `truffleHog`  
**Подход:** анализ истории Git, diff-ов коммитов, регулярных выражений и строк с высокой энтропией.

## 1. Краткое описание выполненной проверки

В рамках лабораторной работы был выполнен поиск чувствительных данных в учебном Git-репозитории. Основной акцент сделан не только на нахождении строк, похожих на секреты, но и на их интерпретации: что именно было найдено, почему это представляет риск, где такой секрет должен храниться в нормальной инфраструктуре и какие действия нужны для устранения проблемы.

Важно учитывать, что удаление секрета из последней версии файла не решает проблему полностью. Если значение уже попадало в коммит, оно остаётся доступным через историю Git. Поэтому при реагировании необходимо не только исправлять код, но и выполнять ротацию секрета, а при необходимости очищать историю репозитория.

# Секрет 1. Пароли, записанные напрямую в исходном коде

| Поле | Данные |
|---|---|
| Коммит | `e8d086ac9b62efebc9937c5b41659b454f2973c3` |
| Дата и сообщение | `2019-09-20`, `All successful` |
| Файл | `webgoat-lessons/challenge/src/main/java/org/owasp/webgoat/plugin/SolutionConstants.java` |
| Примерное место | строки 12–14, интерфейс `SolutionConstants` |
| Найденные значения | `String PASSWORD = "!!webgoat_admin_1234!!";` и `String PASSWORD_TOM = "thisisasecretfortomonly";` |

## Почему это является секретом

В файле обнаружены реальные строковые значения, похожие на пароли администратора и пользователя Tom. Они объявлены как константы Java-класса, то есть становятся частью исходного кода и могут быть прочитаны любым человеком, имеющим доступ к репозиторию или его истории.

Опасность такого подхода в том, что пароль фактически распространяется вместе с приложением. Даже если разработчик потом удалит эти строки из текущей версии, они всё равно будут доступны через старые коммиты. Кроме того, наличие комментария `TODO should be random generated when starting the server` показывает, что значение планировалось заменить генерацией, но временное решение осталось в кодовой базе.

## Как правильно хранить

Пароли не должны храниться в репозитории. Более корректные варианты:

- передавать значение через переменные окружения;
- хранить секреты в Vault, AWS Secrets Manager, Azure Key Vault или аналогичном хранилище;
- для учебных и тестовых стендов генерировать пароль при запуске приложения;
- не коммитить локальные конфигурационные файлы с реальными значениями.

## Рекомендации по исправлению

Нужно удалить пароль из кода, заменить его чтением из безопасного источника, добавить файл с локальными настройками в `.gitignore`, выполнить ротацию скомпрометированного пароля и очистить историю репозитория с помощью BFG Repo-Cleaner или `git filter-repo`.

# Секрет 2. JWT-токен со слабым ключом подписи

| Поле | Данные |
|---|---|
| Коммит | `e8d086ac9b62efebc9937c5b41659b454f2973c3` |
| Дата и сообщение | `2019-09-20`, `All successful` |
| Файл | `webgoat-lessons/jwt/src/main/resources/lessonPlans/en/JWT_weak_keys` |
| Примерное место | добавленный в diff блок с JWT |
| Найденное значение | JWT, начинающийся с `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...` |

## Почему это является секретом

JWT сам по себе не всегда является секретом, но в данном случае он несёт чувствительную информацию и связан с проблемой слабого ключа подписи. В payload токена указаны данные пользователя Tom и его роль, связанная с управлением проектом. Если ключ HMAC слабый, злоумышленник может подобрать его офлайн и после этого выпускать новые токены с изменёнными правами.

Риск особенно серьёзный, если такой пример переносится из учебного материала в реальную систему. Тогда токен и подход к его подписи становятся точкой обхода авторизации.

## Как правильно хранить

В учебных материалах должны использоваться только явно фиктивные значения, например `EXAMPLE_TOKEN` или `DO_NOT_USE_IN_PRODUCTION`. Для реального приложения ключ подписи JWT должен быть длинным, случайным, криптографически стойким и храниться вне репозитория.

## Рекомендации по исправлению

Следует удалить реальный токен из документации, заменить его безопасным примером, усилить ключ подписи, настроить регулярную ротацию ключей и хранить их в защищённом хранилище секретов. Также желательно добавить автоматическую проверку репозитория на JWT и другие токены.

# Секрет 3. Секретные значения в конфигурации Travis CI

| Поле | Данные |
|---|---|
| Коммит | `5dd6b3190592fca16b6d2ea5a5c7f5485be04ebf` |
| Дата и сообщение | `2019-11-17`, `Adjust lesson template (#704)` |
| Файл | `.travis.yml` |
| Примерное место | блоки `deploy.api_key.secure` и `env.global` |
| Найденные значения | Travis CI API key, Docker Hub login/password, Slack webhook token |

## Почему это является секретом

В конфигурационном файле CI/CD обнаружены значения, относящиеся к публикации релизов, работе с Docker Hub и отправке уведомлений в Slack. Даже если эти значения представлены в зашифрованном виде, они всё равно являются секретами, потому что находятся внутри репозитория и используются процессом сборки.

Главная проблема заключается в том, что компрометация ключей Travis CI или неправильная настройка прав доступа может привести к раскрытию сразу нескольких чувствительных данных. Кроме того, хранение таких значений в Git ухудшает контроль ротации и усложняет аудит.

## Как правильно хранить

Секреты CI/CD нужно хранить в настройках самой CI/CD-платформы, а не в файле репозитория. Для Travis CI это могут быть Environment Variables в настройках проекта. Для GitHub Actions — `Secrets and variables`, а для более зрелой схемы — OIDC и временные токены вместо постоянных ключей.

## Рекомендации по исправлению

Необходимо удалить секреты из `.travis.yml`, перенести их в безопасное хранилище CI/CD, заменить пароли Docker Hub на токены с минимально необходимыми правами, отозвать старые значения и настроить secret scanning в pipeline.

# Секрет 4. Статический Anti-CSRF токен

| Поле | Данные |
|---|---|
| Коммит | `1a83e2825e2b1e040e2a2042677f03727f654150` |
| Дата и сообщение | `2019-11-03`, `Code style (#696)` |
| Файл | `webgoat-lessons/csrf/src/main/java/org/owasp/webgoat/csrf/ForgedReviews.java` |
| Примерное место | около строки 52 |
| Найденное значение | `private static final String weakAntiCSRF = "2aa14227b9a13d0bede0388a7fba9aa9";` |

## Почему это является секретом

Anti-CSRF токен предназначен для защиты от подделки запросов. Чтобы такая защита работала, значение должно быть непредсказуемым, уникальным для пользователя или сессии и проверяться на серверной стороне. В найденном примере токен является статической строкой, одинаковой для всех случаев.

Если злоумышленник узнаёт это значение один раз, он может использовать его повторно. Поскольку строка находится в репозитории, её нельзя считать неизвестной или защищённой.

## Как правильно хранить

Anti-CSRF токены не должны быть постоянными константами. Их нужно генерировать на сервере с использованием криптографически стойкого генератора случайных чисел, привязывать к сессии пользователя и проверять при каждом изменяющем запросе.

## Рекомендации по исправлению

Следует убрать статический токен из кода и использовать встроенную защиту фреймворка, например Spring Security CSRF protection. Если защита реализуется самостоятельно, нужно обеспечить генерацию, хранение, проверку и истечение срока действия токена.

# Секрет 5. Пароль в модуле восстановления доступа

| Поле | Данные |
|---|---|
| Коммит | `1a83e2825e2b1e040e2a2042677f03727f654150` |
| Дата и сообщение | `2019-11-03`, `Code style (#696)` |
| Файл | `webgoat-lessons/password-reset/src/main/java/org/owasp/webgoat/password_reset/ResetLinkAssignment.java` |
| Примерное место | около строки 47 |
| Найденное значение | `static final String PASSWORD_TOM_9 = "somethingVeryRandomWhichNoOneWillEverTypeInAsPasswordForTom";` |

## Почему это является секретом

В модуле сброса пароля обнаружено значение, которое выглядит как пароль пользователя Tom. Это особенно опасно, потому что механизм восстановления доступа должен работать с одноразовыми токенами, а не хранить или сравнивать реальные пароли в исходном коде.

Дополнительно в том же контексте раскрывается адрес `tom@webgoat-cloud.org`. Связка email + пароль повышает риск компрометации учётной записи, если подобный код окажется в реальном проекте.

## Как правильно хранить

Система сброса пароля не должна знать текущий пароль пользователя. Вместо этого нужно формировать одноразовый reset-токен, хранить в базе только его хеш, задавать срок жизни и запрещать повторное использование после успешного сброса.

## Рекомендации по исправлению

Нужно удалить пароль из класса, реализовать безопасный процесс сброса пароля, хранить пароли только в виде стойких хешей (`bcrypt`, `Argon2`, `PBKDF2`) и выполнить ротацию всех учётных данных, которые ранее были опубликованы в истории Git.

## 3. BFG Repo-Cleaner

BFG Repo-Cleaner — это инструмент для быстрой очистки истории Git-репозитория от случайно попавших туда файлов и секретов. Он применяется, когда секрет уже был закоммичен и простого удаления из текущей версии недостаточно.

Типичный сценарий использования:

1. заменить или отозвать скомпрометированный секрет;
2. удалить его из истории Git с помощью BFG Repo-Cleaner или `git filter-repo`;
3. выполнить принудительную публикацию очищенной истории;
4. предупредить участников проекта, чтобы они заново синхронизировали локальные копии репозитория.

При этом важно понимать: очистка истории не отменяет факт утечки. Если секрет уже был доступен другим людям, его всё равно нужно считать скомпрометированным и обязательно ротировать.

---

## 4. Автоматизация поиска секретов в CI/CD

Поиск секретов можно и нужно автоматизировать. На практике проверку стоит встроить в несколько мест:

- pre-commit hook на рабочей станции разработчика;
- обязательная проверка в merge request / pull request;
- отдельный этап CI/CD pipeline перед сборкой и деплоем;
- регулярное сканирование истории репозитория.

Для этого подходят truffleHog, Gitleaks, detect-secrets и встроенные механизмы GitHub/GitLab. Такой подход правильный, потому что позволяет находить проблему до попадания кода в основную ветку. Однако автоматическая проверка не заменяет правила хранения секретов: разработчики всё равно должны использовать vault, переменные окружения и токены с минимальными правами.

## 5. Итоговый вывод

В ходе анализа были выделены пять разных типов чувствительных данных: обычные пароли, JWT-токен, CI/CD-секреты, Anti-CSRF токен и пароль в механизме восстановления доступа. Все найденные примеры демонстрируют одну общую проблему: секреты не должны находиться в исходном коде, конфигурационных файлах репозитория или учебной документации без явной пометки, что это безопасный пример.

Корректная стратегия защиты включает три обязательных шага: не хранить секреты в Git, автоматически проверять репозитории на утечки и немедленно ротировать значения, которые уже были опубликованы.
