### вывод по части 1

во всех трех случаях проблема не просто в ошибке в коде а в неверной логике защиты api

- в n8n не проверялось принадлежит ли объект текущему пользователю
- в better auth сервер доверял userid из тела запроса без проверки сессии
- в jmix не было никаких лимитов на размер загружаемого файла

## часть 2

выбрал вариант с самостоятельным поиском недостатка в уязвимом приложении

после запуска контейнера открыл приложение по адресу `http://localhost:8080/` потом перешел по `http://localhost:8080/createdb` чтобы наполнить базу тестовыми данными

дальше стал проверять какие данные можно получить через api без авторизации

запрос к `http://localhost:8080/users/v1` вернул список пользователей

```json
{"users":[{"email":"mail1@mail.com","username":"name1"},{"email":"mail2@mail.com","username":"name2"},{"email":"admin@mail.com","username":"admin"}]}
```

потом попробовал открыть данные конкретного пользователя по имени в url запрос к `http://localhost:8080/users/v1/name1` вернул

```json
{"username":"name1","email":"mail1@mail.com"}
```

аналогично получилось и по другим пользователям вывод - приложение отдает данные просто по username в url без какой-либо проверки

потом проверил другие данные запрос к `http://localhost:8080/books/v1` вернул

```json
{"Books":[{"book_title":"bookTitle82","user":"name1"},{"book_title":"bookTitle98","user":"name2"},{"book_title":"bookTitle68","user":"admin"}]}
```

это подтвердило что api отдает связанные данные тоже без проверки прав

дальше решил проверить можно ли еще и изменять данные отправил запрос на смену email

```bash
curl -X PUT "http://localhost:8080/users/v1/name1/email" -H "Content-Type: application/json" -d '{"email":"hacker@mail.com"}'
```

сервер ответил

```json
{"status":"fail","message":"Invalid token"}
```

email не изменился значит запись защищена токеном а вот чтение нет

### найденная уязвимость

в приложении есть bola - broken object level authorization

сервер отдает объект только по идентификатору из url и не проверяет имеет ли запрашивающий право его видеть в данном случае идентификатором выступает username можно перебирать имена и получать чужие данные без авторизации

### тип недостатка

owasp api top 10 - broken object level authorization

приложение не выполняет проверку доступа на уровне конкретного объекта и просто отдает данные по параметру из url

### меры предотвращения

1. проверять права доступа к каждому объекту при каждом запросе
2. требовать аутентификацию перед просмотром данных
3. не отдавать данные только по username в url
4. убрать или ограничить выдачу списка всех пользователей
5. возвращать только минимально необходимые данные

## вывод

через api удалось читать данные любых пользователей без авторизации просто подставляя имена в url изменение данных при этом защищено токеном но чтение нет это классический пример bola когда нет проверки доступа на уровне объектов
