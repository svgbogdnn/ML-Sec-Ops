## ход выполнения

в этой работе нужно было развернуть инструмент sast для мобильных приложений, просканировать apk и составить план по митигации найденных рисков.

для анализа я использовал mobsf. контейнер был запущен через docker на отдельном порту, потому что порт `8000` уже был занят другим сервисом:

```bash
docker run -d --name mobsf-hw7-alan -p 8010:8000 opensecurity/mobile-security-framework-mobsf:latest
```

после запуска интерфейс был доступен по адресу `http://localhost:8010`. api key взял из логов контейнера.

для скана я взял официальный apk клиента F-Droid:

```bash
curl -s -L https://f-droid.org/F-Droid.apk -o F-Droid.apk
```

дальше загрузил apk в mobsf и запустил статический анализ через api:

```bash
curl -F "file=@F-Droid.apk" http://localhost:8010/api/v1/upload -H "Authorization: $API_KEY"
curl -X POST -d "hash=$HASH&scan_type=apk&file_name=F-Droid.apk" http://localhost:8010/api/v1/scan -H "Authorization: $API_KEY"
```

после завершения скана выгрузил pdf отчет через `/api/v1/download_pdf`. файл с отчетом mobsf лежит рядом с работой и называется `mobsf_report.pdf`.

## основные результаты анализа

### dangerous permissions

mobsf нашел 10 разрешений, которые попали в критичные или dangerous. для F-Droid часть из них объяснима, потому что приложение ставит apk, работает с репозиториями, камерой для qr-кодов и локальным обменом. но все равно каждое такое разрешение надо проверять.

самые важные разрешения:

- `BLUETOOTH_CONNECT` и `BLUETOOTH_SCAN` - нужны для поиска и подключения nearby устройств, но дают доступ к bluetooth окружению;
- `READ_EXTERNAL_STORAGE` и `WRITE_EXTERNAL_STORAGE` - чтение и запись во внешнее хранилище;
- `MANAGE_EXTERNAL_STORAGE` - широкий доступ к файлам во внешнем хранилище;
- `WRITE_SETTINGS` - изменение системных настроек;
- `REQUEST_INSTALL_PACKAGES` - возможность запрашивать установку apk;
- `POST_NOTIFICATIONS` - показ уведомлений;
- `CAMERA` - доступ к камере, скорее всего для сканирования qr-кодов;
- `ACCESS_COARSE_LOCATION` - примерное местоположение, часто связано с bluetooth или wi-fi сканированием.

главный риск тут не в самом факте наличия разрешений, а в том, что F-Droid является менеджером приложений. если злоумышленник сможет использовать эти возможности через баг в приложении, последствия будут заметнее, чем у обычного клиента.

### network security

в network security mobsf показал 2 high, 1 warning и 7 secure.

high находки:

```text
Base config is insecurely configured to permit clear text traffic to all domains.
Base config is configured to trust user installed certificates.
```

первая проблема означает, что базовая конфигурация сети разрешает cleartext traffic. если какой-то запрос уйдет по http, его можно перехватить или изменить в сети.

вторая проблема в том, что приложение доверяет пользовательским сертификатам. это удобно для некоторых сценариев отладки или корпоративных прокси, но для приложения, которое скачивает apk и индексы репозиториев, это повышает риск mitm.

warning:

```text
Base config is configured to trust system certificates.
```

само по себе доверие системным сертификатам нормально, но для загрузки приложений и метаданных репозиториев лучше дополнительно использовать pinning или проверку подписи данных.

положительный момент: для отдельных доменов, например `f-droid.org`, `github.com`, `gitlab.com` и связанных доменов, cleartext traffic запрещен.

### manifest analysis

в manifest analysis найдено 1 high и 9 warning.

high:

```text
App can be installed on a vulnerable unpatched Android version 6.0-6.0.1, [minSdk=23]
```

приложение поддерживает android 6.0. это уже старая версия платформы, которая не получает нормальные обновления безопасности. для приложения, которое устанавливает другие apk, поддержка старых устройств увеличивает риск.

warning находки:

- `android:allowBackup=true` - данные приложения можно попытаться забрать через adb backup при включенной отладке;
- несколько activity экспортированы через `android:exported=true`;
- `PanicPreferencesActivity`, `PanicResponderActivity`, `AddRepoActivity`, `AppDetailsActivity`, `MainActivity` доступны другим приложениям;
- `SystemJobService` и несколько receiver экспортированы и защищены разрешениями, уровень защиты которых нужно дополнительно проверять.

часть exported activity ожидаема, например deep links для открытия страниц приложений или добавления репозитория. но такие точки входа должны очень строго проверять входящие данные.

### certificate analysis

high проблем в certificate analysis нет, но есть 2 warning.

```text
Application vulnerable to Janus Vulnerability
Certificate algorithm might be vulnerable to hash collision
```

первое связано с тем, что приложение подписано с поддержкой v1 signature scheme. в отчете видно, что v2 и v3 тоже включены, поэтому риск ниже, чем при одной только v1 подписи, но старую схему лучше оставлять только если нужна поддержка старых android.

второе предупреждение связано с SHA1withRSA. mobsf пишет, что sha1 имеет проблемы с коллизиями, хотя манифест указывает SHA256withRSA. это надо перепроверить в процессе подписи релизов.

### code analysis

в code analysis нет high находок. mobsf показал 7 warning, 2 info и 1 secure.

warning находки:

- приложение создает временные файлы;
- в файлах могут быть hardcoded sensitive data;
- приложение читает и пишет во внешнее хранилище;
- используется небезопасный генератор случайных чисел;
- используется md5;
- используется sha1;
- есть раскрытие ip адресов.

info находки:

- приложение пишет данные в логи;
- приложение копирует данные в clipboard.

secure находка:

```text
This App uses SSL certificate pinning to detect or prevent MITM attacks.
```

это хороший момент, потому что для менеджера приложений защита от mitm особенно важна. но pinning не отменяет проблему общей сетевой конфигурации, где cleartext разрешен на базовом уровне.

### shared library binary analysis

в нативных библиотеках анализировался `libandroidx.graphics.path.so` для разных архитектур.

критичных high проблем не видно: nx, pie, relro и stack canary включены. символы stripped.

основной warning:

```text
The binary does not have any fortified functions.
```

это означает, что для части native сборок не включены fortified functions. они дают дополнительные проверки против некоторых ошибок работы с памятью.

## план по митигации рисков

### 1. dangerous permissions

нужно проверить каждое dangerous permission и оставить только те, которые реально нужны.

`REQUEST_INSTALL_PACKAGES` для F-Droid ожидаемо, но его использование должно быть ограничено только сценариями установки проверенных apk. `MANAGE_EXTERNAL_STORAGE` и `WRITE_SETTINGS` стоит пересмотреть отдельно, потому что это слишком широкие разрешения.

камера должна запрашиваться только перед сканированием qr-кода. bluetooth и location должны запрашиваться только перед nearby-функциями, а не заранее.

### 2. cleartext traffic

нужно запретить cleartext traffic в base config. базовая конфигурация должна быть безопасной по умолчанию.

если http нужен для локального обмена или пользовательских репозиториев, лучше разрешать его точечно и явно показывать предупреждение пользователю. для основных доменов F-Droid должен использовать только https.

### 3. user installed certificates

для загрузки apk и индексов репозиториев лучше не доверять пользовательским ca без дополнительной проверки. если такая поддержка нужна, ее можно оставить только для debug-сборок или сделать отдельной настройкой с явным предупреждением.

важные данные репозитория нужно проверять криптографически, например через подписи индексов и apk, чтобы даже при mitm нельзя было незаметно подменить пакет.

### 4. min sdk

`minSdk=23` означает поддержку android 6.0. лучше поднять минимальную версию хотя бы до android 8 или android 10, если это допустимо для аудитории приложения.

если старые версии нельзя отключить сразу, для них стоит ограничивать самые рискованные функции и явно учитывать старые баги платформы.

### 5. exported components

для всех exported activity, service и receiver нужно проверить, действительно ли им нужен внешний доступ.

если компонент не должен открываться извне, надо поставить:

```xml
android:exported="false"
```

если внешний доступ нужен, например для deep links, нужно валидировать uri, package name, intent extras и не выполнять опасные действия только на основе внешнего intent.

### 6. allowBackup

для релизной сборки лучше отключить backup:

```xml
android:allowBackup="false"
```

если backup нужен, надо настроить backup rules и исключить базу, токены, настройки репозиториев и другие чувствительные данные.

### 7. подпись приложения

нужно проверить процесс подписи релизов. v2 и v3 должны быть включены обязательно. v1 стоит оставлять только если это нужно для поддержки старых устройств.

sha1 в подписи лучше не использовать. для новых релизов надо применять sha256 или более сильный алгоритм.

### 8. внешнее хранилище

чувствительные данные нельзя хранить во внешнем хранилище. apk, индексы и кеши надо разделять по важности.

служебные данные приложения должны лежать в приватной директории. если файлы нужно отдавать наружу, лучше использовать content provider с ограничением доступа.

### 9. временные файлы

временные файлы нужно создавать через приватный cache directory приложения и удалять сразу после использования.

если во временный файл попадает apk или индекс репозитория, после скачивания надо проверять подпись и хеш, а потом очищать ненужные временные данные.

### 10. hardcoded sensitive data

нужно вручную проверить строки, которые mobsf пометил как возможные hardcoded credentials. часть таких находок может быть ложной, например названия http headers или тестовые строки.

если там окажутся реальные токены, ключи или пароли, их нужно убрать из apk. секреты не должны попадать в мобильное приложение, потому что apk можно разобрать.

### 11. md5 и sha1

md5 и sha1 надо заменить на sha256 или sha512 там, где хеш связан с безопасностью.

если md5 или sha1 используются только как техническая контрольная сумма для кеша, это можно оставить после ревью, но в коде должно быть понятно, что это не криптографическая защита.

### 12. insecure random

в местах, где случайные значения используются для токенов, ключей, имен временных файлов или идентификаторов, нужно использовать `SecureRandom`.

обычный `Random` можно оставлять только для незащищенных сценариев, где предсказуемость не влияет на безопасность.

### 13. логи и clipboard

логи нужно почистить от чувствительных данных: url приватных репозиториев, локальных путей, токенов, ошибок подписи и данных пользователя.

clipboard лучше не использовать для чувствительной информации. если копирование нужно, стоит предупреждать пользователя и очищать clipboard после короткого времени.

### 14. native libraries

для `libandroidx.graphics.path.so` стоит включить fortified functions:

```bash
-D_FORTIFY_SOURCE=2
```

остальные защитные признаки уже выглядят нормально: nx, pie, relro, stack canary и stripped symbols включены.

## вывод

я просканировал F-Droid версии 1.23.2. mobsf поставил приложению score 62/100 и grade A. критичных находок немного, но есть важные риски: cleartext traffic в base config, доверие пользовательским сертификатам, поддержка старого android 6.0, exported components, dangerous permissions и использование слабых md5/sha1 в коде.

главный план митигации: запретить cleartext по умолчанию, аккуратно ограничить доверие пользовательским ca, поднять min sdk, проверить exported components, убрать лишние dangerous permissions и заменить слабые криптографические места. mobsf удобно использовать как автоматический шаг в ci/cd перед публикацией новой apk сборки.
