# Лабораторная работа №2. OWASP API Top 10

## Часть 1. CVE, связанные с REST API

CVE за последний год, попадающие под категории OWASP API Security Top 10.

| CVE | Источник | Тип (OWASP API Top 10) | Недостаток | Причина | Последствия |
|---|---|---|---|---|---|
| **CVE-2025-14777 (Keycloak)** | https://nvd.nist.gov/vuln/detail/CVE-2025-14777 | API1:2023 Broken Object Level Authorization | Пользователь с правами на один ресурс может обратиться к ресурсу другого клиента, подставив чужой `resourceId` | Права проверяются по `resourceServer`, а запрос к БД идёт только по `resourceId` — несоответствие между уровнем проверки и уровнем действия | Чтение, изменение и удаление чужих объектов; нарушение изоляции клиентов |
| **CVE-2025-20348 (Cisco Nexus Dashboard)** | https://nvd.nist.gov/vuln/detail/CVE-2025-20348 | API5:2023 Broken Function Level Authorization | Низкопривилегированный пользователь через REST API может вызывать административные функции | На части эндпойнтов отсутствовала проверка роли пользователя перед выполнением операции | Эскалация привилегий, загрузка и изменение системных файлов, утечка служебной информации |
| **CVE-2025-56520 (Dify)** | https://nvd.nist.gov/vuln/detail/CVE-2025-56520 | API7:2023 Server Side Request Forgery | Сервер выполняет HTTP-запросы по произвольному URL из пользовательского ввода | Переменная `BLACKLIST_IPS` не задана в конфигурации по умолчанию, поэтому блокировка внутренних адресов фактически не работала | Обращение к внутренним сервисам, обход сетевых ограничений, утечка данных из закрытого контура |

### Вывод по части 1

Все три уязвимости объединяет одна общая черта: приложение либо вообще не проверяет права доступа, либо проверяет их не на том уровне. В Keycloak - права проверяются по одному идентификатору, а действие выполняется по другому. В Cisco - роль пользователя не верифицируется перед вызовом привилегированных функций. В Dify - сервер доверяет внешнему вводу при формировании исходящих запросов.

Разработчики добавляют проверку аутентификации, но забывают про авторизацию на уровне конкретного объекта или функции.

## Часть 2. Практическое исследование уязвимого приложения

Запустил контейнер через `docker-compose up -d`, перешёл на `http://localhost:8080`, выполнил инициализацию базы по ссылке `/createdb`.

---

### Шаг 1. Разведка без авторизации

Первым делом проверяю, что отдаёт API без каких-либо токенов.

**GET** `http://localhost:8080/users/v1`

```json
{"users":[
  {"email":"mail1@mail.com","username":"name1"},
  {"email":"mail2@mail.com","username":"name2"},
  {"email":"admin@mail.com","username":"admin"}
]}
```

Список всех пользователей с email доступен без аутентификации.

**GET** `http://localhost:8080/users/v1/name1`

```json
{"username":"name1","email":"mail1@mail.com"}
```

Данные конкретного пользователя тоже отдаются без токена — достаточно знать `username`.

**GET** `http://localhost:8080/books/v1`

```json
{"Books":[
  {"book_title":"bookTitle82","user":"name1"},
  {"book_title":"bookTitle98","user":"name2"},
  {"book_title":"bookTitle68","user":"admin"}
]}
```

API отдаёт связанные данные всех пользователей без проверки прав.

---

### Уязвимость 1 — Broken Object Property Level Authorization + Broken Function Level Authorization

**Тип:** API3:2023 + API5:2023  
**Суть:** приложение раскрывает персональные данные пользователей (email, имена) через публичные эндпойнты без аутентификации.  
**Меры:**
- Закрыть `/users/v1` — доступ только для администратора
- Требовать авторизацию для `/users/v1/{username}`
- Возвращать только необходимый минимум данных (не раскрывать email в публичном списке)

---

### Шаг 2. Поиск скрытых эндпойнтов

Попробовал несколько нестандартных путей:

**GET** `http://localhost:8080/users/v1/_debug`

```json
{"users":[
  {"admin":false,"email":"mail1@mail.com","password":"pass1","username":"name1"},
  {"admin":false,"email":"mail2@mail.com","password":"pass2","username":"name2"},
  {"admin":true,"email":"admin@mail.com","password":"pass1","username":"admin"}
]}
```

Открытый debug-эндпойнт без авторизации возвращает пароли всех пользователей в открытом виде. Включая администратора.

---

### Уязвимость 2 — Security Misconfiguration

**Тип:** API8:2023  
**Суть:** debug-эндпойнт `/users/v1/_debug` оставлен активным в production-окружении и доступен без авторизации. Возвращает пароли в открытом (нехешированном) виде.  
**Меры:**
- Отключить debug-эндпойнты в production полностью
- Если debug нужен в dev — закрыть его авторизацией
- Никогда не хранить и не возвращать пароли в открытом виде — только хеши

---

### Шаг 3. Проверка защиты от брутфорса

Попробовал логин с неправильными данными несколько раз подряд:

```
GET http://localhost:8080/users/v1/login?username=name1&password=wrongpass
→ {"status":"fail","message":"User not found"}

(повторил 15 раз — никаких ограничений)
```

Никакого rate limiting, капчи, блокировки по IP или временной задержки не обнаружено.

---

### Уязвимость 3 — Broken Authentication

**Тип:** API2:2023  
**Суть:** приложение хранит пароли в открытом виде (видно из `/users/v1/_debug`) и не ограничивает количество попыток входа. Это делает брутфорс тривиальным.  
**Меры:**
- Хешировать пароли (bcrypt / argon2)
- Ввести rate limiting на эндпойнт логина
- Реализовать временную блокировку после N неудачных попыток

---

### Шаг 4. Проверка возможности изменения чужих данных

Попробовал изменить email пользователя без авторизации:

```bash
curl -X PUT "http://localhost:8080/users/v1/name1/email" \
  -H "Content-Type: application/json" \
  -d '{"email":"hacker@mail.com"}'
→ {"status":"fail","message":"Invalid token"}
```

Повторная проверка:

```
GET http://localhost:8080/users/v1/name1
→ {"username":"name1","email":"mail1@mail.com"}
```

Email не изменился — операции записи требуют токен. Тем не менее операции чтения остаются полностью открытыми.

### Итоговая таблица найденных уязвимостей

| # | Эндпойнт | Тип уязвимости | Критичность |
|---|---|---|---|
| 1 | `/users/v1`, `/users/v1/{username}` | API3 + API5: данные пользователей без авторизации | Высокая |
| 2 | `/users/v1/_debug` | API8: открытый debug с паролями в открытом виде | Критическая |
| 3 | `/users/v1/login` | API2: нет защиты от брутфорса + пароли не хешированы | Высокая |

### Общий вывод

Приложение демонстрирует классический набор ошибок при проектировании API: аутентификация добавлена только на операции записи, а чтение данных (в том числе критических — пароли через debug) доступно без каких-либо проверок. Уязвимость BOLA здесь особенно показательна — сервер не различает «я хочу посмотреть свои данные» и «я хочу посмотреть данные любого другого пользователя».
