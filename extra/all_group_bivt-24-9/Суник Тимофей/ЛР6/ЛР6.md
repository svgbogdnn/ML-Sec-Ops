# Отчёт по лабораторной работе
## Изучение CI/CD с точки зрения инструментов ИБ
### Инструмент: truffleHog | Репозиторий: `OtusTeam/DevSecOps_secret-finding`

---

## Методология

Для сканирования использовался инструмент **truffleHog** — анализатор git-репозиториев, который ищет секреты (пароли, ключи, токены) двумя методами:
- поиск по регулярным выражениям;
- вычисление энтропии Шэннона для строк длиннее 20 символов (алфавиты base64 и hex).

**Команда запуска:**
```bash
trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git | tee -a log.txt
```

Инструмент прошёл по всей истории коммитов каждой ветки и проверил каждый diff на наличие чувствительных данных.

## Аналитика найденных секретов

### Секрет №1 — Hardcoded GITHUB_TOKEN

| Параметр | Значение |
|----------|----------|
| **Расположение** | `.github/workflows/release.yml` |
| **Фрагмент** | `env: GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5` |
| **Тип** | Персональный токен доступа GitHub (64 символа hex, высокая энтропия) |

**Почему это секрет:**
Токен предоставляет API-доступ к GitHub от имени владельца: возможность делать push, создавать релизы, управлять репозиториями. Злоумышленник, получивший токен, получает полный контроль над CI/CD-пайплайном и репозиторием.

**Рекомендации по устранению:**
- Использовать встроенный секрет `${{ secrets.GITHUB_TOKEN }}` в GitHub Actions.
- Хранить токены в менеджерах секретов: **GitHub Secrets**, **HashiCorp Vault**, **AWS Secrets Manager**.
- Никогда не хардкодить токены в файлах конфигурации или коде.
- Немедленно отозвать скомпрометированный токен через настройки GitHub.

### Секрет №2 — Приватный RSA-ключ

| Параметр | Значение |
|----------|----------|
| **Расположение** | `webgoat-server/privatekey.key` |
| **Фрагмент** | Блок от `-----BEGIN PRIVATE KEY-----` до `-----END PRIVATE KEY-----` |
| **Тип** | Приватный ключ RSA (2048 бит) |

**Почему это секрет:**
Обладатель приватного ключа может расшифровывать трафик, подписывать данные от имени сервера или выдавать себя за легитимный сервис. Ключ, попавший в репозиторий (даже удалённый из последующих коммитов), считается **полностью скомпрометированным** — его необходимо отозвать и перевыпустить.

**Рекомендации по устранению:**
- Добавить `*.key`, `*.pem` в файл `.gitignore`.
- Хранить приватные ключи в **HSM** (Hardware Security Module) или в зашифрованных хранилищах (Ansible Vault, Vault by HashiCorp).
- В CI/CD передавать ключи через переменные окружения или секреты пайплайна.
- Для разработки и тестов генерировать отдельные «throwaway»-ключи, которые не используются в production.

### Секрет №3 — Хеш пароля в тестовом коде

| Параметр | Значение |
|----------|----------|
| **Расположение** | `webgoat-lessons/missing-function-ac/src/test/java/org/owasp/webgoat/missing_ac/DisplayUserTest.java` |
| **Фрагмент** | `assert(displayUser.getUserHash().equals("cplTjehjI/e5ajqTxWaXhU5NW9UotJfXj+gcbPvfWWc="))` |
| **Тип** | Base64-хеш пароля (предположительно SHA-256 от `"password1"`) |

**Почему это секрет:**
Хеш пароля позволяет злоумышленнику восстановить исходный пароль с помощью радужных таблиц или брутфорса, особенно если хеш не содержит соль. Хранение хешей реальных паролей в тестовом коде — нарушение принципа минимальной экспозиции данных.

**Рекомендации по устранению:**
- В тестах использовать заведомо фиктивные данные: `"dummy_hash"`, `"test_user"`.
- В реальных приложениях хранить пароли с использованием адаптивных алгоритмов хеширования: **bcrypt**, **Argon2**, **scrypt**.
- Хеши передавать через переменные окружения или тестовые фикстуры, не зашивать в исходный код.

### Секрет №4 — Java-сериализованный эксплойт (Insecure Deserialization)

| Параметр | Значение |
|----------|----------|
| **Расположение** | `webgoat-lessons/insecure-deserialization/src/test/java/org/owasp/webgoat/deserialization/DeserializeTest.java` |
| **Фрагмент** | `String token = "rO0ABXNyADFvcmcuZHVtbXku..."` (base64 сериализованного объекта `VulnerableTaskHolder`) |
| **Тип** | Готовый эксплойт — сериализованный объект, выполняющий `echo hello` при десериализации |

**Почему это секрет:**
Строка является рабочим **gadget-цепочкой** для атаки на небезопасную десериализацию (OWASP A8). Даже находясь в тестовом коде, она демонстрирует уязвимость и предоставляет злоумышленнику шаблон для атаки на production-систему.

**Рекомендации по устранению:**
- Не хранить эксплойты в репозитории — генерировать их динамически в изолированной тестовой среде.
- В приложении полностью исключить десериализацию объектов из ненадёжных источников.
- Перейти на безопасные форматы обмена данными: **JSON**, **Protobuf**, **MessagePack**.
- Если десериализация необходима — использовать белые списки разрешённых классов (`ObjectInputFilter` в Java 9+).

### Секрет №5 — Закодированный URL для эксфильтрации данных

| Параметр | Значение |
|----------|----------|
| **Расположение** | `webgoat/main/project/JavaSource/org/owasp/webgoat/lessons/BlindScript.java` |
| **Фрагмент** | `private final static String WEBGOAT_URL = "aHR0cDovL2xvY2FsaG9zdC9XZWJHb2F0L2NhdGNoZXI/UFJPUEVSVFk9eWVz"` |
| **Тип** | Base64-закодированный URL: `http://localhost/WebGoat/catcher?PROPERTY=yes` |

**Почему это секрет:**
URL является частью вредоносной функциональности (spyware) — используется для отправки украденных данных (кеш браузера) на удалённый сервер. Попытка скрыть адрес через base64 — это **обфускация, а не защита**: truffleHog обнаруживает такие строки по высокой энтропии. Жёстко закодированный адрес позволяет злоумышленнику управлять направлением утечки данных.

**Рекомендации по устранению:**
- Подобные адреса не должны присутствовать в коде.
- Для легитимных внешних вызовов — использовать переменные окружения или конфигурационные файлы вне репозитория.
- Применять белые списки доменов и валидацию URL на уровне приложения.
- Внедрить Content Security Policy (CSP) для ограничения внешних запросов.

## Дополнительные вопросы

### Что такое BFG Repo-Cleaner?

**BFG Repo-Cleaner** — утилита для удаления чувствительных данных из **всей истории** git-репозитория. Работает быстрее и проще, чем стандартный `git filter-branch`.

**Возможности:**
- Удалить файлы по имени или шаблону (`*.key`, `*.pem`).
- Заменить текст (пароль, токен) во всех коммитах на `***REMOVED***`.
- Удалить большие бинарные файлы, случайно попавшие в историю.

**Зачем нужен:** если секрет попал в репозиторий (даже если уже удалён в более новом коммите), он остаётся виден через историю — именно это эксплуатирует truffleHog. BFG позволяет **полностью зачистить историю**, чтобы злоумышленник не мог найти секрет даже при переборе коммитов.

```bash
# Пример: заменить все вхождения пароля в истории
bfg --replace-text passwords.txt my-repo.git
git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

### Автоматизация поиска секретов в CI/CD

Автоматизация является **обязательной практикой** в DevSecOps. Ручное сканирование не масштабируется при большом количестве разработчиков и коммитов.

**Уровни автоматизации (от раннего к позднему):**

| Уровень | Инструмент | Когда срабатывает |
|---------|-----------|-------------------|
| **Pre-commit хук** | `git-secrets`, `gitleaks` | До коммита, на машине разработчика |
| **Pull Request проверка** | `truffleHog`, `gitleaks` в CI | При открытии PR |
| **CI/CD пайплайн** | GitHub Actions, GitLab CI | При каждом push в ветку |
| **Периодическое сканирование** | `truffleHog` по расписанию | Cron-задача, полная проверка истории |

**Пример шага в GitHub Actions:**
```yaml
- name: Secret Scanning
  uses: trufflesecurity/trufflehog@main
  with:
    path: ./
    base: ${{ github.event.repository.default_branch }}
    head: HEAD
```

**Вывод:** автоматизация — правильный подход, но не серебряная пуля. Она должна сочетаться с:
- обучением разработчиков правилам хранения секретов;
- правильно настроенными менеджерами секретов;
- настройкой правил исключений для снижения числа ложных срабатываний.
