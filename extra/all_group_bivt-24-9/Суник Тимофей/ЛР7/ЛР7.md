## 3. Конфигурация пайплайна `.gitlab-ci.yml`

```yaml
include:
  - template: Security/Container-Scanning.gitlab-ci.yml
  - template: Security/Dependency-Scanning.gitlab-ci.yml
  - template: Security/Secret-Detection.gitlab-ci.yml
  - template: Security/SAST.gitlab-ci.yml

stages:
  - build
  - test
  - security

build:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY
  script:
    - docker build --pull -t "$CI_REGISTRY_IMAGE" ./app
    - docker push "$CI_REGISTRY_IMAGE"
  only:
    - master

variables:
  DOCKER_IMAGE: "$CI_REGISTRY_IMAGE"
  SECURE_LOG_LEVEL: 'debug'
  CS_IMAGE: "$CI_REGISTRY_IMAGE"
```

> **Примечание:** шаблон `Security/License-Scanning.gitlab-ci.yml` был удалён в GitLab 15.9+. Начиная с этой версии информация о лицензиях зависимостей включена в результаты Dependency Scanning автоматически.

## 5. Аналитика найденных уязвимостей

### 5.1 SAST (Semgrep) — уязвимости в исходном коде

Инструмент: **Semgrep**, файл: `app/server.js`

#### Уязвимость: SQL Injection (Critical) × 3

| # | Расположение | Severity | Идентификатор |
|---|-------------|----------|---------------|
| 1 | `app/server.js:24` | Critical | A1:2017 - Injection |
| 2 | `app/server.js:43` | Critical | A1:2017 - Injection |
| 3 | `app/server.js:81` | Critical | A1:2017 - Injection |

**Описание:** Пользовательский ввод напрямую конкатенируется в SQL-запрос без параметризации. Это позволяет злоумышленнику изменять структуру запроса, получать доступ к данным БД, удалять или модифицировать данные.

**Пример уязвимого кода:**
```javascript
// Уязвимо — строки 24, 43, 81
const query = "SELECT * FROM users WHERE id = " + req.params.id;
db.query(query, ...);
```

**Рекомендации по устранению:**
- Использовать **параметризованные запросы** (Prepared Statements)
- Применять ORM-библиотеки (Sequelize, Knex.js)
- Валидировать и санитизировать пользовательский ввод

```javascript
// Безопасный вариант
const query = "SELECT * FROM users WHERE id = ?";
db.query(query, [req.params.id], ...);
```

### 5.2 Dependency Scanning (Gemnasium) — уязвимые зависимости

Инструмент: **Gemnasium**, файл: `app/package-lock.json`

#### Critical уязвимости

| CVE | Описание | CVSS | EPSS |
|-----|----------|------|------|
| CVE-2023-26136 | Prototype Pollution (Improperly Controlled Modification of Object Prototype) | 9.8 | 6% |
| CVE-2021-44906 | Prototype Pollution in `minimist` | 9.8 | 1% |
| CVE-2023-45311 | OS Command Injection | 9.8 | 1% |
| CVE-2021-3918 | Prototype Pollution in `json-schema` | 9.8 | 1% |
| Gemnasium-05cfa2e8 | Uncontrolled Search Path Element | 9.8 | — |

#### High уязвимости (выборка)

| CVE | Описание | CVSS | EPSS |
|-----|----------|------|------|
| CVE-2022-46175 | Prototype Pollution | 8.8 | 44% |
| CVE-2021-37712 | Path Traversal в `node-tar` | 8.6 | 0% |
| CVE-2021-32804 | Path Traversal в `node-tar` | 8.1 | 85% |
| CVE-2021-32803 | Path Traversal в `node-tar` | 8.1 | 0% |
| CVE-2024-45296 | ReDoS в `path-to-regexp` | 7.5 | 0% |
| CVE-2021-3807 | ReDoS (Inefficient Regex) | 7.5 | 0% |
| CVE-2020-28469 | Uncontrolled Resource Consumption | 7.5 | 1% |
| CVE-2021-3777 | Incorrect Comparison | 7.5 | 0% |
| CVE-2022-21803 | Prototype Pollution | 7.5 | 0% |

**Общее описание проблем с зависимостями:**

- **Prototype Pollution** — злоумышленник может модифицировать прототип базовых JS-объектов (`Object.prototype`), что приводит к изменению поведения приложения, обходу проверок безопасности или RCE.
- **Path Traversal** — позволяет выйти за пределы разрешённой директории и получить доступ к произвольным файлам системы.
- **ReDoS** — специально сформированная строка вызывает катастрофический откат регулярного выражения, что приводит к отказу в обслуживании (DoS).
- **OS Command Injection** — пользовательский ввод попадает в системную команду без санитизации.

**Рекомендации по устранению:**
- Обновить все зависимости до последних патченных версий: `npm audit fix`
- Заменить неподдерживаемые пакеты на современные аналоги
- Регулярно запускать `npm audit` как часть CI/CD
- Использовать `.npmrc` с `audit=true` для автоматических проверок

### 5.4 Container Scanning

Статус: ⚠️ Failed (allowed to fail)

**Причина:** джоб `build` настроен только на ветку `master` (`only: master`), тогда как пайплайн запускался на ветке `main`. В результате Docker-образ не был собран и запушен в GitLab Registry, поэтому Container Scanning не смог найти образ для анализа.

**Решение:**
```yaml
build:
  only:
    - main   # изменить с master на main
```

## 7. Выводы

В ходе лабораторной работы был настроен **Secure Pipeline** в GitLab CI с четырьмя типами security-сканирования. По результатам работы пайплайна выявлено **86 уязвимостей**, из которых:

- **SAST** обнаружил 3 критических SQL-инъекции непосредственно в исходном коде `server.js` — это уязвимости первого уровня по OWASP Top 10 (A1: Injection), требующие немедленного исправления.
- **Dependency Scanning** выявил множество уязвимостей в устаревших зависимостях, включая Prototype Pollution с CVSS 9.8 и Path Traversal с EPSS до 85%.
- **Secret Detection** не выявил секретов в коде — что является положительным результатом.
- **Container Scanning** не отработал из-за отсутствия собранного образа, что требует корректировки конфигурации пайплайна.

Интеграция security-инструментов в CI/CD позволяет обнаруживать уязвимости на ранних этапах разработки, до попадания кода в production, что соответствует принципу **Shift Left Security** в DevSecOps.
