В современных условиях разработки REST API является основным каналом обмена данными. Это сместило фокус атак с классических инъекций на сложные логические уязвимости и ошибки контроля доступа. Настоящий отчет опирается на [стандарты OWASP](https://owasp.org/www-project-api-security/) и разделен на теоретический разбор актуальных CVE за 2025–2026 годы и практический аудит тестового стенда.


## Часть I. Анализ критических уязвимостей (CVE) в REST API (2025–2026)

Анализ реальных инцидентов показывает, что недостаточная аутентификация и провалы в авторизации объектов остаются главными рисками. Ниже представлен краткий разбор трех показательных уязвимостей.

| Идентификатор | Продукт | Оценка | Категория (CWE) | OWASP API Top 10 | Источник |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **CVE-2026-39351** | Frappe Framework | Medium | CWE-862 (Missing Auth) | API1:2023 (BOLA) | [NIST](https://nvd.nist.gov/vuln/detail/CVE-2026-39351) |
| **CVE-2025-20348** | Cisco Nexus Dashboard | Medium | CWE-201 (Info Exposure) | API5:2023 (BFLA) | [NIST](https://nvd.nist.gov/vuln/detail/CVE-2025-20348) |
| **CVE-2026-33580** | OpenClaw | - | CWE-307 (Rate Limit) | API4:2023 (Consumption) | [NIST](https://nvd.nist.gov/vuln/detail/CVE-2026-33580) |

*   **CVE-2026-39351 (Frappe):** Ошибка в механизме REST API (Link Expansion). Сервер не проверял права доступа при раскрытии ссылочных связей. Это позволяло неавторизованным пользователям получать доступ к защищенным моделям данных (Doctypes).
*   **CVE-2025-20348 (Cisco):** Уязвимость авторизации на уровне функций. API проверял наличие активной сессии, но не роль пользователя. В результате пользователи с низкими привилегиями могли вызывать админ-эндпоинты для выгрузки логов и образов.
*   **CVE-2026-33580 (OpenClaw):** Отсутствие лимитов на количество запросов (Rate Limiting) в эндпоинте веб-хуков Nextcloud. Позволяло злоумышленникам применять брутфорс для подбора общих секретов (shared secrets).


## Часть II. Практический аудит: Стенд `ket9/otus-devsecops-owasp-rest`

### 1. Ход рассуждений и неудачные попытки

Первоначальный тест базировался на классических векторах для веб-приложений, которые оказались неэффективны против REST-архитектуры:
*   **SQL-инъекции (SQLi):** Попытки отправить `' OR 1=1 --` возвращали статусы `400` или `404`. Встроенный ORM-фреймворк успешно блокировал нетипизированный ввод.
*   **XSS-атаки:** Внедрение `<script>` в параметры игнорировалось сервером. REST API отдает `application/json`, который браузер не исполняет как разметку, что делает XSS-векторы на бекенде бессмысленными.
*   **Командные инъекции (CMDi):** Слепой фаззинг (Blind Fuzzing) с операторами `| ls -la` не дал результатов.

### 3. Обнаружение маршрутов

Изучение HTML-кода заглушки на `localhost:8080/` раскрыло список доступных API-маршрутов:
*   `/users/v1`
*   `/users/v1/{username}`
*   `/users/v1/_debug`

### 3. Эксплуатация найденных уязвимостей (OWASP API)

**Уязвимость №1: Утечка отладочных данных (API8 + API3)**
*   **Вектор:** `GET http://localhost:8080/users/v1/_debug` (без токенов и аутентификации).
*   **Ответ:** Возвращен полный дамп БД. Объекты включали скрытые поля: `password` (в открытом виде) и логический флаг `isAdmin: true`.
*   **Классификация:** 
    *   [API8:2023 Security Misconfiguration](https://owasp.org/API-Security/): Оставленный в production отладочный эндпоинт.
    *   [API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/): Сервер слепо сериализует все свойства объекта базы данных, включая пароли, не проверяя права клиента на просмотр этих свойств.

**Уязвимость №2: Broken Object Level Authorization (API1)**
*   **Вектор:** `GET http://localhost:8080/users/v1/admin`
*   **Ответ:** Возврат приватных данных профиля пользователя "admin".
*   **Классификация:** [API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/). Приложение принимает ID ресурса (`username`), ищет его и возвращает, полностью игнорируя проверку принадлежности этого ресурса запрашивающему субъекту (которого здесь вообще нет, так как доступ анонимный). Это позволяет спарсить (enumerating) всю базу пользователей.

## Часть III. Меры предотвращения и DevSecOps

Для защиты REST API недостаточно установки WAF. Требуется следование принципам безопасного дизайна и интеграция практик согласно [OWASP DevSecOps Guideline](https://owasp.org/www-project-devsecops-guideline/).

**Защита архитектуры (BOLA и BOPLA):**
*   Обязательная аутентификация (JWT/OAuth2) для всех бизнес-маршрутов.
*   Сверка ID запрашиваемого объекта с ID владельца внутри сессионного токена в каждом контроллере.
*   Использование DTO (Data Transfer Objects) для контроля возвращаемых свойств, чтобы пароли и флаги администратора физически не могли попасть в JSON-ответ.

**Устранение ошибок конфигурации:**
*   Хранение паролей исключительно в виде криптографических хешей (argon2/bcrypt).
*   Жесткое разделение конфигураций сред (отключение `_debug` маршрутов в Production).

**Безопасный CI/CD:**
*   Интеграция SAST/DAST сканеров в сборочный конвейер для автоматического выявления забытых отладочных маршрутов и уязвимых зависимостей до релиза.

### Вывод

Практический аудит подтверждает, что логические уязвимости BOLA и BOPLA доминируют в REST API. Отсутствие контроля на уровне свойств объектов и оставленные разработчиками отладочные бэкдоры приводят к полному компрометированию баз данных без использования сложных инструментов взлома.
