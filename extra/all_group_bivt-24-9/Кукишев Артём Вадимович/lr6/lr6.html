Для проверки репозитория использовался инструмент truffleHog, запущенный в Docker-контейнере на базе python:buster.

docker run -it -p 8080:8080 python:buster /bin/bash
pip install truffleHog
trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git | tee -a log.txt

Для извлечения лога из контейнера использовался встроенный HTTP-сервер Python:

python -m http.server 8080

Большинство срабатываний оказались ложными — хэши зависимостей из pom.xml, минифицированный JS. Все реальные секреты сосредоточены в одном коммите 34f1faad на ветке develop. Именно поэтому сканирование только текущего HEAD без истории коммитов пропустило бы все находки.

Найденные секреты

1. GitHub Personal Access Token

Файл/строка: .github/workflows/release.yml, переменная GITHUB_TOKEN

- GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
+ GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5

Почему секрет: 64 hex-символа — формат GitHub PAT образца 2021 года. С таким токеном можно создавать релизы и пушить в репозиторий. Даже после замены на ${{ secrets.GITHUB_TOKEN }} токен остаётся в истории git.

Правильное хранение: Хранить в GitHub Actions Secrets и подставлять через ${{ secrets.NAME }}. Утёкший токен необходимо немедленно отозвать в настройках GitHub.

2. Приватный RSA-ключ (PKCS#8)

Файл/строка: webgoat-server/privatekey.key

-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSkAgEAAoIBAQCpuOH6AnMc/xdJ
...
-----END PRIVATE KEY-----

Почему секрет: Рядом в том же коммите лежит certificatesigningrequest.csr — значит, пара генерировалась для TLS-сертификата. Любой, кто склонировал репозиторий, может расшифровать перехваченный трафик или выдать себя за сервер.

Правильное хранение: Приватные ключи не должны попадать в git. Добавить *.key, *.pem в глобальный .gitignore, хранить в HashiCorp Vault, Kubernetes Secrets или AWS/GCP Secret Manager. При утечке — отозвать сертификат и перевыпустить.

3. Файл .env с паролями

Файл/строка: docker/.env

APP_SECRET=666666666666666
USER=alex675
PASSWORD=#!qerge34t423sdfvdsfgeR

Почему секрет: Два независимых секрета. APP_SECRET — ключ подписи сессий/JWT: зная его, можно сгенерировать валидную cookie от имени любого пользователя; значение из пятнадцати шестёрок не имеет криптографической стойкости. USER/PASSWORD — учётные данные приватного репозитория пакетов, используемые в Dockerfile при установке зависимостей.

Правильное хранение: APP_SECRET генерируется через openssl rand -hex 32 и передаётся через переменную окружения. Учётные данные переносятся в CI/CD Secrets. В репозитории остаётся только .env.example с именами переменных без значений, сам .env добавляется в .gitignore.

4. Строки подключения к PostgreSQL

Файл/строки: docker-compose-postgres.yml, строки 10 и 19

jdbc:postgresql://webgoat_db:5432/webgoat?user=webgoat&password=webgoat
postgresql://webgoat:webgoat@webgoat_db:5432

Почему секрет: truffleHog распознал их по детекторам JDBC и Postgres. Логин и пароль содержатся в открытом виде прямо в строке подключения. Значение webgoat в качестве пароля — типичный дефолтный credential, первым проверяемый при атаке.

Правильное хранение: Передавать через переменные окружения (POSTGRES_USER, POSTGRES_PASSWORD), реальные значения хранить в .env (не в git) или Secret Manager. Не использовать одинаковые значения для имени пользователя, пароля и имени базы данных.

5. JWT-токен в тестовом коде

Файл/строка: webgoat-lessons/jwt/src/test/java/org/owasp/webgoat/jwt/JWTFinalEndpointTest.java

private static final String TOKEN_JERRY =
    "eyJraWQiOiJ3ZWJnb2F0X2tleSIsImFsZyI6IkhTNTEyIn0...VNrp2ZXA";

Почему секрет: Подписанный JWT с алгоритмом HS512 и kid: webgoat_key. Если токен валиден, его достаточно скопировать и использовать в заголовке Authorization: Bearer для доступа к API от имени пользователя. Кроме того, готовый токен упрощает атаку по подбору секрета подписи.

Правильное хранение: В тестах JWT генерировать динамически в @BeforeEach, подписывая отдельным тестовым ключом. Секрет подписи хранить в CI/CD Secrets. Если токен уже попал в репозиторий — production-ключ подписи считать скомпрометированным и сменить.

Дополнительные вопросы

Что такое BFG Repo-Cleaner

BFG Repo-Cleaner — утилита для переписывания истории git-репозитория, более быстрая и удобная замена git filter-branch. Используется, когда секрет уже попал в историю коммитов и простое удаление из последнего коммита недостаточно. Умеет удалять файлы по имени из всей истории и заменять конкретные строки на маркер ***REMOVED***.

bfg --delete-files privatekey.key
bfg --replace-text secrets_to_remove.txt
git reflog expire --expire=now --all && git gc --prune=now --aggressive
git push --force

Важно: BFG не трогает текущий HEAD — секрет нужно сначала убрать вручную. И даже после очистки истории токен/ключ необходимо считать скомпрометированным и отозвать — репозиторий могли уже склонировать.

Можно ли автоматизировать поиск секретов

Да, и это правильный подход. Автоматизацию строят в три слоя: pre-commit хук (gitleaks, detect-secrets) блокирует секрет до попадания в коммит; обязательный шаг в CI/CD пайплайне падает и блокирует мёрдж при обнаружении; встроенный сканер платформы (GitHub Secret Scanning, GitLab Secret Detection) ловит уже загруженные секреты.

Минусы: много ложных срабатываний на хэшах зависимостей и тестовых данных, произвольные пароли без явных паттернов могут не детектироваться. Pre-commit можно обойти флагом --no-verify, поэтому серверная проверка обязательна. Главное — автоматизация фиксирует факт утечки, но ротацию ключей всё равно выполняет человек. Правильный подход сочетает сканирование с хранением секретов в специализированных хранилищах с самого начала.

Вывод

С помощью truffleHog удалось найти 5 разнотипных секретов. Все они попали в репозиторий через единственный коммит 34f1faad на ветке develop и не видны в текущем состоянии ветки main — без анализа полной истории коммитов все утечки были бы пропущены. Это наглядно показывает ценность инструментов вроде truffleHog и необходимость встраивать проверку секретов в CI/CD как можно раньше, а не только сканировать постфактум.
