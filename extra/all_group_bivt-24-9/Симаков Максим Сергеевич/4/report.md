## Фрагмент кода 1

```python
#!/usr/bin/env python3
from flask import Flask

from mod_api import mod_api

app = Flask('vuln_app')
app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

app.register_blueprint(mod_api, url_prefix='/api')
```

**Недостаток:** секретный ключ `SECRET_KEY` захардкожен прямо в исходном коде.

В Flask `SECRET_KEY` используется для подписи сессионных куки и защиты от CSRF. Если код попадёт в систему контроля версий или произойдёт утечка репозитория, злоумышленник получит ключ и сможет:
- подделывать сессионные куки и входить под любым пользователем,
- обходить CSRF-защиту,
- расшифровывать данные, которые приложение шифрует этим ключом.

**Рекомендации по устранению:**

- Вынести ключ в переменную окружения и читать через `os.environ.get('SECRET_KEY')`.
- Добавить `.env`-файл в `.gitignore`, чтобы он никогда не попал в репозиторий.
- Использовать разные ключи для dev и prod окружений.
- При компрометации немедленно ротировать ключ — все активные сессии при этом сбрасываются, что является ожидаемым поведением.

## Фрагмент кода 2

```python
from flask_wtf import Form
from wtforms import TextField

class LoginForm(Form):
    username = TextField('username')
    password = TextField('password')
```

**Недостатки:**

1. **Пароль — обычное текстовое поле.** `TextField` отображает вводимые символы открытым текстом. Любой, кто смотрит на экран, видит пароль. Браузер также может предложить сохранить его в автодополнении как обычный текст.

2. **Отсутствие валидаторов.** Форма принимает любые данные без ограничений: пустые строки, сколь угодно длинные значения, некорректные форматы. Это открывает путь к ошибкам на уровне базы данных и позволяет обходить ожидаемую логику приложения.

**Рекомендации по устранению:**

- Заменить `TextField` для пароля на `PasswordField` — он скрывает символы и отключает автодополнение браузера по умолчанию.
- Добавить валидаторы: `DataRequired()` для обоих полей, `Length(min=8, max=128)` для пароля, `Length(max=64)` для имени пользователя.
- Для поля `username` при необходимости добавить `Regexp` или `Email`-валидатор в зависимости от ожидаемого формата.

## Фрагмент кода 3

```python
def post(self):
    username = self.get_argument('username')
    password = self.get_argument('password').encode('utf-8')
    email = self.get_argument('mail')

try:
    username = username.lower()
    email = email.strip().lower()
    user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})
    user.validate()
    save_user(self.db_conn, user)
except Exception, e:
    return self.render_template("success_create.html")
```

**Недостатки:**

1. **Пароль хранится в открытом виде.** Пароль кодируется в байты (`.encode('utf-8')`), но не хэшируется перед сохранением. При компрометации базы данных все пароли пользователей немедленно доступны злоумышленнику.

2. **Неверная обработка исключений.** При любой ошибке (включая настоящие сбои: дублирующийся username, ошибка БД, невалидные данные) обработчик `except` всё равно отдаёт страницу `success_create.html`. Пользователь думает, что регистрация прошла успешно, хотя на деле аккаунт не создан. Это и логическая ошибка, и потенциальная точка для обхода бизнес-логики.

**Рекомендации по устранению:**

- Хэшировать пароль перед сохранением с использованием стойкого алгоритма: `bcrypt`, `argon2` или хотя бы `PBKDF2`. В Python удобно использовать библиотеку `passlib` или встроенный `hashlib` с PBKDF2.
- Разделить обработку ошибок: успех показывать только при реальном успехе, ошибку — логировать и возвращать пользователю адекватное сообщение. Никогда не глотать исключения через голый `except Exception`.
- Конкретные ошибки (например, `IntegrityError` при дублировании) обрабатывать отдельно и сообщать пользователю: «Имя пользователя уже занято».

# ЧАСТЬ 2

## 1. Какие наиболее распространённые атаки предотвращает Django?

Django предоставляет встроенную защиту от нескольких классов атак из OWASP Top 10, если не отключать её намеренно:

**SQL-инъекции** — ORM Django автоматически параметризует все запросы к базе данных. Пользовательский ввод никогда не конкатенируется напрямую с SQL-кодом. Уязвимость остаётся возможной только при использовании `raw()` или `cursor.execute()` с ручной конкатенацией строк.

**XSS (Cross-Site Scripting)** — шаблонизатор Django по умолчанию экранирует все переменные при выводе: `<`, `>`, `"`, `'`, `&` заменяются на HTML-сущности. Вредоносный скрипт в пользовательском вводе не выполнится в браузере. Если разработчик явно помечает данные как безопасные через `mark_safe()` или фильтр `|safe`, защита отключается — это намеренное решение, которое требует осознанности.

**CSRF (Cross-Site Request Forgery)** — `CsrfViewMiddleware` генерирует уникальный токен для каждой сессии и проверяет его наличие в небезопасных HTTP-методах (POST, PUT, DELETE, PATCH). Без токена запрос отклоняется. Это блокирует атаки, при которых сторонний сайт пытается отправить запрос от имени авторизованного пользователя.

**Clickjacking** — `XFrameOptionsMiddleware` добавляет заголовок `X-Frame-Options: DENY` или `SAMEORIGIN`, запрещая встраивать страницы в `<iframe>` на других сайтах. Это предотвращает атаки, при которых поверх легитимной страницы накладывается прозрачный вредоносный элемент.

**Инъекции через заголовок Host** — Django валидирует заголовок `Host` по списку `ALLOWED_HOSTS`. Запросы с неожиданным значением `Host` отклоняются, что предотвращает атаки типа Host Header Injection при формировании ссылок для сброса пароля.

**Брутфорс паролей** — встроенная система аутентификации автоматически хэширует пароли с использованием стойких алгоритмов (PBKDF2 с SHA-256 по умолчанию, можно переключить на Argon2 или bcrypt). При сравнении хэшей используется `hmac.compare_digest()` для защиты от timing-атак.

## 2. Как устроено управление пользовательскими сессиями в Django?

Сессии в Django позволяют серверу «помнить» пользователя между отдельными HTTP-запросами (HTTP — протокол без состояния).

**Архитектура:** данные сессии хранятся на стороне сервера, клиент получает только уникальный идентификатор — `session_id`. Это принципиально безопаснее подхода, при котором данные хранятся в куки целиком, потому что при перехвате куки атакующий получает только бессмысленный идентификатор, а не реальные данные.

**Жизненный цикл сессии:**

1. Подключается `SessionMiddleware` в `MIDDLEWARE` — он добавляет объект `request.session` к каждому запросу.
2. При первом обращении Django создаёт новую сессию и генерирует случайный `session_id`.
3. Данные сессии сохраняются на сервере (по умолчанию — в таблице `django_session` в БД).
4. В браузер уходит `Set-Cookie: sessionid=<случайная_строка>`.
5. При следующих запросах браузер отправляет куки обратно, Django находит сессию по идентификатору и загружает её данные.
6. В коде данные доступны как словарь: `request.session['user_id'] = user.id`.

**Бэкенды хранения:** Django поддерживает несколько вариантов хранения сессий:
- `db` (по умолчанию) — в таблице базы данных,
- `cache` — в кэше (Redis, Memcached) — быстрее, но данные могут потеряться при очистке кэша,
- `file` — в файловой системе,
- `signed_cookies` — данные хранятся прямо в куки, но подписываются SECRET_KEY (объём ограничен ~4 КБ).

**Сериализация:** по умолчанию используется JSON. Это безопаснее устаревшего `pickle`, который позволял выполнять произвольный код при десериализации скомпрометированных данных сессии.

**Безопасность куки сессии** — ключевые настройки:

| Настройка | Что делает |
|---|---|
| `SESSION_COOKIE_HTTPONLY = True` | JavaScript не может читать куки — защита от XSS-кражи сессии |
| `SESSION_COOKIE_SECURE = True` | Куки передаются только по HTTPS |
| `SESSION_COOKIE_SAMESITE = 'Lax'` | Защита от части CSRF-атак на уровне куки |
| `SESSION_COOKIE_AGE = 1209600` | Время жизни сессии в секундах (по умолчанию 2 недели) |
| `SESSION_EXPIRE_AT_BROWSER_CLOSE = False` | Сессия живёт до истечения `AGE`, а не до закрытия браузера |

**Ротация сессии:** при входе пользователя в систему Django автоматически создаёт новый идентификатор сессии (`request.session.cycle_key()`). Это предотвращает Session Fixation — атаку, при которой злоумышленник заранее подсовывает жертве известный ему `session_id`.

**Завершение сессии:** при выходе из системы вызов `request.session.flush()` удаляет данные сессии из базы и сбрасывает куки. Устаревшие сессии автоматически удаляются командой `python manage.py clearsessions`.
