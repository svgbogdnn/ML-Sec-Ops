- https://nvd.nist.gov/vuln/detail/CVE-2021-29625
- https://nvd.nist.gov/vuln/detail/CVE-2021-42360

Поиск по ключевым словам `php xss` с фильтром по дате публикации 01/01/2021–31/12/2021 на NVD вернул **10 записей**. Поиск выполнялся через Advanced Search на nvd.nist.gov. Даже этот не полный срез — только то, где в описании явно упоминается PHP — показывает, что XSS в PHP-компонентах встречается регулярно даже спустя многие годы изучения этой уязвимости.

## CVE-2021-29625 — Adminer

Adminer — это однофайловый веб-инструмент управления базами данных, написанный на PHP. Он предоставляет браузерный интерфейс для работы с MySQL, MariaDB, PostgreSQL, SQLite и другими СУБД: просматривать и редактировать таблицы, выполнять SQL-запросы напрямую, импортировать и экспортировать дампы, управлять пользователями и правами доступа. Из-за однофайлового формата Adminer удобен в развёртывании — достаточно залить один `.php`-файл на сервер.

Уязвимость затрагивает версии 4.6.1–4.8.0. Проблема в функции `doc_link()` в файле `adminer/include/editing.inc.php` — она формирует ссылку на документацию конкретной СУБД по имени таблицы. Когда пользователь передаёт некорректное, но синтаксически допустимое имя таблицы, функция вставляет его в атрибут `href` тега `<a>` без вызова `htmlspecialchars()`. Из-за этого злоумышленник может внедрить JavaScript прямо в ссылку, которая потом выполняется в браузере жертвы — аутентифицированного пользователя Adminer.

Тип уязвимости: **Reflected XSS** (CWE-79), CVSS 6.1.

Исправление простое: в версии 4.8.1 добавлен вызов `htmlspecialchars()` вокруг параметра в `doc_link`. Также помогает строгий CSP в браузере.

Источники:
- https://nvd.nist.gov/vuln/detail/CVE-2021-29625
- https://github.com/vrana/adminer/commit/4043092ec2c0de2258d60a99d0c5958637d051a7

## CVE-2021-42360 — Starter Templates (WordPress плагин)

Starter Templates — PHP-плагин для WordPress от компании Brainstorm Force, установлен более чем на миллионе сайтов. Он позволяет быстро импортировать готовые макеты страниц из библиотеки шаблонов (поддерживает Elementor, Gutenberg, Beaver Builder) и разворачивать полноценный сайт за несколько кликов. Функция импорта блоков работает через AJAX-обработчик `astra-page-elementor-batch-process`.

Уязвимость в версиях до 2.7.1: обработчик принимал параметр `$_POST['url']` — ссылку на JSON с содержимым блока — без какой-либо валидации источника. Любой пользователь с правом `edit_posts` (роль Contributor и выше) мог указать в этом параметре URL на свой сервер с заранее подготовленным JSON, содержащим произвольный JavaScript. Сервер загружал этот JSON и внедрял его содержимое на целевую страницу. Нужный нonce для запроса был виден прямо в исходнике дашборда WordPress.

В итоге: страница сайта перезаписывается вредоносным скриптом. Любой посетитель, в том числе администратор, видит страницу — и JavaScript выполняется в его браузере. Это открывает путь к угону сессии администратора и полному захвату сайта.

Тип уязвимости: **Stored XSS** (CWE-79), CVSS 7.6.

Уязвимость исправлена в версии 2.7.1 через 3 дня после обнаружения командой Wordfence.

Источники:
- https://nvd.nist.gov/vuln/detail/CVE-2021-42360
- https://www.wordfence.com/blog/2021/11/over-1-million-sites-impacted-by-vulnerability-in-starter-templates-plugin/

# ЧАСТЬ 2

Скачал и запустил образ:

```
docker pull ket9/otus-devsecops-xss
docker run -d -p 8888:80 ket9/otus-devsecops-xss:latest
```

Перешёл на http://localhost:8888/ — приложение отдало главную страницу "XSS lab" с двумя ссылками: `XSS-1` и `index.php`.

## Первый взгляд

Открыл `/XSS-1/`. Увидел минималистичную страницу: заголовок "XSS lab", раздел "Comments" и форму с одним полем ввода "comment?" и кнопкой "Save Data". Раздел комментариев — это место, где сохраняются и отображаются введённые данные. Первая мысль — это Stored XSS: если приложение не экранирует пользовательский ввод перед отображением, сохранённый скрипт будет выполняться у каждого пользователя, открывшего страницу.

## Проверка базового пейлоада

Ввёл в поле комментария:

```
<script>alert('XSS')</script>
```

Нажал "Save Data". Страница перезагрузилась — скрипт сохранился и тут же выполнился в браузере (в headless-окружении alert не виден визуально, но тег `<script>` присутствует в DOM). Приложение не экранирует ввод перед сохранением.

## Подтверждение выполнения в контексте браузера

Чтобы наглядно доказать, что скрипт выполняется именно в браузере клиента, использовал пейлоад, который изменяет содержимое страницы:

```
<script>document.querySelector('h1').innerText = 'HACKED';</script>
```

После отправки и перезагрузки страницы заголовок "XSS lab" изменился на **HACKED** — это однозначно подтверждает выполнение произвольного JavaScript в контексте браузера клиента.

## Доступ к сессионным данным

Попробовал вытащить куки:

```
<script>alert(document.cookie);</script>
```

Скрипт выполнился — `document.cookie` доступен из внедрённого кода. В данном случае куки оказались пустыми (тестовое окружение без сессий), но в реальном приложении здесь были бы сессионные токены. Получив их, атакующий может отправить куки на свой сервер и угнать сессию жертвы.

## Описание уязвимости

Приложение сохраняет пользовательский ввод из поля "comment?" и напрямую вставляет его в HTML-страницу без какой-либо обработки. Браузер воспринимает вставленный `<script>` как полноценный JavaScript и выполняет его в контексте страницы — со всеми правами, которые у этой страницы есть: доступ к `document.cookie`, к `localStorage`, возможность делать запросы от имени пользователя.

## Тип уязвимости

| Что нашли | Тип |
|---|---|
| Сохранение произвольного HTML в базу | Stored XSS (CWE-79) |
| Выполнение `<script>` при просмотре страницы | Выполнение JS в контексте браузера клиента |
| Доступ к `document.cookie` из пейлоада | Угроза угона сессии |

**Тип:** Stored XSS — вредоносный скрипт сохраняется на сервере и выполняется у всех пользователей, открывших страницу. Это делает Stored XSS опаснее Reflected: атака не требует от жертвы перехода по специально сформированной ссылке.

## Меры предотвращения

Корневая причина — отсутствие экранирования пользовательского ввода при выводе. Чтобы защититься:

1. **Экранировать все пользовательские данные** при выводе в HTML. Нужно заменять опасные символы на безопасные HTML-сущности:
   - `<` → `&lt;`
   - `>` → `&gt;`
   - `"` → `&quot;`
   - `'` → `&#039;`
   - `&` → `&amp;`

   В PHP для этого используется функция `htmlspecialchars($input, ENT_QUOTES, 'UTF-8')` — применять при каждом выводе пользовательских данных в HTML.

2. **Content Security Policy (CSP)** — заголовок, ограничивающий источники допустимых скриптов. Даже если XSS-пейлоад попадёт на страницу, строгий CSP запретит его выполнение.

3. **Валидация на входе** — ограничить допустимые символы в поле комментария. Для текстовых комментариев теги вообще не нужны — их можно отклонять на уровне формы.

4. **HttpOnly и Secure флаги на куки** — если кражу куки не удалось предотвратить, флаг `HttpOnly` запрещает JavaScript читать куки, что отрезает один из самых популярных векторов Stored XSS.

5. **Sanitization-библиотеки** для случаев, когда HTML действительно нужен в выводе (например, WYSIWYG-редакторы) — использовать проверенные библиотеки типа HTMLPurifier, которые удаляют опасные теги и атрибуты, оставляя безопасную разметку.
