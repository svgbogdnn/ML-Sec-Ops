ЛР 4. Симуляция XSS-атаки

1. CVE за 2021 год

Искал через NVD. Полный год одним запросом API не принимает, максимум 120 дней, поэтому разбил 2021 год на несколько интервалов и считал по ключевому запросу cross-site scripting PHP

Команды были такого вида:

curl -s 'https://services.nvd.nist.gov/rest/json/cves/2.0?keywordSearch=cross-site%20scripting%20PHP&pubStartDate=2021-01-01T00:00:00.000&pubEndDate=2021-04-30T23:59:59.999' | jq -r '.totalResults'

Получилось:

  • 01.01.2021 - 30.04.2021: 11
  • 01.05.2021 - 28.08.2021: 9
  • 29.08.2021 - 26.12.2021: 6
  • 27.12.2021 - 31.12.2021: 0

Всего по такому поиску вышло 26 CVE. Тут важно, что это не вообще все XSS за 2021 год, а именно найденные NVD по словам cross-site scripting и PHP. Если искать по XSS PHP, результат меньше, потому что часть описаний использует полную фразу, а не сокращение

CVE-2021-43698, phpWhois

Ссылка: https://nvd.nist.gov/vuln/detail/CVE-2021-43698

phpWhois - это PHP-библиотека для WHOIS-запросов. Через нее можно из PHP-кода получить данные по домену, IP или AS. В README проекта прямо показан пример с phpWhois\Whois, методом lookup() и выводом результата по домену

В этой CVE проблема была в example.php. По описанию NVD, скрипт завершался через exit и печатал сообщение пользователю, а в это сообщение попадал $_GET['query']. Если в query передать HTML/JS, сервер вставит его в страницу без нормального экранирования. Это типичный XSS через отражение пользовательского ввода в HTML

Источник по назначению компонента: https://github.com/phpWhois/phpWhois

CVE-2021-43808, Laravel Blade

Ссылка: https://nvd.nist.gov/vuln/detail/CVE-2021-43808

Laravel - PHP-фреймворк для веб-приложений, а Blade - его шаблонизатор. Blade-файлы обычно лежат с расширением .blade.php, компилируются в обычный PHP и используются для сборки HTML-представлений

В CVE уязвимость касается Blade в Laravel до версий 8.75.0, 7.30.6 и 6.20.42. По описанию NVD, проблема связана с тем, что можно было угадать SHA-1 hash placeholder родительского шаблона через распространенные имена секций. Если родительский шаблон содержит подходящую HTML-структуру, это открывает XSS. Исправление сделали через вычисление placeholder во время запроса и случайный hash, уникальный для каждого запроса.

Источник по назначению Blade: https://laravel-docs.readthedocs.io/en/stable/blade/

2. Практика на стенде

Образ скачал:

docker pull ket9/otus-devsecops-xss

При запуске на 8080 сразу получил ошибку, потому что у меня на этом порту уже висел контейнер из прошлой лабы:

Bind for 0.0.0.0:8080 failed: port is already allocated

тобы не останавливать старый контейнер, стенд XSS запустил на соседнем порту:

docker run -d -p 8081:80 ket9/otus-devsecops-xss:latest

Контейнер поднялся, в логах был Apache:

Apache/2.4.25 (Debian) PHP/7.0.33 configured -- resuming normal operations

Открыл корень:

curl -i http://127.0.0.1:8081/

Ответ был HTTP/1.1 200 OK, на странице ссылка на XSS-1:

<b><div class='item'><a href='XSS-1'>XSS-1</a></div></b>

Дальше открыл форму:

curl -i http://127.0.0.1:8081/XSS-1/

Там обычная форма комментария:

<form method="POST" action="index.php">
    comment? <br/>
    <input type="textarea" rows="4" cols="90" name="comment">
    <input type="submit" name="submit" value="Save Data">
</form>

Сначала проверил логику по исходнику внутри контейнера. В index.php комментарий берется из $_POST["comment"], пишется в /tmp/comments.txt, потом файл читается обратно и каждый кусок печатается прямо в HTML:

echo "<p>$comments[$i]</p><hr />\n";

Тут уже видно слабое место: перед выводом нет htmlspecialchars, поэтому браузер воспримет введенный HTML как разметку страницы, а не как текст комментария

Проверил это payload с script:

curl -i -X POST \
  --data-urlencode "comment=<script>alert('xss-lab-4')</script>" \
  http://127.0.0.1:8081/XSS-1/index.php

Ответ приложения:

<h2>Comments</h2><p><script>alert('xss-lab-4')</script>

</p><hr />

После открытия http://127.0.0.1:8081/XSS-1/ в браузере скрипт выполняется и появляется alert с текстом xss-lab-4. Тут атака не одноразовая: payload сохранился в /tmp/comments.txt, поэтому он срабатывает при каждом следующем открытии страницы комментариев

Тип уязвимости

Это stored XSS, он же persistent XSS. Пользовательский ввод сохраняется на сервере, потом без экранирования попадает в HTML-ответ и выполняется в браузере клиента

По CWE это CWE-79, Improper Neutralization of Input During Web Page Generation

Конкретное место в стенде:

echo "<p>$comments[$i]</p><hr />\n";

Проблема не в самом сохранении комментария, а в выводе. Значение из файла считается доверенным, хотя туда до этого попал ввод пользователя

Как предотвращать

Самое прямое исправление для этого стенда - экранировать комментарий перед выводом:

$safeComment = htmlspecialchars($comments[$i], ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
echo "<p>{$safeComment}</p><hr />\n";

Какие символы нужно нейтрализовать в HTML-контексте:

  • < и > - чтобы пользователь не мог открыть тег script, img, svg, iframe
  • " и ' - чтобы нельзя было вылезти из HTML-атрибута и добавить обработчик вроде onerror
  • & - чтобы нельзя было собирать HTML-сущности и обходить часть фильтрации

Я бы не делал защиту через черный список слов script, alert, onerror. Это быстро ломается вариантами вроде <img src=x onerror=...>, SVG, смешанным регистром и кодировками. Нормальный вариант - выводить пользовательский комментарий как текст, а не как HTML. Для PHP это htmlspecialchars с ENT_QUOTES и явной кодировкой UTF-8

Дополнительно:

  • ограничить длину комментария, например 1000-2000 символов
  • если HTML в комментариях не нужен, не разрешать его вообще
  • если HTML нужен, использовать проверенный sanitizer с allowlist тегов и атрибутов
  • поставить CSP, например запретить inline script, но это уже второй слой, а не замена экранированию
  • для cookie ставить HttpOnly и SameSite, чтобы XSS было сложнее использовать для кражи сессии
