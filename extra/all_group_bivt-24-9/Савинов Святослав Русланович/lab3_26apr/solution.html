Часть I

OWASP API Security Top-10 за 2023 год (новая версия пока в разработке): https://owasp.org/www-project-api-security/

Чекнул три разные категории из топ10.

CVE-2025-12903

https://nvd.nist.gov/vuln/detail/CVE-2025-12903

Плагин Payment Plugins Braintree For WooCommerce, версии до 3.2.78 включительно. REST-эндпоинт wc-braintree/v1/3ds/vaulted_nonce принимает token ID, но не проверяет кому он принадлежит. Любой неаутенифицированный пользователь передаёт чужой токен и получает payment nonce, дальше можно списать деньги с чужой карты.

Категория: API1:2023 BOLA. Дыра потому что эндпоинт зарегистрирован с permission_callback = __return_true, то есть ownership токена и аутентификация просто не проверяются.

CVE-2025-56449

https://nvd.nist.gov/vuln/detail/CVE-2025-56449

Obsidian Scheduler 5.0.0 - 6.3.0. Проверка статуса блокировки реализована только на UI-слое, REST API использует общий механизм Basic Auth и не сверяет статус юзера в БД из-за недостоаточной синхронизации между этими двумя слоями. По итогу аккаунт, заблокированный в UI за непрохождение MFA-enrollment, всё равно лезет через API и выполняет админские действия. Категория: API2:2023 Broken Authentication.

CVE-2025-20348

https://nvd.nist.gov/vuln/detail/CVE-2025-20348

Cisco Nexus Dashboard и NDFC до 4.1(1g). На REST-эндпоинтах нет проверки роли, аутентифицированный пользователь с низкими правами лезет в админские операции (читает настройки HTTP Proxy / NTP, грузит образы и портит уже загруженные). Сервер проверяет только сам факт логина, саму роль не сверяет. Это API5:2023 Broken Function Level Authorization.

Часть II

Итак, контейнер запустил (docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest:latest), базу наполнил через /createdb (ответ {"message": "Database populated."}), протыкаем эндпоиты. На localhost:8080 приложение отдаёт свой список. Сразу бросается в глаза /users/v1/_debug с подписью "посмотреть подробную информацию обо всех пользователях".

Открываю в браузере:

http://localhost:8080/users/v1/_debug

{"users":[
  {"admin":false,"email":"mail1@mail.com","password":"pass1","username":"name1"},
  {"admin":false,"email":"mail2@mail.com","password":"pass2","username":"name2"},
  {"admin":true,"email":"admin@mail.com","password":"pass1","username":"admin"}
]}

Опа открытые пароли. GET без токена и cookie, статус 200, в ответе все юзеры вместе с флагом admin. Зная адрес эндпоинта, сразу заходим под админом (admin / pass1).

Для сравнения обычный /users/v1:

{"users":[
  {"email":"mail1@mail.com","username":"name1"},
  {"email":"mail2@mail.com","username":"name2"},
  {"email":"admin@mail.com","username":"admin"}
]}

Тут пароли уже не отдаются, только email и username. То есть авторы знали что password это чувствительное поле, просто забыли про дебаг.

Уязвимость 1

Тип: API3:2023 Broken Object Property Level Authorization (BOPLA). Это именно BOPLA, а не только API8:2023 Security Misconfiguration: BOPLA про то что сервер возвращает чувствительные свойства объекта (password, admin) без проверки прав на эти свойства, и даже за авторизацией такое поле возвращать нельзя. То что эндпоинт ещё и открыт всем без логина, это сверху уже API8 Misconfig (отладочный эндпоинт остался в проде).

Описание: /users/v1/_debug отдаёт пароли всех юзеров системы в открытом виде по обычному GET без авторизации.

Меры предотвращения:

  • удалить _debug из прода или закрыть админской авторизацией
  • пароли хранить только хешем (bcrypt / argon2), password не возвращать в API ни при каких условиях
  • ограничить состав возвращаемых полей через DTO, чтобы случайно не утекло чего-то лишнего

Уязвимость 2

Дальше пробую посмотреть данные конкретного юзера по имени:

http://localhost:8080/users/v1/name1

{"username": "name1", "email": "mail1@mail.com"}

http://localhost:8080/users/v1/admin

{"username": "admin", "email": "admin@mail.com"}

Тоже без токена и cookie, 200 OK. Любой неаутентифицированный пользователь может получить данные любого юзера, просто подставив имя в URL. Не такая страшная как _debug (тут хотя бы пароля нет), но вместе с публичным /users/v1 это даёт полное перечисление учёток в системе.

Тип: API1:2023 Broken Object Level Authorization.

Описание: эндпоинт /users/v1/{username} отдаёт данные пользователя по любому имени без проверки что запрашивающий имеет право это видеть.

Меры предотвращения:

  • требовать токен на всех эндпоинтах с пользовательскими данными
  • сверять username в URL с владельцем токена (либо разрешать доступ только админам)
  • не светить полный список пользователей в /users/v1 без авторизации

Приложение собрало почти все из топ10.
