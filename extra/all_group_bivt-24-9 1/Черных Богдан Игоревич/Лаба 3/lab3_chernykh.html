🔸 1 CVE-2021-42078

Название CVE — CVE-2021-42078
Источник

https://nvd.nist.gov/vuln/detail/CVE-2021-42078

Для чего используется компонент
PHP Event Calendar — это веб-календарь / планировщик на PHP, который используется для создания, отображения и управления событиями на сайте. Его можно применять для расписаний, календарей мероприятий, встреч, напоминаний и других событий, которые нужно показывать пользователям через веб-интерфейс. Компонент поддерживает day, week, month, year, agenda и resource views, а также встроенные напоминания.

Компонент на PHP
обработчик событий /server/ajax/events_manager.php, уязвимый параметр title.

Функционал компонента
Компонент предоставляет функционал календаря событий: добавление событий, редактирование событий, отображение календаря в разных режимах, просмотр расписания, работу с событиями через веб-интерфейс и хранение данных событий. Это готовая календарная система, которую можно встроить в сайт или использовать как основу для event management.

Описание уязвимости
Уязвимость находится в обработке названия события календаря. Когда пользователь создает или редактирует событие, приложение принимает значение параметра title. Однакое это значение недостаточно очищается и безопасно не экранируется перед дальнейшим отображением на странице. Из-за этого вместо обычного названия события можно передать HTML/JavaScript-код. В NVD написано, что это допускало persistent XSS через параметр title в /server/ajax/events_manager.php и это может использоваться для выполнения действий на странице в контексте других пользователей или для дефейса сайта.

Тип уязвимости
Persistent XSS / Stored XSS.

Причина уязвимости
Главная причина — приложение доверяет пользовательскому вводу в поле title и не приводит его к безопасному виду перед выводом в HTML. То есть сервер должен был воспринимать название события как обычный текст, но из-за отсутствия нормального экранирования опасные символы вроде < > " ' & могли сохранить свое специальное значение в HTML. В результате тег <script> или другой HTML-код попадал в страницу как настоящая разметка.

Последствия
Злоумышленник может внедрить JavaScript-код в событие календаря. Когда другой пользователь откроет это событие или страницу с календарем, скрипт выполнится в его браузере. Это может привести к выполнению действий от имени пользователя, подмене содержимого страницы или краже пользовательских данных.

🔸 2 CVE-2021-42078

Название CVE — CVE-2021-29625
Источник

https://nvd.nist.gov/vuln/detail/CVE-2021-29625

Для чего используется компонент
Adminer — это инструмент для управления базами данных через браузер. Он написан на PHP и распространяется как один PHP-файл. Его используют как легкую альтернативу phpMyAdmin: администратор или разработчик открывает Adminer в браузере, подключается к базе данных и управляет таблицами, записями, SQL-запросами и экспортом данных.

Компонент на PHP
функция doc_link, уязвимый параметр — формирование ссылок на документацию.

Функционал компонента
Adminer позволяет подключаться к серверу базы данных, выбирать или создавать базы, просматривать таблицы, поля, индексы, внешние ключи и триггеры, добавлять и удалять таблицы и колонки, выполнять SQL-команды, редактировать записи, экспортировать структуру и данные в SQL или CSV. Также есть поддержка работы с таблицами, индексами, представлениями, процедурами, функциями и триггерами.

Описание уязвимости
В Adminer уязвимость связана с тем, как приложение формировало ссылку на документацию через функцию doc_link. Adminer — это PHP-инструмент для управления базами данных через браузер, поэтому внутри интерфейса он динамически показывает таблицы, ошибки, ссылки и служебные элементы.
Проблема возникала в версиях Adminer 4.6.1–4.8.0. XSS затрагивает пользователей MySQL, MariaDB, PgSQL и SQLite. При определенных условиях данные, связанные с работой с таблицами / документацией, могли попасть в HTML-страницу без достаточного экранирования. В результате злоумышленник мог добиться выполнения JavaScript-кода в браузере пользователя Adminer.
Уязвимость была исправлена в версии 4.8.1.

Тип уязвимости
Stored XSS.

Причина уязвимости
Причина — неправильное экранирование данных при генерации HTML. Функция doc_link формировала HTML-ссылку, но некоторые значения не были достаточно безопасно обработаны перед вставкой в страницу. Если вставлялось неправильное, но допустимое имя таблицы, вызывалась функция doc_link; при этом параметр таблицы не экранировался должным образом, что и приводило к XSS на стороне клиента. То есть, Adminer вставлял часть данных в HTML-контекст без достаточного экранирования, из-за чего можно было брокнуть HTML и внедрить JavaScript.

Последствия
Злоумышленник мог добиться выполнения JavaScript-кода в браузере пользователя Adminer. Adminer обычно используется для работы с базами данных, то есть пользователь внутри такого интерфейса может иметь высокие привилегии. Выполнение XSS в таком контексте может привести к краже данных сессии, выполнению действий от имени пользователя или подмене содержимого страницы.

Скачал образ (docker pull ket9/otus-devsecops-xss), запустил его (docker run -d -p 8080:80 ket9/otus-devsecops-xss:latest).

Зашел на:

http://localhost:8080/

Нажал на XSS-1 и меня перевело на:

http://localhost:8080/XSS-1/

На странице было поле для ввода под comment? и кнопка Save Data. Сначала я проверил как вообще работает поле комментария. Ввел базовый текст test.
После нажатия на Save Data текст появился ниже в блоке комментариев. Значит приложение сохраняет введенные данные и потом выводит их обратно на страницу.

Дальше решил проверить воспринимает ли приложение введенный текст как обычный текст или как HTML.
Ввел <b>Hello</b>.
После сохранения слово Hello отобразилось жирным шрифтом. Значит приложение не экранирует HTML теги, а вставляет введенные данные прямо в страницу как HTML.

После этого попробовал базовый XSS-пейлоад 

<script>alert('XSS')</script>

и нажал Save Data.
После сохранения появилось попап уведомление с текстом XSS. Следовательно браузер выполнил мой JavaScript-код. То есть введенный скрипт не был отфильтрован или экранирован, а попал на страницу как настоящий код.

Дальше обновил страницу и снова перешел на:

http://localhost:8080/XSS-1/

Скрипт снова выполнился. То есть код не просто отразился один раз после отправки формы, а сохранился в коментах и продолжил выполняться при повторном открытии страницы.
ㅤ

Тип уязвимости

Stored XSS / хранимый Cross-Site Scripting.
Вредоносный скрипт сохраняется приложением, а потом снова отображается и выполняется у пользователя при открытии страницы. По OWASPу Stored XSS это ситуация когда пользовательский ввод сохраняется на сервере, например в комментарии, а затем возвращается другим пользователям без безопасной обработки и выполняется в браузере.

Причина уязвимости

Причина в том, что приложение берет данные из поля comment? и вставляет их в HTML-страницу без нормальной обработки. Опасными символами в таком случае являются < > " ' & и они не заменяются на безопасные HTML-сущности. Поэтому браузер воспринимает строку <script>alert('XSS')</script> не как обычный текст, а как настоящий JavaScript-код.

Возможные последствия

  1. Выполнение JavaScript-кода в браузере пользователя.
  2. Подмена содержимого страницы.
  3. Выполнение действий от имени пользователя.
  4. Попытка доступа к данным, которые доступны странице.
  5. Перенаправление пользователя на другой сайт.

Меры предотвращения

Чтобы исправить такую уязвимость, нужно не выводить пользовательский ввод в HTML как есть. В первую очередь нужно экранировать специальные символы при выводе:

< → <
> → >
" → "
' → '
& → &

Тогда строка <script>alert('XSS')</script> будет показана на странице как обычный текст, а не выполнится как скрипт.

Также нужно —

  1. Использовать HTML encoding для всех пользовательских данных перед выводом на страницу.
  2. Не разрешать HTML теги в комментариях, если они там не нужны.
  3. Проверять данные на стороне сервера, а не только в браузере.
  4. Использовать безопасные шаблонизаторы с автоматическим экранированием.
  5. Добавить Content Security Policy, чтобы ограничить выполнение inline JavaScript.
  6. Для cookie использовать флаг HttpOnly чтобы JavaScript не мог читать сессионные cookie.
