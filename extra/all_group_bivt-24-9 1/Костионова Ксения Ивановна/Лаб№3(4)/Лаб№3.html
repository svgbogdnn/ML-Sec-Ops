Часть 1. Поиск CVE с XSS в PHP-компонентах (2021 год)

CVE-2021-24284 Компонент: Royal Addons For Elementor (WordPress плагин на PHP) Функционал: Расширение для конструктора страниц Elementor, добавляет новые виджеты, шаблоны и функции для создания сайтов на WordPress без кодинга. Суть уязвимости: В файле royal-elementor-addons/includes/widgets/posts.php параметр post_id из GET-запроса выводился на страницу без экранирования. Злоумышленник мог передать вредоносный JavaScript-код, который выполнялся в браузере любого пользователя, открывшего страницу с этим параметром. Тип: Reflected XSS

CVE-2021-39302 Компонент: PHPBack (PHP-скрипт для создания сайта обратной связи) Функционал: Платформа для сбора идей, фидбека и голосований от пользователей. Позволяет создавать категории, модерировать предложения, управлять пользователями. Суть уязвимости: В файле includes/functions.php функция filter() некорректно обрабатывала пользовательский ввод. Параметр query из URL передавался в echo без санитизации, что позволяло внедрить произвольный JavaScript-код. Тип: Reflected XSS

Часть 2. Практика на стенде otus-devsecops-xss

Подготовка

docker pull ket9/otus-devsecops-xss
docker run -d -p 8080:80 ket9/otus-devsecops-xss:latest

Открыла http://localhost:8080, увидела ссылки на XSS-1 и index.php.

Ход рассуждений

  1. Кликнула на index.php. Ничего интересного, та же страница. Перешла на XSS-1, увидела форму с полем comment? и кнопкой save data.

  2. Ввела текст: Привет. После сохранения увидела свой комментарий на странице. Ок, данные сохраняются.

  3. Попробовала ввести в формает html: <b>жирный текст</b>. Текст стал жирным. Приложение не экранирует HTML-теги.

  4. Ввела: <script>alert('XSS')</script>. После сохранения появилось всплывающее окно с текстом XSS. То есть и скрипт выполняется. Это XSS.

  5. Закрыла вкладку, открыла заново, перешла на XSS-1. Окно снова появилось. Значит скрипт сохранился на сервере и выполняется у каждого, кто открывает страницу. Это Stored XSS.

Лог неудачных кспериментов:

  1. Попробовала закодировать: %3Cscript%3Ealert('XSS')%3C/script%3E - ничего не произошло.
  2. Попробовала добавить пробелы: < script > - браузер не распознал тег.
  3. Пробовала через адресную строку: .../XSS-1/index.php?comment=<script>alert(1)</script> - параметр не читается из URL, только из POST-формы.

Найденная уязвимость

Описание: Приложение принимает пользовательский ввод в поле комментария и сохраняет его в базу данных без экранирования. При отображении комментариев на странице содержимое вставляется напрямую в HTML, что позволяет выполнить произвольный JavaScript-код в браузере любого пользователя. Тип: Stored XSS - скрипт сохраняется на сервере и выполняется при каждом просмотре страницы. Меры предотвращения:

  1. Экранирование вывода:

    Перед вставкой пользовательских данных в HTML заменять опасные символы на их безопасные эквиваленты:

    • < → &lt;
    • > → &gt;
    • " → &quot;
    • ' → &#x27;
    • & → &amp;

  2. Content Security Policy:

    Добавить HTTP-заголовок:

    Content-Security-Policy: default-src 'self'; script-src 'self'

    Это запретит браузеру выполнять скрипты из внешних источников и inline-скрипты, если они попали в страницу.

  3. HttpOnly для сессионных кук:

    Установить флаг HttpOnly для cookie сессии, чтобы JavaScript не мог прочитать их:

    setcookie('session_id', $value, [
    'httponly' => true,
    'secure' => true,
    'samesite' => 'Strict'
]);
