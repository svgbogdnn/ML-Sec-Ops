## Часть 1. Анализ уязвимостей в Python-коде

### Фрагмент кода 1
**Недостаток:** SECRET_KEY жестко прописан в исходном коде. Если код попадет в публичный репозиторий, злоумышленник сможет получить доступ к ключу и подделывать сессионные куки, токены сброса пароля и другие данные.

**Рекомендации по устранению:**
1. Вынести ключ в переменные окружения
2. Не коммитить файл с ключами в git
3. Для генерации ключа использовать `secrets.token_hex(32)`
4. Использовать разные ключи для разных окружений

### Фрагмент кода 2
**Недостаток:** Поле для пароля использует обычный `TextField` - пароль будет виден при вводе. Также отсутствуют валидаторы на полях - можно отправить пустой логин/пароль или слишком длинные строки.

**Рекомендации по устранению:**
1. Заменить `TextField` на `PasswordField` для скрытия ввода
2. Добавить валидацию на сложность пароля (цифры, спецсимволы)

### Фрагмент кода 3
**Недостаток:** Пароль сохраняется в открытом виде - при утечке базы все пароли будут скомпрометированы. Обработка исключений слишком общая и показывает ошибочное сообщение - пользователь видит success даже если регистрация не прошла.

**Рекомендации по устранению:**
1. Хешировать пароль перед сохранением
2. Разделить обработку ошибок
3. Выводить достоверные сообщения - не только об успехе

## Часть 2. Модель безопасности Django

Django из коробки защищает от следующих атак:
- SQL Injection - ORM использует параметризованные запросы
- XSS - Шаблонизатор автоматически экранирует переменные при выводе в HTML
- CSRF - CSRF-токены на всех формах, middleware проверяет заголовок
- Clickjacking - Middleware `XFrameOptionsMiddleware` добавляет заголовок `X-Frame-Options: DENY` |
- SSL/HTTPS - Настройки `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE` принудительно включают HTTPS

**Хранение сессий:** Django хранит сессии на стороне сервера, а в браузере клиента остается только идентификатор сессии. Это безопаснее, чем хранение данных в cookie, потому что пользователь не может изменить содержимое сессии. При логине Django автоматически создаёт новый ключ сессии и удаляет старый. Это защищает от фиксации сессии, когда злоумышленник пытается подсунуть жертве свой sessionid.
