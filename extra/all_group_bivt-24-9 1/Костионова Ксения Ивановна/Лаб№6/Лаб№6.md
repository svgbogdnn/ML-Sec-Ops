### Подготовка

```powershell
docker run -it -v .:/opt/results python:3.12-buster bash

apt update && apt install -y git
pip install trufflehog

trufflehog git https://github.com/OtusTeam/DevSecOps_secret-finding.git --json > /opt/results/scan.log
```

### Найденные секреты

#### Секрет №1: Приватный RSA-ключ
| Поле | Значение |
|------|----------|
| **Файл** | `webgoat-server/privatekey.key` |
| **Строка** | 1–28 |
| **Контекст** | `-----BEGIN PRIVATE KEY-----` ... `-----END PRIVATE KEY-----` |

**Почему это секрет:**
- Файл содержит полноценный приватный RSA-ключ в формате PEM
- Ключ может использоваться для подписи артефактов, аутентификации по SSH или расшифровки данных
- При компрометации злоумышленник получает полный доступ ко всему, что защищено этим ключом

**Как должно быть:**
- Никогда не коммитить приватные ключи в репозиторий
- Хранить ключи в защищённом хранилище: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault
- Для CI/CD использовать переменные окружения, настроенные в интерфейсе платформы (GitHub Secrets, GitLab CI Variables)
- Для локальной разработки - файл `~/.ssh/id_rsa` с правами `600`, добавленный в `.gitignore`

#### Секрет №2: Захардкоженный GitHub Token
| Поле | Значение |
|------|----------|
| **Файл** | `.github/workflows/release.yml` |
| **Строка** | 75 |
| **Контекст** | `GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5` |

**Почему это секрет:**
- Строка с высокой энтропией - типичный формат токена GitHub
- Токен даёт доступ к репозиторию: пуш кода, создание релизов, управление workflows
- Даже если токен позже заменили на `${{ secrets.GITHUB_TOKEN }}`, он остался в истории коммитов

**Как должно быть:**
- Использовать встроенный механизм GitHub Actions: `${{ secrets.GITHUB_TOKEN }}`
- Для внешних интеграций - хранить токены в `Settings → Secrets and variables → Actions`
- Регулярно ротировать токены и ограничивать их права (scope)
- Для полной очистки истории использовать `git filter-branch`

#### Секрет №3: Серийные данные для тестов десериализации
| Поле | Значение |
|------|----------|
| **Файл** | `webgoat-lessons/insecure-deserialization/src/test/java/.../DeserializeTest.java` |
| **Строка** | ~70, ~85, ~100 |
| **Контекст** | `String token = "rO0ABXNyADFvcmcuZHVtbXkuaW5zZWN1cmUuZnJhbWV3b3JrLlZ1bG5lcmFibGVUYXNrSG9sZGVy..."` |

**Почему это секрет:**
- Строки `rO0ABX...` - это Java-сериализованные объекты в base64
- В данном случае это тестовые пейлоады для урока по insecure deserialization
- Хотя это учебные данные, в реальном проекте такие строки могут содержать чувствительную информацию или быть использованы для атаки

**Как должно быть:**
- Для тестов использовать моки и фикстуры вместо реальных сериализованных данных
- Если тестовые данные необходимы - генерировать их динамически в `@BeforeEach`
- Не хранить в коде примеры эксплойтов, даже для обучения; выносить в отдельную документацию с пометкой `EXAMPLE`

#### Секрет №4: Хеш пользователя в тесте
| Поле | Значение |
|------|----------|
| **Файл** | `webgoat-lessons/missing-function-ac/src/test/java/.../MissingFunctionACUsersTest.java` |
| **Строка** | ~45 |
| **Контекст** | `assertThat(displayUser.getUserHash()).isEqualTo("cplTjehjI/e5ajqTxWaXhU5NW9UotJfXj+gcbPvfWWc=")` |

**Почему это секрет:**
- Base64-строка с высокой энтропией - похоже на криптографический хеш
- В учебном контексте это тестовое значение, но в реальном проекте такие хардкоды могут раскрыть алгоритм хеширования или стать вектором для атаки на сравнение хешей

**Как должно быть:**
- Для тестов использовать генерацию ожидаемых значений на лету, а не хардкод
- Если хеш должен быть фиксированным - документировать его происхождение и пометить как `@TestOnly`
- В продакшене никогда не сравнивать хеши через `==` или `equals`, использовать `MessageDigest.isEqual()` для защиты от timing-атак

#### Секрет №5: JWT Payload в документации
| Поле | Значение |
|------|----------|
| **Файл** | `webgoat-lessons/jwt/src/main/resources/lessonPlans/en/JWT_libraries_assignment.adoc` |
| **Строка** | 10 |
| **Контекст** | `eyJzdWIiOiIxMjM0NTY3ODkwIiwidXNlciI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTUxNjIzOTAyMn0` |

**Почему это секрет:**
- Это base64-кодированный payload JWT-токена
- После декодирования видно: `"admin": true, "user": "John Doe"` - тестовые данные для урока
- В реальном проекте такие примеры могут быть использованы злоумышленником для понимания структуры токенов

**Как должно быть:**
- В документации использовать только явно помеченные примеры: `EXAMPLE_TOKEN_PLACEHOLDER`
- Не включать реальные или даже тестовые токены в файлы, которые попадают в репозиторий
- Для учебных целей выносить примеры в отдельный файл `.examples/` с `.gitkeep` и пометкой `DO NOT COMMIT REAL DATA`

### Выводы

1. truffleHog находит не только очевидные секреты - он детектирует строки с высокой энтропией, даже если это тестовые данные или документация. Это полезно, но требует ручной фильтрации ложных срабатываний.

2. История коммитов - это тоже риск. Даже если секрет удалили в последнем коммите, он остаётся в `.git/objects`. Для полной очистки нужен `BFG Repo-Cleaner`.
