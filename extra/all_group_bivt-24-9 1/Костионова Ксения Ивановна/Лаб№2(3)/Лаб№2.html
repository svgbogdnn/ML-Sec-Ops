Часть 1. Поиск CVE по уязвимостям REST API (2025 год)

1. Источники информации

CVE-2025-61757

  • Тип: API1:2023 Broken Object Level Authorization + API5:2023 Broken Function Level Authorization
  • Описание: Критическая уязвимость в REST WebServices компонента Oracle Identity Manager. Позволяет неаутентифицированному злоумышленнику выполнить произвольные команды на сервере через специально сформированный запрос к публичному API.
  • Причина: Отсутствие проверки прав доступа на уровне объекта и функции - любой запрос к REST-эндпоинту обрабатывался без верификации токена или роли пользователя.

CVE-2025-46569

  • Тип: API7:2023 Server Side Request Forgery / Injection
  • Описание: Уязвимость в Open Policy Agent, позволяющая через манипуляции с путем в HTTP-запросе к Data API внедрить Rego-код во внутренний запрос. Может привести к неверным решениям авторизации или утечке переменных окружения.
  • Причина: Небезопасная конкатенация пользовательского ввода из URL-пути в Rego-запрос без хорошей санитизации.

CVE-2025-39545

  • Тип: API5:2023 Broken Function Level Authorization (CWE-862 Missing Authorization)
  • Описание: Плагин miniOrange WordPress REST API Authentication не проверял права доступа к определенным функциям. Аутентифицированный пользователь с низкими привилегиями мог выполнять действия, предназначенные только для администраторов.
  • Причина: Функция проверки прав не валидировала роль пользователя перед выполнением чувствительной операции.

Часть 2. Практика на стенде

Скачала образ и запустила:

docker pull ket9/otus-devsecops-owasp-rest
docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest:latest

Открыла http://localhost:8080, увидела эндпоинты.

Перешла по /createdb для инициализации БД.

Ход рассуждений

  1. Посмотрела, что возвращает приложение по .../users/v1:
{"users":[{"email":"mail1@mail.com","username":"name1"},{"email":"mail2@mail.com","username":"name2"},{"email":"admin@mail.com","username":"admin"}]}

Список пользователей доступен без авторизации, хотя обычно такие данные защищают. Уязвимость.

  1. Поигралась с путями, попробовала добавить _debug - .../users/v1/_debug:
{"users":[{"admin":false,"email":"mail1@mail.com","password":"pass1","username":"name1"},{"admin":false,"email":"mail2@mail.com","password":"pass2","username":"name2"},{"admin":true,"email":"admin@mail.com","password":"pass1","username":"admin"}]}

Вау, пароли в открытом виде, поле admin, и все это без какой-либо авторизации. Уязвимость.

  1. Попробовала залогиниться по .../users/v1/login?username=name1&password=pass1:
{"status":"fail","message":"User not found"}

Повторила 7 раз с неправильными паролями - никаких блокировок, капчей. Брутфорс в чистом виде. Уязвимость.

Уязвимости

  1. Публичный доступ к списку пользователей:
  • Тип: API5:2023 Broken Function Level Authorization + API3:2023 Broken Object Property Level Authorization
  • Суть: любой неаутентифицированный пользователь может получить список всех аккаунтов с личными данными.
  • Меры: требовать авторизацию для доступа к эндпоинту, возвращать только те поля, которые действительно нужны для конкретного сценария.
  1. Debug-эндпоинт с паролями в открытом виде:
  • Тип: API8:2023 Security Misconfiguration + API3:2023 Broken Object Property Level Authorization
  • Суть: служебный путь для отладки остался включенным в продакшене и возвращает пароли и флаги администратора без какой-либо проверки прав.
  • Меры: отключать все debug-эндпоинты через переменные окружения при деплое, никогда не выводить пароли в ответах API, добавить строгую проверку роли перед доступом к чувствительным данным.
  1. Отсутствие защиты от брутфорса на логине:
  • Тип: API2:2023 Broken Authentication
  • Суть: можно бесконечно перебирать пароли без блокировок или капчи - приложение не различает человека и бота.
  • Меры: хешировать пароли, внедрить rate limiting по IP и пользователю, включать капчу после 3-5 неудачных попыток, логировать подозрительную активность.
