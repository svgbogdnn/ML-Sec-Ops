### Фрагмент кода 2:

from flask_wtf import Form  
from wtforms import TextField

class LoginForm(Form):  
username = TextField('username')  
password = TextField('password')

Недостаток состоит в том, что поле пароля объявлено с типом TextField, а не PasswordField, TextField рендерится в браузере как текстовое поле — `<input type="text">`, и пароль отображается открытым текстом при вводе. Любой человек может увидеть пароль, браузер может кешировать значения таких полей и предлагать их в автозаполнении
Нужно заменить TextField на PasswordField из того же пакета wtforms, PasswordField рендерится как `<input type="password">`, скрывая введённые символы

except Exception, e:

Недостаток в том, что в ошибочной логике блока обработки исключений, при любом исключении (ошибка валидации данных, недоступность базы данных) блок except рендерит шаблон success_create.html, то есть показывает пользователю сообщение об успешной регистрации. По сути это означает, что аккаунт не был создан, но пользователь думает, что всё прошло нормально. Помимо этого, исключение нигде не логируется, поэтому разработчик даже не узнает о проблеме
В качестве меры противодействия нужно разделить логику:
успешное создание обрабатывать внутри блока try, в блоке except показывать шаблон с ошибкой и одновременно логировать исключение для диагностики

## Часть II

### Вопрос 1. Какие наиболее распространённые атаки предотвращает Django?

Django защищает от нескольких классических типов атак
SQL-инъекции
Django ORM передаёт пользовательские данные в запрос как параметры, не конкатенирует их со строкой SQL, что исключает возможность инъекции на уровне фреймворка.

XSS (межсайтовый скриптинг)
шаблонизатор Django автоматически экранирует HTML-спецсимволы во всех переменных, которые выводятся в шаблоне. Вредоносный скрипт, введённый через форму, не будет выполнен

CSRF (подделка межсайтовых запросов)
Django включает CsrfViewMiddleware, который добавляет уникальный токен к каждой форме через тег `{% csrf_token %}`. При POST-запросе токен проверяется, и без его совпадения запрос отклоняется

Clickjacking
через XFrameOptionsMiddleware Django добавляет заголовок `X-Frame-Options: DENY`, который запрещает встраивать страницы приложения в iframe на сторонних сайтах

Host Header Injection
настройка ALLOWED_HOSTS ограничивает список допустимых доменов. Запросы с любым другим заголовком Host автоматически отклоняются

### Вопрос 2. Как устроено управление пользовательскими сессиями в Django?

Django реализует сессии через SessionMiddleware. При первом обращении пользователя создаётся уникальный session_id. Этот идентификатор отправляется клиенту в виде HTTP-куки с именем sessionid. Сами данные сессии (словарь с произвольными ключами) хранятся на стороне сервера и привязываются к этому идентификатору. При каждом следующем запросе браузер отправляет куку, Django ищет данные сессии по ключу и предоставляет их через request.session.

Django поддерживает несколько бэкендов хранения, которые задаются через настройку SESSION_ENGINE. По умолчанию данные хранятся в таблице django_session в базе данных. Также доступны хранение в кеше (Redis, Memcached), в файловой системе и в самой куке в подписанном виде (signed_cookies)
Безопасность куки сессии регулируется несколькими настройками. SESSION_COOKIE_HTTPONLY по умолчанию равен True, кука недоступна из JavaScript, что защищает от кражи сессии через XSS. SESSION_COOKIE_SECURE рекомендуется устанавливать в True в продакшне, тогда кука передаётся только по HTTPS. SESSION_COOKIE_SAMESITE со значением Lax ограничивает отправку куки с внешних сайтов, что защищает от CSRF. SESSION_COOKIE_AGE задаёт время жизни сессии, по умолчанию это две недели

При вызове logout() Django удаляет данные сессии с сервера и очищает куку в браузере. При следующем входе пользователю присваивается новый session_id, что исключает атаку session fixation (когда злоумышленник навязывает жертве заранее известный идентификатор сессии).
