ЛР 5. Недостатки в Python-коде и безопасность Django

1. Разбор фрагментов кода

Фрагмент 1

#!/usr/bin/env python3
from flask import Flask

from mod_api import mod_api

app = Flask('vuln_app')
app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

app.register_blueprint(mod_api, url_prefix='/api')

Главный недостаток тут в том, что SECRET_KEY лежит прямо в исходном коде. В Flask этот ключ используется для подписи cookie-based session, CSRF-токенов и других подписанных данных, если приложение или расширения это используют. Если код попадет в репозиторий, архив, лог CI или просто будет показан другому человеку, секрет уже нельзя считать секретом)

Что из этого может выйти: атакующий с известным SECRET_KEY может подделывать подписанные данные приложения. В зависимости от настроек это может превратиться в подделку сессии, обход CSRF-защиты или другой странный баг вокруг доверенных cookie

Как исправить:

  • убрать секрет из кода и читать его из переменной окружения
  • для локальной разработки держать значение в .env, но не коммитить этот файл
  • в production хранить секрет в secret manager или хотя бы в переменных окружения на сервере
  • если ключ уже был опубликован, сгенерировать новый и считать старые сессии скомпрометированными

Пример:

import os

app = Flask('vuln_app')
app.config['SECRET_KEY'] = os.environ['FLASK_SECRET_KEY']

Еще нормально добавить проверку при старте: если переменной нет, приложение должно падать сразу, а не стартовать с каким-нибудь дефолтным ключом

Фрагмент 2

from flask_wtf import Form
from wtforms import TextField

class LoginForm(Form):
    username = TextField('username')
    password = TextField('password')

Первое, что бросается в глаза: пароль описан как TextField. В HTML это обычное текстовое поле, символы будут видны на экране. Для пароля нужно использовать PasswordField, чтобы браузер рендерил поле как <input type="password">

Второй момент - у формы нет валидаторов. Сейчас username и password могут быть пустыми строками, слишком длинными значениями или просто мусором. Да, настоящая проверка логина все равно будет на сервере, но форма должна хотя бы отсеивать пустой ввод и ограничивать размер

Исправленный вариант:

from flask_wtf import FlaskForm
from wtforms import StringField, PasswordField
from wtforms.validators import DataRequired, Length

class LoginForm(FlaskForm):
    username = StringField('username', validators=[DataRequired(), Length(max=150)])
    password = PasswordField('password', validators=[DataRequired(), Length(max=256)])

Про CSRF тут тоже надо помнить. У FlaskForm CSRF-защита обычно включена, если настроен SECRET_KEY, но в шаблоне все равно нужно вывести hidden-поле формы, например {{ form.hidden_tag() }}. Если токен не выводится и не проверяется, логин-форма становится удобной целью для login CSRF

Фрагмент 3

def post(self):
    username = self.get_argument('username')
    password = self.get_argument('password').encode('utf-8')
    email = self.get_argument('mail')
try:
    username = username.lower()
    email = email.strip().lower()
    user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})
    user.validate()
    save_user(self.db_conn, user)
except Exception, e:
    return self.render_template("success_create.html")

Тут сразу несколько проблем

Самая серьезная: пароль просто кодируется в UTF-8 и кладется в объект пользователя. encode('utf-8') не является защитой. Это все еще исходный пароль, только в байтах. Если база утечет, пользовательские пароли сразу можно использовать

Нужно хранить не пароль, а результат password hashing с солью и нормальным алгоритмом. Например bcrypt, argon2 или готовые функции фреймворка, если проект на Django/Flask с подходящим расширением. Для проверки пароля потом сравнивается введенный пароль с хешем через специальную функцию, а не обычным ==

Примерно так:

from argon2 import PasswordHasher

ph = PasswordHasher()
password_hash = ph.hash(self.get_argument('password'))

user = User({
    'username': username,
    'password': password_hash,
    'email': email,
    'date_joined': curtime(),
})

Вторая проблема - обработка исключений. except Exception ловит вообще все: ошибку валидации, ошибку базы, баг в коде. И после этого пользователю показывается success_create.html. То есть регистрация могла не пройти, но интерфейс скажет, что все успешно. Это мешает расследованию ошибок и может ломать логику безопасности

Лучше ловить ожидаемые исключения отдельно:

try:
    user.validate()
    save_user(self.db_conn, user)
except ValidationError as e:
    return self.render_template("register.html", error="Проверьте введенные данные")
except DuplicateUserError:
    return self.render_template("register.html", error="Пользователь уже существует")
except DatabaseError:
    self.logger.exception("User create failed")
    return self.set_status(500)

return self.render_template("success_create.html")

Еще стоит жестче валидировать username и email. Приведение к нижнему регистру это не валидация. Для username нужен допустимый набор символов и ограничение длины, для email - нормальная проверка формата. Иначе в базу и шаблоны могут приехать неожиданные значения

2. Безопасность в Django

Документацию по этому разделу смотрел здесь: https://docs.djangoproject.com/en/4.2/topics/security/

Какие атаки Django помогает предотвращать

Django не делает приложение безопасным автоматически, но закрывает много типовых мест, если пользоваться стандартными механизмами

  • XSS. Шаблонизатор Django по умолчанию экранирует опасные символы в переменных, которые вставляются в HTML. Это помогает против ситуаций, когда пользователь ввел <script>, а приложение потом показывает это другим людям. Но защита работает именно при обычном выводе через шаблоны. Если разработчик ставит safe, отключает autoescape или собирает HTML руками, можно снова получить XSS
  • CSRF. В Django есть CsrfViewMiddleware и шаблонный тег {% csrf_token %}. Для небезопасных методов вроде POST middleware проверяет токен, а для HTTPS еще использует Origin/Referer-проверки. Это защищает от сценария, когда чужой сайт пытается отправить форму от имени уже залогиненного пользователя
  • SQL injection. При работе через ORM запрос и параметры отделены друг от друга. Пользовательские значения передаются как параметры, а не склеиваются в SQL-строку. Но если писать raw SQL, использовать extra() или RawSQL, ответственность снова на разработчике
  • Clickjacking. Django умеет выставлять X-Frame-Options через middleware. Тогда страницу нельзя просто так вставить во frame на чужом сайте и заставить пользователя кликнуть по невидимой кнопке.
  • Host header attacks. Django проверяет Host через настройку ALLOWED_HOSTS, если использовать request.get_host(). Это важно для защиты от поддельного host header, который может влиять на ссылки в письмах, кеширование и CSRF-сценарии

Как устроены пользовательские сессии в Django

Ссылка: https://docs.djangoproject.com/en/4.2/topics/http/sessions/

Сессии включаются через SessionMiddleware. Обычно он уже есть в MIDDLEWARE, если проект создан через django-admin startproject. После этого у каждого request появляется request.session, похожий на словарь

Типичная схема такая:

  • браузер хранит cookie с session id
  • сами данные сессии по умолчанию лежат на сервере в таблице django_session
  • Django по session id находит запись, декодирует данные и дает их view-коду как request.session

То есть при стандартном database-backed backend в cookie нет самих данных пользователя. Cookie содержит только идентификатор сессии. Это лучше, чем складывать в cookie весь профиль или права доступа

Пример работы:

request.session['user_theme'] = 'dark'
theme = request.session.get('user_theme')
del request.session['user_theme']

По умолчанию Django сохраняет сессию не на каждый запрос, а когда она была изменена. Если поменять вложенный объект внутри сессии, Django может не заметить изменение, тогда нужно явно поставить:

request.session.modified = True

Хранилище можно поменять через SESSION_ENGINE. Основные варианты:

  • database backend - стандартный вариант, данные в таблице django_session
  • cached_db - запись идет и в БД, и в cache, чтение чаще из cache
  • cache - данные только в cache, быстрее, но нужно думать о потере данных при eviction
  • file backend - хранение в файлах
  • signed cookies - данные сессии хранятся в cookie, но подписываются через SECRET_KEY

Вариант signed cookies важный: данные подписаны, но не зашифрованы. Пользователь не должен иметь возможность их подделать без SECRET_KEY, но он может их прочитать. Поэтому секретный ключ нельзя светить, а чувствительные данные лучше не класть в cookie-based session

При logout Django вызывает очистку сессии. Например django.contrib.auth.logout() использует flush(): удаляет данные текущей сессии и session cookie, чтобы старые данные нельзя было продолжать использовать из браузера

Из настроек безопасности для session cookie обычно важны:

  • SESSION_COOKIE_HTTPONLY = True, чтобы JavaScript не читал cookie
  • SESSION_COOKIE_SECURE = True на HTTPS, чтобы cookie не уходила по HTTP
  • SESSION_COOKIE_SAMESITE, чтобы снизить риск cross-site отправки cookie
  • нормальный SECRET_KEY, если используются подписанные cookie или другие механизмы подписи

Вывод по сессиям простой: Django дает готовую инфраструктуру, но безопасность зависит от настроек. Стандартная серверная сессия с HttpOnly/Secure/SameSite cookie обычно безопаснее, чем самодельная cookie с JSON и правами пользователя
