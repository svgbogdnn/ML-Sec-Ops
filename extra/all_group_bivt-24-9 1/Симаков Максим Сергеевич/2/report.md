## CVE-2025-27505 — GeoServer

GeoServer — это open-source сервер для работы с геопространственными данными, предоставляет данные через REST API.

Суть проблемы в том, что security-фильтр сервера правильно закрывал пути `/rest` и `/rest/**`, но не учитывал вариант `/rest.html`. Из-за этого злоумышленник мог обойти авторизацию, просто добавив `.html` в конец пути, и получить доступ к служебной информации: список установленных расширений, доступные маршруты, конфигурация.

Причина классическая — разработчики закрыли «очевидные» варианты пути в конфиге, но не подумали об альтернативных представлениях того же ресурса. По OWASP это **API5:2023 — Broken Function Level Authorization**.

Чтобы исправить, нужно обновить GeoServer до исправленной версии и закрывать все варианты пути сразу (`/rest.*`, `/rest/**`), а не только конкретные маршруты. Дополнительно — ограничить доступ к административному API на уровне сети.

## CVE-2024-0404 — AnythingLLM

AnythingLLM — платформа для работы с языковыми моделями. Уязвимость в эндпоинте регистрации по инвайт-коду: `POST /api/invite/:code`.

Эндпоинт принимал JSON и напрямую связывал все поля запроса с моделью пользователя без какой-либо фильтрации. То есть злоумышленник мог добавить в тело запроса поле `"role": "admin"` — и система его послушно применяла:

```
POST /api/invite/validcode
{
  "username": "attacker",
  "password": "password",
  "role": "admin"
}
```

В ответ — успешная регистрация с правами администратора. Причина в том, что не было allowlist разрешённых полей — фреймворк по умолчанию применяет всё что пришло в JSON, это удобно при разработке, но в продакшене приводит вот к этому.

По OWASP — **API3:2023 — Broken Object Property Level Authorization** (в старой редакции это называлось Mass Assignment). Лечится просто: принимать только конкретный список полей через DTO, а чувствительные поля вроде `role`, `is_admin` на публичных эндпоинтах игнорировать полностью.

## CVE-2024-36467 — Zabbix API

Zabbix — система мониторинга, уязвимость в методе `user.update` JSON-RPC API.

Аутентифицированный пользователь с доступом к этому методу мог добавить себя в административные группы пользователей — поле `usrgrps`. Сервер проверял, что пользователь вошёл в систему, но не проверял, имеет ли он право менять именно это поле. В итоге — эскалация привилегий до администратора без какого-либо взлома, просто через штатный API-метод.

По OWASP — **API5:2023 — Broken Function Level Authorization**. Причина та же что и везде: аутентификацию сделали, а гранулярный контроль «кто что именно может менять» — забыли. Патч от вендора + явный запрет изменения `usrgrps` для непривилегированных ролей на уровне бизнес-логики.

# ЧАСТЬ 2

Запустил образ:

```
docker pull ket9/otus-devsecops-owasp-rest
docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest:latest
```

Перешёл на http://localhost:8080/ — приложение сразу отдало в JSON список всех доступных эндпоинтов:

```
/createdb
/users/v1
/users/v1/_debug
/users/v1/register (POST)
/users/v1/login (POST)
/users/v1/{username}
/users/v1/{username}/email (PUT)
/users/v1/{username}/password (PUT)
/books/v1
/books/v1 (POST)
/books/v1/{book}
```

Перешёл на http://localhost:8080/createdb — база заполнена тестовыми данными.

## Первый взгляд на эндпоинты

Уже в самом списке видно кое-что интересное: есть эндпоинт `_debug`. В нормальном продакшне дебаг-маршрутов быть не должно вообще, так что начал именно с него.

## Debug-эндпоинт

```
http://localhost:8080/users/v1/_debug
```

Вернул без какого-либо токена или авторизации:

```json
{"users":[
  {"admin":false,"email":"mail1@mail.com","password":"pass1","username":"name1"},
  {"admin":false,"email":"mail2@mail.com","password":"pass2","username":"name2"},
  {"admin":true,"email":"admin@mail.com","password":"pass1","username":"admin"}
]}
```

Полный дамп всех пользователей: имена, email, пароли в открытом виде, флаг `admin`. Теперь известно всё — кто есть в системе, кто администратор и с каким паролем. Дальше можно раскручивать что угодно.

## Проверка доступа к профилям

Зная имена из предыдущего шага, попробовал получить профиль по имени пользователя:

```
http://localhost:8080/users/v1/admin
http://localhost:8080/users/v1/name1
http://localhost:8080/users/v1/name2
```

Все три вернули данные без каких-либо токенов:

```
{"username": "admin", "email": "admin@mail.com"}
{"username": "name1", "email": "mail1@mail.com"}
```

Любой желающий, зная имя пользователя, может получить его профиль. Никакой проверки «ты это ты, или нет» нет вообще.

## Список всех пользователей

```
http://localhost:8080/users/v1
```

```json
{"users":[
  {"email":"mail1@mail.com","username":"name1"},
  {"email":"mail2@mail.com","username":"name2"},
  {"email":"admin@mail.com","username":"admin"}
]}
```

Список всех пользователей с email — тоже без авторизации. Имена для следующих запросов собирать даже не надо.

## Попытка SQL-инъекции

Параметр `{username}` в URL подозрительно прямолинейный — скорее всего просто подставляется в SQL-запрос. Проверил:

```
http://localhost:8080/users/v1/' OR '1'='1
```

Вернул: `{"username": "name1", "email": "mail1@mail.com"}`

Условие `1=1` всегда истинно, поэтому вернулась первая запись из таблицы. Инъекция работает — параметр конкатенируется в SQL напрямую, плейсхолдеры не используются.

## Описание найденной уязвимости

Главная проблема — дебаг-эндпоинт `/users/v1/_debug`. Он доступен без авторизации и возвращает пароли в открытом виде. Это не просто утечка данных, это полная компрометация всей системы за один запрос.

Дополнительно обнаружены:
- BOLA на `/users/v1/{username}` — читаем чужие профили без токена
- Excessive Data Exposure на `/users/v1` — список всех пользователей без авторизации
- SQL-инъекция через параметр username в URL

## Тип уязвимости

| Что нашли | Категория OWASP API Security Top 10 2023 |
|---|---|
| Debug-эндпоинт с паролями в открытом виде | API8:2023 — Security Misconfiguration |
| Список всех пользователей без авторизации | API3:2023 — Broken Object Property Level Authorization |
| Чтение чужого профиля без токена | API1:2023 — Broken Object Level Authorization (BOLA) |
| SQL-инъекция через username | API10:2023 — Injection |

Основная и наиболее критичная — **API8:2023 Security Misconfiguration**: debug-эндпоинт вообще не должен существовать в продакшн-образе.

## Меры предотвращения

1. Убрать `/users/v1/_debug` из продакшена — такие маршруты только в dev-окружении и только за аутентификацией.
2. Никогда не возвращать пароли в API-ответах, даже хэши.
3. Перед возвратом данных пользователя проверять что запрашивающий — это либо он сам, либо администратор.
4. Использовать параметризованные запросы вместо конкатенации строк в SQL.
5. Возвращать только нужные поля — `password` и `admin` в публичных эндпоинтах не появляются никогда.
