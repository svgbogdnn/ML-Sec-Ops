### Вывод по первой части

После просмотра этих CVE я сделал вывод, что уязвимости REST API часто появляются из-за неправильной серверной логики.

В n8n проблема была в том, что сервер не проверял доступ к конкретному объекту. В weMail API доверял заголовку, который может подставить сам клиент. В XWiki не было ограничения на объем данных, который можно вернуть одним запросом.

То есть REST API нужно защищать не только от классических атак вроде инъекций. Очень важно проверять права доступа, не доверять клиентским данным и ограничивать потребление ресурсов.

## Часть II. Проверка уязвимого стенда

Во второй части я выбрал вариант с самостоятельным поиском недостатка в приложении.

```bash

docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest:latest
```

После запуска я открыл приложение в браузере:

```text
http://localhost:8080/
```

Потом заполнил базу тестовыми данными:

```text
http://localhost:8080/createdb
```

После этого я начал смотреть, какие endpoint доступны в приложении. Я решил начать с GET-запросов, потому что часто бывает так, что изменение данных защищено, а просмотр данных забывают нормально закрыть.

## Ход проверки

### 1. Проверка списка пользователей

Первым делом я попробовал открыть список пользователей:

```text
http://localhost:8080/users/v1
```

Приложение вернуло ответ:

```json
{
  "users": [
    {
      "email": "mail1@mail.com",
      "username": "name1"
    },
    {
      "email": "mail2@mail.com",
      "username": "name2"
    },
    {
      "email": "admin@mail.com",
      "username": "admin"
    }
  ]
}
```

На этом этапе мне показалось странным, что список пользователей отдается без авторизации. Я не передавал ни token, ни cookie, ни какие-то другие данные для входа. При этом API вернул не только username, но и email.

Первый вывод: endpoint публично раскрывает информацию о пользователях.

### 2. Проверка доступа к конкретному пользователю

Дальше я решил проверить, можно ли получить данные конкретного пользователя по имени. Для этого я подставил username прямо в URL:

```text
http://localhost:8080/users/v1/name1
```

Ответ был такой:

```json
{
  "username": "name1",
  "email": "mail1@mail.com"
}
```

После этого я попробовал аналогично обратиться к другим пользователям, например к `name2` и `admin`. Логика проверки была простая: если сервер просто берет username из URL и возвращает объект, то можно получить чужие данные без входа в систему.

Именно так и получилось. Данные возвращались без токена.

Вывод: приложение отдает объект пользователя по идентификатору из URL и не проверяет, можно ли текущему клиенту видеть этот объект.

### 3. Проверка связанных данных

После пользователей я посмотрел endpoint с книгами:

```text
http://localhost:8080/books/v1
```

Ответ приложения:

```json
{
  "Books": [
    {
      "book_title": "bookTitle82",
      "user": "name1"
    },
    {
      "book_title": "bookTitle98",
      "user": "name2"
    },
    {
      "book_title": "bookTitle68",
      "user": "admin"
    }
  ]
}
```

Этот ответ подтвердил, что приложение раскрывает не только пользователей, но и связанные с ними данные. По ответу можно понять, какие книги относятся к каким пользователям, включая администратора.

На этом этапе я уже сделал основной вывод: проблема похожа на отсутствие проверки прав доступа на уровне объекта.

### 4. Проверка возможности изменить данные

Чтобы понять, уязвимость только на чтение или еще и на изменение, я попробовал изменить email пользователя:

```bash
curl -X PUT "http://localhost:8080/users/v1/name1/email" \
  -H "Content-Type: application/json" \
  -d '{"email":"hacker@mail.com"}'
```

Ответ приложения:

```json
{
  "status": "fail",
  "message": "Invalid token"
}
```

Из этого я понял, что изменение данных защищено токеном. То есть просто так поменять email нельзя.

Но проблема все равно остается, потому что чтение пользовательских данных открыто. Для API это тоже уязвимость, потому что нарушается конфиденциальность.

## Найденная уязвимость

В приложении я нашел уязвимость **Broken Object Level Authorization**.

Если объяснить простыми словами, сервер получает идентификатор объекта из URL и сразу возвращает данные, но не проверяет, имеет ли текущий пользователь право видеть этот объект.

В данном случае объект — это пользователь, а идентификатор — `username`.

Пример:

```text
http://localhost:8080/users/v1/name1
```

Ответ:

```json
{
  "username": "name1",
  "email": "mail1@mail.com"
}
```

Проблема в том, что этот запрос работает без авторизации. Если можно подставить `name1`, `name2` или `admin` и получить данные, значит сервер не проверяет доступ к конкретному объекту.

---

## Тип недостатка по OWASP API Top 10

Найденная уязвимость относится к:

**API1:2023 Broken Object Level Authorization**

Почему это именно BOLA:

OWASP описывает BOLA как ситуацию, когда API принимает идентификатор объекта от клиента и не проверяет, имеет ли текущий пользователь право обращаться к этому объекту.

В моем случае идентификатор передается прямо в URL:

```text
/users/v1/name1
```

Правильная логика должна быть такой:

1. проверить, что пользователь авторизован;
2. определить пользователя по токену или сессии;
3. проверить, имеет ли он право смотреть данные `name1`;
4. только потом возвращать ответ.

В приложении этого нет: сервер просто возвращает объект.

---

## Меры предотвращения

Чтобы исправить такую проблему, я бы предложил следующие меры:

1. **Закрыть endpoint с пользовательскими данными авторизацией.**  
   `/users/v1` и `/users/v1/{username}` не должны быть доступны всем подряд.

2. **Проверять права на каждый объект.**  
   Даже если пользователь вошел в систему, сервер должен проверять, может ли он смотреть именно этот объект.

3. **Не доверять username из URL.**  
   Username можно использовать для поиска объекта, но не как доказательство права доступа.

4. **Сделать endpoint `/users/me`.**  
   Тогда сервер сам определяет пользователя по токену, а клиент не может просто подставить чужое имя.

5. **Не отдавать полный список пользователей обычному клиенту.**  
   Если список нужен администратору, он должен быть доступен только администратору.

6. **Возвращать минимум данных.**  
   Если email не нужен, его лучше не отдавать в ответе.

7. **Добавить тесты на авторизацию.**  
   Например, пользователь `name1` не должен получать данные `name2` или `admin`.

8. **Логировать перебор username.**  
   Если один клиент делает много запросов к разным пользователям, это должно считаться подозрительным поведением.

## Итоговый вывод

В ходе проверки стенда я нашел недостаток в REST API: приложение позволяет читать данные пользователей без авторизации, если знать или подобрать username.

Изменение данных защищено токеном, но чтение не защищено. Поэтому найденная проблема относится к **API1:2023 Broken Object Level Authorization**.

Главная причина уязвимости — сервер доверяет идентификатору из URL и не проверяет права доступа к конкретному объекту. Чтобы исправить проблему, нужно требовать авторизацию и проверять доступ на уровне каждого объекта.
