# ЛР 6. Поиск секретов в репозитории

Поднял одноразовый контейнер с питоном и поставил в него trufflehog как в методичке:

```bash
docker run -it -p 8080:8080 python:buster /bin/bash
pip install truffleHog
trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git | tee -a log.txt
```

Репа это WebGoat с подкинутыми секретами. trufflehog идёт по всей истории коммитов каждой ветки, считает энтропию Шеннона для base64 и hex строк длиннее 20 символов плюс гоняет регекспы. видим огромный лог мусора, бОльшая часть это ложные срабатывания на чексуммах из package-lock и на минифицированном js. Выбрал 5 разнотипных секретов, файл лога забрал из контейнера через `python -m http.server 8080`.

## 1. Хардкод GITHUB_TOKEN в релизном workflow

`.github/workflows/release.yml`, строка 75 (trufflehog помечает коммит 34f1faad от 2021-11-22):

```
env:
  GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5
```

Персональный токен доступа к гитхабу, 64 hex символа, по энтропии trufflehog его видит сразу. Через такой токен можно пушить в репу, делать релизы, ходить в api от имени владельца, то есть фактически рулить пайплайном. Что забавно, в соседнем `welcome.yml` всё сделано правильно, там стоит `${{ secrets.GITHUB_TOKEN }}`, а тут вот челы и оставили свой токен прямо текстом.

Хранить надо в Settings > Secrets репозитория и подставлять через `${{ secrets.NAME }}`. Раз токен уже в публичной истории, его считаем утёкшим, отзываем и выпускаем новый.

## 2. Приватный RSA-ключ файлом

`webgoat-server/privatekey.key`, целиком pem-блок (коммит 34f1faad, 2021-11-22):

```
-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSkAgEAAoIBAQCpuOH6AnMc/xdJ
Fo/8z5j+MTLS1yVHANOgQgAxrIczt9uS9vi9UtE0377fL0TQs5Uo97rSuS6ZJ0ac
...
-----END PRIVATE KEY-----
```

Приватный ключ в формате PKCS8, лежит отдельным файлом. Палится регекспом на `BEGIN PRIVATE KEY`. У кого этот ключ, тот может расшифровывать трафик, подписывать данные от имени сервера, по сути притвориться этим сервисом. Приватник вообще не должен попадать в гит ни в каком виде.

Такое кладут в Vault, HSM или секреты кубера, в репе максимум публичная часть. `*.key` и `*.pem` сразу в .gitignore. Этот ключ уже скомпрометирован, перевыпускать.

`webgoat-lessons/jwt/src/test/java/org/owasp/webgoat/jwt/JWTFinalEndpointTest.java`, строка 27 (коммит 82ad0a7c, 2019-09-18):

```java
private static final String TOKEN_JERRY = "eyJraWQiOiJ3ZWJnb2F0X2tleSIsImFsZyI6IkhTNTEyIn0.eyJhdWQiOiJ3ZWJnb2F0Lm9yZyIsImVtYWlsIjoiamVycnlAd2ViZ29hdC5jb20iLCJ1c2VybmFtZSI6IkplcnJ5In0.xBc5FFwaOcuxjdr_VJ16n8Jb7vScuaZulNTl66F2MWF1aBe47QsUosvbjWGORNcMPiPNwnMu1Yb0WZVNrp2ZXA";
```

Готовый подписанный JWT, зашит константой в тест. Три base64 куска через точку, энтропия высокая, trufflehog ловит. Если токен ещё валиден на сервере, им можно ходить по api как пользователь Jerry. Плюс имея целиком хедер, пейлоад и подпись (тут HS512), можно офлайн брутить секрет подписи, а зная его, подписывать любые свои токены, в том числе с правами админа.

Готовые токены в коде не держать. Для тестов генерировать на месте и подписывать заведомо тестовым ключом, а не боевым. Секрет подписи в секретах CI.

## 4. Захардкоженные пароли в исходнике

`webgoat-lessons/challenge/src/main/java/org/owasp/webgoat/challenges/SolutionConstants.java`, строки 34-36 (коммит 82ad0a7c, 2019-09-18):

```java
String PASSWORD = "!!webgoat_admin_1234!!";
String PASSWORD_TOM = "thisisasecretfortomonly";
String ADMIN_PASSWORD_LINK = "375afe1104f4a487a73823c50a9292a2";
```

Тут сразу пачка. `PASSWORD` это пароль админа прямо строкой, `PASSWORD_TOM` пароль юзера, а `ADMIN_PASSWORD_LINK` это 32 hex символа, по виду md5, рабочая ссылка для сброса пароля админа. Последнюю trufflehog цепляет по энтропии, первые две по регекспу на `PASSWORD`. Рядом даже коммент висит `//TODO should be random generated when starting the server`, то есть автор сам в курсе что так нельзя. понятненко

Пароли и секреты в код не зашивать. Генерировать при старте либо брать из переменных окружения, а пароли пользователей хранить только хешем с солью (bcrypt или argon2).

## 5. Строка подключения к базе с паролем (нашлось в истории)

`docker-compose-postgres.yml`. В текущем дереве файла уже нет, но trufflehog достаёт его из старого коммита cb227762 (2021-04-03):

```yaml
- spring.datasource.url=jdbc:postgresql://webgoat_db:5432/webgoat?user=webgoat&password=webgoat
- spring.datasource.password=webgoat
```

это уже интереснй. Кто-то закоммитил compose с логином и паролем от postgres прямо в строке подключения, потом файл удалили, но в истории коммитов креды остались и достаются за пару секунд. Пароль `webgoat` примитивный, но сам факт что строка подключения с паролем была в репе это уже утечка.

Креды БД держать в переменных окружения или секретах CI и прокидывать в контейнер при деплое, в самом compose оставлять только `${POSTGRES_PASSWORD}`. И раз пароль уже светился в истории, его надо менять, а историю чистить.

## Доп: BFG Repo-Cleaner

BFG это утилита для чистки истории гита от того, что туда попадать не должно было. По сути быстрая и удобная замена `git filter-branch`. Умеет вырезать файлы по маске (`*.key`) и менять текст во всех коммитах на `***REMOVED***`.

Нужна как раз для случая как секрет №5: из последнего коммита секрет убрали, а в истории он остался и любой trufflehog его выкопает. BFG проходит по всем коммитам и затирает. Но даже после чистки секрет всё равно считается утёкшим, потому что репу могли уже склонировать, так что менять и отзывать его всё равно надо.

```bash
bfg --replace-text passwords.txt repo.git
git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

## Доп: автоматизация поиска секретов

Да, и это нормальная практика, руками такое не масштабируется. Обычно ставят сразу в несколько мест: pre-commit хук на машине разработчика (git-secrets, gitleaks), чтобы плохой коммит вообще не ушёл, потом обязательный шаг в CI на каждый push или MR, плюс можно включить встроенный сканер гитхаба или гитлаба.

Подход правильный, но не серебряная пуля. Сканеры ловят не всё, особенно произвольные пароли без явного формата, и дают кучу ложных срабатываний (у меня пол-лога это чексуммы). И главное, если секрет уже попал в репу, никакая автоматизация не отменяет того, что его надо отзывать. Так что автосканер это хорошо, но первично, чтобы секреты вообще не лежали в коде, а брались из нормального хранилища. почти все словили
