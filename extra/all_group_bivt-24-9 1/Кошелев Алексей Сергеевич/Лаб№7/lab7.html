Отчет по лабораторной работе №7

1. Ход выполнения работы

В ходе выполнения лабораторной работы был развернут инструмент статического анализа мобильных приложений (MobSF). Сканирование производилось локально.

В качестве объекта исследования было выбрано реальное приложение Anixart (версия 8.5.2). Файл в формате .apk был загружен в веб-интерфейс MobSF для проведения SAST-анализа. По результатам сканирования приложение получило оценку безопасности 51/100 (MEDIUM RISK). Выгруженный PDF-отчет приложен к заданию, а ниже представлена выжимка основных уязвимостей и план по их митигации.

3. Основные находки (Результаты сканирования)

3.1. Опасные разрешения (App Permissions - Dangerous)

Сканер выявил 4 разрешения со статусом Dangerous, которые при неаккуратном использовании могут нарушать безопасность и приватность устройства:

Разрешение Потенциальный риск
WRITE_EXTERNAL_STORAGE Позволяет приложению изменять или удалять любые файлы на внешнем накопителе устройства.
READ_EXTERNAL_STORAGE Позволяет приложению читать любые файлы (включая фото и документы пользователя) из памяти устройства.
REQUEST_INSTALL_PACKAGES Позволяет приложению запрашивать установку других пакетов (может использоваться вредоносами для скрытой установки других APK).
POST_NOTIFICATIONS Позволяет приложению отправлять уведомления, что может быть использовано для спама или фишинга.

3.2. Сетевая безопасность (Network Security)

№ Описание уязвимости Уровень
1 Trust System Certificates: Базовая конфигурация сети настроена на доверие всем системным сертификатам. Это снижает защиту от атак Man-in-the-Middle (MitM) на устройствах, куда злоумышленник (или администратор сети) установил свой корневой сертификат. WARNING

3.3. Анализ манифеста (Manifest Analysis)

№ Описание уязвимости Уровень
1 Vulnerable OS Version (Min SDK): minSdkVersion установлен на 21 (Android 5.0). Приложение можно установить на очень старые версии ОС, имеющие множество незакрытых критических уязвимостей. HIGH
2 Cleartext Traffic Enabled: Флаг android:usesCleartextTraffic="true" разрешает передачу данных по незашифрованному протоколу HTTP для всего приложения. HIGH
3 Exported Components: Множество компонентов (MainActivity, NotificationService, GenericIdpActivity и др.) имеют флаг android:exported="true" без строгой защиты через permissions. WARNING

4. План по митигации обнаруженных рисков

На основе проведенного SAST-анализа сформирован план по устранению недостатков:

4.1. Устранение проблем манифеста и сетевого взаимодействия (High / Warning)

  1. Запрет открытого трафика (Cleartext): В AndroidManifest.xml изменить флаг на android:usesCleartextTraffic="false". Все сетевые запросы (в том числе загрузка рекламы) должны осуществляться строго по протоколу HTTPS.
  2. Изоляция компонентов (Exported): Проверить все Activity и BroadcastReceivers (особенно от Firebase и Yandex Metrica). Установить android:exported="false" там, где внешний вызов не требуется. Если компонент должен вызываться извне, защитить его кастомными разрешениями (signature level).
  3. Обновление Min SDK: Поднять минимально поддерживаемую версию Android хотя бы до API 24 (Android 7.0), а в идеале до API 29, чтобы гарантировать наличие современных встроенных механизмов безопасности ОС.

4.2. Устранение уязвимостей исходного кода (Code Analysis)

  1. Безопасный WebView (Критично): В классе com/yandex/mobile/ads/impl/c2.java (и других связанных с WebView) запретить игнорирование ошибок SSL. Необходимо удалить или переопределить метод onReceivedSslError, чтобы он отклонял соединения с невалидными сертификатами (handler.cancel()).
  2. Отказ от сырых SQL-запросов: Использовать параметризованные запросы (Prepared Statements) или ORM (например, Room), чтобы исключить возможность SQL-инъекций на стороне клиента.
  3. Усиление криптографии: - Полностью отказаться от хеш-функции MD5 в пользу SHA-256 или SHA-512.
    • Заменить использование уязвимого java.util.Random на криптографически стойкий java.security.SecureRandom.
  4. Удаление хардкода: Извлечь ключи и другие захардкоженные секреты из исходного кода. Перенести их хранение в EncryptedSharedPreferences или Android Keystore.

4.3. Оптимизация разрешений (Permissions)

  1. Сокращение разрешений: Оценить реальную необходимость разрешений REQUEST_INSTALL_PACKAGES (обычно не требуется для медиа-приложений и может стать причиной блокировки в Google Play).
  2. Storage API: Для Android 10+ (API 29+) вместо запроса полных прав READ/WRITE_EXTERNAL_STORAGE использовать Scoped Storage, что ограничит доступ приложения только к своим медиафайлам и защитит данные других приложений.
