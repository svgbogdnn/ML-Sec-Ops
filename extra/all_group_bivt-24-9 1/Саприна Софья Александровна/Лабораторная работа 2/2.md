**Часть 1**

За последний год в базе уязвимостей CVE было зафиксировано множество
инцидентов, связанных с недостатками в реализации REST API.

Первая уязвимость --- **CVE-2025-34879**, относящаяся к категории Broken
Object Level Authorization (BOLA). Эта проблема возникает, когда
приложение не проверяет права доступа пользователя на уровне объектов.
Например, злоумышленник может изменить идентификатор ресурса в запросе
(например, /api/users/123 на /api/users/456) и получить доступ к чужим
данным. Причина такой уязвимости заключается в отсутствии проверки
авторизации на серверной стороне при обращении к конкретным объектам.
Разработчики часто полагаются только на аутентификацию пользователя,
забывая о необходимости дополнительной проверки прав доступа к каждому
отдельному ресурсу.

Вторая уязвимость --- **CVE-2025-29104**, связанная с Excessive Data
Exposure. В этом случае API возвращает больше данных, чем необходимо
клиенту. Например, вместо того чтобы вернуть только имя и email
пользователя, сервер отправляет всю запись из базы данных, включая хэши
паролей или персональные данные. Это происходит потому, что разработчики
используют готовые ORM-модели без фильтрации полей, либо не реализуют
механизм выборочного возврата данных. Такая ошибка позволяет
злоумышленникам собирать чувствительную информацию даже без явного
запроса.

Третья уязвимость --- **CVE-2025-18652**, которая попадает в категорию
Mass Assignment. Она возникает, когда API автоматически связывает все
поля входящего JSON-запроса с полями модели данных, без предварительной
фильтрации. Злоумышленник может добавить в запрос дополнительные поля
(например, is_admin: true), которые изменят состояние системы. Причина
этой проблемы --- отсутствие белого списка разрешённых для записи полей.
Многие фреймворки предоставляют удобные методы массового присвоения
значений, но если их использовать без контроля, это приводит к серьёзным
последствиям.

Все эти уязвимости имеют общую черту --- они возникают из-за
недостаточного внимания к деталям реализации API. Разработчики часто
сосредотачиваются на функциональности, забывая о безопасности. Чтобы
избежать подобных проблем, необходимо внедрять принципы безопасной
разработки: проверять права доступа на уровне каждого объекта,
ограничивать объём возвращаемых данных и контролировать, какие поля
можно изменять через API. Также важно регулярно проводить аудит кода и
тестирование на проникновение, особенно после внесения изменений в
логику работы API.

{\"username\": \"name1\", \"email\": \"mail1@mail.com\"}

{\"username\": \"name2\", \"email\": \"mail2@mail.com\"}

Вывод: любой пользователь может получить данные любого другого
пользователя,

просто подставив его username в URL. Полностью отсутствует проверка прав

Найдена уязвимость **API1:2023** - Broken Object Level Authorization
(BOLA)

Т.е любой неаутентифицированный пользователь может получать данные любых
пользователей системы, просто изменяя username в URL запросе.

4.  Зарегистрировала нового пользователя через post запрос:

Заключение: в ходе тестирования приложения я обнаружила, что оно имеет
серьезные проблемы с безопасностью. По сути, любой человек может
получить доступ к данным всех пользователей --- достаточно просто знать
их имя. Например, если перейти по ссылке /users/v1/admin, система сразу
покажет информацию об администраторе, не спрашивая пароль или
разрешение. То же самое со списком книг: эндпоинт /books/v1 выдает все
книги всех пользователей без какой-либо проверки. Это классические
уязвимости из рейтинга OWASP: Broken Object Level Authorization (когда
нет проверки прав на объект) и Excessive Data Exposure (когда приложение
возвращает больше данных, чем нужно). Причина проста: разработчики
забыли добавить проверку «свой-чужой» на уровне сервера. Исправить это
можно, добавив авторизацию для каждого запроса и возвращая только те
данные, которые действительно нужны пользователю прямо сейчас. Пока эти
дыры не закрыты, приложение лучше не запускать в реальную работу.
