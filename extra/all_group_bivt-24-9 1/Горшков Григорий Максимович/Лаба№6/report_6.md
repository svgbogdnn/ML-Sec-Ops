## Ход выполнения

В работе нужно было проверить репозиторий на наличие секретов с помощью инструмента truffleHog.

Для выполнения был поднят Docker-контейнер с Python и установлен truffleHog.

```bash
docker run -d --name trufflehog-lab6 python:buster sleep 3600
docker exec trufflehog-lab6 pip install truffleHog
```

После этого был запущен скан репозитория и вывод сохранен в лог-файл.

```bash
docker exec trufflehog-lab6 bash -c "trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git | tee /log.txt"
docker cp trufflehog-lab6:/log.txt ./log.txt
```

truffleHog анализирует не только текущее состояние файлов, но и историю коммитов. Поэтому лог получился большим: инструмент проходит по diff'ам, ищет строки с высокой энтропией и совпадения по регулярным выражениям.

Большая часть срабатываний оказалась ложной. Например, были найдены строки из минифицированных JavaScript-файлов и хеши из файлов зависимостей. Такие значения похожи на секреты из-за высокой энтропии, но сами по себе не являются учетными данными.

Для отчета были отобраны 5 разных по типу находок: токен GitHub, приватный ключ, зашифрованные секреты Travis CI, пароль в коде и JWT-токен.

## Найденные секреты

### 1. Токен GitHub в релизном пайплайне

Файл/строка: `.github/workflows/release.yml`, строка с переменной `GITHUB_TOKEN`.

```
GITHUB_TOKEN: cee3257f0e59...<замаскировано>...d4894a5
```

Это похоже на токен доступа к GitHub. Такой токен может использоваться для создания релизов, публикации артефактов или выполнения действий от имени пользователя/репозитория. Даже если позже токен заменили на `${{ secrets.GITHUB_TOKEN }}`, в истории коммитов он все равно остается доступным.

Правильный способ хранения: токены GitHub нужно хранить в секретах CI/CD, например в GitHub Actions Secrets, и подставлять через `${{ secrets.NAME }}`. Если токен уже попал в репозиторий, его нужно отозвать и выпустить новый.

### 2. Приватный ключ

Файл/строка: `webgoat-server/privatekey.key`, начало PEM-блока приватного ключа.

```
-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSk...
...
-----END PRIVATE KEY-----
```

Это приватный ключ в формате PEM. Приватные ключи используются для подписи, расшифровки данных или работы TLS/SSL. Если такой ключ попадет к постороннему, злоумышленник может попытаться выдать себя за сервер или расшифровать трафик при определенных условиях.

Правильный способ хранения: приватные ключи нельзя хранить в Git-репозитории. Их нужно размещать в защищенном хранилище секретов: HashiCorp Vault, Kubernetes Secrets, AWS Secrets Manager, GitLab CI/CD Variables или аналогичных решениях. При утечке ключ необходимо отозвать, сертификат перевыпустить, а историю Git очистить.


Это зашифрованные переменные Travis CI. Формально они не лежат в открытом виде, но внутри могут находиться реальные учетные данные: токен GitHub для релизов, логин и пароль Docker Hub, Slack webhook или другие ключи интеграций. Такие значения привязаны к CI/CD-окружению и при компрометации конфигурации могут стать риском.

Правильный способ хранения: секреты должны храниться во встроенном механизме секретов используемой CI/CD-системы. Если проект переехал с Travis CI на GitHub Actions или другую платформу, старые секреты нужно отозвать, удалить из конфигурации и завести новые значения в актуальной системе.

### 4. Пароль прямо в коде

Файл/строка: `webgoat-lessons/password-reset/src/main/java/org/owasp/webgoat/password_reset/ResetLinkAssignment.java`, строки с `PASSWORD_TOM_9` и `TOM_EMAIL`.

```java
static final String PASSWORD_TOM_9 = "somethingVeryRandomWhichNoOneWillEverTypeInAsPasswordForTom";
static final String TOM_EMAIL = "tom@webgoat-cloud.org";
```

Здесь пароль пользователя записан прямо в исходном коде в виде константы. Любой человек с доступом к репозиторию может увидеть это значение. В учебном проекте это может быть частью задания, но в реальном приложении такой подход является утечкой учетных данных.

Правильный способ хранения: пароли нельзя хранить в коде. Для тестовых сценариев значения нужно выносить в переменные окружения или секреты CI/CD. Пароли реальных пользователей должны храниться в базе данных только в виде стойкого хеша с солью, например bcrypt, Argon2 или PBKDF2.

Файл/строка: `webgoat-lessons/jwt/src/test/java/org/owasp/webgoat/jwt/JWTFinalEndpointTest.java`, строка с константой `TOKEN_JERRY`.

```java

```

Это JWT-токен. Если он валиден для приложения, его можно использовать для обращения к API от имени соответствующего пользователя. Кроме того, наличие готового токена в коде может помочь злоумышленнику анализировать структуру токена и пытаться подобрать секрет подписи.

Правильный способ хранения: готовые JWT-токены не следует хранить в репозитории. В тестах их лучше генерировать динамически во время выполнения теста и подписывать тестовым ключом. Секрет подписи JWT должен храниться в секретах CI/CD или в отдельном защищенном хранилище.

## Дополнительные вопросы

### Что такое BFG Repo-Cleaner

BFG Repo-Cleaner — это утилита для очистки истории Git-репозитория. Она используется, когда в историю коммитов попали большие файлы, пароли, токены, приватные ключи или другие чувствительные данные.

Если просто удалить секрет из последнего коммита, он все равно останется в старых коммитах. BFG позволяет переписать историю и заменить найденные секреты на маркер вроде `***REMOVED***`.

При этом важно понимать, что очистка истории не отменяет сам факт утечки. Если секрет уже был опубликован в репозитории, его нужно считать скомпрометированным. Поэтому сначала необходимо отозвать или заменить секрет, а уже потом очищать историю Git.

### Можно ли автоматизировать поиск секретов и насколько это правильный подход

Да, поиск секретов можно автоматизировать, и это правильный подход для DevSecOps.

Обычно автоматизацию делают на нескольких уровнях:

1. pre-commit hook — проверка до попадания изменений в Git;
2. CI/CD pipeline — обязательный этап проверки при push или pull request;
3. регулярное сканирование репозитория и истории коммитов;
4. использование встроенных механизмов платформы, например GitHub secret scanning или аналогов в GitLab.

Автоматизация полезна, потому что разработчик может случайно закоммитить секрет, а сканер способен остановить такую ошибку до попадания в основную ветку. Но автоматизация не является полной заменой правильной архитектуры хранения секретов. Возможны ложные срабатывания, а некоторые произвольные пароли могут не распознаваться автоматически.

Поэтому правильный подход — сочетать автоматический поиск секретов с хранением секретов в специализированных хранилищах, контролем доступа, ротацией ключей и обучением разработчиков.
