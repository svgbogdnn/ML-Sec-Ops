Отчет по домашнему заданию: симуляция XSS-атаки

Дата выполнения: 30.04.2026

Часть I. Поиск CVE за 2021 год

Методика:
- В качестве основной базы использовалась NVD.
- Поиск выполнялся по ключевым словам `php xss`. В документации NVD указано, что несколько слов в `keywordSearch` работают как AND, то есть в описание должны попасть оба слова.
- Для подсчета я выгрузил записи NVD по `keywordSearch=php xss`, затем отфильтровал идентификаторы, начинающиеся с `CVE-2021-`.

Результат:
- Найдено 18 CVE с идентификаторами `CVE-2021-*`, в описании которых встречаются `php` и `xss`.
- Список: CVE-2021-26303, CVE-2021-26304, CVE-2021-26938, CVE-2021-29625, CVE-2021-30134, CVE-2021-32696, CVE-2021-35438, CVE-2021-38143, CVE-2021-39201, CVE-2021-39202, CVE-2021-39249, CVE-2021-40541, CVE-2021-41236, CVE-2021-43698, CVE-2021-44911, CVE-2021-44912, CVE-2021-46426, CVE-2021-46709.
- Дополнительно: если считать не по году в идентификаторе CVE, а по дате публикации записи в NVD за календарный 2021 год, то по тому же запросу получается 12 записей.

Пример 1: CVE-2021-29625, Adminer

Adminer - это open-source средство администрирования баз данных, распространяемое как один PHP-файл. Компонент используется для подключения к СУБД и управления ими через веб-интерфейс: выбор и создание баз данных, просмотр таблиц, индексов и внешних ключей, изменение структуры таблиц, выполнение SQL-запросов, экспорт данных, управление пользователями и правами. Уязвимость CVE-2021-29625 описывает XSS в Adminer 4.6.1-4.8.0; она затрагивала пользователей MySQL, MariaDB, PgSQL и SQLite при определенных условиях, была закрыта в 4.8.1.

Пример 2: CVE-2021-39201, WordPress

WordPress - это свободная CMS, написанная на PHP и обычно работающая с MySQL или MariaDB. Компонент используется для публикации и управления сайтами: записи, страницы, медиа, темы, плагины, пользователи и редактор контента. Уязвимость CVE-2021-39201 позволяла аутентифицированному пользователю с низкими правами, например contributor/author, выполнить XSS в редакторе, обходя ограничение на `unfiltered_html`. Исправление вошло в WordPress 5.8 и минорные обновления старых веток.

Часть II. Практическая проверка XSS на стенде

Подготовка стенда:
- Выполнена команда `docker pull ket9/otus-devsecops-xss`.
- Порт `8080` уже был занят другим контейнером, `8081` тоже был занят, поэтому лабораторный образ был запущен на свободном порту `18080`:
  `docker run -d -p 18080:80 --name otus-devsecops-xss-lab-18080 ket9/otus-devsecops-xss:latest`.
- Страница открывалась по адресу `http://localhost:18080/XSS-1/`.

Ход рассуждений и проверки:

1. При открытии главной страницы приложение показало ссылку `XSS-1`.
2. На странице `XSS-1` была форма комментария:
   `input name="comment"`, отправка методом POST на `index.php`.
3. Сначала был отправлен безопасный тестовый комментарий `hello-test`.
4. В ответ приложение вернуло HTML, где `hello-test` был вставлен в страницу как содержимое комментария. Это показало, что пользовательский ввод выводится обратно в HTML.
5. Затем был отправлен учебный payload:
   `<script>document.body.insertAdjacentHTML("beforeend","<div id=xss-proof>XSS_JS_EXECUTED</div>");console.log("XSS_JS_EXECUTED");</script>`
6. В ответе приложения payload появился как настоящий тег `<script>`, а не как текст `&lt;script&gt;...`.
7. После загрузки страницы через headless Chrome итоговый DOM содержал строку:
   `<div id="xss-proof">XSS_JS_EXECUTED</div>`
8. Этот `div` добавлялся JavaScript-кодом из payload. Значит, скрипт выполнился в контексте браузера клиента.

Вывод:
- Найдена хранимая XSS-уязвимость, то есть Stored/Persistent XSS.
- Класс уязвимости: CWE-79, Improper Neutralization of Input During Web Page Generation.
- Причина: приложение сохраняет комментарий и затем выводит его в HTML без контекстного экранирования.

Меры предотвращения

1. Экранирование при выводе в HTML-контекст.
   Комментарий должен выводиться как текст, а не как HTML. Для PHP при выводе между тегами нужно использовать:
   `htmlspecialchars($comment, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8')`.
   В первую очередь нужно кодировать символы, меняющие структуру HTML:
   - `&` -> `&amp;`
   - `<` -> `&lt;`
   - `>` -> `&gt;`
   - `"` -> `&quot;`
   - `'` -> `&#039;` или `&#x27;`

2. Контекстное экранирование.
   Нельзя использовать одно и то же правило для всех мест вывода. Если данные попадают:
   - в HTML-текст - HTML entity encoding;
   - в HTML-атрибут - attribute encoding и обязательные кавычки вокруг значения;
   - в URL-параметр - percent encoding через `rawurlencode`/`urlencode`, затем attribute encoding при вставке в `href`;
   - в JavaScript-строку - JS string encoding; лучше вообще не вставлять пользовательские данные в inline JS;
   - в CSS - CSS encoding или отказ от пользовательского CSS.

3. Валидация входных данных.
   Для комментария можно ограничить длину, кодировку и набор допустимых символов. Например, разрешить буквы, цифры, пробелы, переносы строк и обычную пунктуацию, но не принимать управляющие символы и NUL. Важно: валидация не заменяет экранирование вывода, а только уменьшает риск и мусор во входных данных.

4. Если нужен форматированный HTML.
   Нельзя просто разрешать произвольный HTML от пользователя. Нужно использовать HTML sanitizer с allowlist-подходом. Разрешать только безопасные теги вроде `b`, `i`, `strong`, `em`, `p`, `ul`, `ol`, `li`, `br`, `a` с проверенными атрибутами. Запрещать:
   - `script`, `iframe`, `object`, `embed`, `svg`, `math`;
   - любые атрибуты `on*`: `onclick`, `onerror`, `onload`, `onmouseover` и т.п.;
   - URL-схемы `javascript:`, опасные `data:` и другие нестандартные схемы;
   - inline style, если нет отдельного безопасного CSS sanitizer.

5. Content Security Policy.
   Настроить CSP как дополнительный барьер, например запретить inline-скрипты и разрешать скрипты только с собственного домена или по nonce/hash. CSP не должна быть единственной защитой, но она снижает ущерб, если где-то пропущено экранирование.

6. Защита cookie и сессий.
   Для сессионных cookie включить `HttpOnly`, `Secure` и `SameSite`, чтобы XSS не мог напрямую прочитать cookie через `document.cookie` и чтобы снизить риск связанных атак.

7. Тесты.
   Добавить регрессионные тесты на вывод комментариев с payload вроде `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, кавычками, угловыми скобками и амперсандом. Ожидаемый результат: эти строки отображаются как текст, а не исполняются браузером.
