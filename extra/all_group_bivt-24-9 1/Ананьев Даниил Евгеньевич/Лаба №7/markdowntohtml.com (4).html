Ход выполнения

В работе нужно было поднять mobsf, отсканировать любое мобильное приложение, разобрать основные находки и составить план по митигации.

Mobsf я развернул через докер, это самый простой способ из всех вариантов в задании.

docker run -d --name mobsf-lab7 -p 8000:8000 opensecurity/mobile-security-framework-mobsf:latest

После старта контейнер слушает на localhost:8000. Из логов забрал rest api ключ, который mobsf генерирует при первом запуске.

В качестве приложения для скана я взял vlc для андроид версии 3.7.0. Это реальное и довольно большое приложение, около 48 мб, с нативным кодом, доступом к сети и куче медиа. Сам apk скачал с официального зеркала.

curl -sL "https://get.videolan.org/vlc-android/last/VLC-Android-3.7.0-arm64-v8a.apk" -o VLC-Android.apk

Дальше через rest api загрузил apk в mobsf и запустил скан.

curl -F "file=@VLC-Android.apk" http://localhost:8000/api/v1/upload -H "Authorization: $API_KEY"
curl -X POST -d "hash=$HASH&scan_type=apk&file_name=VLC-Android.apk" http://localhost:8000/api/v1/scan -H "Authorization: $API_KEY"

Pdf отчет забрал через эндпоинт /api/v1/download_pdf. Сам отчет лежит рядом с этим файлом, называется mobsf_report.pdf.

Основные находки

Опасные разрешения (статус dangerous)

Mobsf нашел 12 разрешений со статусом dangerous. Самые важные из них.

  • READ_LOGS - чтение системных логов. Через это можно потенциально достать чувствительные данные других приложений.
  • MANAGE_EXTERNAL_STORAGE - полный доступ ко всему внешнему хранилищу.
  • WRITE_SETTINGS - изменение глобальных настроек системы.
  • WRITE_EXTERNAL_STORAGE и READ_EXTERNAL_STORAGE - чтение и запись на внешнюю память.
  • RECORD_AUDIO - запись звука с микрофона.
  • SYSTEM_ALERT_WINDOW - возможность рисовать поверх других приложений, типичный вектор для оверлей атак.
  • READ_MEDIA_AUDIO, READ_MEDIA_VIDEO, READ_MEDIA_IMAGES - доступ к медиа на устройстве.
  • BLUETOOTH_CONNECT - подключение к спаренным устройствам.
  • POST_NOTIFICATIONS - показ уведомлений.

Для медиа плеера часть из них логична, но READ_LOGS, WRITE_SETTINGS и SYSTEM_ALERT_WINDOW выглядят избыточными.

Анализ network security

В этой части mobsf не нашел ни одной проблемы. У vlc есть свой network_security_config.xml, и в нем все настроено нормально, без разрешения cleartext трафика на уровне конфига.

Но интересный момент в том, что при этом в самом манифесте флаг usesCleartextTraffic=true, что в манифест анализе подсветилось как high. То есть конфликт между манифестом и сетевой конфигурацией.

Анализ manifest

Здесь mobsf нашел 29 проблем, из них 2 уровня high и 27 уровня warning.

High находки.

  1. App can be installed on a vulnerable unpatched Android version. Min sdk у приложения равен 17, это андроид 4.2. На таких старых версиях много непропатченных уязвимостей.

  2. Clear text traffic is Enabled For App [android:usesCleartextTraffic=true]. В манифесте разрешен открытый http трафик. Даже несмотря на то что в network security config все нормально, наличие этого флага сигнализирует, что какие-то части приложения могут ходить по http без шифрования.

Warning находки в основном про экспортированные компоненты. Куча активити, сервисов, провайдеров и резиверов помечены как exported или доступны другим приложениям без явной защиты permission. Сюда попали MainActivity, VideoPlayerActivity, PlaybackService, FileProvider, ArtworkProvider, RemoteAccessService и еще несколько. Плюс несколько активити с launch mode singleTask или singleInstance, что тоже считается небезопасным.

Отдельно есть warning по сертификату подписи приложения, оно подписано по v1 схеме, а это известная janus уязвимость на старых андроидах. И high про то, что для подписи использован SHA1withRSA, а SHA1 считается устаревшим из-за коллизий.

Анализ кода

Здесь mobsf нашел 1 high находку и 7 warning.

High.

  1. android_world_readable в org/videolan/vlc/gui/video/benchmark/StartActivityOnCrash.java. Файл или sharedpreference сделан world readable, то есть любое приложение на устройстве может его прочитать.

Warning.

  • android_ip_disclosure в зависимостях ktor, в коде встречаются ip адреса.
  • android_read_write_external в коде медиатеки, чтение и запись на внешнее хранилище без проверки. Любое приложение тоже может туда писать.
  • android_temp_file в зависимостях ktor и netty, создаются временные файлы, в которые потенциально могут попасть чувствительные данные.
  • android_insecure_random в netty, используется небезопасный генератор случайных чисел.
  • android_hardcoded в ktor, в коде есть строки, похожие на захардкоженные пароли или ключи.
  • android_sha1 в ktor, использование SHA1 как хеша.
  • android_md5 в ktor и netty, использование md5 как хеша.

Отдельно mobsf отметил как good то, что в приложении используется ssl pinning через ktor.

Анализ бинарей

Из 8 нативных библиотек одна, libc++_shared.so, имеет high находку по тому что в ней не включен стек канарей. Также у нескольких библиотек warning по отсутствию fortify функций и не stripped символам.

План по митигации

Расписываю по каждой из найденных проблем что бы я предложил сделать.

1. Опасные разрешения

  • Пересмотреть список разрешений. READ_LOGS, WRITE_SETTINGS и SYSTEM_ALERT_WINDOW для медиаплеера выглядят лишними и их надо постараться убрать.
  • Если разрешение реально нужно, запрашивать его только в момент использования соответствующей функции, а не сразу при старте приложения.
  • Для доступа к медиа на новых андроидах использовать гранулярные разрешения READ_MEDIA_* вместо общего READ_EXTERNAL_STORAGE.

2. Min SDK 17

  • Поднять min sdk хотя бы до 24 (андроид 7.0). На таких устройствах уже работают современные механизмы безопасности типа improved permissions и более жесткая работа с tls.
  • Объяснять пользователям, что поддержка очень старых устройств снимается из-за безопасности.

3. Cleartext traffic в манифесте

  • Убрать android:usesCleartextTraffic="true" из манифеста. Если открытый http действительно нужен для каких-то локальных кейсов, перечислить домены в network security config с cleartextTrafficPermitted="true", а не на уровне всего приложения.

4. Экспортированные компоненты

  • Пройти по всем активити, сервисам, броадкаст резиверам и контент провайдерам. Если они не должны быть доступны другим приложениям, явно проставить exported="false".
  • Если экспорт нужен, защитить его через android:permission с собственным разрешением signature уровня.
  • Для контент провайдеров вроде FileProvider дополнительно проверить, что доступ ограничен через grantUriPermissions.

5. Launch mode singleTask и singleInstance

  • Использовать standard или singleTop где это возможно. singleTask и singleInstance стоит оставить только там где это реально нужно для специфики приложения.

6. Подпись apk

  • Перевыпустить подпись приложения с использованием SHA256 или сильнее. SHA1 уже считается слабым.
  • Включить подпись по схемам v2 или v3, не оставлять только v1, чтобы исключить риск janus уязвимости на старых андроидах.

7. World readable файл (android_world_readable)

  • В StartActivityOnCrash.java найти место где создается world readable файл или sharedpreference и убрать этот режим. По умолчанию для sharedpreferences надо использовать MODE_PRIVATE.
  • Если данные нужно расшарить с другим приложением, использовать content provider с правами доступа, а не world readable файл.

8. Чтение и запись на внешнее хранилище

  • По возможности переехать на scoped storage и приватную папку приложения.
  • Чувствительные данные вообще не класть на внешнее хранилище, потому что туда имеет доступ любое другое приложение с соответствующим разрешением.

9. Слабые хеши (md5 и sha1)

  • Заменить md5 и sha1 на современные хеши, как минимум SHA-256.
  • Если хеш используется только для контрольной суммы и не для безопасности, оставить как есть, но проверить что эти места действительно не критичны.

10. Insecure random

  • Заменить Random на SecureRandom во всех местах где случайные числа используются для криптографии, токенов, ключей, временных файлов и идентификаторов сессий.

11. Хардкод чувствительных данных

  • Найти что именно нашлось как хардкод. Если это реальные ключи или пароли, вынести их в gradle ресурсы из secrets файла или подгружать с сервера. В репозитории их не хранить.
  • Использовать android keystore для хранения ключей, чувствительных к приложению.

12. Временные файлы

  • Создавать временные файлы только в приватной директории приложения через Context.getCacheDir().
  • Удалять временные файлы сразу после использования.
  • Не писать в них чувствительные данные.

13. Зависимости

  • Большая часть проблем в коде нашлась в зависимостях ktor и netty. Это значит, что напрямую vlc эти проблемы не пишет, но тащит их через библиотеки. Имеет смысл регулярно обновлять зависимости и смотреть в их changelog, чинят ли там подобные вещи.

14. Нативные библиотеки

  • Для libc++_shared.so включить стек канарей через флаг компилятора -fstack-protector-all.
  • Для библиотек где не включен fortify включить через -D_FORTIFY_SOURCE=2.
  • Не забыть стрипать символы перед релизом, чтобы не оставлять подсказки реверсерам.

Вывод

С помощью mobsf удалось получить полный отчет по apk файлу vlc для андроид. Большая часть критических находок не очень страшная для конкретно этого приложения, потому что vlc медиаплеер, а не банковский клиент. Но даже у такого приложения нашлись реальные проблемы, например cleartext traffic в манифесте, world readable файл, использование слабых хешей и подпись по sha1.

Mobsf удобен тем, что покрывает сразу несколько уровней анализа, от разрешений и манифеста до нативных бинарей. И его легко добавить в пайплайн сициди, например через api прогонять каждую новую сборку. План по митигации в основном сводится к стандартным практикам безопасной разработки под андроид, минимум разрешений, нет cleartext, нет экспортированных компонентов без защиты, нормальные хеши и подпись и приватные файлы вместо world readable.
