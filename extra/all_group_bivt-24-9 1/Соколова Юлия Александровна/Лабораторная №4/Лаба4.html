Часть I. CVE за 2021 год с XSS в PHP-компонентах

Когда я начала искать CVE с XSS в PHP-компонентах за 2021 год, честно говоря, не ожидала, что их окажется так много. Казалось бы, XSS — уязвимость давно известная и хорошо задокументированная, но даже в 2021 году она встречается в самых разных местах: от популярных CMS до отдельных плагинов.

Источники

  1. NVD — база уязвимостей: nvd.nist.gov/vuln/search
  2. CVE-2021-29447 (Symfony / Twig): nvd.nist.gov/vuln/detail/CVE-2021-29447
  3. CVE-2021-24307 (WordPress Responsive Menu): nvd.nist.gov/vuln/detail/CVE-2021-24307
  4. Symfony Twig: symfony.com/doc/current/templates.html
  5. WordPress Responsive Menu: wordpress.org/plugins/responsive-menu

CVE-2021-29447 (Symfony / Twig)

Назначение компонента: Symfony — один из самых популярных PHP-фреймворков для разработки веб-приложений. Компонент Twig — это встроенный шаблонизатор Symfony, который отвечает за генерацию HTML-страниц и отображение данных пользователю. Twig используется повсеместно: от вывода текста на странице до формирования писем и API-ответов.

Описание уязвимости: Уязвимость связана с некорректной обработкой пользовательского ввода в шаблонах Twig — данные, полученные от пользователя, выводятся в HTML без надлежащего экранирования. Это позволяет внедрить произвольный JavaScript-код, который выполнится в браузере другого пользователя.

Причина: отсутствие корректного экранирования пользовательского ввода при выводе в HTML.

Последствия:

  • выполнение произвольного JavaScript-кода в браузере пользователя
  • кража cookie и сессионных токенов
  • выполнение действий от имени жертвы

CVE-2021-24307 (WordPress — плагин Responsive Menu)

Назначение компонента: Responsive Menu — плагин для WordPress, предназначенный для создания адаптивного навигационного меню сайта. Он позволяет владельцам сайтов настраивать внешний вид и поведение меню для мобильных устройств через административную панель. Плагин активно использовался на сотнях тысяч сайтов на момент обнаружения уязвимости.

Описание уязвимости: Уязвимость возникает из-за недостаточной фильтрации входных данных в административной панели плагина. Пользователь с правами администратора (или злоумышленник, получивший к ней доступ) может сохранить вредоносный JavaScript-код в настройках меню. При загрузке страницы сайта этот код выполнится в браузере посетителя.

Причина: отсутствие фильтрации и экранирования пользовательского ввода при сохранении настроек плагина.

Последствия:

  • внедрение вредоносного JavaScript на страницы сайта
  • перехват пользовательских сессий
  • выполнение действий от имени посетителей сайта

Общее количество CVE за 2021 год

Для подсчёта я воспользовалась поиском в базе NVD с фильтром по году публикации: pubStartDate=2021-01-01 и pubEndDate=2021-12-31.

По результатам поиска, в 2021 году было зарегистрировано 21 957 уязвимостей.

Источник: nvd.nist.gov/vuln/search

Это число меня впечатлило — почти 22 тысячи CVE за один год. И это только официально зарегистрированные. Среди них XSS в PHP-компонентах встречается десятки раз, что лишний раз подтверждает: уязвимость хорошо известна, но всё равно продолжает появляться снова и снова.

Часть II. XSS-атака на уязвимый стенд

После запуска образа командой docker run -d -p 8080:80 ket9/otus-devsecops-xss:latest я зашла на http://localhost:8080/ и начала изучать приложение.

Шаг 1. Осмотр приложения

На главной странице обнаружила простое приложение с полем для ввода комментария и кнопкой «Save Data». Никакого описания, никаких подсказок — просто форма. Первая мысль: если ввод пользователя сохраняется и потом отображается на странице, это классическое место для проверки на XSS.

Шаг 2. Проверка — как приложение обрабатывает обычный текст

Сначала ввела обычный текст, чтобы понять, как вообще работает форма:

Привет, это тестовый комментарий

После нажатия «Save Data» и обновления страницы текст отобразился как есть. Приложение сохраняет введённое и показывает его при загрузке — значит, это именно тот сценарий, где может сработать хранимый XSS.

Шаг 3. Первая попытка — базовый XSS-пейлоад

Попробовала самый простой и классический вариант:

<script>alert('XSS')</script>

Нажала «Save Data», обновила страницу — и сразу появилось всплывающее окно с текстом XSS. Браузер выполнил JavaScript-код. Это означает, что приложение вставляет ввод пользователя напрямую в HTML без какого-либо экранирования.

Шаг 4. Проверка через атрибут события — альтернативный вектор

Чтобы убедиться, что уязвимость не ограничивается только тегом <script>, попробовала другой вариант через HTML-атрибут:

<img src=x onerror="alert('XSS через onerror')">

Результат тот же — при загрузке страницы браузер попытался загрузить несуществующее изображение и выполнил код в обработчике onerror. Всплывающее окно снова появилось.

Шаг 5. Имитация кражи cookie

Убедившись, что JavaScript выполняется, решила проверить более реалистичный сценарий — имитацию кражи сессионных данных:

<script>alert('Cookie: ' + document.cookie)</script>

Скрипт выполнился и вывел содержимое cookie текущего пользователя. В реальной атаке вместо alert злоумышленник отправил бы эти данные на свой сервер через fetch или XMLHttpRequest.

Тип уязвимости

Обнаруженная уязвимость — хранимый XSS (Stored XSS), также называемый персистентным.

В отличие от отражённого XSS, где вредоносный код передаётся в URL и исполняется только у того, кто перешёл по ссылке, хранимый XSS сохраняется на сервере и выполняется у каждого пользователя, который откроет заражённую страницу. Это делает его значительно опаснее.

Приложение не проверяет и не экранирует введённые данные — пользовательский ввод вставляется в HTML напрямую, как есть.

Меры предотвращения

Основная проблема — данные от пользователя попадают в HTML без обработки. Чтобы это исправить, нужно действовать на нескольких уровнях:

1. Экранирование специальных символов при выводе

Все данные, которые выводятся в HTML, должны проходить через экранирование. Опасные символы и их замены:

  • < → &lt;
  • > → &gt;
  • " → &quot;
  • ' → &#x27;
  • & → &amp;

В PHP для этого используется функция htmlspecialchars():

echo htmlspecialchars($userInput, ENT_QUOTES, 'UTF-8');

2. Валидация входных данных

Помимо экранирования при выводе, стоит проверять данные на входе — например, ограничивать длину, разрешать только ожидаемые символы там, где это возможно (для поля «имя» нет смысла принимать угловые скобки).

3. Content Security Policy (CSP)

CSP — это HTTP-заголовок, который указывает браузеру, откуда разрешено загружать скрипты. Правильно настроенный CSP не позволит выполнить инлайн-скрипт, даже если злоумышленник сумел его внедрить:

Content-Security-Policy: default-src 'self'; script-src 'self'

4. Флаги на cookie

Чтобы JavaScript не мог получить доступ к сессионным cookie даже при успешном XSS, нужно устанавливать флаг HttpOnly:

Set-Cookie: session=...; HttpOnly; Secure

5. Не использовать опасные функции

В PHP и JavaScript существуют функции, которые вставляют данные напрямую в DOM или HTML без экранирования: innerHTML, document.write(), eval(). Их использования с пользовательским вводом следует избегать.

Вывод

В ходе работы я нашла два реальных CVE 2021 года с XSS в PHP-компонентах и на практике провела хранимую XSS-атаку на уязвимом стенде. Самым показательным оказалось то, что уязвимость эксплуатируется буквально одной строчкой — и никаких специальных инструментов не нужно. Достаточно того, что разработчик не добавил htmlspecialchars().
