#### Секрет 3 - **CSR** **(Certificate** **Signing** **Request)**

**Расположение:** webgoat-server/certificatesigningrequest.csr, коммит 34f1faad

**Найденное** **значение:**
  -----BEGIN CERTIFICATE REQUEST-----
  MIIC4zCCAcsCAQAwdDELMAkGA1UEBhMCNDQ...

**Почему** **секрет:** CSR содержит публичный ключ и данные организации. Сам по себе менее критичен, чем приватный ключ, но его наличие в репозитории вместе с privatekey.key подтверждает, что пара ключей скомпрометирована. Утечка CSR даёт атакующему информацию о структуре PKI организации.


**Правильный** **способ** **хранения:** CSR генерируют, отправляют в CA и немедленно удаляют из рабочего каталога. В репозитории не хранят никогда.

#### Дополнительно
**BFG Repo-Cleaner** - это утилита для удаления чувствительных данных из истории репозитория. Работает быстрее стандартного git filter-branch, потому что заточена под вырезать файлы или строки из всех коммитов сразу.

Нужна она, когда секрет уже закоммичен. Просто удалить файл и сделать новый коммит не поможет: данные останутся в истории и будут доступны через git log или git show. BFG переписывает историю, стирая нужные данные из всех коммитов ретроспективно.
 
Минус в том, что после такой чистки хэши всех затронутых коммитов меняются, и приходится делать git push --force. Это ломает историю у всех, кто уже склонировал репозиторий.

Что касается автоматизации — truffleHog и похожие инструменты (gitleaks, detect-secrets) можно запускать прямо в CI/CD пайплайне или через pre-commit хуки. Тогда каждый коммит или pull request будет автоматически проверяться на наличие секретов ещё до того, как код попадёт в основную ветку.

Это правильный подход, потому что стоимость ошибки до мержа мала: просто не пропускаем коммит. А стоимость после - отзыв токена, чистка истории через BFG, уведомление команды, потенциальный инцидент безопасности.
