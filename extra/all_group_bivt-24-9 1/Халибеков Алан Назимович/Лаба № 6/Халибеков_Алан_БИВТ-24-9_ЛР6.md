## ход выполнения

по заданию нужно было проверить git репозиторий на случайно оставленные секреты. для этого я использовал truffleHog, потому что он смотрит не только текущие файлы, но и историю комитов.

запускал все в контейнере с python:

```bash
docker run -d --name trufflehog-lab6 python:buster sleep 3600
docker exec trufflehog-lab6 pip install truffleHog
```

после установки запустил проверку репозитория из задания и сохранил лог:

```bash
docker exec trufflehog-lab6 bash -c "trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git | tee /log.txt"
docker cp trufflehog-lab6:/log.txt ./log.txt
```

вывод получился довольно большой, так как инструмент проходил по истории комитов. часть результатов была похожа на ложные срабатывания, например минифицированные js файлы и хеши из lock-файлов. из найденного я выбрал 5 разных типов секретов.

## найденные секреты

### 1. токен github в workflow

расположение: `.github/workflows/release.yml:12`

```yaml
GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5
```

это похоже на токен доступа к github. признак не только в названии переменной, но и в самом значении: длинная случайная строка с высокой энтропией. если такой токен имеет права на репозиторий, через него можно делать релизы, пушить изменения или выполнять другие действия от имени владельца токена.

правильно хранить такое значение в секретах ci/cd, например в github actions secrets, и обращаться к нему как к `${{ secrets.GITHUB_TOKEN }}` или `${{ secrets.RELEASE_TOKEN }}`. если токен уже оказался в истории git, его надо отозвать и создать новый.

### 2. приватный ключ

расположение: `webgoat-server/privatekey.key:1`

```text
-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSkAgEAAoIBAQCpuOH6AnMc/xdJ
...
-----END PRIVATE KEY-----
```

это приватный ключ в формате pem. такие ключи используются для расшифровки, подписи или настройки tls. если приватный ключ попадает в репозиторий, его может скачать любой, у кого есть доступ к истории проекта. дальше возможна подмена сервера или расшифровка трафика, если ключ реально использовался в окружении.

приватные ключи нельзя хранить в коде. нормальный вариант - vault, secret manager, kubernetes secrets или защищенное хранилище на стороне ci/cd. после утечки ключ надо заменить, а связанный сертификат перевыпустить.

это не открытый пароль, но все равно секреты для ci. travis хранит их в зашифрованном виде и расшифровывает при сборке. по смыслу там могут быть токены для релизов, доступ к docker hub или webhook для уведомлений.

лучше держать такие значения в настройках секретов самого ci/cd, а в репозитории оставлять только ссылки на переменные. если проект переезжает с travis на github actions или другой ci, старые токены надо отключить, потому что они уже не нужны и только увеличивают риск.

### 4. пароль прямо в java-коде

расположение: `webgoat-lessons/password-reset/src/main/java/org/owasp/webgoat/password_reset/ResetLinkAssignment.java:54`

```java
static final String PASSWORD_TOM_9 = "somethingVeryRandomWhichNoOneWillEverTypeInAsPasswordForTom";
static final String TOM_EMAIL = "tom@webgoat-cloud.org";
```

здесь пароль пользователя записан как константа. даже если это учебный проект, по сути это готовый секрет в исходниках. любой человек с доступом к репозиторию увидит пароль без подбора и без доступа к базе.

пароли нельзя хранить в коде. для тестов можно использовать переменные окружения или тестовые секреты, которые создаются при запуске. реальные пользовательские пароли должны храниться только в виде хеша с солью, например bcrypt или argon2.

## дополнительные вопросы

### что такое BFG Repo-Cleaner

BFG Repo-Cleaner - это утилита для чистки истории git. ее используют, когда в репозиторий уже попал секрет или слишком большой файл. инструмент может пройти по истории комитов и заменить найденные значения на заглушку, например `***REMOVED***`.

важный момент: чистка истории не делает утекший секрет снова безопасным. если кто-то уже успел склонировать репозиторий, старое значение могло остаться у него локально. поэтому после BFG все равно нужно отзывать токены, менять пароли и перевыпускать ключи.

### как автоматизировать поиск секретов

поиск секретов можно и нужно автоматизировать. я бы сделал это в нескольких местах:

- pre-commit hook у разработчика, чтобы случайный секрет не попал даже в комит;
- проверка pull request в ci/cd;
- регулярный scan репозитория вместе с историей;
- встроенные инструменты github или gitlab для secret scanning.

это правильный подход, потому что человек может не заметить строку с токеном, а автоматическая проверка сработает каждый раз. но полностью полагаться только на сканер нельзя. у него бывают ложные срабатывания и пропуски, особенно если секрет похож на обычную строку. поэтому главное правило остается таким: секреты надо изначально хранить вне кода.
