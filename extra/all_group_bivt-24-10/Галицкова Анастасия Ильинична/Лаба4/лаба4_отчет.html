Отчет по домашнему заданию: Безопасность в Python и Django

Цель: научиться находить распространенные проблемы в python-коде и понять, как django защищает веб-приложения.

Часть I. Разбор фрагментов кода

Фрагмент 1

Код:

app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

Проблема:

Секретный ключ написан прямо в коде. Если код попадет в git, любой, у кого есть доступ к репозиторию, увидит ключ. Зная ключ, можно подделать куки и войти под любым пользователем.

Решение:

Вынести ключ в переменную окружения. Например:

import os
app.config['SECRET_KEY'] = os.environ.get('SECRET_KEY')

Фрагмент 2

Код:

password = TextField('password')

Проблема:

Поле для пароля сделано как обычное текстовое поле. Пароль не скрывается звездочками, может сохраниться в истории браузера и передается открыто, если нет HTTPS.

Решение:

Использовать PasswordField вместо TextField. И обязательно включить HTTPS.

from wtforms import PasswordField
password = PasswordField('password')

Фрагмент 3

Код:

try:
    username = username.lower()
    email = email.strip().lower()
    user = User({...})
    user.validate()
    save_user(self.db_conn, user)
except Exception, e:
    return self.render_template("success_create.html")

Проблемы:

  • Нет проверки, существует ли уже такой пользователь. Можно перезаписать чужую учетку.
  • Пароль не хэшируется. Скорее всего сохраняется как есть. Если слить базу, все пароли будут видны.
  • В блоке except ловится любая ошибка, но при этом все равно рендерится страница "успех". Пользователь думает, что зарегистрировалась, а на самом деле что-то пошло не так.
  • Синтаксис except Exception, e устарел.

Решение:

  • Проверять уникальность username и email перед сохранением.
  • Хэшировать пароль. Например, через werkzeug.security.generate_password_hash().
  • Обрабатывать конкретные ошибки, а не все подряд. И показывать адекватное сообщение пользователю.
  • Исправить синтаксис на "except Exception as e".

Часть II. Безопасность в Django

1. Какие атаки предотвращает Django?

  • SQL-инъекции. ORM сам экранирует параметры, если не писать сырые запросы.
  • XSS. Шаблоны по умолчанию экранируют все переменные.
  • CSRF. Встроенные токены проверяются при отправке форм.
  • Clickjacking. Добавляется заголовок X-Frame-Options.
  • Path traversal. Проверка путей к файлам.
  • Подбор паролей. Встроенные валидаторы сложности.
  • Атаки на сессии. HttpOnly флаг и поддержка HTTPS.

Все это работает, если пользоваться стандартными инструментами django. Если вручную отключать защиту или писать сырые запросы, дыры появляются.

2. Как устроено управление сессиями в django

Когда пользователь заходит на сайт, django создает уникальный идентификатор сессии (случайную строку). Этот идентификатор кладется в куку с названием sessionid. Сами данные сессии хранятся на сервере. По умолчанию — в таблице django_session базы данных.

При следующем запросе браузер отправляет куку sessionid. Django находит по этому ключу данные в базе и кладет их в request.session. Если код что-то положил в request.session, django сохранит это при ответе.

Настройки безопасности сессий:

  • sessionid — это HttpOnly кука. JavaScript не может ее украсть.
  • Можно включить SESSION_COOKIE_SECURE = True, тогда кука передается только по HTTPS.
  • Можно настроить время жизни сессии через SESSION_COOKIE_AGE.
  • Сессии можно хранить в базе, кэше, файлах или куках. Последний вариант используется редко, потому что данные хранятся у клиента.

Пример работы:

# Запомнить пользователя
request.session['user_id'] = user.id

# Проверить авторизацию
if request.session.get('user_id'):
    ...

# Выйти
request.session.flush()

Сессии не подходят для хранения больших данных (обычно не больше 4 КБ).
