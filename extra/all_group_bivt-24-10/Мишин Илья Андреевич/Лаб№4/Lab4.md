# Часть 1
***Фрагмент 1***
В коде используется захардкоженный  `SECRET_KEY`, который хранится прямо в исходном файле. Такой ключ может попасть в Git, логи, резервные копии или стать известен любому, кто получил доступ к коду.

Исправления: использовать переменные окружения или хранилища секретов

***Фрагмент 2***
Поле password объявлено как TextField, то есть пароль вводится как обычный текст. Это означает, что символы пароля будут отображаться на экране открыто и не валидироваьться.

Исправления: использовать PasswordField для поля с паролем.

***Фрагмент 3***
При возникновении любого исключения выполняется возврат страницы success_create.html, то есть приложение показывает успешное создание пользователя даже в случае ошибки. 
Из кода не видно безопасного хэширования пароля перед сохранением; пароль просто берётся из запроса и передаётся дальше в объект User. Если он сохраняется как есть, это критическая ошибка хранения чувствительных данных.

Исправления: хэшировать пароль перед сохранением. Добавить обработку разных ошибок(для базы и для валидации).

# Часть 2
Django из коробки помогает защищаться от нескольких распространённых веб‑атак, если использовать его механизмы правильно.

1. Cross-Site Scripting (XSS)
2. Cross-Site Request Forgery (CSRF)
3. SQL Injection через ORM Django
4. Clickjacking:
5. Host header attacks
6. Open redirect и некоторые ошибки HTTPS/куки‑настроек

При первом посещении Django создаёт идентификатор сессии и отправляет его браузеру в cookie. Обычно сами данные сессии хранятся на стороне сервера, чаще всего в базе данных, а при каждом следующем запросе Django получает cookie с sessionid, находит соответствующую запись сессии и проверяет, существует ли она и не истёк ли её срок действия.

По умолчанию срок жизни сессии составляет 14 дней , но его можно изменить в настройках. Django сохраняет сессию при изменении её данных, а при включённой настройке может обновлять её на каждом запросе.

Для защиты сессионных cookie используются настройки HttpOnly, Secure и SameSite: HttpOnly запрещает доступ к cookie из JavaScript, Secure разрешает передавать cookie только по HTTPS, а SameSite снижает риск CSRF‑атак.
