Часть I

Фрагмент 1

Недостаток: секретный ключ написани прямо в исходном коде. При попадании в публичные репозитории, злоумышленники могут подделовать сессии пользователей и использовать csrf-атаки.

app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

Исправления: использовать переменные окружения(.env файлы) или хранилища секретов (Vault).

os.getenv('SECRET_KEY')

Фрагмент 2

Недостаток: поле с паролем определено как текстовое. И будет показываться в открытом виде

password = TextField('password')

Исправления: использовать PasswordField для поля с паролем.

password = PasswordField('Пароль', validators=[DataRequired()])

Фрагмент 3

Недостаток: судя по коду, User получает пароль в открытом виде и никак его не хэширует перед сохранием базы. 

user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})

Если злоумышленник получит доступ к базе, то он получит и все пароли юзеров.

Также код отлавливает все исключения, которые могут получаться при валидации и при сохранении в базу. Тем более по умолчанию возвращается страница с успешным сохранением юзера.

except Exception, e:
    return self.render_template("success_create.html")

Исправления: хэшировать пароль перед сохранением. Добавить обработку разных ошибок(для базы и для валидации).

Часть II

Атаки, который django предотвращает:

  • CSRF (django использует секретный ключ для идентификации csrf-токенов)
  • XSS (django экранирует некоторые символы)
  • SQL-инъекции (django использует свой ORM)
  • Атаки на хэши (django добавляет соль к паролям при хэшировании)

При первом посещении django создает id сессии и сохраняет её в куки браузера. Django хранит сессии у себя в базе данных и при обращении юзера проверяет наличие сессии c предоставленным id.

Сессия по умолчанию хранится 14 дней, но этот параметр можно поменять. Джанго также продлевает сессию при изменении данных в ней или на каждый запрос пользователя.
