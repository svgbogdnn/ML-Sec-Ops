***Недостаток:*** Хардкод секретного ключа (SECRET_KEY) в исходном коде. При попадании кода в публичный репозиторий злоумышленники смогут подписывать любые сессии и токены, получая полный контроль над приложением.</br>

***Недостаток:*** Использование TextField для пароля. В HTML это создаст обычное текстовое поле ```<input type="text">```, из-за чего пароль будет виден на экране при вводе. Также отсутствует валидация.</br>
***Рекомендация:*** Использовать PasswordField для скрытия ввода и добавить валидаторы.
### Фрагмент 3
***Недостатки:***
1. Пароль сохраняется в базу данных в открытом виде. При утечке базы все пароли будут скомпрометированы.
2. Слепой обработчик исключений (except Exception). Ошибки валидации или базы данных игнорируются, и пользователю всегда показывается страница успеха, даже если создание аккаунта провалилось.

### Управление пользовательскими сессиями в Django
Django использует cookie-based sessions. Сервер генерирует уникальный случайный ключ (Session Key)

В браузере пользователя сохраняется только этот ключ в cookie (по умолчанию sessionid). Сами данные сессии на клиенте не хранятся.

На сервере данные сессии (словарь) сохраняются в бэкенде. По умолчанию это база данных (django_session таблица), но могут быть использованы cache, file system или Redis.

При первом запросе сервер создает сессию и отправляет ключ в cookie.
При последующих запросах браузер отправляет cookie.
Middleware берет ключ, находит данные в бэкенде и добавляет объект request.session.
