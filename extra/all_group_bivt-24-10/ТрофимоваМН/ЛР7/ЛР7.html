Отчёт по лабораторной работе №7: Развернуть инструмент SAST-анализа и провести SAST тестирование

1. Цель работы

Цель данной работы — развернуть инструмент статического анализа безопасности мобильных приложений MobSF, выполнить SAST-сканирование дистрибутива мобильного приложения (APK-файла) и на основе полученного отчёта выявить критические уязвимости, составить план их митигации.

2. Использованные инструменты и объект исследования

  • Инструмент SAST: MobSF (Mobile Security Framework) v3.1.1, развёрнут через Docker (образ opensecurity/mobile-security-framework-mobsf:v3.1.1)
  • Объект исследования: APK-файл Subway Surf (1.17.0)
    • Имя пакета: com.kiloo.subwaysurf

  • Отчёт MobSF (приложен в формате report.pdf)

4. Анализ уязвимостей высокого уровня (HIGH severity)

4.1. Dangerous permissions

MobSF выделил несколько разрешений со статусом dangerous:

Разрешение Описание
android.permission.INTERNET Полный доступ к сети
android.permission.WRITE_EXTERNAL_STORAGE Чтение/запись на SD-карту
android.permission.READ_PHONE_STATE Доступ к состоянию телефона (IMEI, номер и т.д.)
android.permission.WAKE_LOCK Предотвращение перехода устройства в сон
android.permission.GET_TASKS Получение информации о запущенных приложениях

Особенно критичны READ_PHONE_STATE и GET_TASKS, так как они позволяют собирать идентификаторы устройства и подглядывать за другими приложениями.

4.2. Анализ манифеста (Manifest Analysis) – HIGH

№ Проблема Уровень
1 Broadcast Receiver (BillingReceiver) не защищён, присутствует intent-filter HIGH
2 Broadcast Receiver (com.google.android.gcm.GCMBroadcastReceiver) защищён разрешением, но уровень защиты разрешения требует проверки (разрешение не определено в анализируемом приложении) HIGH
3 Broadcast Receiver (com.nativex.advertiser.ReferralReceiver) не защищён, присутствует intent-filter HIGH

Экспортированные незащищённые приёмники широковещательных сообщений могут принимать вредоносные данные от других приложений, что ведёт к подделке событий, краже данных или отказу в обслуживании.

4.3. Анализ кода (Code Analysis) – HIGH

№ Проблема CVSS Описание
4 Хранение чувствительной информации в коде (пароли, ключи) 7.4 (high) Файлы содержат hardcoded данные
5 Доступ к внешнему хранилищу 5.5 (medium) Любое приложение может читать данные, записанные во внешнее хранилище
6 Использование RSA без OAEP padding 5.9 (medium) Уязвимость к атакам на неправильно дополненный RSA
7 Небезопасный генератор случайных чисел 7.5 (high) Использование недостаточно случайных значений
13 Небезопасная реализация SSL (доверие всем сертификатам) 7.4 (high) Приложение уязвимо к MITM-атакам

Дополнительно:

  • Приложение логирует информацию (CVSS 7.5, high). Чувствительные данные не должны попадать в логи.

4.4. Анализ сертификата и подписи

  • Подпись только v1 signature (v2 и v3 отсутствуют) → уязвимость Janus на Android < 7.0
  • Алгоритм подписи: SHA1withRSA → SHA-1 известен проблемами коллизий

4.5. Network Security

В отчёте MobSF раздел NETWORK SECURITY пуст, что означает отсутствие настроек безопасности сети (например, не задан network_security_config). Это косвенно повышает риск, но явных high-проблем не зафиксировано.

5. План митигации обнаруженных рисков

5.1. Убрать избыточные опасные разрешения

  • Действие: Удалить или заменить разрешения, не критичные для функциональности: READ_PHONE_STATE (если не нужен IMEI/номер), GET_TASKS (удалить, использовать альтернативы), WRITE_EXTERNAL_STORAGE (использовать внутреннее хранилище).
  • Проверка: Запрос разрешений во время выполнения только при реальной необходимости.

5.2. Защитить Broadcast Receiver

  • Действие: Для всех экспортированных ресиверов установить android:exported="false", если они не должны вызываться другими приложениями. Если экспорт необходим, добавить разрешение с уровнем защиты signature.
  • Пример: <receiver android:name=".BillingReceiver" android:exported="false" />

5.3. Обеспечить безопасность данных на диске

  • Действие: Использовать внутреннее хранилище вместо внешнего для чувствительных данных. Включить шифрование файлов (например, EncryptedFile из AndroidX Security). Установить android:allowBackup="false" в манифесте, чтобы предотвратить резервное копирование данных через ADB.

5.4. Исправить криптографические проблемы

  • Действие: Заменить RSA без паддинга на RSA с OAEP. Использовать SecureRandom вместо небезопасных генераторов (например, Random). Перейти на подпись APK Signature Scheme v2/v3 и использовать алгоритм SHA-256 вместо SHA-1.

5.5. Устранить утечку информации через логи

  • Действие: Удалить вызовы Log.d(), Log.i() и т.п., содержащие чувствительные данные. Использовать ProGuard/R8 для удаления логирования в релизной сборке.

5.6. Внедрить безопасную работу с сетью

  • Действие: Добавить network_security_config с запретом cleartextTraffic. Реализовать проверку сертификатов (пиннинг) или использовать библиотеки с безопасными настройками по умолчанию (OkHttp с проверкой). Установить android:usesCleartextTraffic="false" в манифесте.

5.7. Обновить зависимости и трекеры

  • Действие: Проверить все сторонние SDK (AdColony, ChartBoost, Flurry, Inmobi, Kochava, Millennial Media, NativeX) на предмет обновлений без известных уязвимостей. Удалить неиспользуемые трекеры. Для оставшихся – убедиться, что они не запрашивают избыточных разрешений и не передают чувствительные данные в незашифрованном виде.

6. Вывод по работе

В ходе выполнения лабораторной работы был развёрнут инструмент SAST-анализа MobSF, проведено сканирование APK Subway Surf (версия 1.17.0). Получен критический уровень безопасности (10/100). Выявлены многочисленные уязвимости высокого уровня: опасные разрешения, незащищённые Broadcast Receiver, небезопасная работа с хранилищем, слабая криптография, логирование чувствительных данных и проблемы с подписью приложения. Составлен подробный план митигации, охватывающий изменение конфигурации манифеста, исправление криптографических ошибок, усиление сетевой безопасности и ревизию сторонних трекеров. Выполнение этих рекомендаций позволит существенно повысить безопасность приложения и снизить риск его компрометации.
