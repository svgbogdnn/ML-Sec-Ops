# Базовая настройка безопасности Docker-контейнера

## Цель работы

Закрепить на практике материал лекции и научиться на базовом уровне обеспечивать безопасность Docker-контейнеров: анализировать текущего пользователя в контейнере, создавать образы с непривилегированным пользователем, применять дополнительные флаги безопасности, сканировать образы на уязвимости.

---

# Часть I. Анализ стандартного контейнера

## 1. Подготовка и запуск

Скачан минимальный образ alpine:latest из Docker Hub:

docker pull alpine:latest

Просмотр локальных образов:

docker image ls

Вывод:

IMAGE                                   ID             DISK USAGE   CONTENT SIZE   EXTRA
alpine:latest                           5b10f432ef3d       13.1MB         3.95MB

Определение текущего пользователя на хосте:

whoami

Результат:

desktop-sku6s2b\maria

## 2. Запуск оболочки в контейнере и проверка пользователя

docker run -it alpine:latest sh

Внутри контейнера:

whoami

Вывод:

root

После этого работа контейнера завершена (exit).

## 3. Вывод по части I

Стандартный контейнер на основе alpine по умолчанию запускает все процессы от суперпользователя root. Это создаёт риск: в случае компрометации приложения злоумышленник получит максимальные привилегии внутри контейнера, что может способствовать выходу за его пределы. Необходимо минимизировать привилегии.

---

# Часть II. Создание безопасного образа

## 1. Dockerfile с непривилегированным пользователем

Написан Dockerfile, реализующий простой HTTP-сервер на Python от пользователя myuser:

FROM alpine:latest
RUN apk add --no-cache python3
RUN adduser -D myuser
EXPOSE 8080
USER myuser
WORKDIR /home/myuser
CMD ["python3", "-m", "http.server", "8080"]

Дополнительные меры безопасности (указаны в комментариях Dockerfile):

1. HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:8080/ || exit 1 — контролирует работоспособность контейнера.

2. При запуске контейнера использовать флаги:
   - --read-only — корневая файловая система монтируется только для чтения,
   - --cap-drop=ALL — удаляются все capabilities (привилегии ядра),
   - --security-opt=no-new-privileges — запрещает процессам получать дополнительные привилегии,
   - --memory=256m --cpus=0.5 — ограничение ресурсов для предотвращения DoS-атак.

3. Регулярно обновлять образ, использовать COPY вместо ADD, подписывать образы, сканировать на уязвимости (Clair, Trivy).

## 2. Сборка и проверка

docker build -t safe-alpine .

docker run -d -p 8080:8080 --name safe-container safe-alpine

docker exec -it safe-container whoami

Вывод:

myuser

## 3. Вывод по части II

Применение инструкции USER позволяет запускать приложение от непривилегированного пользователя, что соответствует принципу наименьших привилегий. Дополнительные флаги и практики, перечисленные в комментариях, значительно повышают уровень изоляции и снижают поверхность атаки.

# Часть III. Сканирование образа на уязвимости

## 1. Инструмент сканирования

Использован Trivy (Aqua Security) — статический анализатор уязвимостей в образах контейнеров, пакетах и файловых системах.

Установка:

winget install AquaSecurity.Trivy

## 2. Сканирование образа

trivy image alpine:latest

Основные строки вывода:

## 3. Анализ результатов

По данным Trivy, образ alpine:latest на момент проверки не содержит известных уязвимостей. На это повлияли следующие факторы:
- минимальный размер образа и малое количество установленных пакетов (16),
- актуальная версия Alpine Linux (3.23.4),
- оперативное обновление репозиториев сопровождающими.

Однако необходимо учитывать:
- база уязвимостей Trivy обновляется постоянно, поэтому отсутствие CVE сегодня не гарантирует их отсутствие завтра;
- безопасность образа не ограничивается отсутствием уязвимостей в ОС — важно также проверять зависимости самого приложения;
- для production-среды следует внедрить автоматическое сканирование в CI/CD-пайплайн и настроить политики блокировки при обнаружении критических проблем.

## 4. Вывод по части III

Сканирование Trivy подтвердило чистоту выбранного базового образа. Совместно с мерами, реализованными в Dockerfile (непривилегированный пользователь, планируемые флаги запуска), можно считать контейнер подготовленным к безопасной эксплуатации.

## Общий вывод

В ходе лабораторной работы были изучены и применены базовые практики обеспечения безопасности Docker-контейнеров:

1. Анализ привилегий по умолчанию — контейнеры запускаются от root, что небезопасно.

2. Создание безопасного образа — с помощью USER в Dockerfile приложение переведено на работу от myuser. Добавлены комментарии с рекомендациями по флагам запуска и другим мерам.

3. Сканирование уязвимостей — образ alpine:latest проверен утилитой Trivy; уязвимости не обнаружены, однако важна регулярность проверок.

Полученные навыки являются фундаментом для построения более комплексных систем защиты контейнеризированных приложений, включая использование подписанных образов, ограничение capabilities, режим «только чтение» и мониторинг безопасности на всех этапах жизненного цикла..
