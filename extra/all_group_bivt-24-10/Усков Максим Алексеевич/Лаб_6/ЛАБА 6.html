ЛАБА 6. Поиск секретов в репозитории

Цель

Проверить репозиторий на наличие секретов и разобрать найденные значения: где они находятся, почему это секрет и как их правильно хранить.

Для проверки использовался репозиторий из методички:

https://github.com/OtusTeam/DevSecOps_secret-finding.git

develop

Инструмент

В методичке предлагается использовать truffleHog. Он ищет пароли, токены, ключи и другие чувствительные данные в git-репозиториях, в том числе по истории коммитов.

Пример команд для запуска через одноразовый Docker-контейнер:

docker run --rm -it python:buster /bin/bash

pip install truffleHog

trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git | tee -a log.txt

Дополнительно я вручную проверил найденные места в репозитории, чтобы отсеять явные ложные срабатывания и описать только похожие на реальные секреты значения.

Как правильно хранить

1

docker/.env:2

APP_SECRET=666666666666666

APP_SECRET обычно используется приложением как ключ для подписи cookies, JWT, CSRF-токенов или других внутренних механизмов. Если он лежит в репозитории, любой человек с доступом к коду может использовать его для подделки или анализа данных приложения.

Хранить в secret storage: GitHub Actions Secrets, GitLab CI Variables, HashiCorp Vault, AWS Secrets Manager, Kubernetes Secret. В репозитории оставить только .env.example без реального значения.

2

docker/.env:3

USER=alex675

Сам по себе логин не всегда является секретом, но в этом файле он хранится рядом с паролем и образует часть учетных данных. В паре с паролем это уже полноценные credentials для доступа к сервису или приватному ресурсу.

Хранить вместе с паролем в secret storage или передавать через переменные окружения CI/CD. В коде использовать нейтральное имя переменной вроде SERVICE_USERNAME.

3

docker/.env:4

PASSWORD=#!qerge34t423sdfvdsfgeR

Это явно пароль: название переменной PASSWORD, высокая энтропия и наличие спецсимволов. Такой пароль нельзя коммитить, потому что после попадания в git он остается в истории.

Срочно заменить/отозвать пароль. Хранить в менеджере секретов или в защищенных переменных CI/CD. В репозитории хранить только шаблон .env.example с PASSWORD=<set-in-secret-storage>.

4

webgoat-server/privatekey.key:1-28

Приватный RSA-ключ, файл начинается с -----BEGIN PRIVATE KEY-----

Приватный ключ позволяет расшифровывать данные или подписывать сообщения/сертификаты от имени владельца ключа. Если ключ попал в публичный репозиторий, его нужно считать скомпрометированным.

Немедленно отозвать связанный сертификат/ключевую пару и выпустить новую. Хранить ключ в Vault/KMS/Secret Manager или в защищенном хранилище CI/CD. В репозиторий можно класть только публичный ключ или CSR, если это действительно нужно.

5

.github/workflows/release.yml:113

GITHUB_TOKEN=cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5

Значение похоже на токен доступа: длинная hex-строка, явно присвоена переменной GITHUB_TOKEN в release pipeline. Такой токен может давать доступ к GitHub API, релизам, workflow или публикации артефактов.

Отозвать токен и заменить на ${{ secrets.GITHUB_TOKEN }} или отдельный fine-grained token в GitHub Actions Secrets. Права токена должны быть минимальными и ограниченными нужным workflow.



Вывод

В репозитории найдены разные типы чувствительных данных:

  • application secret;

  • логин как часть пары учетных данных;

  • пароль;

  • приватный криптографический ключ;

  • hardcoded GitHub token в CI/CD pipeline.

Главная проблема в том, что секреты лежат прямо в git-репозитории. Даже если потом удалить строки из текущей версии файла, они могут остаться в истории коммитов и быть найденными инструментами вроде truffleHog.

Правильный подход:

  • реальные секреты не хранить в коде;

  • использовать .env.example вместо настоящего .env;

  • передавать значения через переменные окружения;

  • хранить секреты в GitHub Actions Secrets, GitLab CI Variables, HashiCorp Vault, AWS Secrets Manager, Kubernetes Secrets или аналогах;

  • после утечки не просто удалить секрет из файла, а отозвать/ротировать его;

  • при необходимости чистить историю через BFG Repo-Cleaner или git filter-repo.

Дополнительно

Что такое BFG Repo-Cleaner

BFG Repo-Cleaner - это инструмент для быстрой очистки истории git-репозитория от случайно закоммиченных больших файлов, паролей, токенов и ключей. Он переписывает историю репозитория и удаляет секреты из старых коммитов.

Но одного BFG недостаточно: если секрет уже был опубликован, его нужно считать скомпрометированным и обязательно ротировать.

Как автоматизировать поиск секретов

Поиск секретов можно автоматизировать несколькими способами:

  • запускать truffleHog, gitleaks или detect-secrets в CI/CD pipeline;

  • добавить pre-commit hook, который не даст закоммитить секрет локально;

  • включить GitHub Secret Scanning и push protection;

  • сохранять baseline известных ложных срабатываний, чтобы не ломать сборку из-за мусорных находок.

Это правильный подход, потому что секреты лучше блокировать до попадания в репозиторий. Но автоматизация не заменяет ручной анализ: у сканеров бывают false positive и false negative, поэтому найденные значения нужно проверять.
