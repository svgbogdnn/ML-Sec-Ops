Недостаток

Поле password объявлено как обычное текстовое поле (TextField), а не как поле для пароля. Из-за этого пароль отображается на экране в открытом виде при вводе. Это повышает риск утечки через shoulder surfing, запись экрана, автозаполнение браузера и повторное отображение формы.

Для пароля нужно использовать специальное поле PasswordField. Кроме того, для формы авторизации желательно добавить валидацию: обязательность заполнения, ограничения длины, базовую проверку формата логина.

def post(self):

    email = self.get_argument('mail')

    try:
        username = username.lower()
        email = email.strip().lower()
        user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})

        save_user(self.db_conn, user)
    except Exception, e:

Недостаток

Обрабатываются вообще все исключения через except Exception, и при этом в случае ошибки пользователю всё равно показывается шаблон успешного создания аккаунта. Это приводит к скрытию ошибок, неправильной логике приложения и невозможности понять, была ли регистрация реально выполнена.

Рекомендации по устранению

Нужно ловить только ожидаемые типы ошибок, логировать исключения, возвращать пользователю корректное сообщение об ошибке, разделить успешный и не успешный сценарий обработки.

1. Какие наиболее распространённые атаки предотвращает Django?

Django из коробки предоставляет механизмы защиты от ряда распространённых веб-атак.

1.1. XSS (Cross-Site Scripting)

Django автоматически экранирует данные в шаблонах, поэтому пользовательский ввод по умолчанию выводится как текст, а не как исполняемый HTML/JavaScript-код. Это снижает риск внедрения вредоносных скриптов в страницу.

Источник: Security in Django - Cross site scripting (XSS) protection

1.2. CSRF (Cross-Site Request Forgery)

Django содержит встроенную защиту от CSRF-атак. Для HTML-форм и POST-запросов используется специальный CSRF-токен, который проверяется на стороне сервера.

Источник: Security in Django - Cross site request forgery (CSRF) protection

1.3. SQL Injection

При использовании ORM Django запросы к базе данных, как правило, строятся безопасно - с параметризацией, что снижает риск SQL-инъекций. Тем не менее при ручном написании SQL-запросов разработчик всё ещё может допустить ошибку.

Источник: Security in Django - SQL injection protection

1.4. Clickjacking

Django предоставляет встроенные средства защиты от clickjacking, например middleware и заголовки, запрещающие встраивание сайта в iframe на посторонних ресурсах.

Источник: Security in Django - Clickjacking protection

1.5. Host Header Attack и базовые настройки HTTPS-безопасности

Django также содержит механизмы, связанные с проверкой допустимых хостов (ALLOWED_HOSTS) и рекомендациями по безопасной работе через HTTPS.

Источники: - Security in Django - Django settings - ALLOWED_HOSTS —

2. Как устроено управление пользовательскими сессиями в Django?

2.1. Общий принцип работы

Django поддерживает механизм пользовательских сессий через встроенный session framework. Он позволяет сохранять данные между запросами одного и того же клиента. После включения SessionMiddleware у объекта запроса появляется request.session, через который приложение может записывать и читать данные сессии.

Источник: How to use sessions

2.2. Где хранятся сессии

Django поддерживает несколько вариантов хранения сессий: - в базе данных; - в кэше; - в связке база данных + кэш (cached_db); - в файлах; - в cookie браузера (signed_cookies).

По умолчанию Django обычно использует хранение в базе данных через django.contrib.sessions.

Источник: How to use sessions — Configuring the session engine

2.3. Что хранится в cookie

В стандартной конфигурации cookie обычно содержит идентификатор сессии, а сами данные лежат на сервере. Исключение — backend signed_cookies, где данные сессии хранятся прямо в cookie. В этом случае они защищены подписью, но не шифруются, поэтому их нельзя считать конфиденциальными.

Источник: How to use sessions

2.4. Работа через request.session

Объект request.session работает похоже на словарь. В него можно записывать значения по ключу, получать их, удалять и очищать. Это стандартный интерфейс для работы с сессионными данными в Django.

Источник: How to use sessions — Using sessions in views

2.5. Безопасность сессий

Django предусматривает несколько важных механизмов защиты сессий:

  • HttpOnly для session cookie — уменьшает риск доступа к cookie через JavaScript;
  • ротация session key при логине через cycle_key() — снижает риск session fixation;
  • полная очистка сессии при logout через flush();
  • настройка времени жизни cookie и сессии через параметры конфигурации.

Источники: - How to use sessions — Session security - How to use sessions — Examples

2.6. Связь с аутентификацией

Сессии в Django тесно связаны с системой аутентификации. SessionMiddleware управляет сессиями между запросами, а AuthenticationMiddleware использует сессии для привязки пользователя к запросу, чтобы в коде был доступен request.user.

Источник: User authentication in Django
