# Часть I — CVE с XSS в PHP-компонентах за 2021 год

## Общее количество

По данным базы CVEDetails (cvedetails.com, фильтр: год=2021, тип=XSS) за 2021 год
было опубликовано около **2196** CVE, связанных с XSS уязвимостями. Это показывает,
что даже хорошо известная и давно задокументированная уязвимость продолжает
встречаться в огромных количествах — и в первую очередь в PHP-приложениях,
которых в вебе большинство.

---

## CVE-2021-24436 — W3 Total Cache (WordPress плагин)

**Тип:** Reflected XSS  
**CVSS:** 6.1  
**Дата:** июль 2021

### Назначение компонента

W3 Total Cache — PHP-плагин для WordPress, один из самых популярных инструментов
оптимизации производительности сайтов. Он отвечает за кэширование страниц,
объектов базы данных и файлов, минификацию HTML/CSS/JavaScript, а также
интеграцию с CDN-сервисами. На момент обнаружения уязвимости плагин был
установлен на более чем 1 миллионе сайтов по всему миру.

### Суть уязвимости

В административной панели плагина, на странице управления расширениями,
параметр `extension` из URL передавался напрямую в HTML атрибут страницы
без обработки специальных символов. Атакующий мог сформировать вредоносную
ссылку и отправить её администратору сайта. При переходе по ссылке в браузере
администратора выполнялся произвольный JavaScript код например, для кражи
cookies сессии или перехвата учётных данных.

## CVE-2021-39201 — WordPress Block Editor (Gutenberg)

**Тип:** Stored XSS  
**CVSS:** 5.4  
**Дата:** сентябрь 2021

### Назначение компонента

WordPress — система управления контентом, написанная на PHP, которая используется
примерно на 43% всех сайтов в интернете. Block Editor (Gutenberg) это встроенный
визуальный редактор для создания страниц и записей, появившийся в WordPress 5.0.
Он позволяет пользователям составлять контент из блоков: текстовых, медиа,
таблиц, кнопок и других. Редактором пользуются все, кто публикует контент на
WordPress-сайтах авторы, редакторы, администраторы.

### Суть уязвимости

Пользователи с низким уровнем привилегий (авторы, соавторы) могли внедрить
XSS-нагрузку через блочный редактор, обойдя защиту `unfiltered_html` — ограничение,
которое запрещает непривилегированным пользователям вставлять произвольный HTML
и JavaScript. Вредоносный скрипт сохранялся на сервере и выполнялся в браузере
любого пользователя, открывшего заражённую страницу, включая администраторов.
Уязвимость была исправлена в WordPress 5.8.1.

# Часть II — XSS-атака на стенд ket9/otus-devsecops-xss

---

## 1. Ход рассуждений

Запустил образ:

```
docker pull ket9/otus-devsecops-xss
docker run -d -p 8081:80 ket9/otus-devsecops-xss:latest
```

Открыл `http://localhost:8081` — главная страница показала два раздела:
ссылку XSS-1 и ссылку index.php. Перешёл по XSS-1 — открылась страница
с формой Comments, в которой есть текстовое поле для ввода комментария
и кнопка Save Data.

Первая мысль: форма принимает пользовательский ввод и, судя по названию
раздела Comments, сохраняет его на сервере для последующего отображения.
Если приложение не фильтрует HTML-теги при сохранении и отображении — это
уязвимость XSS.

Для проверки ввёл в поле стандартную XSS-нагрузку:

```
<script>alert('XSS')</script>
```

Нажал Save Data. Браузер немедленно показал всплывающее диалоговое окно
с текстом "XSS" — JavaScript выполнился в контексте браузера.

Чтобы убедиться что это именно Stored XSS (а не Reflected), обновил страницу
(Cmd+R). Диалоговое окно появилось снова — скрипт сохранился на сервере
и выполняется при каждой загрузке страницы. На самой странице также появились
визуальные артефакты (лишние линии) — след от тега `<script>`, который
сохранился в базе и отрендерился как HTML.

Вывод: приложение никак не обрабатывает пользовательский ввод перед сохранением
в базу данных и перед выводом на страницу.

---

## 2. Тип найденной уязвимости

**Stored XSS (хранимый межсайтовый скриптинг)**

В отличие от Reflected XSS, где вредоносный скрипт существует только в URL
и выполняется только при переходе по специальной ссылке, в данном случае
скрипт сохраняется на сервере в базе данных. Это значит, что он автоматически
выполняется в браузере каждого пользователя, который откроет страницу с
комментариями без каких-либо дополнительных действий со стороны атакующего.

Это делает Stored XSS более опасным вариантом: один раз внедрённый скрипт
может воздействовать на всех посетителей сайта, включая администраторов.

---

## 3. Меры предотвращения

Основная причина уязвимости это пользовательский ввод попадает в HTML-страницу
без какой-либо обработки. Для защиты нужно закрыть две точки: сохранение
данных и их вывод.

**1. Экранирование специальных HTML-символов при выводе (Output Encoding)**

Самая важная мера. Перед тем как вставить пользовательские данные в HTML,
нужно заменить опасные символы на их безопасные HTML-эквиваленты:

- `<` → `&lt;`
- `>` → `&gt;`
- `"` → `&quot;`
- `'` → `&#x27;`
- `&` → `&amp;`

В PHP для этого используется функция `htmlspecialchars()`:

```php
echo htmlspecialchars($comment, ENT_QUOTES, 'UTF-8');
```

После этого браузер отобразит символы как текст, а не выполнит их как код.

**2. Валидация и очистка данных на стороне сервера (Input Sanitization)**

Перед сохранением в базу данных нужно проверять и очищать входные данные.
Для поля комментария можно полностью запретить HTML теги с помощью `strip_tags()`:

```php
$comment = strip_tags($_POST['comment']);
```

Это удалит все HTML и PHP теги из входных данных, включая `<script>`,
`<img onerror=...>`, `<svg onload=...>` и другие варианты XSS-нагрузок.

**3. Content Security Policy (CSP)**

Дополнительный уровень защиты на уровне HTTP заголовков. CSP позволяет
указать браузеру, какие скрипты разрешено выполнять на странице. Например,
запрет на выполнение inline скриптов (тех что прямо в HTML) значительно
снижает риск XSS даже если фильтрация входных данных была пропущена:

```
Content-Security-Policy: script-src 'self'
```

**4. HttpOnly флаг для cookies**

Если XSS всё же выполнится, атакующий обычно пытается украсть cookies сессии
через `document.cookie`. Установка флага `HttpOnly` на cookies запрещает
JavaScript читать их значения, что ограничивает ущерб от атаки:

```php
setcookie('session', $value, ['httponly' => true, 'secure' => true]);
```
