### 3 CVE за последний год , относящиеся к недостаткам REST API, входящие в owasp top-10 rest api
#### 1. CVE-2025-10611  
По данным NVD, уязвимость CVE-2025-10611 связана с тем, что в нескольких продуктах WSO2 была недостаточно корректно реализована проверка доступа. Из-за этого для некоторых REST API можно было обойти проверки аутентификации и авторизации. В результате злоумышленник мог выполнять административные действия без нужной проверки прав.  
Я бы отнёс эту уязвимость к категории **OWASP API5:2023 Broken Function Level Authorization**, так как проблема здесь не просто в наличии endpoint, а в том, что к отдельным функциям API можно получить доступ без нужных прав. OWASP как раз относит к этому пункту ситуации, когда пользователь может вызвать административный или запрещённый для него метод API.  

**Недостаток:** у REST API слабо реализован контроль доступа к функциям.  
**Причина:** ошибки в проверке авторизации для отдельных API-методов.  

#### 2. CVE-2025-43727  
По данным NVD, уязвимость CVE-2025-43727 связана с ошибкой в реализации механизма аутентификации в REST API. В описании указано, что была допущена **incorrect implementation of authentication algorithm**, из-за чего удалённый неаутентифицированный атакующий мог получить несанкционированный доступ.  
Эту уязвимость можно отнести к категории **OWASP API2:2023 Broken Authentication**. Здесь проблема в том, что механизм аутентификации реализован неправильно, и API не может надёжно отличить настоящего пользователя от постороннего. То есть ошибка находится именно в части проверки личности пользователя при обращении к REST API.
  
**Недостаток:** REST API неправильно выполняет аутентификацию.  
**Причина:** ошибка в реализации алгоритма аутентификации.  
  
#### 3. CVE-2026-26190  
Согласно NVD, в CVE-2026-26190 полный REST API вида **`/api/v1/*`** оказался доступен на служебном metrics/management-порту без какой-либо аутентификации. Это позволяло неаутетнифицированному пользователю получать доступ к бизнес-операциям, в том числе к изменению данных и управлению учётными данными.  
Я бы отнес уязвимость к **OWASP API8:2023 Security Misconfiguration**. Здесь проблема в небезопасной конфигурации: служебный порт оказался настроен так, что через него стал доступен весь REST API без защиты. OWASP относит к этому пункту как раз ошибки конфигурации, лишние открытые интерфейсы и небезопасные настройки по умолчанию.  

**Недостаток:** критичный REST API доступен без аутентификации через служебный порт.  
**Причина:** небезопасная конфигурация приложения и публикация API на management-порту без защиты.

После этого я открыл http://localhost:8080/users/v1/_debug. Этот endpoint оказался доступен без какой-либо авторизации. В ответ приложение вернуло уже более подробную информацию о пользователях, включая поля password и admin.
![[Pasted image 20260418145830.png]]

Далее я сравнил ответы /users/v1 и `/users/v1/_debug` и понял, что через debug-endpoint приложение раскрывает лишние и чувствительные данные пользователей, которые не должны быть доступны без авторизации.

### Найденная уязвимость

В приложении обнаружен открытый debug-endpoint `/users/v1/_debug`, который без авторизации возвращает чувствительные данные пользователей. Через него можно получить:
- email;
- username;
- admin;
- password.

Особенно плохо то, что пароли возвращаются в открытом виде. Такая информация не должна быть доступна обычному пользователю, а тем более без входа в систему.

### Тип OWASP - **API3:2023 Broken Object Property Level Authorization**

Я считаю, что найденный недостаток ближе всего относится к **API3:2023 Broken Object Property Level Authorization**, потому что через API раскрываются свойства объекта пользователя, которые не должны быть доступны клиенту. В данном случае это поля password и admin. То есть проблема заключается не просто в наличии endpointа, а в том, что через него можно получить доступ к чувствительным свойствам объекта.

### Меры предотвращения
- Никогда не возвращать пароли через API.
- Хранить пароли только в виде хеша, а не в открытом виде.
- Удалять debug-endpointы из production-версии приложения.
- Ограничивать доступ к служебным endpointам только администраторам.
- Фильтровать поля в ответах API и отдавать клиенту только действительно нужные данные.
