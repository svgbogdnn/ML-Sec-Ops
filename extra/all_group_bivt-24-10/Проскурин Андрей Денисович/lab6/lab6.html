Цель работы

Закрепить на практике базовые навыки обеспечения безопасности Docker-контейнеров:

  • проверить, от какого пользователя запускается контейнер по умолчанию;
  • настроить запуск контейнера от непривилегированного пользователя;
  • указать дополнительные меры безопасности для Docker-контейнера;
  • просканировать образ на уязвимости с помощью Trivy.

Часть II. Настройка запуска контейнера не от root-пользователя

Dockerfile

Для второй части был создан Dockerfile на основе базового образа alpine:3.20.

FROM alpine:3.20  
  
# Создаем отдельную группу и пользователя без root-прав  
RUN addgroup -S appgroup && adduser -S appuser -G appgroup  
  
# Рабочая директория приложения  
WORKDIR /app  
  
# Меняем владельца рабочей директории  
RUN chown -R appuser:appgroup /app  
  
# Переключаемся на непривилегированного пользователя  
USER appuser  
  
# Команда по умолчанию  
CMD ["sh"]  
  
# Дополнительные настройки безопасности, которые стоит использовать:  
#  
# 1. Не запускать контейнер с флагом --privileged,  
# так как он выдает контейнеру расширенные права на хосте.  
#  
# 2. Запускать контейнер с запретом повышения привилегий:  
# docker run --security-opt no-new-privileges ...  
#  
# 3. Убирать лишние Linux capabilities:  
# docker run --cap-drop=ALL ...  
#  
# 4. Использовать read-only filesystem, если приложению не нужна запись:  
# docker run --read-only ...  
#  
# 5. Ограничивать ресурсы контейнера:  
# docker run --memory=128m --cpus=0.5 ...  
#  
# 6. Не монтировать docker.sock внутрь контейнера,  
# так как это может дать доступ к Docker daemon на хосте.  
#  
# 7. Использовать минимальные и проверенные базовые образы,  
# например alpine или distroless.  
#  
# 8. Регулярно сканировать образ на уязвимости через Trivy/Clair.

  1. В качестве базового образа был выбран минимальный образ:

  1. Была создана отдельная группа appgroup и пользователь appuser без root-прав:

RUN addgroup -S appgroup && adduser -S appuser -G appgroup

Дополнительные меры безопасности

В комментариях Dockerfile были указаны дополнительные меры безопасности, которые можно применять при запуске контейнера.

1. Не использовать --privileged

Флаг --privileged выдает контейнеру расширенные права на хостовой системе. Использование этого флага увеличивает риск компрометации хоста при взломе контейнера.

Небезопасный пример:

docker run --privileged image_name

2. Запускать контейнер с запретом повышения привилегий

Флаг --security-opt no-new-privileges запрещает процессам внутри контейнера получать новые привилегии.

Пример:

docker run --security-opt no-new-privileges secure-alpine:lab

3. Убирать лишние Linux capabilities

Флаг --cap-drop=ALL удаляет все дополнительные Linux capabilities у контейнера.

Пример:

docker run --cap-drop=ALL secure-alpine:lab

4. Использовать read-only filesystem

Флаг --read-only делает файловую систему контейнера доступной только для чтения, если приложению не требуется запись.

Пример:

docker run --read-only secure-alpine:lab

5. Ограничивать ресурсы контейнера

Ограничение памяти и CPU снижает риск злоупотребления ресурсами хостовой системы.

Пример:

docker run --memory=128m --cpus=0.5 secure-alpine:lab

6. Не монтировать docker.sock внутрь контейнера

Монтирование Docker socket внутрь контейнера может дать процессам внутри контейнера доступ к Docker daemon на хосте.

Небезопасный пример:

docker run -v /var/run/docker.sock:/var/run/docker.sock image_name

7. Использовать минимальные базовые образы

Минимальные образы, такие как alpine или distroless, содержат меньше пакетов. Это уменьшает поверхность атаки.

8. Регулярно сканировать образы

Образы необходимо регулярно проверять с помощью сканеров безопасности, например Trivy или Clair.

Пример более безопасного запуска контейнера

Контейнер можно запускать с дополнительными флагами безопасности:

docker run -it \
--security-opt no-new-privileges \
--cap-drop=ALL \
--read-only \
--memory=128m \
--cpus=0.5 \
secure-alpine:lab
