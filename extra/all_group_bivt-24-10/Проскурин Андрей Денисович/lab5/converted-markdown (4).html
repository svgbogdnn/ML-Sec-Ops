ЛР 5. Недостатки в Python-коде и механизмы безопасности Django

Часть I. Анализ фрагментов кода

Фрагмент кода 1

#!/usr/bin/env python3
from flask import Flask

from mod_api import mod_api

app = Flask('vuln_app')
app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

app.register_blueprint(mod_api, url_prefix='/api')

Недостаток

В коде секретный ключ Flask-приложения захардкожен прямо в исходном файле:

app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

Это небезопасно, потому что исходный код обычно доступен нескольким разработчикам, может попасть в Git-репозиторий, в историю коммитов, в CI/CD, в архивы или логи. Если такой ключ утечет, его нельзя считать секретным.

Во Flask SECRET_KEY используется для криптографической подписи важных данных, например session cookie, flash-сообщений и CSRF-токенов при использовании соответствующих расширений. Если злоумышленник узнает этот ключ, он может попытаться подделывать подписанные данные приложения.

Рекомендации по устранению

  1. Убрать секретный ключ из исходного кода.
  2. Передавать его через переменные окружения:
import os

app.config['SECRET_KEY'] = os.environ.get('SECRET_KEY')

  1. использовать secret manager, например:

    • HashiCorp Vault;
    • AWS Secrets Manager;
    • GCP Secret Manager;
    • Kubernetes Secrets;
    • переменные окружения в CI/CD, если нет отдельного хранилища секретов.

  2. Не хранить .env с реальными секретами в Git.

  3. Добавить .env и локальные конфиги в .gitignore.

  4. При подозрении на утечку старый ключ нужно заменить и перевыпустить сессионные данные, потому что старый ключ уже нельзя считать доверенным.

Фрагмент кода 2

from flask_wtf import Form
from wtforms import TextField

class LoginForm(Form):
    username = TextField('username')
    password = TextField('password')

Недостаток

Поле password объявлено как обычное текстовое поле:

password = TextField('password')

Из-за этого пароль может отображаться на экране в открытом виде при вводе. Для формы авторизации это небезопасно, потому что пароль может быть подсмотрен человеком рядом, попасть на запись экрана или быть случайно показан при демонстрации экрана.

Также во фрагменте нет валидаторов. То есть форма не проверяет, что логин и пароль действительно заполнены, не ограничивает длину и не задает базовые требования к вводимым данным.

Рекомендации по устранению

Для пароля нужно использовать специальный тип поля PasswordField, а не обычное текстовое поле.

Пример исправления:

from flask_wtf import FlaskForm
from wtforms import StringField, PasswordField
from wtforms.validators import DataRequired, Length

class LoginForm(FlaskForm):
    username = StringField(
        'username',
        validators=[
            DataRequired(),
            Length(min=3, max=64)
        ]
    )

    password = PasswordField(
        'password',
        validators=[
            DataRequired(),
            Length(min=8, max=128)
        ]
    )

Что это исправляет:

  1. PasswordField скрывает вводимые символы в браузере.
  2. DataRequired() запрещает отправку пустого логина или пароля.
  3. Length() ограничивает длину входных данных.
  4. Использование FlaskForm актуальнее, чем старый Form из flask_wtf.

Фрагмент кода 3

def post(self):
    username = self.get_argument('username')
    password = self.get_argument('password').encode('utf-8')
    email = self.get_argument('mail')

    try:
        username = username.lower()
        email = email.strip().lower()
        user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})
        user.validate()
        save_user(self.db_conn, user)
    except Exception, e:
        return self.render_template("success_create.html")

1. Пароль не хешируется

Пароль берется из запроса и только кодируется в UTF-8:

password = self.get_argument('password').encode('utf-8')

Затем он передается в объект пользователя:

user = User({'username': username, 'password': password, ...})

В коде не видно, что пароль хешируется, солится или обрабатывается специальной функцией для паролей. Если такой пароль сохраняется в базу данных, то при утечке базы злоумышленник получит реальные пароли пользователей.

Кодирование .encode('utf-8') не является защитой. Это просто преобразование строки в байты, а не криптографическая операция.

2. Обрабатываются все исключения подряд

Код ловит любые ошибки:

except Exception, e:

Это слишком широкая обработка исключений. Она скрывает реальные проблемы: ошибку валидации, ошибку базы данных, ошибку сохранения, ошибку формата данных и т.д.

3. При ошибке показывается страница успешного создания

Самая опасная логическая ошибка — при исключении возвращается шаблон успешного создания:

return self.render_template("success_create.html")

То есть пользователь может получить сообщение, что аккаунт создан, хотя на самом деле регистрация могла завершиться с ошибкой. Это ломает бизнес-логику приложения и усложняет расследование проблем.

Как устранять

1. Хешировать пароль перед сохранением

для Python можно использовать passlib, bcrypt, argon2 или встроенные механизмы конкретного фреймворка.

Пример логики:

from passlib.hash import bcrypt

raw_password = self.get_argument('password')
password_hash = bcrypt.hash(raw_password)

В базу нужно сохранять не пароль, а хеш:

user = User({
    'username': username,
    'password_hash': password_hash,
    'email': email,
    'date_joined': curtime()
})

При авторизации нужно сравнивать пароль так:

bcrypt.verify(input_password, user.password_hash)

2. Проверять входные данные

Перед сохранением нужно проверять:

  • что username не пустой;
  • что email имеет корректный формат;
  • что пароль соответствует минимальным требованиям;
  • что длина полей не превышает допустимые значения;
  • что пользователь с таким именем или email еще не существует.

3. Не ловить все исключения подряд

Вместо общего except Exception лучше обрабатывать ожидаемые ошибки отдельно:

try:
    user.validate()
    save_user(self.db_conn, user)
except ValidationError as e:
    return self.render_template("error.html", message="Некорректные данные")
except DatabaseError as e:
    logger.exception("Database error during registration")
    return self.render_template("error.html", message="Ошибка сохранения пользователя")

4. Не показывать успех при ошибке

Шаблон success_create.html должен возвращаться только после реального успешного сохранения пользователя.

Пример более корректной структуры:

try:
    username = username.strip().lower()
    email = email.strip().lower()

    user = User({
        'username': username,
        'password_hash': password_hash,
        'email': email,
        'date_joined': curtime()
    })

    user.validate()
    save_user(self.db_conn, user)

except ValidationError:
    return self.render_template("error.html", message="Ошибка валидации данных")

except DatabaseError:
    logger.exception("Failed to save user")
    return self.render_template("error.html", message="Ошибка при создании пользователя")

return self.render_template("success_create.html")

Часть II. Модель безопасности Django

1. Какие наиболее распространенные атаки предотвращает Django?

1.1. XSS

XSS — это атака, при которой злоумышленник внедряет JavaScript или HTML-код в страницу, которую потом открывает другой пользователь.

Django снижает риск XSS за счет автоматического экранирования данных в шаблонах. Если пользователь ввел строку:

<script>alert(1)</script>

то при обычном выводе в Django template она должна быть показана как текст, а не выполнена как JavaScript.

Пример безопасного вывода:

{{ comment }}

Django экранирует опасные символы в HTML-контексте.

1.2. CSRF

Django защищает от CSRF с помощью CsrfViewMiddleware и CSRF-токенов. Для POST-форм в шаблонах используется:

{% csrf_token %}

Сервер проверяет, что запрос содержит корректный токен. Если токена нет или он неправильный, запрос отклоняется.

1.3. SQL Injection

Django ORM защищает от SQL-инъекций за счет параметризации запросов. Разработчик обычно работает с моделями и queryset, а не склеивает SQL-строки вручную.

Пример:

User.objects.get(username=username)

Такой подход безопаснее, чем ручная подстановка строки в SQL. Но если разработчик использует raw(), extra() или вручную собирает SQL-запросы через форматирование строк, риск SQL-инъекции остается.

1.4. Clickjacking

Django предоставляет защиту через XFrameOptionsMiddleware. Она добавляет заголовок X-Frame-Options, который запрещает или ограничивает встраивание страницы во фреймы.

1.5. Host Header Attack

Django помогает защищаться от атак через поддельный Host header с помощью настройки:

ALLOWED_HOSTS

Разработчик должен явно указать, с каких доменов приложение может обрабатывать запросы. Это снижает риск атак, связанных с генерацией ссылок, сбросом пароля, кэшированием и неправильной обработкой заголовка Host.

1.6. Дополнительные меры безопасности

Django также поддерживает настройки для безопасной работы с HTTPS и cookie:

SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = 'Lax'

Эти настройки помогают снизить риск перехвата cookie, атак через JavaScript и части CSRF-сценариев.

2. Как устроено управление пользовательскими сессиями в Django?

2.1. Общий принцип

Django имеет встроенный session framework. Он позволяет хранить данные между запросами одного и того же пользователя.

Сессии включаются через middleware:

'django.contrib.sessions.middleware.SessionMiddleware'

Когда SessionMiddleware включен, у каждого объекта request появляется атрибут:

request.session

Он работает похоже на словарь Python.

Пример записи в сессию:

request.session['user_id'] = user.id

Пример чтения:

user_id = request.session.get('user_id')

Пример удаления:

del request.session['user_id']

2.2. Где хранятся данные сессии

По умолчанию Django хранит данные сессии на стороне сервера. В cookie браузера при стандартной конфигурации хранится не вся сессия, а только идентификатор сессии.

То есть обычно схема такая:

  1. пользователь заходит на сайт;
  2. Django создает session key;
  3. session key отправляется пользователю в cookie;
  4. сами данные сессии лежат на сервере;
  5. при следующих запросах браузер отправляет cookie;
  6. Django по session key находит данные сессии.

2.3. Варианты хранения сессий

  1. Database-backed sessions — хранение в базе данных. Это стандартный и распространенный вариант.
  2. Cached sessions — хранение в кэше.
  3. Cached database sessions — комбинация кэша и базы данных.
  4. File-based sessions — хранение в файлах.
  5. Cookie-based sessions — хранение данных прямо в cookie, но с криптографической подписью.

Для cookie-based sessions используется настройка:

SESSION_ENGINE = "django.contrib.sessions.backends.signed_cookies"

2.4. Связь с аутентификацией

Обычно используются два middleware:

'django.contrib.sessions.middleware.SessionMiddleware'
'django.contrib.auth.middleware.AuthenticationMiddleware'

SessionMiddleware отвечает за механизм сессии, а AuthenticationMiddleware использует сессию, чтобы определить текущего пользователя и добавить в request объект:

request.user

После успешного логина Django сохраняет в сессии информацию, которая позволяет на следующих запросах определить пользователя.

2.5. Безопасность сессий

Django предусматривает несколько механизмов и настроек для защиты сессий.

HttpOnly

SESSION_COOKIE_HTTPONLY = True

Эта настройка запрещает JavaScript читать session cookie. Это снижает риск кражи cookie при XSS.

Secure

SESSION_COOKIE_SECURE = True

Cookie будет отправляться только по HTTPS. Это важно для production-среды.

SameSite

SESSION_COOKIE_SAMESITE = 'Lax'

SameSite ограничивает отправку cookie в межсайтовых запросах и помогает снижать риск CSRF.

Время жизни сессии

Срок жизни session cookie настраивается через:

SESSION_COOKIE_AGE

Также можно указать, что сессия должна завершаться при закрытии браузера:

SESSION_EXPIRE_AT_BROWSER_CLOSE = True

Очистка сессии при logout

При выходе пользователя из аккаунта Django должен очищать сессию. Для этого используется метод:

request.session.flush()

Он удаляет данные текущей сессии и session cookie. Это нужно, чтобы старые данные не могли быть использованы повторно.

Ротация ключа сессии

При изменении уровня доверия, например после логина, полезна ротация session key. Это снижает риск session fixation, когда злоумышленник заранее навязывает пользователю известный идентификатор сессии.

Для этого используется:

request.session.cycle_key()

2.6. Когда Django сохраняет сессию

Django сохраняет сессию не на каждый запрос, а обычно только когда она была изменена.

Например, сессия считается измененной:

request.session['foo'] = 'bar'

или:

del request.session['foo']

Если изменяется вложенный объект, Django может не понять, что сессия изменилась:

request.session['foo']['bar'] = 'baz'

В таком случае можно явно указать:

request.session.modified = True

2.7. Важные риски

Основные риски:

  • слабый или утекший SECRET_KEY;
  • отключенный HttpOnly;
  • использование cookie-based sessions для чувствительных данных;
  • работа без HTTPS;
  • слишком долгий срок жизни сессии;
  • неправильная настройка SESSION_COOKIE_DOMAIN;
  • отсутствие очистки старых сессий.

Итоговый вывод

В первой части были найдены типовые ошибки в Python/Flask-коде:

  1. секретный ключ хранится прямо в исходном коде;
  2. пароль в форме объявлен как обычное текстовое поле;
  3. пароль не хешируется перед сохранением, а ошибки регистрации скрываются и показывается успешный результат.

Во второй части рассмотрены механизмы безопасности Django. Django помогает защищаться от XSS, CSRF, SQL Injection, clickjacking и некоторых атак через Host header. Управление сессиями реализовано через SessionMiddleware.
