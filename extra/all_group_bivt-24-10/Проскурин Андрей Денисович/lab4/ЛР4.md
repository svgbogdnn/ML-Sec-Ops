# Часть I. CVE за 2021 год: XSS в PHP-компонентах

## Как я искал

Я искал CVE за 2021 год, где в описании есть XSS / Cross-Site Scripting, а уязвимый компонент относится к PHP-приложениям, PHP-библиотекам или PHP-based CMS / plugins.

Критерии отбора:
- CVE относится к 2021 году;
- в описании указана XSS-уязвимость;
- компонент написан на PHP или является PHP-приложением / PHP-плагином;
- причина связана с тем, что пользовательский ввод выводится на страницу без корректного экранирования или санитизации.

По выбранному фильтру я насчитал 8 подходящих CVE.

## Подробное описание двух CVE

## 1. CVE-2021-3783 — YOURLS

**Компонент:** YOURLS  
**Ссылка на CVE:** https://nvd.nist.gov/vuln/detail/CVE-2021-3783  
**Официальный сайт:** https://yourls.org/  
**GitHub:** https://github.com/YOURLS/YOURLS

### Для чего используется компонент

YOURLS расшифровывается как Your Own URL Shortener. Это self-hosted сервис для сокращения ссылок, написанный в основном на PHP. Его можно развернуть на своем сервере и использовать как собственный аналог bit.ly или TinyURL.

### Какой функционал предоставляет

YOURLS позволяет:
- создавать короткие ссылки;
- управлять списком ссылок через админ-панель;
- смотреть статистику переходов;
- использовать API для интеграции с другими приложениями;
- подключать плагины;
- разворачивать приватный или публичный сервис сокращения ссылок.

### В чем суть уязвимости

В CVE указано, что YOURLS был уязвим к Improper Neutralization of Input During Web Page Generation, то есть к XSS. Проблема возникает, когда пользовательский ввод попадает в HTML-страницу без безопасного экранирования. В таком случае браузер может воспринять введенную строку не как обычный текст, а как HTML или JavaScript.

### Причина

Основная причина — недостаточная обработка пользовательских данных перед выводом на страницу. Если специальные символы вроде `<`, `>`, `"`, `'`, `&` не преобразуются в HTML-сущности, пользователь может внедрить тег `<script>` или другой HTML-код.

## 2. CVE-2021-43698 — phpWhois

**Компонент:** phpWhois  
**Ссылка на CVE:** https://nvd.nist.gov/vuln/detail/CVE-2021-43698  
**GitHub:** https://github.com/phpWhois/phpWhois

### Для чего используется компонент

phpWhois — это PHP-библиотека для выполнения Whois-запросов. Она используется в PHP-приложениях, когда нужно получить регистрационные данные о домене, IP-адресе или автономной системе.

### Какой функционал предоставляет

phpWhois позволяет:
- выполнять Whois-запросы из PHP-кода;
- получать raw-ответ Whois-сервера;
- получать разобранные данные, если для конкретного регистратора есть обработчик;
- работать с доменными именами;
- выполнять Whois-запросы по IP и AS.

### В чем суть уязвимости

В CVE указано, что XSS находилась в файле `example.php`. Проблема была связана с тем, что сообщение, выводимое пользователю через `exit`, содержало значение из `$_GET['query']`. Если это значение не экранировать, в него можно передать HTML или JavaScript-код.

### Причина

Причина — прямой вывод пользовательского параметра из GET-запроса в HTML-ответ без безопасного преобразования.

# Часть II. Симуляция XSS-атаки на учебном стенде

## Ход рассуждений и проверки

### Шаг 1. Проверка обычного ввода

Сначала я ввел обычный комментарий без специальных символов:

```text
test comment
```

После отправки комментарий появился на странице. вывод, что приложение принимает пользовательский ввод и выводит его обратно в HTML-страницу.

### Шаг 2. Проверка специальных символов

Дальше я попробовал ввести набор символов, которые имеют значение для HTML:

```text
< > & " '
```

Приложение не показало явной ошибки. Символы не были нормально нейтрализованы как безопасный текст. Поэтому я предположил, что данные могут вставляться в страницу без корректного HTML-экранирования.

### Шаг 3. Проверка HTML-инъекции

После этого я попробовал ввести простой HTML:

```html
<b>test</b>
```

Если бы приложение экранировало ввод, браузер показал бы строку буквально как текст: `<b>test</b>`. Но тег был обработан как HTML. Это означает, что приложение не просто показывает комментарий как текст, а позволяет браузеру интерпретировать введенную разметку.

### Шаг 4. Проверка выполнения JavaScript

Для безопасной учебной проверки я использовал простой payload, который только показывает всплывающее окно:

```html
test<script>alert('XSS')</script>
```

После отправки комментария браузер выполнил JavaScript-код, и появилось всплывающее окно с текстом:

```text
XSS
```

Это подтверждает, что пользовательский ввод выполняется в контексте браузера клиента.

### Шаг 5. Проверка сохранения

После обновления страницы комментарий остался на странице, и скрипт снова выполнился. Из этого я сделал вывод, что уязвимость не просто отраженная, а сохраненная: вредоносный ввод сохраняется приложением и выполняется при повторном открытии страницы.

---

## Описание найденной уязвимости

В приложении найдена XSS-уязвимость в форме комментариев.

Суть проблемы: приложение принимает пользовательский ввод, сохраняет его и затем выводит обратно на страницу без корректного экранирования. Из-за этого браузер воспринимает введенный текст как HTML/JavaScript и выполняет его.

Пример:

```html
test<script>alert('XSS')</script>
```

Ожидаемое безопасное поведение: строка должна быть показана как обычный текст.

Фактическое поведение: тег `<script>` был обработан браузером, и JavaScript-код выполнился.

---

## Тип найденной уязвимости

Тип уязвимости: **XSS — Cross-Site Scripting**.

Подтип: **Stored XSS / Persistent XSS**, потому что payload сохраняется в комментарии и выполняется повторно при открытии страницы.

Также уязвимость можно связать с CWE-79: Improper Neutralization of Input During Web Page Generation.

---

# Меры предотвращения

## 1. Экранировать пользовательский ввод при выводе

Главная мера — не выводить пользовательский ввод в HTML как есть. Все данные, пришедшие от пользователя, нужно считать недоверенными.

При выводе в HTML нужно преобразовывать специальные символы:

| Символ | Безопасная замена |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#x27;` или `&#039;` |
| `/` | `&#x2F;` при необходимости |

Например, строка:

```html
<script>alert('XSS')</script>
```

должна выводиться на странице как текст:

```html
&lt;script&gt;alert(&#x27;XSS&#x27;)&lt;/script&gt;
```

Для PHP можно использовать:

```php
echo htmlspecialchars($comment, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
```

Важно применять экранирование именно при выводе данных на страницу, потому что один и тот же ввод может использоваться в разных контекстах: HTML-текст, HTML-атрибут, JavaScript, URL или CSS.

---

## 2. Использовать разные правила для разных контекстов

HTML-экранирование подходит не для всех случаев. Нужно учитывать, куда именно вставляется пользовательское значение.

Примеры:
- если значение вставляется между HTML-тегами, нужно HTML entity encoding;
- если значение вставляется в HTML-атрибут, нужно attribute encoding и обязательные кавычки вокруг значения;
- если значение попадает в URL, нужно URL encoding;
- если значение используется внутри JavaScript-строки, нужно JavaScript encoding;
- лучше вообще не вставлять пользовательский ввод напрямую в `<script>`, `<style>`, обработчики событий и опасные атрибуты.

---

## 3. Запретить опасные HTML-конструкции

Если комментарии должны быть обычным текстом, то HTML нужно полностью запрещать.

Нужно запрещать или удалять:
- `<script>`;
- `<style>`;
- `<iframe>`;
- `<object>`;
- `<embed>`;
- обработчики событий: `onclick`, `onerror`, `onload`, `onmouseover` и похожие;
- ссылки с `javascript:`;
- ссылки с `data:`, если они не нужны по бизнес-логике.

Если пользователям все-таки разрешен ограниченный HTML, нужно использовать allowlist-подход. Например, разрешить только безопасные теги:

```text
<b>, <i>, <br>, <p>
```

И отдельно запретить любые JavaScript-события и опасные атрибуты.

---

## 4. Валидировать ввод

Для комментариев можно ввести ограничения:
- максимальная длина комментария;
- запрет управляющих символов;
- нормализация кодировки в UTF-8;
- проверка, что поле не пустое;
- если HTML не нужен — принимать и хранить только обычный текст.

Но одной валидации недостаточно. Даже после валидации все равно нужно экранировать вывод.

---

## 5. Настроить Content Security Policy

CSP не исправляет саму ошибку в коде, но снижает риск эксплуатации. Например, можно запретить inline-скрипты:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

Такой заголовок усложнит выполнение внедренного JavaScript-кода. Но CSP должна быть дополнительной мерой, а не заменой экранирования.

---

## 6. Защитить cookie

Чтобы уменьшить последствия XSS, cookie сессии должны иметь защитные флаги:

```http
HttpOnly
Secure
SameSite=Lax или SameSite=Strict
```

`HttpOnly` не даст JavaScript напрямую читать cookie. Это не убирает XSS, но снижает возможный ущерб.

---

## Итоговый вывод

На учебном стенде была найдена XSS-уязвимость в форме комментариев. Приложение сохраняет пользовательский ввод и выводит его на страницу без безопасного экранирования. В результате удалось вставить JavaScript-код и убедиться, что он выполняется в браузере.

Тип уязвимости — Stored XSS. Основная причина — отсутствие корректного output encoding для пользовательских данных. Основная мера защиты — экранировать спецсимволы при выводе, валидировать ввод, не разрешать опасные HTML-конструкции и дополнительно использовать CSP.
