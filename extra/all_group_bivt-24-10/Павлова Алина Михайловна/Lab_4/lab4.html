Лабораторная работа №4: Симуляция XSS-атаки

Часть I: Анализ XSS-уязвимостей в PHP-компонентах за 2021 год

Общее количество CVE за 2021 год

По данным National Vulnerability Database (NVD), общее количество уязвимостей за 2021 год составляет ~20 140.

Среди них значительную долю занимают XSS-уязвимости в веб-приложениях на PHP, что подтверждает актуальность проблемы даже для хорошо изученного типа атак.

Источники статистики:

  • https://cve.mitre.org/statistics/
  • https://nvd.nist.gov/vuln/search

1. CVE-2021-43698 — XSS в phpWhois

Параметр Значение
CVE CVE-2021-43698
Дата публикации 29 ноября 2021
CNA MITRE
Источник NVD

Компонент: phpWhois

Назначение компонента:
Библиотека для выполнения WHOIS-запросов — получения информации о зарегистрированных доменных именах.

Функционал:

  • Получение информации о владельцах доменов
  • Просмотр данных о DNS-серверах
  • Проверка статуса домена
  • Получение контактной информации регистранта
  • Анализ доменной инфраструктуры

Описание XSS-уязвимости:
В файле example.php параметр $_GET['query'] выводится на страницу без должной экранизации. Функция exit завершает скрипт и выводит сообщение, содержащее пользовательский ввод напрямую в HTML. Это позволяет злоумышленнику внедрить произвольный JavaScript код, который выполнится в браузере пользователя.

Причина:
Отсутствие экранирования пользовательского ввода перед выводом в HTML. Не используется функция htmlspecialchars() или аналогичные механизмы защиты.

Последствия:

  • Выполнение произвольного JavaScript в браузере жертвы
  • Кража сессионных cookies
  • Компрометация учётных записей

2. CVE-2021-21345 — XSS в phpMyAdmin

Параметр Значение
CVE CVE-2021-21345
Дата публикации 2021
CNA MITRE
Источник NVD

Компонент: phpMyAdmin

Назначение компонента:
Веб-интерфейс для администрирования баз данных MySQL.

Функционал:

  • Создание, редактирование и удаление баз данных
  • Выполнение SQL-запросов
  • Управление таблицами и записями
  • Настройка прав доступа пользователей
  • Экспорт/импорт данных (SQL, CSV, XML, JSON)
  • Администрирование сервера MySQL
  • Управление пользователями и привилегиями

Описание XSS-уязвимости:
Отражённая XSS-уязвимость в параметре table. Злоумышленник может внедрить вредоносный JavaScript код, который выполнится в контексте браузера администратора при открытии специально сформированной ссылки.

Причина:
Недостаточная экранизация пользовательского ввода перед выводом в HTML. Параметр table не проходит должную фильтрацию и санитизацию.

Последствия:

  • Кража сессионных cookies администратора
  • Получение полного контроля над базой данных
  • Выполнение действий от имени администратора
  • Компрометация всей системы управления БД

Часть II: Практическая симуляция XSS-атаки

Ход рассуждений и действия

Шаг 1: Запустила Docker-контейнер с образом ket9/otus-devsecops-xss:latest.

docker pull ket9/otus-devsecops-xss:latest
docker run -d -p 8080:80 ket9/otus-devsecops-xss:latest
docker ps

Шаг 2: Открыла приложение по адресу http://localhost:8080/XSS-1/index.php. Обнаружила форму для ввода комментариев.

Шаг 3: Ввела тестовую строку TEST_XSS_12345 и проверила, отображается ли она на странице. Текст отобразился без изменений, что указывает на отсутствие фильтрации.

Шаг 4: Внедрила XSS-пейлоад:

<script>alert('XSS_SUCCESS')</script>

Шаг 5: После нажатия кнопки "Save Data" появилось всплывающее окно браузера с сообщением XSS_SUCCESS.

Шаг 6: При обновлении страницы окно появляется снова, что указывает на Stored XSS — скрипт сохранился в базе данных и выполняется при каждой загрузке страницы.

Вывод: Приложение не экранирует пользовательский ввод перед выводом в HTML, что позволяет выполнить произвольный JavaScript в контексте браузера пользователя. Это критическая уязвимость безопасности.

Ответ приложения

Всплывающее окно браузера alert() с текстом XSS_SUCCESS и XSS.

Тип найденной уязвимости

Stored Cross-Site Scripting (XSS) — межсайтовый скриптинг второго порядка.

Злоумышленник внедряет вредоносный JavaScript код в форму комментария, который сервер сохраняет в базе данных без должной санитизации. При каждом посещении страницы другими пользователями скрипт выполняется в их браузерах.

Последствия

  1. Выполнение произвольных скриптов в браузере пользователя
  2. Кража сессионных cookies и метаданных сессии
  3. Компрометация учётных записей пользователей
  4. Подмена содержимого страницы
  5. Перенаправление на фишинговые сайты
  6. Выполнение действий от имени жертвы

Меры предотвращения

1. Экранирование специальных символов при выводе в HTML:

Символ HTML-сущность
< &lt;
> &gt;
" &quot;
' &#x27;
& &amp;

В PHP использовать функцию htmlspecialchars() с флагом ENT_QUOTES:

echo htmlspecialchars($user_input, ENT_QUOTES, 'UTF-8');

2. Валидация и фильтрация входных данных:

  • Использовать белые списки (whitelist) для разрешённых символов
  • Отклонять ввод, содержащий теги <script>, <img>, <svg>, <body>
  • Блокировать обработчики событий: onerror, onload, onclick, onmouseover

3. Content Security Policy (CSP): Настроить HTTP-заголовок:

Content-Security-Policy: default-src 'self'; script-src 'self'

Это запретит выполнение inline-скриптов и скриптов из внешних источников.

4. Использование безопасных фреймворков:

  • Современные шаблонизаторы (Twig, Blade) автоматически экранируют вывод
  • Не отключать авто-экранирование без крайней необходимости

5. HttpOnly флаг для cookies:

setcookie('session', $value, [
    'httponly' => true,
    'secure' => true,
    'samesite' => 'Strict'
]);

Это предотвратит кражу cookies через JavaScript.

6. Регулярное тестирование:

  • Проводить статический анализ кода (SonarQube, PHPStan)
  • Использовать динамическое тестирование (OWASP ZAP, Burp Suite)
  • Проводить penetration testing
