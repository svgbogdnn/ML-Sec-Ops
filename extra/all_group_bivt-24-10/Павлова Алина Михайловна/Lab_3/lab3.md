# Часть 1

## 1\. CVE-2025-54554 — Broken Authentication / Information Disclosure

**Источник:** [https://cve.org/CVERecord?id=CVE-2025-54554](https://cve.org/CVERecord?id=CVE-2025-54554)

**Недостаток:** Неаутентифицированные запросы к REST API компонента tiaudit в Tera Insights tiCrypt позволяют получить информацию о внутренних SQL-запросах и структуре базы данных.

**Причина:** Отсутствие проверки аутентификации на конечных точках API и небезопасная обработка ошибок, которая раскрывает внутреннюю логику приложения.

**Категория OWASP API Security Top 10:** API2:2023 Broken Authentication

## 2\. CVE-2025-46363 — Security Misconfiguration / Path Traversal

**Источник:** [https://cve.org/CVERecord?id=CVE-2025-46363](https://cve.org/CVERecord?id=CVE-2025-46363)

**Недостаток:** Уязвимость обхода пути (Relative Path Traversal) в REST API шлюза Dell Secure Connect Gateway позволяет низкопривилегированному пользователю получать доступ к ограниченным ресурсам через манипуляции с путями.

**Причина:** Недостаточная санитизация входных параметров пути в API-запросах; сервер не проверяет, что запрашиваемый ресурс находится внутри разрешенной директории.

**Категория OWASP API Security Top 10:** API8:2023 Security Misconfiguration

## 3\. CVE-2025-4166 — Improper Inventory Management / Log Leakage

**Источник:** [https://cve.org/CVERecord?id=CVE-2025-4166](https://cve.org/CVERecord?id=CVE-2025-4166)

**Недостаток:** Плагин Key/Value v2 в HashiCorp Vault может непреднамеренно раскрывать чувствительные данные в логах сервера и аудита при обработке неправильно сформированных полезных нагрузок через REST API.

**Причина:** Небезопасное логирование — приложение записывает содержимое запросов или ошибок без маскирования конфиденциальных данных.

**Категория OWASP API Security Top 10:** API9:2023 Improper Inventory Management

# Часть 2

## Разведка эндпоинтов

После запуска контейнера и инициализации БД через /createdb, я изучила интерфейс приложения. На главной странице доступен список эндпоинтов REST API:

*   /createdb — создание базы данных
*   /users/v1 — просмотр информации обо всех пользователях
*   /users/v1/\_debug — просмотр подробной информации обо всех пользователях
*   /users/v1/register — регистрация нового пользователя
*   /users/v1/login — вход в приложение
*   /users/v1/{username} — просмотр пользователя по имени
*   /users/v1/{username}/email — изменить email пользователя
*   /users/v1/{username}/password — изменить пароль пользователя
*   /books/v1 — все книги

## 1\. Найденная уязвимость: доступ к /users/v1/\_debug

### Ход рассуждений:

Я обратила внимание на эндпоинт /users/v1/\_debug, который предположительно предназначен для отладки. Перейдя по этому адресу без какой-либо авторизации, я получила доступ ко всем данным пользователей, включая их пароли в открытом виде.

### Ответ приложения:

    {
      "users": [
        {
          "admin": false,
          "email": "mail1@mail.com",
          "password": "pass1",
          "username": "name1"
        },
        {
          "admin": false,
          "email": "mail2@mail.com",
          "password": "pass2",
          "username": "name2"
        },
        {
          "admin": true,
          "email": "admin@mail.com",
          "password": "pass1",
          "username": "admin"
        }
      ]
    }

### Выводы:

Приложение не проверяет права доступа к чувствительным данным. Любой пользователь (даже неаутентифицированный) может получить пароли всех учетных записей, включая администратора. Это критическая уязвимость, позволяющая полностью компрометировать систему.

### Описание уязвимости:

Эндпоинт /users/v1/\_debug возвращает все поля таблицы пользователей, включая пароли в plaintext (открытом виде), без какой-либо проверки аутентификации или авторизации. Это нарушает принцип минимальных привилегий и позволяет злоумышленнику получить учетные данные всех аккаунтов.

### Тип уязвимости по OWASP API Security Top 10:

**API3:2023 — Broken Object Property Level Authorization** (также классифицируется как Excessive Data Exposure)

### Меры предотвращения:

1.  **Никогда не возвращать пароли в ответах API** — даже в хешированном виде лучше не показывать.
2.  **Реализовать проверку прав доступа**: эндпоинт \_debug должен быть доступен только администраторам или полностью отключен в production.
3.  **Хранить пароли только в хешированном виде** (bcrypt, argon2, scrypt).
4.  **Использовать механизмы контроля доступа на уровне свойств объектов** (property-level authorization).
5.  **Удалить отладочные эндпоинты** из производственной среды.
