# Лабораторная работа №6: Поиск секретов в репозитории с помощью truffleHog

---

## Введение

Для этой лабораторной работы я проанализировала репозиторий [DevSecOps_secret-finding](https://github.com/OtusTeam/DevSecOps_secret-finding.git) на наличие случайно закоммиченных секретов: паролей, ключей, токенов и других чувствительных данных.

Поскольку установка truffleHog через Docker была ограничена сетевыми проблемами (TLS handshake timeout при доступе к Docker Hub), я использовала альтернативный метод:
1. Клонировала репозиторий локально: `git clone ...`
2. Проанализировала историю коммитов через `git log -p --all | grep -iE "password|secret|token|key"`
3. Искала паттерны, характерные для секретов, в диффах изменений

### 1. Пароль от Artifactory в pom.xml

**Где лежит:** `pom.xml`, коммит `14becbb2cd27bb0f14dfb216748db08ff4e819df`

```xml
<plugin>
    <groupId>org.jfrog.buildinfo</groupId>
    <artifactId>artifactory-maven-plugin</artifactId>
    ...
    <publisher>
        <username>deployer</username>
        <password>Asdf1243?[2#323</password>
        ...
    </publisher>
</plugin>
```

**Почему это секрет:**  
Это пароль от репозитория артефактов Artifactory в открытом виде. С этими учётными данными можно:
- Загружать вредоносные артефакты в репозиторий
- Скачивать приватные зависимости
- Использовать эти данные для атак на другие сервисы (при переиспользовании пароля)

**Как хранить нормально:**
- Использовать переменные окружения в CI/CD: `${env.ARTIFACTORY_PASSWORD}`
- Хранить в секрет-менеджере (Jenkins Credentials, HashiCorp Vault, AWS Secrets Manager)
- Использовать `settings.xml` с зашифрованным паролем (`mvn --encrypt-password`)
- Никогда не коммитить пароли в `pom.xml`

### 2. GitHub Token / API Key

**Где лежит:** в истории коммитов, файл конфигурации CI/CD

```text
GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5
```

**Почему это секрет:**  
Строка длиной 64 символа в шестнадцатеричном формате — типичный формат GitHub Personal Access Token или API-ключа. Такой токен даёт доступ к:
- Чтению и записи в репозитории
- Управлению GitHub Actions workflows
- Доступу к приватным данным организации

**Как хранить нормально:**
- Использовать **GitHub Actions Secrets** для хранения токенов в CI/CD
- Хранить в секрет-менеджере (Vault, AWS Secrets Manager)
- Использовать переменные окружения: `$GITHUB_TOKEN`
- Устанавливать минимально необходимые права (scopes) для токена
- Регулярно ротировать токены и отзывать неиспользуемые

### 3. Hardcoded JWT Password в Java-коде

**Где лежит:** `src/main/java/.../HashingAssignment.java` (и аналогичные файлы)

```java
public static final String PASSWORD = "bm5nhSkxCXZkKRy4";
private static final String JWT_PASSWORD = "bm5n3SkxCX4kKRy4";
```

**Почему это секрет:**  
Пароли для подписи JWT-токенов захардкожены в исходном коде. Злоумышленник с доступом к коду может:
- Подделывать любые JWT-токены
- Получать доступ от имени любого пользователя
- Обходить аутентификацию и авторизацию
- Компрометировать всю систему аутентификации

**Как хранить нормально:**
- Использовать переменные окружения: `System.getenv("JWT_SECRET")`
- Хранить в секрет-менеджере (Vault, AWS Secrets Manager)
- Генерировать криптографически стойкие секреты при деплое
- Никогда не хранить секреты в исходном коде, даже в константах

```text
-----END PRIVATE KEY-----
```

**Почему это секрет:**  
Это полноценный приватный RSA-ключ в формате PEM. С ним можно:
- Аутентифицироваться на серверах без пароля (SSH, TLS)
- Подписывать запросы и данные от имени владельца ключа
- Расшифровывать данные, зашифрованные соответствующим публичным ключом
- Выдавать себя за сервис или пользователя

**Как хранить нормально:**
- Никогда не коммитить приватные ключи в репозиторий
- Использовать `ssh-agent` для временного хранения ключей в памяти
- Хранить ключи в защищённом хранилище с ограниченным доступом (Vault, AWS KMS)
- Использовать `passphrase` для дополнительной защиты ключа
- Регулярно ротировать ключи и отслеживать их использование

### 5. JWT Token в тестовом коде

**Где лежит:** тестовый Java-файл (например, `SessionManagementTest.java`)

```java
var token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.NFvYpuwbF6YWbPyaNAGEPw9wbhiQSovvSrD89B8K7Ng";
```

**Почему это секрет:**  
Полный подписанный JWT-токен, захардкоженный в коде. Хотя это может быть тестовый токен, в реальных проектах такие токены могут:
- Давать доступ к защищённым эндпоинтам без аутентификации
- Раскрывать структуру пейлоада и алгоритм подписи
- Быть использованы для атак, если секрет подписи слабый или известен

**Как хранить нормально:**
- Генерировать токены динамически в тестах через аутентификацию
- Использовать mock-объекты вместо реальных токенов
- Не хранить токены в коде, даже тестовом
- Использовать environment-specific конфигурации для тестовых данных

## Дополнительные вопросы

###  Что такое BFG Repo-Cleaner и для чего он предназначен?

**BFG Repo-Cleaner** — это утилита для быстрой очистки истории Git-репозитория от больших файлов и чувствительных данных (паролей, ключей, токенов, сертификатов).

**Зачем он нужен:**  
Если секрет уже попал в историю коммитов, просто удалить его из текущего файла недостаточно — он останется во всех предыдущих версиях. BFG переписывает историю репозитория, удаляя нежелательные данные из всех ревизий.

**Отличия от `git filter-branch`:**
- Работает в 10–50 раз быстрее
- Проще в использовании (меньше команд, понятный синтаксис)
- Специализирован именно для удаления файлов и строк по паттернам

**Пример использования:**
```bash
# Удалить файл с ключами из всей истории
bfg --delete-files id_rsa

# Удалить строки, содержащие определённый пароль
bfg --replace-text passwords.txt

# После очистки обязательно выполнить:
git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

**Важно:** После очистки истории нужно:
1. Перевыпустить все скомпрометированные ключи и пароли
2. Предупредить всех разработчиков, у кого есть локальные копии репозитория
3. Принудительно запушить изменения: `git push --force`

### Как можно автоматизировать процесс поиска секретов и насколько это правильный подход?

**Способы автоматизации:**

1. **Pre-commit хуки** — запуск сканера перед каждым коммитом:
   ```yaml
   # .pre-commit-config.yaml
   repos:
     - repo: https://github.com/dxa4481/truffleHog
       rev: master
       hooks:
         - id: trufflehog
           args: ['--regex', '--entropy=False']
   ```

2. **CI/CD пайплайн** — сканирование на каждом пуше/мердже:
   ```yaml
   # .github/workflows/secrets-scan.yml
   name: Secrets Scan
   on: [push, pull_request]
   jobs:
     scan:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v3
         - name: Run truffleHog
           run: |
             pip install truffleHog
             truffleHog . --regex --entropy=False
   ```

3. **Периодическое сканирование** — cron-задача с `gitleaks` или `truffleHog` для мониторинга всех репозиториев организации.

4. **Git hook на сервере** — проверка пушей на уровне Git-сервера (GitLab, Gitea).

**Правильный ли это подход?**  **Да, автоматизация — правильный и необходимый подход**, потому что:

| Преимущество | Описание |
|-------------|----------|
| Исключает человеческий фактор | Разработчики могут случайно закоммитить секрет, автоматизация ловит это до попадания в main |
| Раннее обнаружение | Блокировка проблемного кода на этапе коммита/пуша, а не после деплоя |
| Масштабируемость | Работает одинаково для 1 или 100 репозиториев |
| Соответствие требованиям | Помогает соблюдать security policies и стандарты (PCI DSS, SOC2) |

 **Но важно помнить о ограничениях:**

| Проблема | Решение |
|----------|---------|
| Ложные срабатывания | Настройка правил, тюнинг паттернов, ручной аудит срабатываний |
| Пропуски (false negatives) | Комбинация нескольких сканеров, регулярное обновление правил |
| Секреты в истории | Использовать BFG Repo-Cleaner для ретроспективной очистки |
| Обучение команды | Автоматизация не заменяет awareness: разработчики должны понимать, что нельзя коммитить |

**Вывод:** Правильный подход — это **комбинация**:
-  Автоматизация для быстрого поиска подозрительных мест
-  Ручной аудит для фильтрации ложных срабатываний
-  Обучение команды безопасным практикам
-  Интеграция с secret-менеджерами для правильного хранения
