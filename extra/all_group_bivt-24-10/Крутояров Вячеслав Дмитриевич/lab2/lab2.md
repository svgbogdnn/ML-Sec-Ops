## Часть 1

# 1) CVE-2025-12030 (Уязвимость в плагине ACF to REST API для WordPress)

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-12030

Тип по OWASP: API1:2023 — Broken Object Level Authorization (BOLA)

Недостаток: Авторизованный пользовательможет изменять права доступа к объектам, которые ему не принадлежат, отправляя специальный REST API запрос

Причина: Недостаточная проверка прав на стороне сервера. Метод update_item_permissions_check() проверяет только то, что у пользователя в принципе есть право edit_posts, но система забывает проверить, является ли запрашивающий пользователь истинным владельцем конкретного объекта, айдишник которого он передает в запросе

# 2) CVE-2025-61928 (Уязвимость в библиотеке авторизации Better Auth)

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-61928

Тип по OWASP: API2:2023 — Broken Authentication

Недостаток: Критический обход аутентификации. То есть неаутентифицированный злоумышленник может сгенерить валидный апи ключ для абсолютно любого пользователя системы и получить полный доступ к чужому аккаунту для выполнения несанкционированных действий

Причина: Фатальная логическая ошибка на бэкенде аутентификации. Если сессия отсутствует, но злоумышленник вручную подставляет чужой userId в тело запроса, переменная authRequired переключается в значение false. Сервер слепо доверяет переданному id и выполняет запрос к базе данных без проверки пароля или токена

# 3) CVE-2025-66573 (Уязвимость в Solstice Pod API)

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-66573

Тип по OWASP: API5:2023 — Broken Function Level Authorization

Недостаток: Любой неавторизованный пользователь из сети может извлечь активные ключи сессий, версии сервера и другие критические системные данные, просто обратившись к эндпоинту /api/config

Причина: Полное отсутствие механизма контроля доступа на административном уровне api. Эндпоинт, который по бизнес логике должен отдавать конфигурацию системы только доверенным административным узлам, оставлен открытым для любых входящих запросов

## Часть 2

Зашел на http://localhost:8080/, увидел там все эндпоинты:
{ "создать базу": "/createdb",     "посмотреть информацию обо всех пользователях": "/users/v1",     "посмотреть подробную информацию обо всех пользователях": "/users/v1/_debug",     "регистрация нового пользователя": "/users/v1/register (HTTP POST)",     "вход в приложение": "/users/v1/login (HTTP POST)",     "просмотр пользователя по имени": "/users/v1/{username}",     "удалить пользователя по имени (только для админов)": "/users/v1/{username} (HTTP DELETE)",     "изменить email пользователя": "/users/v1/{username}/email (HTTP PUT)",     "изменить пароль пользователя": "/users/v1/{username}/password (HTTP PUT)",     "все книги": "/books/v1",     "добавить книгу": "/books/v1 (HTTP POST)",     "просмотр книги": "/books/v1/{book}",      } 

Инициализировал бд, отправив запрос на /createdb. Получил: { "message": "Database populated." }

Дальше сделал базовый get запрос на /users/v1, чтобы посмотреть список пользователей. Приложение вернуло 3 учетные записи (name1, name2, admin), но только с публичной информацией (email и username)

"посмотреть подробную информацию обо всех пользователях": "/users/v1/_debug" выглядит подозридельно, поэтому ч решил отправит get запрос по этому адресу. Получил полный дамп базы пользователей, который включал скрытые поля

{"admin": false,
"email": "mail1@mail.com",
"password": "pass1",
"username": "name1"}

Значит обычный пользователь, даже неавторизованный, имеет прямой доступ к отладочному эндпоинту, который раскрывает конфиденциальные данные всей системы. Приложение возвращает полные объекты пользователей, включая их пароли в открытом виде и внутренние флаги привилегий. Это критическая утечка информации

Это API3:2023 — Broken Object Property Level Authorization (это ситуация, когда api неправильно контролирует доступ к отдельным свойствам объекта, отдавая клиенту избыточные данные, которые не требуются для работы бизнес-логики)

# Меры предотвращения:

1. Ограничение отладочных функций: Полностью удалить или жёстко закрыть авторизацией _debug-эндпоинты перед релизом приложения

2. Использование DTO (Data Transfer Objects): Настроить сервер так, чтобы для ответа клиенту формировался специальный безопасный объект, содержащий только разрешенные поля (например, только username), а системные свойства (такие как password или флаг admin) отфильтровывались на уровне бэкенда

3. Единый слой контроля доступа: внедрить обязательную проверку прав (например, наличие сессии и роли администратора) для любых эндпоинтов, раскрывающих массивы пользовательских данных
