# Часть 1
#### 1) SSRF в GitLab Webhooks REST API
https://nvd.nist.gov/vuln/detail/CVE-2025-6454 - Тип (OWASP API Top 10):
API7:2023 — Server Side Request Forgery (SSRF).

*Недостаток:*  
В GitLab есть уязвимость в функциональности веб‑хуков: при конфигурации webhook пользователь может указать кастомные HTTP‑заголовки и URL так, что GitLab формирует и отправляет HTTP‑запросы от имени сервера к произвольным адресам, включая внутренние. Это позволяет злоумышленнику использовать GitLab как SSRF‑прокси, обращаться к внутренним сервисам в инфраструктуре компании и потенциально вытаскивать оттуда чувствительные данные или выстраивать дальнейшую атаку.

*Причина:*  
Недостаточная валидация данных, которые задают параметры исходящего запроса (URL, заголовки), сервер без ограничений доверяет значениям, пришедшим от клиента.

#### 2)Неконтролируемая рекурсия в API NVIDIA Triton Inference Server
https://nvd.nist.gov/vuln/detail/CVE-2025-23325 - ближе всего к API4:2023 -Unrestricted Resource Consumption (ресурсное истощение через входные данные API).

*Недостаток:*  
REST API Triton принимает специальные входные данные, которые приводят к неконтролируемой рекурсивной обработке внутри сервера. В результате один специально сформированный запрос может "загнать" процесс в глубокую рекурсию и вызвать отказ в обслуживании (DoS).

*Причина:*  
В коде обработки входных данных нет ограничений на глубину рекурсивных структур и нет защитных проверок, которые бы вовремя останавливали обработку.

#### 3) BOLA в Onlook  API
https://nvd.nist.gov/vuln/detail/CVE-2025-63783 -Тип (OWASP API Top 10):API1:2023 - Broken Object Level Authorization (BOLA).

*Недостаток:*
В mutation‑эндпоинтах (операции обновления/удаления проектов и управления тегами) сервер принимает project_id из REST‑запроса и выполняет операцию над этим проектом, не проверяя, принадлежит ли он текущему пользователю. Из‑за этого аутентифицированный пользователь может подставить идентификатор чужого проекта и менять или удалять данные других пользователей.

*Причина:*
Объектный уровень авторизации не реализован: есть только факт аутентификации, но нет проверки, что пользователь владеет конкретным проектом, к которому обращается.

Потом отправил запрос на /users/v1/debug  ( который выглядел подозрительно ) и получил ответ вида :

`"email": "mail1@mail.com",`

Очевидно, что обычный и неавтиризованный пользователь не должен иметь доступ к такому ввиду данных, поэтому это довольно опасная уязвимость.

Ее тип - API3:2023 — Broken Object Property Level Authorization.
OWASP описывает это как ситуацию, когда API неправильно контролирует доступ к отдельным свойствам объекта, а не к самому объекту целиком. 

Меры предотвращения:
1. Убрать или жёстко ограничить _debug‑эндпоинты
2. Проверка конфигурации перед релизом
3. Единый слой авторизации для «чувствительных» эндпоинтов
