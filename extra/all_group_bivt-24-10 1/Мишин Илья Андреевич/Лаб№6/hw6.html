Поиск секретов в репозитории

Для этой лабораторной работы я проверил репозиторий: https://github.com/OtusTeam/DevSecOps_secret-finding

Задача была найти секреты в репозитории и описать, почему это секреты и как их правильно хранить.

Для проверки можно использовать TruffleHog или Gitleaks. В моём случае были найдены несколько подозрительных мест, где в коде лежат пароли, токены и ключи.

1. Приватный ключ

Где найдено:
webgoat-server/privatekey.key

-----BEGIN PRIVATE KEY-----

MIIEvgIBADANBgkqhkiG9w0BAQEFAASC...

-----END PRIVATE KEY-----

Это приватный ключ. Такие ключи нельзя хранить в репозитории, потому что с их помощью можно подписывать данные или использовать ключ вместо настоящего владельца.

Приватные ключи нужно хранить в специальных хранилищах секретов, например Vault или в секретах CI/CD. Если ключ уже попал в Git, его лучше считать скомпрометированным и заменить.

2. Пароль в .env файле

Где найдено:
docker/.env, строки 3–4

USER=alex675

PASSWORD=#!qerge34t423sdfvdsfgeR

Тут прямо указан пользователь и пароль. Если репозиторий увидит кто-то посторонний, он сможет использовать эти данные для входа в сервис.

Файл .env с реальными паролями не нужно коммитить. Его надо добавить в .gitignore, а в репозитории оставить только пример .env.example без настоящих значений.

3. GitHub token в workflow

Где найдено:
.github/workflows/release.yml, строка 75

GITHUB_TOKEN: cee3257f0e59d1d4975a35429cffc3d8b5fabe15ca2e9d47243cbc446d4894a5

GitHub token даёт доступ к действиям в репозитории. Через него можно делать релизы, пушить изменения или выполнять другие операции, если у токена есть такие права.

Токен нельзя писать прямо в workflow-файле. Нужно использовать секреты GitHub Actions:

GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Если токен уже попал в репозиторий, его надо удалить и перевыпустить.

4. App Secret

Где найдено:
docker/.env, строка 2

APP_SECRET=666666666666666

APP_SECRET обычно используется приложением для подписи cookie, сессий или токенов. Если этот ключ известен другим людям, они могут попробовать подделать данные приложения.

Такое значение должно быть случайным и длинным. Хранить его надо в переменных окружения или в секретах CI/CD, а не в репозитории.

5. Пароль к PostgreSQL в строке подключения

Где найдено:
docker-compose-postgres.yml

jdbc:postgresql://webgoat_db:5432/webgoat?user=webgoat&password=webgoat

Также встречается такой вариант:

postgresql://webgoat:webgoat@webgoat_db:5432

В строке подключения указан логин и пароль от базы данных. Даже если пароль выглядит тестовым, всё равно это плохая практика, потому что в настоящем проекте так можно случайно открыть доступ к базе. Логин и пароль от базы надо выносить в переменные окружения или секреты CI/CD. В репозитории можно оставить только шаблон или пример без настоящего пароля.

Что делать, если секрет уже попал в Git

Если секрет уже был закоммичен, просто удалить его из файла недостаточно. Он всё равно останется в истории коммитов. Для очистки истории можно использовать:

  • BFG Repo-Cleaner;

  • git filter-repo.

Но даже после удаления из истории секрет всё равно лучше заменить, потому что он уже мог быть скопирован.

Как это можно автоматизировать

Чтобы такие ошибки не попадали в репозиторий, можно добавить проверку секретов:

  • локально перед коммитом;

  • в CI/CD pipeline;

  • при каждом pull request;

  • периодически по расписанию для всей истории репозитория.

Для этого подходят инструменты

  • TruffleHog;

  • Gitleaks;

  • detect-secrets.

Вывод

В репозитории были найдены несколько секретов: приватный ключ, пароль в .env, GitHub token, App Secret и пароль к PostgreSQL.

Все эти данные нельзя хранить в коде, потому что они могут дать доступ к сервисам, базе данных или репозиторию. Правильнее хранить их в переменных окружения, секретах CI/CD или специальных хранилищах секретов.

Также лучше сразу настроить автоматическую проверку, чтобы секреты не попадали в Git в будущем.
