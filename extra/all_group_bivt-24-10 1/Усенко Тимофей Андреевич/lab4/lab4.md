## Фрагмент 1

```python
#!/usr/bin/env python3
from flask import Flask
from mod_api import mod_api

app = Flask('vuln_app')
app.config['SECRET_KEY'] = 'F0cUzh8BgYJSLXAU8qDmClM0dE8GJTpsiyVEl3BCqQMCABp1U$f%'

app.register_blueprint(mod_api, url_prefix='/api')
```

### Недостаток

Секретный ключ (`SECRET_KEY`) захардкожен прямо в исходном коде приложения.
Flask использует этот ключ для подписи cookies, сессий и других криптографических
операций. Если исходный код попадёт в открытый доступ (например, будет
случайно залит на GitHub), злоумышленник получит возможность подделывать
подписанные данные — в частности, подменять содержимое сессионных cookies
и выдавать себя за любого пользователя, включая администратора.

Помимо этого, один и тот же ключ используется во всех средах (разработка,
тестирование, продакшн), что означает: компрометация ключа в любой из них
затрагивает все остальные.

### Рекомендации

Секретный ключ нельзя хранить в коде. Его нужно вынести в переменные окружения
и читать из них при запуске приложения:

```python
import os
app.config['SECRET_KEY'] = os.environ.get('SECRET_KEY')
```

Переменные окружения задаются на сервере или через `.env`-файл, который
добавляется в `.gitignore` и никогда не попадает в репозиторий. Для каждой
среды должен быть свой уникальный ключ. Длина ключа должна быть не менее
32 символов, ключ должен генерироваться случайным образом.

## Фрагмент 2

```python
from flask_wtf import Form
from wtforms import TextField

class LoginForm(Form):
    username = TextField('username')
    password = TextField('password')
```

### Недостаток

Поле `password` объявлено как `TextField` это обычное текстовое поле. Это означает
что пароль отображается в браузере открытым текстом при вводе (type="text"),
а не скрытым (type="password"). Любой, кто смотрит на экран, увидит пароль.
Кроме того, браузер может кэшировать или автодополнять такое поле как обычный
текст, что создаёт дополнительные риски утечки.

Также в форме нет никакой валидации данных не проверяется ни минимальная
длина пароля, ни другие ограничения.

### Рекомендации

Для поля пароля нужно использовать `PasswordField` вместо `TextField`.
Это автоматически устанавливает тип поля `type="password"` в HTML,
что скрывает вводимые символы:

```python
from flask_wtf import Form
from wtforms import TextField, PasswordField
from wtforms.validators import DataRequired, Length

class LoginForm(Form):
    username = TextField('username', validators=[DataRequired()])
    password = PasswordField('password', validators=[DataRequired(), Length(min=8)])
```

Дополнительно стоит добавить валидаторы: `DataRequired()` запрещает пустые
поля, `Length(min=8)` задаёт минимальную длину пароля.

## Фрагмент 3

```python
def post(self):
    username = self.get_argument('username')
    password = self.get_argument('password').encode('utf-8')
    email = self.get_argument('mail')
    try:
        username = username.lower()
        email = email.strip().lower()
        user = User({'username': username, 'password': password, 'email': email, 'date_joined': curtime()})
        user.validate()
        save_user(self.db_conn, user)
    except Exception, e:
        return self.render_template("success_create.html")
```

### Недостаток

Пароль сохраняется в базу данных в открытом виде в переменную `password`
записывается просто байтовое представление строки (`.encode('utf-8')`),
никакого хэширования не происходит. Это критическая ошибка: при любой
утечке базы данных все пароли пользователей окажутся скомпрометированы.

Второй недостаток это логика обработки ошибок полностью сломана. В блоке
`except` при возникновении любого исключения (в том числе при ошибке
сохранения пользователя) приложение рендерит шаблон `success_create.html`.
То есть пользователь видит сообщение об успехе даже если регистрация
фактически не произошла. Это вводит пользователя в заблуждение и скрывает
реальные ошибки.

### Рекомендации

Пароль перед сохранением нужно хэшировать с помощью надёжного алгоритма.
Для этого в Python используется библиотека `bcrypt` или встроенный модуль
`hashlib` с алгоритмом SHA-256 и солью. Наиболее предпочтительный вариант —
`bcrypt`, так как он специально разработан для хэширования паролей и медленно
работает намеренно, что защищает от перебора:

```python
import bcrypt

password_hash = bcrypt.hashpw(password, bcrypt.gensalt())
user = User({'username': username, 'password': password_hash, ...})
```

Блок `except` нужно исправить так, чтобы ошибки обрабатывались корректно —
успех показывался только при реальном успехе, а при исключении пользователь
получал понятное сообщение об ошибке:

```python
try:
    save_user(self.db_conn, user)
    return self.render_template("success_create.html")
except Exception as e:
    return self.render_template("error.html", message=str(e))
```

## Вопрос 1. Какие наиболее распространённые атаки предотвращает Django?

**SQL-инъекции** — Django использует ORM (Object-Relational Mapping), который
автоматически параметризует все запросы к базе данных. Пользовательские данные
никогда не подставляются напрямую в SQL-строку, поэтому инъекция невозможна.

**XSS (межсайтовый скриптинг)** — шаблонизатор Django по умолчанию экранирует
все переменные перед выводом в HTML. Символы `<`, `>`, `"`, `'`, `&`
автоматически заменяются на безопасные HTML-сущности, поэтому вредоносный
скрипт, введённый пользователем, будет отображён как текст, а не выполнен.

**CSRF (подделка межсайтовых запросов)** — Django включает встроенную защиту
от CSRF. При каждой сессии генерируется уникальный токен, который должен
присутствовать в каждом POST-запросе. Если токен отсутствует или не совпадает,
запрос отклоняется. Это не позволяет злоумышленнику заставить браузер
пользователя отправить запрос от его имени с другого сайта.

**Clickjacking** — Django предоставляет middleware `XFrameOptionsMiddleware`,
который добавляет заголовок `X-Frame-Options: DENY` к ответам сервера.
Это запрещает встраивать страницы сайта в iframe на других сайтах, что
блокирует атаки с подменой интерфейса.

**Брутфорс паролей** — Django ограничивает количество попыток входа
и поддерживает подключение капчи. Встроенная система аутентификации
хранит пароли исключительно в виде хэшей с использованием алгоритма PBKDF2.

## Вопрос 2. Как устроено управление пользовательскими сессиями в Django?

Django реализует сессии через встроенный модуль `django.contrib.sessions`.
Механизм работает следующим образом.

**Хранение данных сессии.** Сессионные данные хранятся на стороне сервера,
а не в cookies. По умолчанию Django сохраняет их в базе данных в таблице
`django_session`, но можно настроить хранение в кэше (Redis, Memcached)
или в файловой системе. В cookie браузера хранится только идентификатор
сессии (`session_key`) — случайная строка длиной 32 символа.

**Создание сессии.** При первом запросе пользователя Django создаёт новую
запись в таблице сессий с уникальным ключом. Этот ключ отправляется браузеру
в cookie `sessionid`. При последующих запросах браузер автоматически отправляет
этот cookie обратно, и Django находит соответствующую запись в базе данных
и восстанавливает данные сессии.

**Безопасность.** Cookie с идентификатором сессии по умолчанию имеет флаг
`HttpOnly` — это запрещает JavaScript читать его значение, что защищает
от кражи сессии через XSS. Если в настройках включён HTTPS, Django также
устанавливает флаг `Secure`, запрещающий передачу cookie по незащищённому
соединению. Время жизни сессии настраивается параметром `SESSION_COOKIE_AGE`
(по умолчанию 2 недели). При выходе пользователя из системы запись сессии
удаляется из базы данных через `request.session.flush()`, а cookie очищается.

**Данные сессии.** Внутри сессии данные хранятся как словарь Python и
сериализуются в JSON перед записью в базу данных. Получить или записать
данные в сессию можно через объект `request.session`:

```python
# записать
request.session['user_id'] = user.id

# прочитать
user_id = request.session.get('user_id')

# удалить
del request.session['user_id']
```
