Часть 1

Я брала данные с сайта CVE Mitre

1.  CVE-2023-52251 (Broken Object Level Authorization - BOLA)

Ошибка в REST API одного из сервисов позволяла пользователю получить доступ к данным другого пользователя, просто подставив чужой ID в URL запроса. Причина: Отсутствие проверки прав владения объектом на стороне сервера.

1.  CVE-2024-21645 (Broken Function Level Authorization)

Обычный пользователь мог получить доступ к административным эндпоинтам API (например, /api/admin/config). Причина: Недостаточная проверка ролей доступа для специфических методов API.

1.  CVE-2023-34107 (Unrestricted Access to Sensitive Business Flows)

Злоумышленники могли массово создавать аккаунты или совершать покупки через API, так как не было ограничений на количество запросов (Rate Limiting). Причина: Отсутствие механизмов защиты от автоматизированных атак и перебора.

Часть 2

Для тестирования эндпоинтов и анализа HTTP-запросов я использовала инструментарий Postman.

1\. Подготовка среды и инициализация

Первым делом необходимо развернуть локальное приложение. Для наполнения базы данных начальными значениями был выполнен запрос к эндпоинту: http://localhost:8080/createdb.

2\. Исследование структуры API

Для понимания архитектуры системы я обратилась к корневому адресу http://localhost:8080/. Приложение вернуло список всех доступных маршрутов (endpoints), что позволило составить карту дальнейших действий.

3**.** Анализ защищенности данных пользователей

При изучении списка эндпоинтов внимание привлек отладочный маршрут http://localhost:8080/users/v1/\_debug. При его вызове сервис возвращает полный массив данных пользователей.

Обнаруженная проблема**:** Ответ сервера содержит критическую информацию: пароли в незашифрованном виде и уровни привилегий. Это классический пример уязвимости API3:2023 Broken Object Property Level Authorization. Обычный пользователь получает доступ к полям объекта, которые должны быть скрыты.

Рекомендации по устранению:

- Внедрение фильтрации выходных данных на стороне сервера (Data Filtering).
- Обязательное хеширование паролей с использованием современных алгоритмов (например, Argon2 или bcrypt) вместо хранения открытого текста.

4\. Тестирование механизмов авторизации (Смена пароля)

Далее я проверила, насколько корректно API разграничивает права доступа при выполнении операций записи.

1.  Авторизация: Я вошла в систему под учетной записью name2 через эндпоинт /users/v1/login и получила валидный токен доступа.
2.  Атака: Используя полученный токен, я попыталась отправить запрос на изменение пароля для пользователя name1.
3.  Результат: Сервер одобрил запрос, позволив изменить чужие учетные данные.

Техническое заключение**:** Данный дефект классифицируется как API1:2023 — Broken Object Level Authorization (BOLA). Проблема заключается в том, что сервер проверяет наличие токена, но не проверяет, принадлежит ли конкретный ресурс (профиль пользователя) владельцу этого токена.

Способы защиты:

- Логика владения: Перед выполнением запроса сервер должен сверять ID из токена с ID изменяемого ресурса.
- Безопасные идентификаторы**:** Переход от предсказуемых имен пользователей к UUID, что затруднит перебор целей.
- Дополнительная проверка: Ввод текущего пароля как обязательное условие для установки нового.
