# Лабораторная работа №3  

## Часть 1

### CVE-2025-10611

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-10611

Уязвимость была найдена в нескольких продуктах WSO2. Проблема заключалась в том, что некоторые REST API endpoint недостаточно проверяли права пользователя. Из-за этого можно было обходить проверки авторизации и выполнять административные действия без нужных привилегий.

Причина: отсутствие проверки прав доступа для отдельных функций API.

Тип уязвимости: Broken Function Level Authorization.

---

### CVE-2025-61757

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-61757

Уязвимость относится к Oracle Fusion Middleware Identity Manager. В одном из REST endpoint отсутствовала обязательная аутентификация. Из-за этого удалённый пользователь мог получить доступ к важным функциям системы без входа в систему.

Причина: отсутствие механизма аутентификации для REST API endpoint.

Тип уязвимости: Broken Authentication.

---

### CVE-2025-69221

Источник: https://nvd.nist.gov/vuln/detail/CVE-2025-69221

Уязвимость была обнаружена в LibreChat. API позволял просматривать конфигурацию приватных AI-агентов, если злоумышленник знал идентификатор объекта. При этом сервер не проверял, имеет ли пользователь доступ к конкретному объекту.

Причина: отсутствие проверки прав доступа на уровне объекта.

Тип уязвимости: Broken Object Level Authorization.

# Часть 2

Сначала был запущен контейнер:

docker run -d -p 8080:8080 ket9/otus-devsecops-owasp-rest:latest

После запуска открыл приложение:

http://localhost:8080/

И заполнил базу данных:

http://localhost:8080/createdb

---

## Просмотр endpoint

После запуска были доступны следующие endpoint:

/users/v1
/users/v1/_debug
/users/v1/login
/users/v1/register
/users/v1/{username}

Сразу обратил внимание на `/users/v1/_debug`, так как debug endpoint обычно не должны быть доступны обычным пользователям.

---

## Проверка debug endpoint

Выполнил запрос:

curl http://localhost:8080/users/v1/_debug

В ответ API вернул список пользователей, их почту, пароли и информацию о том, кто является администратором.

Из этого стало понятно, что endpoint раскрывает важные данные без какой-либо авторизации.

---

## Вход под администратором

Так как через debug endpoint удалось получить пароль администратора, решил попробовать выполнить вход.

Запрос:

curl -X POST http://localhost:8080/users/v1/login \
-H "Content-Type: application/json" \
-d '{"username":"admin","password":"pass1"}'

После этого сервер успешно выдал токен администратора.

---

## Проверка административных функций

После получения токена была выполнена попытка удалить пользователя.

Запрос:

curl -i -X DELETE http://localhost:8080/users/v1/name1 \
-H "Authorization: Bearer $TOKEN"

Пользователь был успешно удалён.

---

# Вывод

В ходе работы удалось получить доступ к debug endpoint `/users/v1/_debug`, который раскрывал чувствительные данные пользователей, включая пароли и роли.

С помощью этих данных получилось выполнить вход под администратором и получить административный JWT token. После этого удалось удалить пользователя через административный endpoint.

Основная найденная уязвимость:

`API8:2023 — Security Misconfiguration`

Также частично присутствует:

`API3:2023 — Broken Object Property Level Authorization`

так как API раскрывает чувствительные свойства объектов пользователей.

---

# Меры предотвращения

- убрать debug endpoint из production;
- ограничить доступ к служебным endpoint;
- не хранить пароли в открытом виде;
- использовать хеширование паролей;
- не возвращать чувствительные поля через API;
- ограничивать доступ к административным функциям;
- проводить аудит REST API перед публикацией.
