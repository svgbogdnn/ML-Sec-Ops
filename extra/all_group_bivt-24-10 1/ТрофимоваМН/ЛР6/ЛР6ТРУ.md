# Лабораторная работа №6: Изучение существующих CI/CD с точки зрения доступных инструментов ИБ

## Цель работы
Проверить репозиторий на наличие секретов с помощью инструментов анализа кода, изучить подходы к автоматизации поиска чувствительных данных в CI/CD.

## Инструменты
- **TruffleHog** — утилита поиска секретов в истории Git (высокая энтропия, регулярные выражения).
- **Docker** — контейнеризация окружения (`python:buster`).

## Порядок выполнения
1. Запущен контейнер: `docker run -it python:buster /bin/bash`
2. Установлен TruffleHog: `pip install truffleHog`
3. Сканирование репозитория: `trufflehog https://github.com/OtusTeam/DevSecOps_secret-finding.git --json | tee results.json`
4. Анализ вывода, фильтрация ложных срабатываний, группировка по типам секретов.

## Аналитика найденных секретов

### 1. AWS Access Key и Secret Access Key
- **Расположение:** `.travis.yml` (строка с `access_key_id: AKIAJQLKPGHXRH2AH5QA`, а также зашифрованный `secret_access_key`)
- **Почему является секретом:** Access Key ID и Secret Key предоставляют полный доступ к сервисам AWS (S3, EC2 и др.). Компрометация позволяет злоумышленнику управлять ресурсами, воровать данные, запускать вредоносные активности.
- **Правильный способ хранения:** Никогда не коммитить ключи в репозиторий. Использовать секретные переменные CI/CD (GitHub Actions Secrets, GitLab CI Variables), сервисы управления секретами (AWS Secrets Manager, HashiCorp Vault). Скомпрометированные ключи немедленно отозвать через AWS IAM.

### 2. Зашифрованные секреты Travis CI и Heroku
- **Расположение:** `.travis.yml` (блоки `deploy.api_key.secure`, `notifications.slack.secure`, `env.global.secure` и аналогичные)
- **Почему является секретом:** Хранящиеся в Base64 зашифрованные строки — это токены доступа к Heroku, Slack, Docker Hub и другим сервисам. Хотя они зашифрованы для Travis CI, их наличие в открытом коде увеличивает риск расшифровки при утечке ключа шифрования или злоупотреблении контекстом CI.
- **Правильный способ хранения:** Перенести все секреты в защищённое хранилище CI/CD (секретные переменные проекта), не хранить в файлах конфигурации. Удалить `secure`-блоки из истории Git с помощью BFG Repo-Cleaner.

### 3. Анти-CSRF токен
- **Расположение:** `webgoat-lessons/csrf/src/main/java/org/owasp/webgoat/plugin/ForgedReviews.java` и `webgoat-lessons/csrf/src/main/resources/html/CSRF.html` (значение `2aa14227b9a13d0bede0388a7fba9aa9`)
- **Почему является секретом:** Данный токен используется для проверки подлинности запросов при защите от CSRF. Раскрытие токена позволяет злоумышленнику формировать валидные поддельные запросы и обходить защиту.
- **Правильный способ хранения:** Удалить хардкод из исходников, заменить на переменную окружения или генерировать токен на стороне сервера. Использовать встроенные CSRF-механизмы фреймворка без необходимости хранения токена в коде.

### 4. Хардкод паролей и ключей
- **Расположение:** `webgoat-lessons/challenge/src/main/java/org/owasp/webgoat/plugin/SolutionConstants.java`
- **Содержимое:** `PASSWORD_TOM = "thisisasecretfortomonly"`, `PASSWORD_LARRY = "larryknows"`, `JWT_PASSWORD = "victory"`, `ADMIN_PASSWORD_LINK = "375afe1104f4a487a73823c50a9292a2"`, `PASSWORD_TOM_9 = "somethingVeryRandomWhichNoOneWillEverTypeInAsPasswordForTom"`.
- **Почему является секретом:** Пароли и секретные ключи в открытом виде позволяют любому, кто имеет доступ к репозиторию, пройти аутентификацию, подписать JWT-токены или получить административные привилегии.
- **Правильный способ хранения:** Вынести все пароли в переменные окружения или специализированные секретные хранилища (HashiCorp Vault). Пересоздать все скомпрометированные пароли. Использовать аннотации вроде `@Value("${jwt.secret}")` для инжекта значений на этапе выполнения.

### 5. JWT Signing Key в тестах
- **Расположение:** `webgoat-lessons/jwt/src/test/java/org/owasp/webgoat/plugin/JWTFinalEndpointTest.java` (строка `String key = "deletingTom";`)
- **Почему является секретом:** Ключ используется для подписи JWT-токенов. Попадание в репозиторий раскрывает ключ, с помощью которого злоумышленник может создавать произвольные валидные токены для любого пользователя системы.
- **Правильный способ хранения:** Даже для тестов не следует хранить секретные ключи в коде. Использовать временные случайно сгенерированные ключи во время выполнения тестов, либо получать ключ из переменной окружения, заданной в CI.

## Общие рекомендации по автоматизации
- Внедрить сканирование секретов (TruffleHog, Gitleaks) в CI/CD-пайплайн на этапе pull request.
- Дополнить pre-commit-хуками для предотвращения попадания секретов в коммиты.
- При обнаружении утечки использовать BFG Repo-Cleaner для полной очистки истории Git.

## Вывод
В результате анализа репозитория обнаружены пять разнотипных секретов, связанных с облачными ключами, токенами CI/CD, паролями и ключами подписи. Все они представляют серьёзную угрозу безопасности. Применение инструментов вроде TruffleHog и соблюдение правил хранения секретов позволяют минимизировать риски утечек конфиденциальных данных в процессе разработки.
