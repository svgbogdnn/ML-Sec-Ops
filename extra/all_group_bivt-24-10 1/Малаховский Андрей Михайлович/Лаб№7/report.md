## 1. Цель

Цель - развернуть инструмент для SAST-анализа мобильных приложений, выполнить статическое тестирование APK-файла и подготовить план по снижению обнаруженных рисков.

В работе использовался инструмент MobSF. Для анализа было выбрано Android-приложение NewPipe в формате APK. После загрузки APK в MobSF был сформирован отчет статического анализа, на основе которого были отдельно рассмотрены разрешения приложения, сетевые настройки, AndroidManifest.xml и результаты анализа кода.

## 3. Развертывание MobSF

Для выполнения работы MobSF был развернут через Docker
Сначала был загружен Docker-образ MobSF:

```bash
docker pull opensecurity/mobile-security-framework-mobsf:latest
```

После загрузки образа был запущен контейнер:

```bash
docker run -it --rm -p 8000:8000 opensecurity/mobile-security-framework-mobsf:latest
```

После запуска контейнера в терминале отобразилась информация о старте MobSF и стандартные учетные данные:

```text
Default Credentials: mobsf/mobsf
Listening at: http://0.0.0.0:8000
```

Далее веб-интерфейс был открыт в браузере по адресу:

```text
http://127.0.0.1:8000
```

MobSF успешно запустился, после чего появилась возможность загрузить APK-файл для анализа.

## 6. Анализ разрешений приложения

В разделе `Application Permissions` были проверены разрешения, которые запрашивает приложение. По заданию отдельно выделены разрешения со статусом `dangerous`.

| № | Разрешение | Статус | Назначение | Потенциальный риск |
|---|---|---|---|---|
| 1 | `android.permission.WRITE_EXTERNAL_STORAGE` | dangerous | Запись, изменение и удаление данных во внешнем хранилище | Приложение может сохранять данные во внешнюю память. Данные во внешнем хранилище потенциально могут быть доступны другим приложениям или пользователю через файловую систему. |
| 2 | `android.permission.SYSTEM_ALERT_WINDOW` | dangerous | Отображение системных окон поверх других приложений | При небезопасной реализации такое разрешение может использоваться для перекрытия интерфейса других приложений и фишинговых сценариев. В NewPipe оно, вероятно, связано с режимом всплывающего плеера. |
| 3 | `android.permission.POST_NOTIFICATIONS` | dangerous | Отправка уведомлений пользователю | Может использоваться для навязчивых уведомлений или раскрытия части информации на экране блокировки, если уведомления содержат чувствительные данные. |

Также приложение использует несколько обычных разрешений, например `INTERNET`, `ACCESS_NETWORK_STATE`, `WAKE_LOCK`, `FOREGROUND_SERVICE`, `RECEIVE_BOOT_COMPLETED`. Они не имеют статуса `dangerous`, но часть из них все равно важна для понимания поведения приложения: например, `INTERNET` нужен для работы с сетевым контентом, а `RECEIVE_BOOT_COMPLETED` позволяет запускать компоненты после загрузки устройства.

## 8. Manifest Analysis

В разделе `Manifest Analysis` MobSF обнаружил 1 проблему уровня `High` и 9 предупреждений.

### 8.1. Проблема уровня High

| № | Обнаруженная проблема | Severity | Описание риска | Комментарий |
|---|---|---|---|---|
| 1 | App can be installed on a vulnerable unpatched Android version 5.0-5.0.2, `[minSdk=21]` | High | Приложение может быть установлено на старые версии Android, которые имеют известные неисправленные уязвимости и не получают нормальные обновления безопасности. | Риск связан не с конкретной функцией приложения, а с поддержкой устаревшей платформы. Пользователь на старом Android может быть более уязвим к системным атакам. |

MobSF рекомендует поддерживать Android версии не ниже Android 10 / API 29, так как старые версии Android хуже защищены и обычно уже не получают обновления безопасности.

## 12. Приоритетный порядок исправлений

Я бы исправлял найденные проблемы в следующем порядке:

1. Проверить возможность повышения `minSdkVersion`, так как это единственная проблема уровня `High`.
2. Проверить экспортированные компоненты в `AndroidManifest.xml`, особенно те, которые принимают внешние intent.
3. Разобраться с хранением данных: внешнее хранилище, SQLite и backup.
4. Вручную проверить возможные hardcoded secrets.
5. Проверить raw SQL-запросы и заменить опасные места на параметризованные запросы.
6. Проверить использование случайных чисел и заменить генератор на `SecureRandom` там, где это связано с безопасностью.
7. Повторно просканировать APK в MobSF и приложить обновленный отчет, если изменения вносились в проект.
